# 后端接口参考 V1

> 更新时间：2026-10-20
> 范围：当前 Rust 后端工作区中实际注册的 HTTP 路由，以及 Rust Gateway 当前接受的外部路径。本文记录实现现状，不代表所有路由都已部署、启用或可被外部客户端访问。
> 事实优先级：路由注册源码与运行配置高于本文；路径约束见[统一接口路径规范](../规范/统一接口路径规范_V5.md)。

## 1. 阅读说明

- 路径参数使用 Axum 风格 `{id}` 表示；请求路径中应替换为实际参数值。
- 标为“服务路由”的接口是服务 router 中已注册的路径；标为“Gateway 暴露”的接口还需同时存在网关路由或前缀代理。服务端进程直连端口并不等于客户端应绕过 Gateway。
- TrustGraph `/main/api/v1/**` 和 Monitor `/api/v1/monitor/**` 在 Gateway 按服务前缀转发，最终是否存在仍由服务 router 决定。Gateway 某些代理路由使用 Axum `any` 接收后转发，表中方法以服务 handler 实际注册的 HTTP 方法为准；`any` 不表示上游支持任意方法。
- `ORG_SCOPE` 组织治理路由、SDK 集成授权路由、身份映射路由和测试控制路由有额外配置门控；未启用时路由不会注册或功能不可用。
- 表中“权限检查”不代替鉴权。所有请求仍受 Gateway 身份校验、服务端网关签名验证及相应服务的权限策略约束。
- 查询参数、DTO 字段和业务校验由各路由所属源码中的 extractor、DTO 与 handler 定义；本文不推测未在下表说明的参数或字段。

## 2. 通用 HTTP 契约

### 2.1 请求与身份

- 普通 JSON API 使用 `Content-Type: application/json`。具体请求 DTO 的字段命名以对应类型定义为准；Identity 普通 DTO 通常使用 `camelCase`，SDK 授权 DTO 使用 `snake_case`。
- JWT v2 `roles` claim 只接受字符串数组（`Vec<String>`）；缺失时按空数组处理，旧 scalar/null 形状拒绝解码。Identity 新签发 token 不发 `permissions`；其遗留 decode slot 仅用于 refresh 拒绝携带授权上下文，不是授权入口。Gateway HMACv3 `X-Action-Codes` 相关签名字段保持原样，且该兼容透传字段不替代 PolicyEngine 授权。
- 外部认证由 Gateway 处理。需要认证的外部请求使用 `Authorization: Bearer <access-token>`；Gateway 验证 JWT/会话后清洗客户端伪造的内部身份头，再注入可信身份上下文。
- 服务间下游请求必须校验 Gateway 签名头：`X-Gateway-Auth`、`X-Gateway-Ts`、`X-Gateway-Signature`。携带网关元数据但签名无效时必须拒绝，不能回退信任客户端身份头。
- 公共免凭证不是由接口自身任意声明；Gateway 只允许配置白名单中的方法与路径。当前白名单为 `POST /api/v1/auth/sessions`、`POST /api/v1/auth/register`、`POST /api/v1/auth/password/forgot`、`POST /api/v1/auth/password/reset/{token}`、`POST /api/v1/auth/verification/send`、`POST /api/v1/auth/verification/verify` 和 `POST /v1/app/users/login`。具体启用仍可能受 Gateway 配置限制。
- `X-Trace-Id` 可由调用方提供；响应跟踪字段是否有值依运行时中间件及 handler 实现。可信身份、租户、卡片和权限头不可由客户端自行指定来扩大权限。
- 授权按用户、有效授权卡、资源、动作和租户范围判定。缺失、冲突或未证明的权限状态必须拒绝或返回待处理，不得以旧快照或 source 数据绕过授权入口。

参考：[统一消息协议与智能层消息规范](../规范/统一消息协议与智能层消息规范_2026-03-18.md)、[Rust 后端编码规范](../规范/Rust后端编码规范_V1.0.md)。

### 2.2 Rust 响应外壳

当前 Rust HTTP handler 使用 `astral_common::contract::ApiResponse<T>`。JSON 字段采用 `camelCase`；可选字段可能因 `None` 被省略。成功响应的常见结构如下：

```json
{
  "success": true,
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": 1791633600,
  "traceId": "..."
}
```

实现字段：`success`、`code`、`message`、`data`、`errorType`、`decision`、`reasonCode`、`requiredPermission`、`requestPath`、`requestMethod`、`timestamp`、`traceId`。字段存在性依具体成功/错误构造路径而异；不得假定每个响应都包含全部可选字段。

规范中的 `payload` 消息 Envelope 是长期目标契约，不是当前所有 Rust runtime 已实现的 HTTP 外壳。现状仍以 `data` 为业务数据字段。

### 2.3 错误与追踪

业务错误通常通过 `ApiResponse` 返回，并按错误类型使用对应 HTTP 状态。认证/权限拒绝和关键写操作应关注 `traceId`、`requestPath`、`requestMethod`、`errorType` 与 `decision`；具体错误码和原因值按 handler、中间件及 `astral_common` 错误映射实现核实。不要只依据 HTTP 200 推断业务授权结果，SDK 集成决策另有其签名响应契约。

### 3.1 管理员辅助重置密码的权限边界

`POST /api/v1/auth/users/{id}/password` 精确要求 `identity_users:reset-password`，不再映射到 `identity_users:create`。`identity_users` 原有 CRUD 动作保持有效；创建用户、创建卡片及受控 MFA POST 路由的动作映射不变。公开的重置令牌流程 `/api/v1/auth/password/reset/{token}` 和本人修改密码流程不改用该辅助重置权限。

- **独立授权**：仅持有 `identity_users:create`、`identity_users:update` 或旧 `write` 别名不足以辅助重置密码；`write` 仍只展开为 create/update/delete。已有 `*` action 授权仍按通配合同覆盖新动作，部署前必须核对其主体、卡片、租户和授权来源，不能把新增动作等同于撤销已有通配授权。
- **范围校验不变**：目标用户 ID 来自路径；与 query 目标冲突时拒绝。服务端仍解析目标用户的 tenant/domain/owner，并经过活动调用者卡、PolicyEngine、已发布证据、SoD 和宿主最终栅栏检查；归属缺失、歧义或依赖不可用不能用调用者租户补齐。
- **授予边界**：单租户部署可向负责辅助重置的平台运维管理员授予该专用权限；多租户部署应只向目标企业内部受权管理员授予该企业范围内的专用权限。平台资料管理、租户管理或用户创建权限不隐含密码重置权，不按角色直接放行。
- **兼容变化**：`BREAKING CHANGE`（`identity-assisted-password-reset-20261020`），自包含本变更的代码部署起生效；HTTP 方法、路径和请求 DTO 不变，但原来仅依赖 create/write 的辅助重置请求会被拒绝。需逐主体、活动卡和租户核对有效授权来源，按既有 source mutation / projection / audit 流程显式授予新权限；不批量改名、不全局撤销旧 create、不自动从旧权限复制新权限。
- **迁移与回滚**：本代码变更不修改 schema 或运行时授权数据。上线前完成最小授权与通配授权核对；回滚旧代码会恢复 create/write 可重置密码的旧边界，不能视为安全等价回滚。已授予新权限的撤销仍须走正式授权变更与投影流程，不通过直接删除或重放历史事件处理。

## 4. TrustGraph 权限治理

服务完整前缀为 `/main/api/v1`。Gateway 对 `/main/api/v1/{*path}` 进行前缀转发，但服务端只接受下列已注册路径。业务 router 使用权限检查中间件；接口要求、租户/域范围和管理员条件由对应 handler 再次约束。

### CURRENT V6 DTO 变更说明

- RuleSet summary/entry DTO 使用 canonical `ruleSetId`/`sourceType` 与 `entryId`/`resourceType`/`actionCode`；旧摘要 `id`/`refType`、entry `resource`/`action` 不再作为 HTTP 输出或输入别名。binding DTO 的 `refType` 仍表示 `BASE`/`OVERLAY`。请求未知键会被拒绝。旧 Rust entity 若仍保留 serde 字段，不构成 HTTP DTO 兼容承诺。
- `condition_json` 只接受单条件 `{ "conditionType": "OwnerOnlyCondition", "params": {} }` 或单键 `{ "allOf": [...] }`、`{ "anyOf": [...] }`、`{ "not": {...} }`。类型名使用原生 PascalCase；条件别名/包装/混合形式拒绝；TimeRange 参数使用 `timezone`，`timeZone` 拒绝。发布写入在 source mutation 前校验 condition。
- 恒定占位的域/租户归属字段不再出现在 DTO：Identity `Domain.orgId`、`Tenant.orgId`/`domainId`，以及 TrustGraph `DomainDto.orgId`。Identity Domain/Tenant request DTO 对未知旧键 fail-closed。真实 tenant/domain 关系仍通过 `tenant_domain_map` 表示；此变更不删除实际映射或组织授权字段。
- `/main/api/v1/card-templates/{id}` 的现有 HTTP 更新路由不变；handler 仍以经过 Gateway 验证的正数 actor 调用 required `update_template_with_context`。若请求缺少 `x-request-id`，HTTP 边界为该请求生成一次 UUID 并在该操作重试中复用；这不承诺跨独立 HTTP 请求幂等，也不改变其他模板路由。
- Identity 登录 DTO 当前只返回规范字段 `accessToken`、`refreshToken`、`tokenType`、`expiresInMillis`、`refreshExpiresInMillis` 与可选 `user`、`currentCard`、`availableCards`、`permissions`、`roles`、`enterprises`、`session`；不输出重复的 `token` 或 `identity_card`。这些 response/display 字段不构成授权入口。JWT v2/session/family/JTI 语义不变，Argon2id 是唯一密码验证格式；旧 BCrypt/MD5 凭证须显式重置，不自动迁移。

#### 4.5.1 PolicyEngine HitStats response (CURRENT V6)

`GET /main/api/v1/stats` returns `ApiResponse<HitStats>`. Its `data` object serializes with camelCase and contains exactly these fields; no legacy aliases are emitted:

```json
{
  "evaluationCount": 0,
  "allowCount": 0,
  "denyCount": 0,
  "timingNs": {
    "cardContextCheckNs": 0,
    "initialEvidenceLoadNs": 0,
    "finalEvidenceReloadNs": 0,
    "evidenceMatchNs": 0,
    "totalNs": 0
  }
}
```

Layer-specific `L1`/`L2`/`L3` hit counters are removed. The separate database-backed `/main/api/v1/hit-stats/*` routes above do not expose this `HitStats` struct and are not part of this stats-schema change.

## 7. 不可当作当前接口的路径

下列路径未由当前 Rust 路由注册支持，禁止从历史设计或猜测补入调用方：

- `/identity/**`：不存在的身份外部前缀；Rust Identity 主路径为 `/api/v1/auth/**`。
- `/api/v1/users/{id}/permissions`：不是当前用户权限摘要入口；Identity 使用 `/api/v1/auth/me/permissions`。TrustGraph 的按用户授权管理路径则为 `/main/api/v1/users/{user_id}/permissions`。
- `/api/v1/migration/**`：没有已实现的迁移 HTTP API。
- `/authz/**`：没有对应路由。
- `/main/api/v1/integrations/authorization-decisions` 的 `GET`：集成授权入口只注册 `POST`。
- `/api/v1/auth/cards/switch`：切换卡片的当前路径是 `/api/v1/auth/sessions/switch-card`，见 Identity 路由表。
- `/api/v1/monitor/cache` 与 `/api/v1/monitor/consistency-check`：历史 Monitor 诊断路径已随 CURRENT V6 Redis/旧 oracle 清理退役，当前 Monitor 未注册这些路由；不得作为可用接口调用。
- `/main/api/v1/templates/{id}/apply` 与 `/main/api/v1/templates/{id}/apply/async`：Rust TrustGraph CURRENT V6 已移除此旧 template-apply surface；模板 sync/materialization 与 RuleSet binding 仍是不同路径和语义。
- `/main/api/v1/compliance/overview` 与 `/main/api/v1/compliance/report`：Rust TrustGraph CURRENT V6 未注册这些旧 compliance aliases。

以上 TrustGraph V6 route-contract 记录是软件接口合同，不表示部署已切换；完整路径基线日期与路由事实源见 [统一接口路径规范 V5](../规范/统一接口路径规范_V5.md)。
