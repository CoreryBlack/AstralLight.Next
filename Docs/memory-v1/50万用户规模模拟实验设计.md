# 50 万用户大规模模拟实验设计（2026-11-19）

> 目标：在 DarkStar memory—v1 当前实现上，模拟接近真实生产的 50 万用户复杂授权环境，
> 覆盖随机比例的不同规则集配置（部分重复 + 完全不同）、真实用户请求分布，
> 以及「运行时上下文缺失 → 受控 DB 路径增量补齐」等特殊路径。
> 本文是实验设计；它不声称生产验收，也不改变 §15.10 的采用边界。

## 1. 硬容量边界（实测约束，实验规模据此拆解）

| 约束 | 当前值 | 来源 | 对 50 万用户的影响 |
|---|---|---|---|
| 单根摘要键上限 `MAX_ROOT_DIGEST_KEYS` | **4,096** | `memory_v1_digest.rs:46`；生产入口 `check_root_digest_capacity`（service.rs:298）按**九表行数总和 + 规则集数**计键 | ❗ 单根最多承载 ~4,096 行。50 万用户不可能全量装入单根 —— 这是设计边界，不是缺陷 |
| 冷加载捕获上限 `MAX_ROWS` | 100,000 | `memory_v1_candidate_loader.rs:40` | 单次冷加载捕获同样封顶 10 万行 |
| 读取预算 `max_bindings_per_read` | 256 | `memory_v1_service.rs:56` | 每卡绑定聚合预算 |
| 规则集规模 | ≤4,096 条规则 / 版本 | `权限引擎与规则结构设计.md` | 单版本规则数可支撑 |

**结论：50 万用户规模以「分片多根」模拟 —— 多个进程级根实例，每根承载一段用户分片，
单个根内遵守 4,096 键上限；这正是生产部署为该体量必须采用的形态。**

## 2. 规模拆解（每根分片）

单根预算（≤4,096 键 = 9 表行数 + 规则集数）：

| 项 | 每根 | 说明 |
|---|---|---|
| 用户 | 2,000 | 50 万 ÷ 250 根 |
| 身份卡 | 2,000 | 每用户 1 张 |
| 租户 | 25 | 5 层 × 5 每层，含父子链 |
| 用户卡 | 4,000 | 每用户 2 张（BASE + 部分带 OVERLAY DENY） |
| 规则集 | 20 | 共享库：全仓 200 个规则集池，每根随机取 20 |
| 规则集版本 | 20 | 每集 1 版（首版，同事务确认） |
| 绑定 | ~4,000 | 每卡 1 绑定，规则集从该根池随机选 |
| 绑定确认 | 4,000 | 每绑定 1 条 |
| 变更确认 | 20 | 每规则集 1 条 |
| **键合计** | **≤4,090** | 2,000+2,000+25+4,000+20+20+4,000+4,000+20 = 12,085 ❌ 超限 |

修正 —— 键计数是**九表总和 + 规则集数**，因此每根用户卡+绑定+确认合计必须压缩：

| 项 | 每根（修正） | 说明 |
|---|---|---|
| 用户 | 600 | 50 万 ÷ ~833 根 ≈ 834 根分片 |
| 身份卡 | 600 | 每用户 1 |
| 租户 | 10 | 2 层 × 5 |
| 用户卡 | 600 | 每用户 1 张（50% 实验组再叠加 OVERLAY DENY 卡 → 另计） |
| 规则集 | 10 | 从 200 集共享池随机抽 |
| 版本 | 10 | 每集 1 版 |
| 绑定 | 600 | 每卡 1 |
| 绑定确认 | 600 | 每绑定 1 |
| 变更确认 | 10 | 每集 1 |
| **合计** | **3,090** | ≤4,096 ✓ 留 1,000 余量给运行时增量补载（见 §5） |

50 万用户 ÷ 600/根 ≈ **834 个分片根**。实验不逐根实例化 834 个进程根（进程安装槽是
一次性的），而是**按根种子分组生成 834 份候选行集**：
1. 分片 0（种子固定）实际安装为进程根，承载全部行为实验；
2. 其余 833 份用同一生成器仅做**安装校验**（`install_isolated_test_root` 成功即弃），
   证明生成器对任意分片都满足全部候选约束 —— 这是规模可扩展性的结构证据。

## 3. 随机规则集配置（部分重复 + 完全不同）

共享规则集池 200 个，按三层混合比例生成，固定种子可复现：

| 层 | 占比 | 内容 |
|---|---|---|
| 全局共享层 | 20% | 40 个「平台公共」规则集（`document:read`、`workspace:read` 等），**所有分片**都以高概率抽到 → 跨分片重复 |
| 租户族共享层 | 30% | 60 个按租户族（10 个租户族 × 6 集）生成，同族分片重复、异族不同 |
| 分片私有层 | 50% | 100 个按 `(root_seed, shard_index)` 派生的独有规则集，**完全不同** |

规则条目在合同闭集内随机：`ruleId/resource/action/effect/validity/ownerScope/tenantScope`，
资源从 12 个注册资源抽，动作按资源抽，效果 70% ALLOW / 30% DENY，
30% 条目带 validity 窗口、scope 按绑定聚合语义随机（self/all × self/self+descendants）。
**期望（assert）**:每分片的规则集指纹集合中，全局层必然重复、私有层零重复 ——
用 `hash_bytes` 集合断言「部分重复 + 完全不同」的两个方向都成立。

## 4. 用户请求模拟

用户请求按真实分布驱动（固定种子）：

| 请求类型 | 占比 | 路径 |
|---|---|---|
| 自有对象读（owner=self, tenant=own） | 60% | `evaluate_memory_v1`，对象三元组来自宿主记录表（同 P0-A 模式） |
| 跨 owner 读 | 15% | 期望 ScopeDenied→DENY |
| 跨租户读 | 10% | 期望 ScopeDenied→DENY |
| 未注册资源 | 5% | 期望 UnregisteredResource→DENY |
| 类型级读（无 target） | 5% | 期望 ALLOW |
| 窗口未开/已闭对象 | 5% | 期望 NoMatch→DENY 或 pending |
| 登录+评估全链 | 余量 | 真实 Identity login → session → 评估 |

**独立参考预言机**（与 `complete_observation.rs` 同模式）：按夹具行集独立重算
每个请求的期望结果，全量对账（目标是每轮 10 万次评估全对齐）。
同时记录 ALLOW/DENY/PENDING 计数与 P50/P95/P99 延迟（复用 `recheck_cost` 的百分位函数）。

## 5. 运行时缺失与增量补载（特殊情况）

规范 §15.10.3 合同：服务期发现上下文未加载 → 本次请求触发受控 MySQL 一致性读取 →
校验缺失范围及关系闭包 → **同一 owner 原子补入**事实+索引+根版本/hash →
同一读者进入新读取阶段重新评估 → 后续完整请求不查 DB。
DB 落后不得覆盖内存修改或复活撤销；不能证明安全合并时 PENDING/DENY。

**实现现状核对**（必查，不臆造）：当前 `astral-authorization-root` 公开 API 中
**没有**服务期受控补入原语 —— `install_candidate`（一次性）、
`execute_mutation_with_precondition`（11 种管理变更）存在，但「以非管理身份把
候选行原子并入 Serving 根」的增量合并 API 尚未实现（`单机唯一共享根设计.md` §8
明确列为待实现：「当前仍没有……缺失补齐」）。

因此本实验的补载组按下述**两层口径**执行，绝不伪造已实现的合并语义：

1. **管理变更通道补载（已实现，可测）**：把「服务期发现缺失」落到已验收的
   11 种管理变更上 —— 对缺失卡走 `UserCardCreate`、缺失绑定走
   `BindingCreate{row, confirmation}`，在同一进程根上模拟「请求触发补齐 →
   补齐后同根重新评估 → 后续不查库」。断言：
   补载前该请求 PENDING/DENY（fail-closed）、补载后同请求复评 ALLOW、
   补载**不复活**已撤销绑定（先 remove 再补 → 仍 DENY）、
   并发补载与撤权竞争（撤权提交后补载 CAS 失败）。
2. **缺口如实记录**：真正的「候选行级原子并入 + 覆盖状态标记」没有实现。
   实验输出 `gap=` 行显式列出该缺口，论文与证据只声明第 1 层。
   这与 §15.10「未实现不得当作已验收」一致。

## 6. 特殊情况矩阵

| # | 场景 | 注入方式 | 期望 |
|---|---|---|---|
| S1 | 服务期缺失→管理通道补载→复评 ALLOW | 见 §5.1 | PENDING→ALLOW，无复活 |
| S2 | 补载 vs 撤权竞争 | CAS 前置版本 | 后写者赢，败者 CAS 拒绝 |
| S3 | 撤权后的 held/fresh | 复用 recheck_cost 模式 | held PENDING / fresh DENY |
| S4 | 大规则集（1,024+ 条/版本） | 池内注入大版本 | 评估正确，匹配计划走 hash 查找 |
| S5 | 窗口边界群（validity 未来开/已闭） | 随机条目 | 参考预言机逐点一致 |
| S6 | 会话撤销 | revoke 后复评 | final check 拒绝 |
| S7 | 跨分片同规则集（全局层） | 两分片同集 | 各自根内独立判定一致 |
| S8 | 摘要键满 4,096 | 生成满负荷分片 | 安装拒绝（`RowBudgetExceeded`/`digest key capacity`） fail-closed |

## 7. 执行形态与产物

- 位置：`astral-single-node/src/memory_v1_scale_tests.rs`（新模块，库测试，进程内）；
  负载档用 `--ignored` + 子进程隔离（同 `recheck_cost` 模式），套件登记进
  `tests-suite/MANIFEST.toml`（`paper_*` 计数不变 —— 本套件是独立 `scale` 系列，
  不混入论文 lane）。
- 参数：`SCALE_USERS`（默认 500_000，可降为 50_000 烟测）、`SCALE_ROUNDS`、
  `SCALE_EVALS_PER_SHARD`（默认 10 万总评估）。
- 产物行：`scale: shards=834 users=500000 rulesets=200 overlap=… | evals=… allow=… deny=… pending=… p50/p95/p99=… | gap=…`
- 参考预言机全量对账失败即 FAIL；不因规模放宽任何断言。

## 8. 明确不做

- 不修改生产代码、不放宽任何上限常量；
- 不连接真实 MySQL（规模组全部进程内；如需真实库冷加载另立批准项）；
- 不把「管理通道补载」表述为已实现的「候选行级增量合并」；
- 不宣称 834 分片的进程级部署已验证 —— 验证的是单分片结构合法性 + 生成器全域约束满足。
