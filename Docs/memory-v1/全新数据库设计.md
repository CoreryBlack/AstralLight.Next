# memory-v1 全新数据库设计

> 状态：概念设计与离线候选，不是迁移脚本，不代表实现或生产验收。对应 [数据库结构候选](数据库结构候选.sql) 不得直接对数据库执行。
>
> 本基线采用全新数据库，不迁移旧数据；旧库只作为业务事实和技术参考，不自动清空、删除或覆盖现有环境。本文不覆盖现行工程规范和生产执行门禁。
>
> 2026-11-16 用户就消息持久化、审计和重启恢复作出的设计决定见本文 §7；Rust 规范 §15.10.4 已登记 A/A1 目标边界。消息协议及 B-4 的持久实现等细节仍未闭合，不代表新方案已经实现或获生产验收。

## 1. 定位与范围

MySQL 保存新系统的持久事实，并作为单机进程冷启动时一致性快照的来源。服务期正式授权由进程中唯一共享内存权威提供，规则判断由 `PolicyEngine.evaluate()` 完成；所需上下文未加载时，本次请求可触发受控查库并安全补入根，再从根评估，完整后续授权请求不查 DB。MySQL 行不直接构成放行；并发和旧数据覆盖边界见[唯一根设计](单机唯一共享根设计.md)。数据库同时作为规则集版本库，目标保存从第一版到最新版的每一份完整规则集结构。

当前只设计授权核心关系：用户、身份卡、分层租户、用户卡、规则集版本、用户卡绑定和明确确认的追溯骨架；确认中的操作标识仅是审计关联候选，不是完整审计记录。认证凭证和会话、资源归属、规则词汇、职责分离、租户共享、首次超管建立和完整落盘机制尚需单独合同，不可因核心骨架存在就声称数据库足以支持正式服务。

## 2. 概念关系

```text
User ── 1:1 ── IdentityCard                认证身份，不授予权限
  │
  └── 1:N ── UserCard ── N:1 ── Tenant ── parent ──> Tenant
                  │
                  └── Binding（BASE / OVERLAY） ──> RuleSet
                        │                            └── Version 1..N
                        └── Confirmation                  └── version + content
                                                               + timestamp + hash
```

图表示目标关系和逻辑职责，不要求卡和规则集一定同租户；跨租户规则集能否复用仍待确定，未证明时不能放行。父子租户不自动继承成员或权限；同事、角色名称和组织关系不能产生绑定。每个有效授权关系必须有明确确认，确认由有权人员执行并可追溯。

数据库可通过唯一键保证每个用户最多一张身份卡；“每位完整用户恰有一张”需由初始化、写入 owner 和冷加载整体验证。租户自关联约束可拒绝直接自环，多节点环仍须由 owner 和冷加载验证。资源类型、动作、对象归属、完整确认、哈希正确性及规则组合语义不能仅靠外键证明。

候选 DDL 的九张表对应 `memory_user`、`memory_identity_card`、`memory_tenant`、`memory_user_card`、`memory_rule_set`、`memory_rule_set_version`、`memory_card_rule_set_binding`、`memory_binding_confirmation` 和 `memory_rule_set_change_confirmation`。后两张表只表达追溯关系，不能证明确认人具备权限或确认仍有效；用户、卡、租户、规则集和绑定的状态与资格尚未建模，资源归属和完整审计也不在此骨架内。规则内容暂存为完整字节，不代表规则语言已确定。

新增的 `astral_types::memory_v1::MemoryId` 只定义一个独立的 16 字节标识编解码选择：UUID 网络字节序与文本十六进制从左到右对应，字符串及 Serde 编码仅接受和输出小写、带连字符的 `8-4-4-4-12` 形式，不限制 UUID 版本或变体。全零值原样保留，不证明身份有效或授权；标识生成、各字段映射与生命周期仍待确定。此类型尚未接入候选 DDL、数据库或现有身份运行路径，不提供旧 `i64` 映射，也不代表正式协议已部署。

绑定确认和规则修改确认候选引用已存储的规则集版本，因此数据库应用时必须满足版本外键；不能由这一外键推断消息或数据库事务已落盘。授权和确认按 §7 的 A/A1 目标同次内存发布，并等待对应本机连续持久消息前缀后才可报告管理成功；MySQL 在后台按序处理，具体恢复与对账合同仍待完成。

## 3. 规则集版本与确认

一份规则集版本的逻辑结构为：

```text
version + content + timestamp + H(规范编码(version, content, timestamp))
```

`hash` 不包含自身；算法、编码规则、时间戳含义及规则语言尚待确定。候选使用不透明的内容字节用于保留精确编码；应用 owner 必须对结构化内容按确定性编码，防止依赖数据库 JSON 格式化、字符集或字段顺序改变哈希输入。受影响的身份、租户、状态等事实须进入内容或由其他可信的一致性合同绑定。数据库存储 hash 不证明真实性、授权确认或落盘完成。

多张卡可以分别经确认绑定同一规则集；经授权修改规则集并在共享根原子生效后，现有有效绑定立即使用新内容，不要求逐卡重新确认。确认如何覆盖后续修改、操作者权限、影响范围和审计需在写入合同中明确；不能从同事或组织关系自动产生新绑定。`OVERLAY` 可追加允许或拒绝，明确拒绝可阻止该卡从 `BASE` 取得对应权限；具体匹配、冲突和其他来源语义待设计。

数据库的规则集版本是不可覆盖的完整版本记录的目标，不等于共享根的进程实例和单调版本；内存按用户确定的方式在原规则集权威上原子更新，不以保留旧完整根为目标。数据库保存版本与内存生效之间存在异步边界：消息尚未持久化时崩溃，已在内存生效的版本可能丢失，不能声称数据库已保存所有曾生效版本。消息、顺序、重复写对账、版本缺口、容量和失败通知须依 §7 闭合并验证。

## 4. 生命周期和失败边界

- 冷启动按 §7 核验和恢复本机持久消息，将可证明的变更按序补齐 MySQL，再从单个一致性快照加载授权必需的完整事实，验证关系、覆盖、规则内容和版本后才能进入正式服务。当前候选没有定义完整冷加载清单或实现该恢复链。
- 修改经 Gateway → TrustGraph → PolicyEngine 授权后，由受限 owner 对共享根中的事实、关系、索引、规则集四部分和根元数据进行一致原子更新；不能以数据库写入或旧投影作为另一个授权生效点。
- A/A1 目标要求管理成功先证明本机连续持久消息前缀，不等待 MySQL；崩溃恢复先以持久消息按序补齐 MySQL，再从一致性快照重建。未进入持久通道的内存变更和撤权仍可能丢失；不能保证每次崩溃都有可用于对账的记录。该目标尚未实现或验收，详见 §7。
- 有权人员首次建立超管时，超管管理模块根据系统已有接口构造全权限规则集并绑定用户卡；首次空库如何建立信任、确认、审计、恢复及接口变化如何更新覆盖仍须定义。正常请求不凭超管标识绕过引擎。
- 清理、停用、删除和跨租户变更必须先定义所有权及授权含义；本候选不以级联删除代替撤权或审计。

## 7. 消息持久化与恢复的增量决策（2026-11-16）

以下是用户已确认的目标设计，不表示消息通道已经实现或可恢复；§15.10.4 已同步目标边界，未决协议细节仍需闭合。

1. **运行时权威**：可信内存根建立后，授权变更在根中原子生效；MySQL 是冷启动、受控缺失补全和异步备份的数据来源，不等待 MySQL 写入才使变更生效。
2. **成功响应（方案 A）**：授权变更在内存生效后，自研通道持久化该变更及恢复所需的前序变更；确认满足持久化条件后才向操作者返回成功。消息持久化失败或结果未知时，不声称变更未发生，而应告知结果待核对。MySQL 继续异步更新。
3. **内存提交关联**：授权事实、关系、索引等状态更新与对应的待持久化记录在同一次内存原子提交中产生；提交前预留记录空间，容量不足时不提交新的管理变更，正常授权读取继续。提交失败不得产生可恢复的已生效消息。
4. **重启恢复**：崩溃重启时先处理通道中已持久化且符合恢复条件的变更消息，补齐 MySQL，再从一致性快照建立新的内存根。已返回成功的变更在约定的持久化故障范围内应可恢复；未进入持久消息通道的内存变更仍可能丢失。
5. **持久化故障范围（方案 A1）**：自研通道以本机持久存储为成功确认依据，不要求第二个故障域同步确认。持久化确认必须包含相应数据的可靠刷写；在文件系统、设备正确执行刷写且存储仍完整可用的前提下，应能恢复进程崩溃、系统崩溃和断电前已确认的消息。本机磁盘或整机永久损坏、消息文件损坏或丢失不在此承诺范围内；若 MySQL 尚未包含变更，已返回成功的变更可能无法自动恢复。无法证明恢复所需消息完整、连续及与数据库状态一致时，不得进入正式授权服务，应先对账或恢复。
6. **统一变更顺序**：纳入本协议的授权事实变更按内存原子生效顺序形成统一序列。序号与事实更新、待持久化记录在同一次内存提交中产生；提交失败不得形成可恢复变更或无法解释的序列缺口。消息通道只确认连续持久化前缀：前序消息未确认或结果未知时，后续变更不能返回成功；允许在满足连续前缀的条件下批量刷写。MySQL 按同一顺序异步应用，重启时按该顺序补齐后再建立内存根。此顺序不要求正常授权读取或其他业务请求排队；它是变更流顺序，不等同规则集版本、根实例/版本或数据库全部事实的全局版本。
7. **数据库应用与对账**：按统一顺序消费已持久化消息时，在同一个 MySQL 事务中写入该变更涉及的授权事实、处理回执和数据库已处理进度；回执关联稳定操作标识、消息序号和内容摘要。事务提交后才能确认数据库已处理该消息。崩溃或提交结果未知时，先核对回执和进度：回执存在且内容一致则不重复应用；确认尚未应用后以原消息重试；状态无法证明或标识对应内容不一致时停在该位置并对账，不跳过继续恢复。批量操作中操作标识与各消息/条目的关联仍须明确。该数据库确认不改变方案 A：操作者无需等待 MySQL 写入。
8. **未持久化窗口的权限使用（方案一）**：授权变更在内存原子生效后，后续请求立即按更新后的根判断；新增加的权限无需等待变更消息持久化即可用于业务。用户接受的边界是：若业务已经使用新权限，而变更尚未进入持久消息通道就发生崩溃，该次未收到成功响应的授权变更及其待持久化记录可能丢失，业务效果不会随之自动撤销，重启后也未必能还原完整授权依据。消息已持久化与业务日志存在与否分别判断，日志或告警不能保证补回丢失的授权事实。后续管理变更即使依赖这次授权，在其前序消息未确认持久化时也不得返回成功，仍遵循统一变更顺序。
9. **管理变更与审计共用消息**：内存提交前准备完整的 T2 审计内容，包含操作者、目标、动作、变更摘要、前后状态等 B-4 要求的适用字段；无法形成完整审计内容时不提交变更。授权事实与包含该审计内容的待持久化记录在同一次内存原子提交中产生；本机持久消息达到方案 A 的连续前缀要求后可返回成功，但此时 MySQL 审计表未必已写入。异步消费时，授权事实、独立 append-only 审计行、处理回执及处理进度在同一个 MySQL 事务提交，重试与未知结果依第 7 项对账。内存已生效后的消息持久化失败或结果未知不得表述为变更未发生；消息持久化前崩溃时，该变更及待持久化审计内容可能丢失。操作者因响应超时看到待核对，不等于变更未生效；如果实际生效的变更后来持久化，仍须生成相应审计行。这与真正未作出授权判断的 PENDING 不写持久审计行分别处理。
10. **DENY 审计（方案一）**：引擎作出 DENY 后立即阻止业务操作，并生成独立审计消息，使用同一自研通道的本机持久化能力。返回 403 前，必须同时确认 DENY 审计消息已可靠持久化，以及本次判断所读取的授权状态对应的变更消息已按统一顺序持久化（包括形成所需连续前缀的前序消息）；无需等待判断之后发生的无关变更。MySQL 审计行异步写入，确认本机持久化不等于审计表已落盘。审计消息或授权依据的持久化失败、结果未知或无法证明时，仍拒绝业务操作，对外返回 503 审计不可用或依据待确认，并按可用证据对账或重试；引擎实际判断仍是 DENY，不能伪装成 PENDING 审计。若消息未持久化即崩溃，该次 DENY 的审计仍可能丢失；若持久化结果未知而消息实际已经持久化，后续应按实际结果处理。此确认不单独保证能够完整还原每次历史判断：基础快照、历史消息及其保留期限仍须另行定义。DENY 审计失败时的事件标识、重试预算、容量隔离、告警以及审计表消费的恢复协议仍待设计。真正的 PENDING 不写持久审计行，适用 B-4 的告警留痕另行处理；原有对外响应合同需相应调整。
11. **跨重启的未知操作（方案一）**：客户端发起管理变更前取得当前服务的启动标识，并将其与该操作的稳定标识一起保存；重试和结果查询沿用原有标识。重启后先根据持久消息和数据库回执查找该操作，核对操作内容及查询权限；若能证明结果则按证据报告。若查不到且该操作属于此前启动周期，返回结果未知、需要核对，不自动重新执行：它可能从未到达，也可能已在旧内存中生效而相关记录在持久化前丢失。经人工核对后如需重新申请，须显式发起新的操作并重新经引擎授权；新的操作不证明旧操作未曾生效，业务后果仍需由操作者评估。本方案不要求为每次管理变更额外持久化执行前预约；启动标识与操作标识的完整性绑定、客户端保存、查询授权、并发去重及记录保留期限仍待细化。
12. **尚待设计**：本机持久化确认的具体协议及刷写和存储假设；跨重启的变更流身份、序号和恢复边界；启动标识与操作身份的可靠绑定、并发重复请求、批量条目身份及保留期限；回执与进度核验、部分写入和未知结果对账的细则；DENY 审计消息的故障恢复和容量隔离；积压、容量和故障恢复。§15.10.4 已登记 A/A1 目标与替代关系，B-4 的持久实现和上述细节仍需闭合，不得仅凭合同登记作为生产采用证据。
