# memory-v1 全新数据库设计

> 状态：概念设计与离线候选，不是迁移脚本，不代表实现或生产验收。对应 [数据库结构候选](数据库结构候选.sql) 不得直接对数据库执行。
>
> 本基线采用全新数据库，不迁移旧数据；旧库只作为业务事实和技术参考，不自动清空、删除或覆盖现有环境。本文不覆盖现行工程规范和生产执行门禁。

## 1. 定位与范围

MySQL 保存新系统的持久事实，并作为单机进程冷启动时一致性快照的来源。服务期正式授权由进程中唯一共享内存权威提供，规则判断由 `PolicyEngine.evaluate()` 完成；所需上下文未加载时，本次请求可触发受控查库并安全补入根，再从根评估，完整后续授权请求不查 DB。MySQL 行不直接构成放行；并发和旧数据覆盖边界见[唯一根设计](单机唯一共享根设计.md)。数据库同时作为规则集版本库，目标保存从第一版到最新版的每一份完整规则集结构。

当前只设计授权核心关系：用户、身份卡、分层租户、用户卡、规则集版本、用户卡绑定和明确确认的追溯骨架；确认中的操作标识仅是审计关联候选，不是完整审计记录。认证凭证和会话、资源归属、规则词汇、职责分离、租户共享、首次超管建立和完整落盘机制尚需单独合同，不可因核心骨架存在就声称数据库足以支持正式服务。

## 2. 概念关系

```text
User ── 1:1 ── IdentityCard                认证身份，不授予权限
  │
  └── 1:N ── UserCard ── N:1 ── Tenant ── parent ──> Tenant
                  │
                  └── Binding（BASE / OVERLAY） ──> RuleSet
                        │                            └── Version 1..N
                        └── Confirmation                  └── version + content
                                                               + timestamp + hash
```

图表示目标关系和逻辑职责，不要求卡和规则集一定同租户；跨租户规则集能否复用仍待确定，未证明时不能放行。父子租户不自动继承成员或权限；同事、角色名称和组织关系不能产生绑定。每个有效授权关系必须有明确确认，确认由有权人员执行并可追溯。

数据库可通过唯一键保证每个用户最多一张身份卡；“每位完整用户恰有一张”需由初始化、写入 owner 和冷加载整体验证。租户自关联约束可拒绝直接自环，多节点环仍须由 owner 和冷加载验证。资源类型、动作、对象归属、完整确认、哈希正确性及规则组合语义不能仅靠外键证明。

候选 DDL 的九张表对应 `memory_user`、`memory_identity_card`、`memory_tenant`、`memory_user_card`、`memory_rule_set`、`memory_rule_set_version`、`memory_card_rule_set_binding`、`memory_binding_confirmation` 和 `memory_rule_set_change_confirmation`。后两张表只表达追溯关系，不能证明确认人具备权限或确认仍有效；用户、卡、租户、规则集和绑定的状态与资格尚未建模，资源归属和完整审计也不在此骨架内。规则内容暂存为完整字节，不代表规则语言已确定。

新增的 `astral_types::memory_v1::MemoryId` 只定义一个独立的 16 字节标识编解码选择：UUID 网络字节序与文本十六进制从左到右对应，字符串及 Serde 编码仅接受和输出小写、带连字符的 `8-4-4-4-12` 形式，不限制 UUID 版本或变体。全零值原样保留，不证明身份有效或授权；标识生成、各字段映射与生命周期仍待确定。此类型尚未接入候选 DDL、数据库或现有身份运行路径，不提供旧 `i64` 映射，也不代表正式协议已部署。

绑定确认和规则修改确认候选引用已存储的规则集版本，因此落盘时必须先满足版本外键；内存可以先完成更新并返回成功，不能由这一外键推断版本和确认已一起落盘。版本、确认和其他相关事实如何排序、形成一致快照及处理部分失败，仍须在持久化合同中解决。

## 3. 规则集版本与确认

一份规则集版本的逻辑结构为：

```text
version + content + timestamp + H(规范编码(version, content, timestamp))
```

`hash` 不包含自身；算法、编码规则、时间戳含义及规则语言尚待确定。候选使用不透明的内容字节用于保留精确编码；应用 owner 必须对结构化内容按确定性编码，防止依赖数据库 JSON 格式化、字符集或字段顺序改变哈希输入。受影响的身份、租户、状态等事实须进入内容或由其他可信的一致性合同绑定。数据库存储 hash 不证明真实性、授权确认或落盘完成。

多张卡可以分别经确认绑定同一规则集；经授权修改规则集并在共享根原子生效后，现有有效绑定立即使用新内容，不要求逐卡重新确认。确认如何覆盖后续修改、操作者权限、影响范围和审计需在写入合同中明确；不能从同事或组织关系自动产生新绑定。`OVERLAY` 可追加允许或拒绝，明确拒绝可阻止该卡从 `BASE` 取得对应权限；具体匹配、冲突和其他来源语义待设计。

数据库的规则集版本是不可覆盖的完整版本记录的目标，不等于共享根的进程实例和单调版本；内存按用户确定的方式在原规则集权威上原子更新，不以保留旧完整根为目标。数据库“保存每一版”与“内存一致后可先成功”之间存在明确边界：如果尚未落盘就崩溃，已生效版本可能丢失，不能声称数据库已保存所有曾生效版本。持久化队列、顺序、重复写对账、版本缺口、容量和失败通知须单独设计。

## 4. 生命周期和失败边界

- 冷启动从单个 MySQL 一致性快照加载授权必需的完整事实，验证关系、覆盖、规则内容和版本后才能进入正式服务。当前候选没有定义完整冷加载清单。
- 修改经 Gateway → TrustGraph → PolicyEngine 授权后，由受限 owner 对共享根中的事实、关系、索引、规则集四部分和根元数据进行一致原子更新；不能以数据库写入或旧投影作为另一个授权生效点。
- 内存原子更新并确认一致后可以返回成功，不能将成功解释为数据库已持久化。崩溃后从 MySQL 最新一致性快照重建，不主动恢复未落盘内存操作；未落盘撤权可能丢失。应由可用审计、监督或启动检查发现异常并提示检查最近权限变更，不能保证每次崩溃均留下记录。
- 有权人员首次建立超管时，超管管理模块根据系统已有接口构造全权限规则集并绑定用户卡；首次空库如何建立信任、确认、审计、恢复及接口变化如何更新覆盖仍须定义。正常请求不凭超管标识绕过引擎。
- 清理、停用、删除和跨租户变更必须先定义所有权及授权含义；本候选不以级联删除代替撤权或审计。

## 5. 待完成合同

1. 规则语言中 `OVERLAY DENY` 的精确资源/动作匹配、多来源冲突、条件、有效期、优先级和未知输入处理。
2. 规则集精确编码、hash 算法、版本号和时间戳规范，确认对共享版本变更的授权范围及审计。
3. 规则归属与跨租户可用范围，同租户多卡、重复绑定和各对象生命周期。
4. 完整冷启动事实：资源归属及可信 owner、资格、SoD、系统注册表、约束和覆盖证明。
5. 首次超管建立、用户凭证、会话/切卡、失效与审计恢复；接口变化时全权限规则集如何更新。
6. 单机内存提交与 MySQL 版本建档的排队、重试、失败报告、异常发现、重启快照及已接受的丢失边界。
7. 可重现的 Rust 验证、受控 MySQL DDL/约束/一致性测试、容量与并发验证，以及剩余合同和生产采用条件。
