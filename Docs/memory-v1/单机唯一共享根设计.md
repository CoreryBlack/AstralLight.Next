# memory-v1 单机唯一共享根设计

> 状态：目标设计，2026-11-12；当前候选代码尚未实现本合同，不构成正式授权、数据库集成或生产验收。
>
> 范围：单个受监督的组合进程，围绕新版用户、双卡、租户与规则集建立一个进程内关系对象权威；不兼容旧数据库和旧授权结构。工程合同以 [Rust 规范 §15.10](../规范/Rust后端编码规范_V1.0.md#1510-memory-v1-单机内存权威合同2026-11-12) 为准。

## 1. 定义与边界

整个单机系统在一个受监督进程内只有一个**当前有效授权根**。`astral-single-node` 是组合和生命周期 owner，负责创建并保留唯一根管理者、注入同源访问能力，以及启动和关闭顺序；`astral-authorization-root` 持有并维护根的内容、一致关系、索引及元数据。Identity、TrustGraph、PolicyEngine 和业务模块不能各自构建独立的运行授权根。不同测试或明确隔离的实验可创建候选，但不能安装为同一个服务实例的第二权威；多进程共享不在本设计内。

唯一根是逻辑上的关系对象数据库：存放授权所需的用户、身份卡、用户卡、租户、规则集及其版本、绑定、确认、状态、适用资源归属和限制事实，以及它们的关系和访问索引。根不自行决定 ALLOW；`PolicyEngine.evaluate()` 是正式授权判断入口。数据库承担冷启动、缺失补齐所需的持久数据读取及跨崩溃保存，不是内存完整时的当前授权裁判。

唯一根不是要求一个巨大对象内存地址永不变化，也不意味着只有一个线程或一份引用。稳定的是唯一管理者和唯一对外可见的当前权威；内部可以采用 HAMT、结构共享、局部替换或等价技术。构建中的候选及在途请求持有的一致视图不是第二个可独立提交、对外服务的权威。重启形成新的实例身份，不把旧进程内存当作当前根。

## 2. 对象与预建关系

冷启动从单个 MySQL 一致性快照读取新版授权事实，校验后建立对象、关系与索引。关系在构建或授权变更时维护，不在普通请求中重新从数据库行拼装。请求按索引定位对象并沿既有关系遍历，允许为本次评估创建小型只读视图、引用集合或计算结果；具体是否采用直接安全引用或 ID 索引由实现选择，必须证明一致性和生命周期，不能声称无分配或无锁。

```text
用户 A ─ 身份卡 A ─ 用户卡 A ─ 绑定 A [BASE] ─┐
用户 B ─ 身份卡 B ─ 用户卡 B ─ 绑定 B [BASE] ─┼─ 共享规则集 R ─ 当前版本
用户 C ─ 身份卡 C ─ 用户卡 C ─ 绑定 C [BASE] ─┘
                         └──── 绑定 D [OVERLAY] ─ 规则集 O ─ 当前版本
每张用户卡关联其用户和租户；每条绑定关联各自确认与适用状态。
```

多卡共享同一规则集对象和版本内容，不为每张卡复制一套规则。每条绑定和确认分别存在；不因组织或同事关系创建绑定。经授权确认的共享规则集修改在根内原子生效，立即影响现有有效绑定，不默认逐卡重新确认；变更确认覆盖范围、规则冲突及权限语义按相应规则合同确定，不能由关系图推断 ALLOW。

根按需要维护 `用户→身份卡/用户卡`、`租户→用户卡/子租户`、`用户卡→绑定→规则集/当前版本/确认`、`规则集→直接绑定及影响对象` 等正反向关系。反向关系描述影响，不自动授予权限。事实、关系和索引必须在同一可观察状态中一致；不能先发布部分关系，亦不能因为路径已建立而略过用户、卡、租户、确认、资源和状态检查。

## 3. 创建、共享与生命周期

1. 组合进程组织 DB 适配器开启一致性快照，加载完整数据范围，并由根管理者建立及校验对象、关系、索引、完整性状态、根实例、版本和预存内容 hash。明确区分已证明不存在、未加载、缺失、无效与不可验证。
2. 完整冷启动及必要消费者就绪后才开放正式请求。创建或安装第二个可服务 owner 必须被构造边界及启动检查拒绝；缺乏唯一性证明时不可开放 listener。仅凭 owner 类型不可克隆不足以证明进程唯一。
3. 模块获得由同一管理者派发的最小读取或受限修改能力。可克隆只读句柄是能力与生命周期隔离的实现选项，不是一份根、线程或一份规则数据；句柄不替代引擎授权，也不保证无锁。句柄数量、引用计数和同步成本须实测。
4. 根管理者存活覆盖所有消费者；关闭时停止接收新请求、按运行合同结束消费者后再销毁管理者。管理者失效、根状态不可信或无法证明实例一致时受影响请求 PENDING/DENY，不转用另一份根。

## 4. 读、修改和最终复核

正常请求由组合入口在首次需要根事实时创建一个贯穿本次完整生命周期的请求级读者；同一进程内参与请求的模块共享该读者，在同一读取阶段直接取得一致的对象关系与根实例、版本、预存 hash 和状态。引擎校验身份、双卡、租户、确认、规则、资源和限制。最终 ALLOW 前只核对同一根实例、单调版本、预存 hash、状态及可信时间；不再次遍历完整图或重算完整 hash。若元数据或可信时间不满足条件，不放行。最终检查通过的本次生命周期可以继续；后续请求重新判断。请求结束、取消或失败时释放读者；缺失补齐后同一读者受控进入新阶段并重新取得全部授权依赖。完整请求、并发和资源生命周期见[请求生命周期与共享根读取设计](请求生命周期与共享根读取设计.md)。

经授权的管理请求沿 Gateway → TrustGraph → PolicyEngine → 根读取 → 授权通过 → 根受限变更执行；管理请求是正式授权请求的一类，TrustGraph 的模块身份、接口路径或“超管”标记都不能绕过引擎。引擎评估时必须绑定本次具体管理动作、目标用户/用户卡/租户/规则集/绑定范围、拟提交变更摘要及稳定操作标识；TrustGraph 只能使用与该授权结果绑定的受限修改能力，不能把一次普通业务 ALLOW、另一项管理 ALLOW 或客户端自报参数转换成写权限。根在提交前还须校验授权结果未过期、目标和变更摘要未被替换、根版本/CAS 前提仍成立；不一致时拒绝提交并重新发起完整管理请求。其他影响授权的写者也须进入同一受控 owner。变更时受影响对象、关系、索引与版本/hash 原子对读者可见，不暴露中间态。

当前候选采用全局版本，任何提交都会使在途旧观察失效，即使修改与该请求无关。是否引入可证明依赖覆盖的更细粒度复核是后续优化，不能仅因关系图分支不相交就取消全局复核。并发技术不得引入请求和写入共用的开关门；短时同步、CAS 或结构共享等手段必须分别证明一致性、性能和资源边界。

## 5. 服务期缺失与增量补齐

冷启动目标是加载完整上下文；运行时发现某一请求的上下文确实未装载时，允许**该请求触发**对新版 MySQL 的受控一致性读取，并把缺失对象、关系、索引和覆盖状态作为同一根的一次增量更新。补齐完成后，本次请求从该根取得完整一致上下文并经引擎判断，最终复核通过才能 ALLOW；后续命中完整上下文的请求直接读根，不查询 DB。也就是说本次请求可以等待查库和补齐，数据库行本身不直接给出授权决定。

缺失、明确不存在、已撤销/删除、加载失败和根整体失效必须区分：已由当前内存权威确认的不存在、撤销或删除不能被数据库旧记录复活；根失效、完整性无法判断或无法安全限制影响范围时不能把它当普通缺失继续放行。未知、失败、超时、预算耗尽或查不到且无法证明不存在时，本次 PENDING/DENY；可证明完整且无匹配授权则 DENY。

一次补齐至少满足：

1. 根据可信请求上下文确定缺失范围及其关系闭包，在单个一致性读取边界内取得全部必要事实，区分空与不完整，并验证双卡、租户、状态、确认、规则、资源及引用；未经确认的关系不能补成授权。
2. 读取前记录同一根实例和版本，以及目标范围的存在/缺失状态；读取期间不阻塞无关请求。相同缺失的并发工作可合并，但不是授权证明。
3. 提交前在同一 owner 下验证读取前提仍成立，检查根实例、并发修改、目标范围和与已存在内存对象的冲突。DB 可能落后于内存：不得覆盖已有较新的内存事实、撤销标记或有效关系，不得因数据库中存在就推翻当前根；无法证明安全合并时丢弃候选并保持 PENDING/DENY。可用根版本变化触发有限重试，但版本不变本身不证明数据库事实完整、更新或与内存一致。
4. 以一个原子状态转换安装完整补齐块、关联索引、覆盖标记和新的根版本/hash；失败或取消不留下半块。之后本次请求从根重新取得完整上下文和元数据，执行正常鉴权与最终复核。补齐不是绕过显式确认的授权变更，也不制造新授权关系。
5. 设置有界范围、行数、字节、等待时间和并发；取消、数据库不可用、冲突或不可验证时安全失败，并记录必要的关联、结果和审计信息。数据库读取及根安装的具体隔离、覆盖证明、删除标记与持久化顺序必须在实现和采用前落成可验证合同。

## 6. 持久化与恢复

经授权的修改在内存原子完成并确认一致后可返回成功；这不证明 MySQL 或审计已落盘。崩溃后从 MySQL 最新一致性快照重建，不主动恢复此前未落盘操作；授权或撤权均可能丢失，应依可用审计、监督或启动证据提示检查最近权限变更，不能保证每次崩溃都有完整证据。内存权威与数据库持久化队列之间的顺序、失败、未知结果对账和提示仍需单独设计与验收。

## 7. 现状、验证与未决事项

现有实现是候选：`install_process_root` 经进程一次性安装槽创建唯一 `RootOwner`（`ArcSwap` 不可变快照加 HAMT 索引，消费者只持弱只读句柄），请求读者已接入完整请求生命周期（见[请求生命周期与共享根读取设计](请求生命周期与共享根读取设计.md) §6）。正式 ALLOW 只在 Serving 根下由 `PolicyEngine::evaluate_memory_v1` 给出，而生产没有 Serving 采纳路径；仅测试特性 `test-support` 可在隔离测试中采纳夹具根。另有显式实验采纳等级：`RootOwner::adopt_experimental` 在重新推导表行数、规则集单版本与 schema 合同后，仅对运维逐一点名确认的十类未证事实族放行，并把采纳记录存入服务快照；`astral-single-node` 的 `memory-v1-experimental` profile 用它从一个一致快照冷加载并只在回环地址服务 HTTP（见请求生命周期设计 §6，含一次真实 MySQL 端到端运行）。该等级不是生产采纳，不证明数据来源、覆盖、确认权威或持久化，正式路径仍拒绝。当前仍没有正式冷加载与覆盖证明、缺失补齐、全部写者覆盖及管理变更 CAS 提交；候选摘要不证明数据来源、完整性、确认、状态或规则语义。未完成采用合同与验证前，正式入口在生产中保持 PENDING，正式 listener 不开放。正式单机路径现在在就绪拒绝之前执行只读启动预检（`astral-single-node/src/memory_v1_preflight.rs`）：一致读取候选库，经进程根安装器安装后报告生产等级仍不能证明的事实族，随即释放根；预检不采纳、不发布、不服务，报告为空时仍由就绪门拒绝，故不开放 listener。

实施验证至少覆盖：同进程重复安装拒绝、同源能力与 owner 销毁、冷启动预建关系、共享 BASE 和单卡 OVERLAY 隔离、授权变更原子可见、首次缺失同请求补齐和后续无 DB、空/缺失/撤销区分、并发补齐及补齐与撤权竞争、DB 落后不能覆盖根、失败/取消/预算边界、最终复核与时钟、全部写者覆盖、MySQL 快照和崩溃恢复。所有测试使用 Rust；真实依赖和部署须有独立证据。已有一次实验 profile 下的真实 MySQL 冷加载运行（手工夹具数据），不覆盖补齐、故障、崩溃恢复与持久化。

待细化：全量冷加载后可证明的合法未加载范围及外部来源；对象布局和安全引用生命周期；hash 编码、状态和覆盖标记；共享规则集变更确认范围；数据库落后与删除标记的可验证合并协议；可信资源归属、规则匹配及会话；预算和性能。以上未决项不以文档或候选代码宣称已解决。
