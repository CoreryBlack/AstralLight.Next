# memory-v1 权限引擎与规则结构设计

> 状态：目标设计与讨论稿；规则语言、具体字段、实现和生产验收尚未完成。
>
> 范围：保留基础权限引擎，并按 memory-v1 的双卡、分层租户、规则集和共享内存权威重新设计规则内容及读取方式。本文不是最终 API、DDL 或代码实现。
>
> 旧基线：本地 `main` 提交 `9ab15556e7d44f99f32b8ba1e16f9beca4604ce9`。保留基础引擎及可复用能力，不意味着必须兼容旧模板、旧规则数据格式或旧授权发布机制。本文不覆盖现行工程规范与生产执行门禁。

## 1. 已确定方向

- 保留基础权限引擎，`PolicyEngine.evaluate()` 是正式授权的统一判断入口；Gateway 负责认证与清洗，TrustGraph 负责规则等治理和获准后的修改，共享根负责提供统一的授权事实与受限原子更新。
- 规则内容结构按照 memory-v1 重新设计：以规则集为规则定义与复用单位，经明确确认后绑定到具体租户的用户卡；不再依赖卡模板、模板规则或等级作为授权概念。
- 每个用户有独立身份卡和一个或多个可属于不同租户的用户卡；身份卡证明身份，用户卡承载对应租户中的授权上下文。
- 租户可分层，但不因上下级、同部门或同事关系自动推断或继承权限；每一项实际授权关系须由有权人员明确确认。
- 用户卡与规则集绑定保留 `BASE` / `OVERLAY` 层；`OVERLAY` 可以添加允许规则，也可以明确拒绝某项 `BASE` 权限，具体资源动作匹配与多条规则的冲突细节待定义。
- 规则集修改在内存权威原子更新并确认一致后立即对其现有绑定生效；数据库作为版本库保存各完整版本，持久化完成前的崩溃边界保持不变。
- 超管管理模块按系统接口构建并维护覆盖全部权限的规则集；超管请求仍与其他用户一样经引擎判断，不因超管标识直接放行。
- 正式请求从同一个共享内存权威读取完整一致的必要上下文；首次读取后，允许前只复核根实例、版本、预存内容 hash、状态与可信时间。服务期不以 SQL miss 直接放行。

## 2. 基础引擎保留什么

保留的是引擎作为**统一判断内核**的职责和可复用的基础能力，而不是提前声称旧实现所有代码可以原样使用：

| 能力 | memory-v1 目标 |
| --- | --- |
| 统一评估入口 | 接收可信请求上下文并给出可解释的授权决策；调用方不以角色名、身份卡或数据库源行绕过引擎。 |
| 上下文与资格校验 | 检查用户、身份卡、当前用户卡、租户之间的关系以及适用状态、有效期；信息缺失或不一致时不能放行。 |
| 资源和动作匹配 | 根据正式注册的资源、动作和可信资源归属进行匹配；具体资源标识、通配和动作别名按新规则合同定义。 |
| 规则组合 | 对用户卡的已确认有效绑定及其适用规则进行评估；冲突、条件、限制与层级语义必须有明确合同。 |
| 限制性检查 | 适用时检查资源归属、资格和职责分离等事实；哪些事实必须纳入完整上下文以具体请求与规则合同为准。 |
| 失败与可解释性 | 区分明确不允许与上下文不可用；决策保留必要原因和规则来源，敏感操作与授权变更遵循审计合同。 |
| 新鲜度复核 | 首次读取完整上下文；允许前校验实例、版本、预存 hash、状态和可信时间，变化或无法确认时不放行。 |

保留概念不代表旧 matcher 对所有新规则都可用。旧接口、编译器、索引、缓存和解释步骤分别评估其语义、所有权和复用价值；若与新合同不一致则需调整或替换。

## 3. 模块职责与请求路径

本节定义 `memroy-v1` 的**目标职责**，作为后续改造的边界，不表示现有 crate 已具备对应能力或完成接线。新版以[全新数据库设计](全新数据库设计.md)和 memory-v1 模型为准，不兼容旧数据库、旧数据和旧结构；`main` 及实验分支已有实现只作为设计和技术参考。下列名称对应当前 workspace 的模块，是否保留某个旧实现、拆分或调整依赖，须在具体改造中核对。

当前共享根仅有行模型、HAMT 与局部运行时等实验候选：候选 owner 和读句柄不证明数据来源、完整性或授权，也未实现全局唯一 owner、完整状态与全部写入口。现有单机组合与数据库读面仍有旧链路，尚未按下表完成统一接线；在完成适用合同及采用验证前，不得把候选作为正式授权证据。

### 3.3 依赖方向与数据所有权

- 单进程组合根装配各模块、创建唯一根 owner 并注入能力；Gateway、Identity、TrustGraph、引擎等只持有职责所需的接口，不能通过共享可变全局对象绕开 owner。
- 共享根拥有运行时授权事实及其一致索引；TrustGraph 等业务 owner 负责经授权的业务意图、确认与受限修改，不直接维护第二份可独立决定授权的事实。用户、双卡、租户、规则和绑定的具体修改 owner 及交接合同须逐项闭合。
- 业务服务拥有业务对象及可信资源归属的产生过程；哪些归属与限制事实需要进入根、如何绑定业务对象版本及处理并发变化，须在完整上下文合同中确定，不能凭客户端输入补足。
- 数据库拥有已持久化的数据和规则集版本档案；内存权威拥有当前进程的运行态。两者的时序和故障边界由持久化合同定义，内存成功不等于持久化成功。
- 公共类型和接口应指向稳定的语义边界；根不依赖 Gateway、Identity 或 TrustGraph 的具体运行时实现，也不把完整业务状态塞进所有模块的共享状态。

### 3.4 请求、变更与启动

**授权请求目标路径：**

```text
客户端 → Gateway：认证、清洗和传递可信身份上下文
              ↓ 首次需要根事实时创建请求级读者
       TrustGraph / 业务服务：共享读者，提出资源和动作，提供可信资源归属
              ↓
       PolicyEngine.evaluate()：使用同一读者的读取阶段
              ↓
       共享根：用户 + 身份卡 + 当前用户卡 + 租户
              + 已确认绑定 + 规则集及规则 + 适用限制事实
              ↓
       引擎：资格与范围检查 → 规则匹配与组合 → 决策
              ↓ 允许前仅复核元数据和可信时间
       ALLOW / DENY / PENDING → 操作或结束 → 释放请求级读者
```

这是目标流程，不表示具体函数签名或阶段顺序已经冻结；可信资源归属的 owner 和共享根读取接口需单独定义。同一请求的参与模块共享一个请求级读者；缺失补齐后在同一请求生命周期内受控刷新阶段，旧阶段的授权依赖和判断须重新读取及评估。生命周期、并发及跨进程边界见[请求生命周期与共享根读取设计](请求生命周期与共享根读取设计.md)。`PENDING` 表示无法取得或证明所需上下文，而不是将未经确认的授权当作有效。已证明无匹配的完整上下文应拒绝；判定类型与外部响应合同见 §3.5（2026-11-14 确认）。

**管理变更目标路径：** Gateway → TrustGraph → `PolicyEngine.evaluate()` → 共享根读取 → 授权通过 → TrustGraph 调用与本次授权绑定的受限方法 → 同一共享根原子更新事实、关系、索引、版本和内容 hash。管理请求必须把具体管理动作、操作者、目标租户/用户卡/规则集/绑定范围、拟变更摘要和稳定操作标识纳入引擎上下文；TrustGraph 身份、路径、角色名或超管标识不能替代该判断。根提交前校验授权结果与目标、摘要、根版本/CAS 前提仍一致，任何替换、过期、重放或并发冲突都拒绝提交并重新评估。引擎负责判断管理操作是否获准，不直接承担规则维护或自行生成授权关系。授权完成与写入之间的并发变化、写入前提和冲突处理需形成具体合同并验证，不能只凭一次独立鉴权断言修改仍然安全。

**管理动作与留痕（2026-11-14 确认）**：任何修改类请求——包括系统管理员对规则集的增删改查与各项确认——都是 T2 管理变更请求（§3.6），必须经 `PolicyEngine.evaluate()` 校验后由受限修改能力执行，**无任何身份或路径例外**；每次修改留痕（操作者、动作、对象、范围、变更摘要、operationId 与根版本关联；审计内部来源枚举见 §3.5）。这是"非法确认"的根源预防机制：**确认动作本身就是一个需要授权的请求**，引擎按操作者自己的绑定与规则判定其确认资格，无资格者的确认请求得到 DENY，而非事后审计追责。治理动作以普通规则表达——资源/动作在注册表登记后即可被规则集授予（如"确认绑定"即某资源×某动作的 ALLOW），确认权不另立独立模型；资格细则（治理动作清单、确认范围与批量确认）归批次 B，首个治理权威的建立归批次 C 初始化设计。读取类治理请求同样经引擎（无旁路），审计频率按栈规范执行。

**冷启动与持久化目标路径：** `astral-single-node` 组织 `astral-db` 从 MySQL 一致性快照加载新版数据，由唯一根构建并核对对象、预建关系及索引，就绪后才处理正式授权请求；运行中的获准变更在根内原子生效，持久化可在内存生效后跟进。服务期所需上下文未加载时，本次请求可触发受控查库；完整校验并安全原子补入同一根后，本次重新从根读取并经引擎评估，后续完整请求不查 DB。数据库行不直接构成 ALLOW。补齐冲突及失败边界见[唯一根设计](单机唯一共享根设计.md)。持久化顺序和异常告警尚未完成设计；崩溃后以 MySQL 最新快照重建，未落盘变更可能丢失。

### 3.5 判定类型与外部响应合同（2026-11-14 确认）

本节是已确认的合同草案：判定类型集合、规则效果闭集、外部 `reasonCode` 清单与 HTTP 映射。实现尚未按本节迁移（现实现仍输出两个通用码，迁移映射见下），不构成已采用证据。

**判定类型三型闭集**：`ALLOW` / `DENY` / `PENDING`（与现实现 `MemoryV1Decision` 一致；main 旧路径同为三型）。

- **ALLOW**：同一读取阶段取得完整一致上下文，聚合判定通过，最终复核（根实例、版本、预存 hash、状态、可信时间）通过；产出绑定本次评估的 admission。多绑定/多规则的聚合与冲突细节（如 deny-wins）属批次 A 冲突合同，**不随本节确认**。
- **DENY**（403）：命中显式 `DENY` 规则；绑定存在、上下文完整且已证明无匹配授权；会话用户卡无任何绑定。读状态"无效"（失效/停用）的 DENY 归属随批次 B 生命周期合同确定，本节不预置。
- **PENDING**：上下文未加载且受控补齐不可用或未完成；上下文不完整或不可验证；最终复核失败（版本漂移、时钟回拨、元数据变化）；绑定确认/版本/哈希校验不过；路由未适配 memory—v1（TrustGraph 中间件层拒绝，不进引擎评估）。

**规则效果闭集**：`ALLOW` / `DENY` 两种。现实现已固化（serde `SCREAMING_SNAKE_CASE`、`deny_unknown_fields`、≤4096 条规则、≤256 字节字段）；这些上限随批次 A 规则语言合同一并冻结。

**外部 `reasonCode`（v1 冻结清单；新增或改名须修订本合同）**：

| HTTP | reasonCode | 含义 | 可重试 |
| --- | --- | --- | --- |
| 403 | `AUTHORIZATION_RULE_DENIED` | 命中显式 `DENY` 规则 | 否 |
| 403 | `AUTHORIZATION_NO_MATCH` | 绑定存在、上下文完整，已证明无匹配授权 | 否 |
| 403 | `AUTHORIZATION_CARD_UNBOUND` | 会话用户卡无任何绑定 | 否 |
| 503 | `AUTHORIZATION_ROUTE_NOT_ADAPTED` | 路由未适配 memory—v1；变更路由在受限管理写路径实现前一律此码 | 是 |
| 503 | `AUTHORIZATION_CONTEXT_UNLOADED` | 上下文未加载且受控补齐不可用或未完成 | 是 |
| 503 | `AUTHORIZATION_CONTEXT_INVALID` | 上下文无效或不可验证（坏绑定：当前版本缺失/确认无效/防伪不过）；已触发受控补齐或升级告警（2026-11-14 A-1 追加，用户选定专属码；名称可再议） | 是 |
| 503 | `AUTHORIZATION_PENDING` | 兜底：可重试 PENDING 中未被上表枚举的情形 | 是 |
| 500 | `AUTHORIZATION_ROOT_UNAVAILABLE` | 根 owner 消失、根状态不可信（Invalid/Stopped）或无法证明根实例一致 | 否（需人工干预） |

`AUTHORIZATION_ROOT_UNAVAILABLE` 使用 500 是有意区分可重试性：可重试 PENDING 保持 503（客户端退避重试；进程内断路器经 `AuthorizationPendingRefusal` 标记计为成功），根级故障以 500 表达基础设施不可用、需人工干预——跨进程 HTTP 传输不携带进程内标记，届时只能凭状态码区分可重试性，故该区分必须落在状态码上。

**审计内部细分（批次 B 审计合同承接冻结）**：对外 `reasonCode` 之外，审计事件携带结构化来源枚举——DENY 来源 `rule_deny / no_match / card_unbound`，PENDING 来源 `context_unloaded / route_not_adapted / root_unavailable / fence_drift` 等。对外码随合同演进，审计枚举是"为何被拒/为何待定"的持久事实源，两者独立维护。

**非判定类型**：401（Gateway 认证失败）、404/405（路由未挂载）、Gateway 本地容量耗尽 503（按状态码计入断路器）不属于引擎判定类型，不在本清单内。

**实现迁移映射（未执行，实现期完成并同步更新既有断言）**：现实现仅输出 `AUTHORIZATION_DENIED`（403）与 `AUTHORIZATION_PENDING`（503）。迁移：显式 DENY → `AUTHORIZATION_RULE_DENIED`；无匹配 → `AUTHORIZATION_NO_MATCH`；未绑卡 → `AUTHORIZATION_CARD_UNBOUND`；未适配路由 → `AUTHORIZATION_ROUTE_NOT_ADAPTED`；未加载 → `AUTHORIZATION_CONTEXT_UNLOADED`；坏绑定/上下文无效 → `AUTHORIZATION_CONTEXT_INVALID`（2026-11-14 A-1 新增）；其余可重试 PENDING 保持 `AUTHORIZATION_PENDING`；根不可用 → `AUTHORIZATION_ROOT_UNAVAILABLE` 并由 503 改 500。受影响的既有断言（隔离全路径测试与 E2E 的 OVERLAY DENY、未绑定卡、未适配路由 503、根 owner 消失 503 等）在迁移时同步更新。

### 3.6 可处理请求类型与请求结构（2026-11-14 设计）

本节定义 memory—v1 路径可处理的请求类型集合、各类型请求的结构与构造责任、结构层 fail-closed 校验。判定输出类型见 §3.5；请求生命周期（作用域、读者、释放）见[请求生命周期与共享根读取设计](请求生命周期与共享根读取设计.md)。

**请求类型集合（可处理范围）**：

| 类型 | 名称 | 处理入口 | 进判定三型 | 现状 |
| --- | --- | --- | --- | --- |
| T1 | 受保护业务请求 | TrustGraph memory—v1 中间件 → `PolicyEngine::evaluate_memory_v1` | 是 | 已实现；可处理路由白名单当前仅 `GET /main/api/v1/permission-rules/registry`，其余路由一律 PENDING |
| T2 | 受保护管理变更请求 | 引擎评估管理意图 → 与授权绑定的受限写能力 → 根 CAS 提交 | 是 | 未实现；全部变更路由当前一律 `AUTHORIZATION_ROUTE_NOT_ADAPTED`，骨架不代表可提交 |
| T3 | 会话请求（登录/登出） | Identity 会话权威 | 否（不产出 admission） | 已实现 login/logout；登录用本次登录自己的请求读者核对卡绑定；刷新/切卡待批次 D |
| T4 | 公开/认证入口请求 | 各自协议，不读取根事实 | 否 | 正式路径未接线；不得为套用本设计虚构身份卡或授权上下文 |
| T5 | 结构性拒绝 | Gateway 清洗、验签、凭证与路由层 | 否 | 已实现（401/404/405） |

**T1 请求结构的分层构造**——核心不变式：**身份、卡、租户不进请求体**，只能从会话绑定取得：

1. **分发/Gateway 层**（认证与准入后）：不构造引擎请求，只提供会话绑定能力与请求作用域——`VerifiedSessionFacts`（私有字段 + 只读访问器：`session_id`、`session_version`、`identity`、`issued_at`、`expires_at`、`revocation_generation`；调用方不能把客户端提供的 UUID 变成已认证主体）、`RequestSessionExtension`（弱引用请求作用域，不可序列化，绑定到其他作用域即拒绝）、`RequestRootBudget` 准入（耗尽立即 503、不排队，作用域与读者租约释放后归还名额）。
2. **TrustGraph 中间件层**（构造引擎请求）：由冻结路由映射与现行 HTTP 方法→动作推断表得出 `resource` / `action`；`target` 取服务端确定的对象标识字节；`operation_id` 与 `operation_fingerprint` 由 request_binding 派生；先校验会话绑定本作用域且经已证明的会话传输到达，否则 PENDING。
3. **引擎层**：`MemoryV1Request { resource, action, target, operation_id, operation_fingerprint }` + 会话能力 + 根句柄；identity 只从会话取得，请求体不含身份字段。

**T1 字段合同**：

| 字段 | 来源 | 必选 | v1 参与匹配 | 合同要点 |
| --- | --- | --- | --- | --- |
| `resource` | 冻结路由映射 | 是 | 是（精确） | 不得取客户端原始字段；资源须在注册表登记 |
| `action` | 冻结路由映射 + 方法推断（GET/HEAD→read，POST→create，PUT/PATCH→update，DELETE→delete） | 是 | 是（精确） | 同上 |
| `target` | 服务端确定的对象标识与归属属性；统一路径下 v1 类型级路由暂为 None | 否 | 否，v1 仅冻结进 admission；对象级路由接入时由 handler 提供归属属性供 scope 谓词消费（§4.10） | 对象级授权（v2）须以可信资源归属证明为前置；不得凭客户端自报扩大读取范围 |
| `operation_id` | 调用方 `x-request-id`，经校验（恰一值、长度与字符集；写请求必须提供，读请求可用请求本地 UUID） | 是 | 否 | 操作关联标识，审计关联主键之一；≤64 字节 |
| `operation_fingerprint` | 服务端计算：域分隔 `ASTRAL_HTTP_REQUEST_V7` + method + 原始 URI + 有界请求体的 SHA-256（请求体先缓冲后恢复；2 MiB 上限、10 秒超时，失败即拒） | 是 | 否 | 冻结进 admission，防摘要替换 |
| 身份/卡/租户 | 会话绑定 + 根内用户-身份卡-用户卡-租户四角关系校验 | — | — | 不进请求体；请求体出现身份自报字段由 Gateway 清洗，下游混入旧身份头即拒绝 |

**T2 管理变更请求结构（骨架预留，批次 B 落地）**：T1 全部字段，另加管理意图四元组——治理动作闭集（绑定/解绑/确认/规则集建立/版本发布等，批次 B 冻结）、`MemoryId` 目标范围（用户卡/规则集/绑定/租户/确认）、拟变更摘要（根提交前防替换）、幂等 `operation_id`（根提交 CAS 前提，规范 §15.10.3 已冻结该要求）。

**结构层 fail-closed 校验清单**：路由不在冻结映射 → `AUTHORIZATION_ROUTE_NOT_ADAPTED`（503）；会话未绑定本作用域或会话传输标记缺失 → 503 PENDING；`operation_id` 缺失/多值/非法或指纹派生失败 → 结构性拒绝（400/408/413）；凭证无效、过期或撤销 → 401（Gateway 层，不进判定）；容量耗尽 → 503（Gateway 本地，非判定类型）。

**随批次待决**：`resource` 是否引入 `type:id` 复合表达（v2 通配前提，main 形态已登记于[基线继承文档](main基线可继承语义与重新设计边界.md)）；T2 治理动作闭集与 scope 表达（批次 B）；T4 公开入口清单（待设计）；刷新/切卡路由（批次 D）。

## 4. 新版规则：概念结构

规则集、规则条目、用户卡绑定及确认的统一逻辑结构以[统一规则集结构设计](统一规则集结构设计.md)为入口；本节说明引擎所需的规则要素，不另行定义第二套结构。

### 4.1 分层说明

新版应区分“谁获得规则”“规则适用于什么”与“请求是否可放行”：

```text
用户卡（某用户在某租户的授权载体）
    └── 经有权人员确认的绑定（BASE 或 OVERLAY）
          └── 规则集（规则定义与复用单位）
                └── 规则条目（资源、动作及其他经确定的规则内容）
```

实际判断还需身份、卡、租户、绑定、规则集与条目状态、有效期和可信资源归属等相关事实。规则集名称、卡的存在或租户父子关系不能代替规则命中。多张卡可绑定同一规则集，其原子修改立即影响既有有效绑定；具体数据库表结构未定。

### 4.2 新规则需要表达的内容

下表是**设计要素，不是最终字段清单或已实现功能**。是否由规则条目、规则集、绑定或资源上下文承载，需避免重复来源和语义冲突。

| 要素 | 需要回答的问题 | 当前边界 |
| --- | --- | --- |
| 规则及规则集身份 | 哪条规则、属于哪个规则集，如何追踪变更？ | 规则集由版本号、内容、时间戳和前三者计算出的 hash 组成；规则身份与关联方式待定，规则集版本不同于共享根版本。 |
| 资源 | 可操作什么类型或具体对象，资源归属如何确定？ | 归属来自可信服务端事实；对象级、类型级及通配语义待定义。 |
| 动作 | 能对资源执行什么操作？ | 使用已注册动作；动作别名、通配和组合语义待定义。 |
| 效果 | 命中时允许还是拒绝？ | 支持允许和明确拒绝；`OVERLAY` 可拒绝对应 `BASE` 权限。具体匹配范围和多个规则冲突的完整顺序待定义。 |
| 适用范围 | 规则在什么租户、用户卡、资源范围内有效？ | 卡和资源的租户边界必须明确；跨租户授权及范围表达待单独决定。 |
| 生效状态与时间 | 什么时候、在什么状态下可使用？ | 相关对象的启停与有效期均需定义并使用可信时间；具体放在哪一层待定。 |
| 条件与限制 | 是否限定额外上下文或职责分离？ | 是否支持条件表达式、支持哪些类型及失败语义待定；不能把无法解析的条件视为满足。 |
| 来源和确认 | 这张卡为什么有这项授权、由谁确认、如何撤销？ | 每项实际授权关系须有明确确认并可追溯；具体确认粒度、版本和审计合同待定。 |
| 绑定层 | 该规则集由哪张卡以 `BASE` 或 `OVERLAY` 绑定？ | 层属于绑定，非规则集来源；`OVERLAY` 可追加允许或拒绝对应 BASE 权限，精确冲突合同待定义。 |

候选 SQL 或旧 `permission_rule`、`rule_set_entry` 中存在 `condition`、`priority`、`DENY` 等字段，不证明新版正式引擎已经实现这些语义。新版已确定需要 `OVERLAY` 拒绝；条件与优先级已裁剪出 v1，规则条目结构（含两级时限）见 §4.4，聚合冲突细节仍待批次 A 冲突合同。

### 4.3 示例：只展示概念，不是协议

```text
租户：财务部 A1
用户卡：用户 B 的 A1 卡
绑定：经确认，将「报销基础」规则集绑定到该卡（BASE）
规则集「报销基础」：
  - 规则 R1：资源「报销单」；动作「查看」
  - 规则 R2：资源「报销单」；动作「提交」
请求：B 使用 A1 卡查看一张服务端确认归属 A1 的报销单
```

引擎还须确认身份、用户卡、绑定及规则在请求时有效，并依据新规则合同判断资源和动作是否命中。示例中的 B 具有经确认的绑定，不意味着同部门的 C 自动取得该绑定；也不意味着 B 能仅凭 A1 与 A2 的父子关系访问 A2 的报销单。资源范围、共享规则变更及冲突语义尚未决定，示例不预先确定这些行为。

### 4.4 规则条目结构 v1（2026-11-14 确认，含两级时限）

**设计依据**：2026-11-14 对主流策略引擎的调研——Cedar（`@id` 注解、forbid-override、时间走 `context` 条件）、AWS IAM（`Sid`、显式 deny 永远压制、时间走 `Condition`）、XACML 3.0（target+condition+effect，deny-overrides 等标准合并算法）、Zanzibar（过期份额建模为带时间戳的嵌套关系，求值时比较）、SpiceDB（caveats → v1.40+ 将过期关系提升为一等字段）。v1 无条件语言（带条件输入 fail-closed 拒绝），故时限采用**数据流派一等字段**，不走条件表达式。

**规则条目**（规则集 content 内的规范编码；`deny_unknown_fields`，未知字段或未知效果使该版本解析失败、不可采纳）：

| 字段 | 类型与约束 | 必选 | 语义 |
| --- | --- | --- | --- |
| `ruleId` | string ≤64B，规则集版本内唯一 | 是 | 稳定身份，审计与解释锚点（Cedar `@id`、IAM `Sid` 同型） |
| `resource` | string ≤256B | 是 | 资源类型标识，须在注册表登记；v1 精确匹配，通配为 v2 预留 |
| `action` | string ≤256B | 是 | 已注册动作；v1 精确；语义为动作集合，一条一动作即集合的一个元素 |
| `effect` | `"ALLOW"` \| `"DENY"` | 是 | 效果闭集（§3.5） |
| `validity` | `{ "from": Unix秒\|null, "until": Unix秒\|null }` | 否（缺省 = 开区间） | 条目级时限；`from < until` 校验，违反则解析失败 |
| `ownerScope` / `tenantScope` | `ownerScope ∈ {self, all}`；`tenantScope ∈ {self, self+descendants}`（跨企业显式映射另计，§4.10） | 否（缺省最严 `self`/`self`） | 可见性范围谓词；双层生效 = 条目 scope ∩ 绑定 scope（§4.10）；对 ALLOW/DENY 对称 |

**两级时限语义（用户确认两级都支持）**：

- **绑定级**：`memory_card_rule_set_binding` 增列 `valid_from` / `valid_until`（可空 = 开区间，语义为 Unix 秒）——这是 schema 候选的修订需求，随批次 A/B 编码合同冻结时统一落 DDL，不在本节单独改候选文件；
- **有效窗口 = 绑定窗口 ∩ 条目窗口**；窗口判定：`from ≤ t` 且（`until` 为空或 `t < until`），`t` 为根可信时间观察；
- 窗口外或交集为空 → 该规则对该卡**不适用**（跳过，非 DENY）；全部不适用且无其他有效授权 → `AUTHORIZATION_NO_MATCH`（403，§3.5）；
- 窗口对两种效果**对称**：过期的 `OVERLAY DENY` 同样停止拒绝；
- 读阶段以一次可信时间观察完成分类；最终复核重观察可信时间并复核胜出规则的窗口仍成立，边界穿越或时间条件无法确认 → PENDING/DENY（规范 §15.10.3）；
- 条目时限变更 = 规则内容变更 = 新版本（走规则集修改确认）；绑定窗口变更 = 管理变更（T2），须确认、不动规则集版本——两者的确认细则随批次 B 确认权合同冻结。

**v1 明确不支持**（继承裁剪，见[基线继承文档 §2.3](main基线可继承语义与重新设计边界.md)）：条件表达式、优先级。

**冲突语义的行业证据**：聚合 deny-wins 是 Cedar forbid-override、IAM 显式 deny 压制、XACML deny-overrides 三大引擎的独立收敛，现行实现与之一致——批次 A 冲突合同以此为基准；`first-match` 在主流中属少数派（XACML first-applicable）。该基准的正式确认仍归批次 A 冲突合同。

### 4.5 绑定形态与聚合语义（2026-11-14，部分确认）

**绑定形态（用户确认）**：

- 一张用户卡的默认绑定形态：**多个 BASE 共享规则集绑定 + 至多一个 OVERLAY 规则集绑定**；
- OVERLAY 规则集的修改与 BASE 共享集**相同**：直接在规则集源上修改产生新版本（走规则集修改确认），**不是追加新的 OVERLAY 绑定**；
- "针对某卡撤销某权限"通过该卡 OVERLAY 规则集中的 DENY 实现。用户确认的例子：BASE 有 ALLOW「新增x-001」，该卡 OVERLAY 有 DENY「新增x-001」→ DENY **直接压制 BASE 中对应的 ALLOW**，返回 DENY；
- **OVERLAY-only（无 BASE）合法**，定位为：针对极特殊用户、内部创建、不走正常发卡流程，直接以 OVERLAY-only 满足极特殊需求；正常发卡流程为 BASE+OVERLAY。其治理约束（谁有权创建、如何审计）归批次 B 确认权合同。

**聚合语义（对单卡求值，随绑定形态确认）**：

- 适用规则 = 该卡全部适用绑定（全部 BASE + 至多一个 OVERLAY）的规则经两级窗口（§4.4）过滤后的条目；
- 任一条 DENY 命中同 (resource, action) → **DENY**（压制该卡对应的所有 ALLOW）；无任何 ALLOW 命中 → `AUTHORIZATION_NO_MATCH`；否则 ALLOW；
- 窗口外的规则不适用（跳过），不影响聚合，也不构成坏绑定。

**绑定唯一性与版本新鲜度（2026-11-14 确认）**：

- **禁止同卡同规则集双绑**：`(user_card_id, rule_set_id)` 组合**至多一条绑定**（不分层）——规避"统一版本被当作 OVERLAY 再发一次"；装载违例拒绝采纳（fail-closed），写入违例拒绝（批次 B 受限写路径实现时生效），schema 候选修订加入该唯一键；
- **版本新鲜度不变式**：每个有效绑定（BASE 与 OVERLAY 同此）求值时**一律使用规则集当前最新已发布版本**，不存在"绑定停留在旧版本"的状态；版本推进经规则集修改确认后原子生效于全部绑定（逐卡不重新确认，规范 §15.10.1 已冻结）；绑定确认记录中的 `version_bytes` 是绑定时刻的历史事实（追溯用途），**不冻结**求值版本；某卡需要保持旧行为时，通过其 OVERLAY 写 DENY/ALLOW 表达，而不是留在旧版本；
- **连带合同需求——"当前版本"机制**：候选 schema 明文未定义当前版本指针、且禁止从最大值或时间戳推断当前版本（候选注释 6）；"保证最新"要求"当前版本"有**显式确定机制**（发布标记或当前指针），列入 schema 修订与编码合同（批次 A/C）；
- **实现迁移注记**：现行实现要求"绑定确认的 `version_bytes` 必须等于所选版本"——在新不变式下规则集每次出新版本都会使全部绑定落入确认不匹配 → PENDING；实现期须改为"绑定确认有效 + 当前版本具备变更确认"，随 reasonCode 与时限求值迁移一并执行。

**坏数据处置合同（2026-11-14 A-1 确认，用户逐项决定）**：

- **装载期（A-1.1）**：发现坏数据（防伪/确认/引用闭合失败）→ **拒绝装载**，系统不自动修复；运维团队依据最终日志归因、确认并**修复数据库内容**后重新装载（统一告警等级 L4）；
- **服务期三级响应（A-1.2）**：
  1. **拒绝放行 + 可重试提醒**：坏绑定命中即 PENDING（`AUTHORIZATION_CONTEXT_INVALID`，503），绝不跳过坏绑定继续算；
  2. **受控查库补全**：触发由坏绑定引起的**内存增量构建**（服务期补齐语义），并发送通知（L2）——数据库可解则修复内存状态、重新评估放行；
  3. **升级**：数据库也无法解决 → 上升至告警通知（L3）、向用户明确提示该功能异常、警告运维团队排查。
  实现依赖批次 C-3（根协调器/补齐）；**C-3 落地前为两级**：拒绝放行 + 直接升级告警（跳过补全级）。修复性重读必须遵守补齐合并约束（不得复活撤销、不得覆盖较新内存事实），"内存状态本身可疑时的优先级"细则归 C-3 合并协议；
- **统一告警等级（A-1.4）**：建立统一完善的警告等级体系。初稿四级：**L1 提醒**（可重试、自动缓解中）/ **L2 通知**（自动缓解已启动并留痕）/ **L3 警告**（缓解失败、用户可见异常、运维应排查）/ **L4 告警**（系统性失效、必须立即人工介入）；完整体系为跨批次新设计项（monitor/审计细化），本节锁定坏数据各环节的落位：装载拒绝=L4、补全通知=L2、升级=L3；
- **不自动恢复（A-1.5，同三级响应）**：系统不编造、不跳过、不超时放行；升级后保持拒绝直至数据修复，修复动作本身过引擎并留痕；
- **根源预防层清单（A-1.6 确认）**：(卡,规则集)唯一、每卡至多一个 OVERLAY、版本新鲜度、显式当前版本机制、代际栅栏+CAS、确认过引擎+留痕——六层消除常规坏数据；残余源（崩溃半截发布→C-2，绕过根写库→C-4）由对应批次关闭；
- **衔接确认（A-1.7）**：批次 C-2 落地前，崩溃半截发布数据在装载期被拦 = 正确行为，不算缺陷。

**聚合冲突合同已闭合**：见 §4.8（2026-11-14 A-2 确认），本节不再有未确认项。

### 4.6 代际栅栏与修改窗口（2026-11-14 确认）

移植 main 的代际栅栏机制（source_generation 总账、栅栏声明、发布 CAS 核对、读者版本对章；证据见[基线继承文档 §2.4](main基线可继承语义与重新设计边界.md)），应用于 BASE/OVERLAY 规则集的修改路径。

**栅栏声明（修改登记）**：任一 BASE/OVERLAY 规则集的修改，发起时除已冻结的管理请求上下文（操作者、对象、目标范围、拟变更摘要、稳定 operationId，§15.10.3）外，绑定**栅栏声明三元组**：目标规则集当前版本 `V_rs`、根全局版本 `V_root`、预存内容 hash——受限修改能力核验这些是发起方实际观察到的值。

**修改窗口与拦截**：

- 同一对象**同时只允许一个进行中的修改**：窗口内对同一对象的第二笔修改，栅栏直接打回（CAS 前提不成立），重新发起完整评估；
- 窗口内**碰到被修改对象的读请求立即 PENDING**（503 可重试，reasonCode 用 `AUTHORIZATION_PENDING` 兜底码），**不排队、不等待**——用户确认采用此语义：这是 fail-closed 安全失败，不是"请求与写入共用的开关门"（排队等待被 §15.10.3 排除）；
- 未涉及被改对象的请求完全不受影响。

**完成与放行（版本一致才可放行）**：

- 修改完成 = 新内容构造 + **hash 重算** + **新根版本**，一次原子发布（原子可见 §15.10.3 已冻结）；
- 发布前提：声明的 `V_rs` = 实际当前版本、`V_root` = 根当前版本——**一致才发布生效**；不一致（并发抢先、重放、摘要替换）→ 本次修改作废、零副作用、重新评估发起（§15.10.3 已冻结 CAS 前提，栅栏将其显式化为同对象修改互斥）；
- 发布后：根版本 = `V_root + 1`，对象当前版本指向新版本，新 hash 对全部读者原子可见；
- 读侧放行始终经最终复核（已冻结）：请求读取阶段绑定的版本 = 根当前版本、预存 hash 一致、可信时间有效 → ALLOW；修改窗口内读到的旧版本，复核时因根版本已推进 → PENDING——即"版本号与栅栏声明一致才可放行"的读侧表达。

**与冻结合同的关系**：正确性由"原子快照 + CAS 发布 + 最终复核"承载（均已在 §15.10.3 冻结，不新增开关门）；"拦截"实现为立即 PENDING 的安全失败，承担避免白跑与同对象写-写互斥的运维语义，不承担正确性职责。

**批次 B 延伸**：撤权专属栅栏（main 的 `revoke_fence`：只增不减、永不超前总账、零值 = 未发生撤权）随批次 B 撤权路径移植，撤销传播继承"版本一致才可放行"语义。

### 4.7 修改影响隔离与依赖范围复核（2026-11-14 用户追加确认）

**新规**：共享根维护多个 BASE 和 OVERLAY 规则集；**修改其中一个，仅影响涉及该对象的请求，其他 BASE/OVERLAY 正常服务**。

**语义分解**：

1. **对象级版本轨**：每个规则集维护自己的单调当前版本与内容 hash；根全局版本继续存在（根实例、状态、审计序），但不再是读路径复核的唯一依据。
2. **修改影响隔离（读侧）**：
   - 修改 R 的窗口内，仅"依赖集包含 R"的请求被拦截——实现在读者解析绑定时遇到带活跃栅栏的规则集立即中止 → PENDING（无需读完整个上下文，即 §4.6 的"立即 PENDING"按对象生效）；
   - 依赖集不含 R 的请求照常评估与服务；
   - 在途请求（已过读取阶段）：最终复核改为**依赖范围比对**——逐一核对读取阶段登记的（对象 → 版本）是否仍一致；R 已变 → 涉及 R 的在途请求 PENDING；其他请求复核通过、正常放行。
3. **依赖向量的可证明覆盖**：[单机唯一共享根设计 §4] 对细粒度复核的告诫是"不能仅因关系图分支不相交就取消全局复核"——本节以**构造性覆盖**回应：评估所用事实结构上必经请求读者（类型化只读接口，禁止旁路取事实），读者对每类触达事实登记（对象 → 版本）；复核集合 = 登记集合，不多不少。v1 依赖集 = 会话卡的绑定集（绑定集版本）+ 各绑定所选规则集的当前版本 + 根实例/状态/可信时间；批次 B 扩展到用户/卡/租户事实版本。旁路取事实由测试守卫排除。
4. **写侧不变**：栅栏声明与 CAS 前提仍含根全局版本（不同对象的修改经全局版本串行，冲突者重新发起；对象级写并发留作后续优化）；同对象互斥不变。
5. **根全局 hash 的角色调整**：根级预存 hash 保留为根完整性/采纳元数据；读路径复核使用对象级版本 + hash——若继续要求全局 hash 不变，任何无关修改都会使全部在途请求失效，与本次新规矛盾。
6. **撤权衔接（批次 B）**：解绑/撤权使"会话卡绑定集版本"+1 → 该卡在途请求复核失败 → 撤权对在途请求即时生效，与"撤权在复核前发布则旧判断不能放行"的冻结语义衔接。

**文档同步义务**：本条修订[单机唯一共享根设计](单机唯一共享根设计.md) §4 与[请求生命周期与共享根读取设计](请求生命周期与共享根读取设计.md) §3 中"全局版本变化即使与本请求无关也使旧观察失效"的候选语义，随批次 A 合同完稿同步改写正文；规范 §15.10.3 的"复核版本"措辞届时一并澄清为对象级依赖版本。

**残余风险（如实记录）**：正确性从"全局版本一刀切"转移到"依赖登记的完整性"上——覆盖性由构造保证，但任何绕过读者的事实访问都会造成未登记依赖，必须由守卫测试持续排除；此风险写入批次 A 验证清单。

### 4.8 聚合冲突合同（2026-11-14 A-2 确认）

**算法定源（用户确认 A-2.1）**：main 的专用算法——ALLOW-only 热状态上的顺序确定性匹配 + 缺省拒绝——是本合同的基础；memory-v1 在其上引入 DENY 规则后的自然扩展即聚合 deny-wins。**当适用规则中不含 DENY 时，两者语义等价**（main 的 first-match 在 ALLOW-only 状态下只影响解释引用哪条授权，不影响判定结果）；差别仅在 memory-v1 增加了 DENY 压制与两级窗口。算法冻结为**唯一语义**：无算法选择字段、无运行时开关、无身份或路径例外（§3.4）；引入新语义须修订本合同与规范 §15.10，不是运行时配置。

**精确语义**：

| 要素 | 定义 |
| --- | --- |
| 输入封闭集合 | 本会话卡全部适用绑定（全部 BASE + 至多一个 OVERLAY）经两级窗口过滤后的规则条目；其他卡、租户父子、对象级 target 不在输入内 |
| 命中 | resource+action 精确相等且窗口有效 |
| DENY 压制 | 任一 DENY 命中 → 压制本卡全部 ALLOW（跨绑定全局；层仅作 provenance，§4.5） |
| 决策次序 | ① 任一 DENY 命中 → **DENY**；② 无 DENY 但存在坏绑定（版本/确认/防伪不可验证）→ **PENDING**；③ 无 DENY、无坏绑定、有 ALLOW → **ALLOW**；④ 无任何命中 → **NO_MATCH（DENY，403）** |
| 关系不一致 | 身份/卡/租户四角关系不一致 → **DENY**（已证明的错配，确定性拒绝）——与"不可验证 → PENDING"严格区分，不得混淆 |
| 顺序无关性 | 结果与绑定枚举顺序、规则排列顺序无关；实现短路（发现 DENY 即停）为性能自由度，不得破坏该性质 |

**A-2.4 用户选定 B：确定性 DENY 优先**。已由合法绑定命中 DENY 时，其他绑定坏**不**使请求转为 PENDING——结果为 DENY。论证：deny-wins 下 ALLOW 永远无法压制 DENY，故结果与坏绑定内容无关，属"可证明确定的拒绝"（规范 §15.10.3"上下文不完整时 PENDING/**DENY**"明文允许）；该论证依赖本合同的唯一算法，须以测试固化。**与 A-1.2 的关系**：判定与数据修复解耦——坏绑定的发现无论请求结果如何都按 A-1.2 留痕/通知/触发补全；仅当请求判定依赖坏绑定时才进入 PENDING 三级响应。

**实现迁移（未执行，随 reasonCode/两级时限迁移一并）**：现行实现在坏绑定上短路返回 Pending（`policy-engine/src/memory_v1_formal.rs:196-216`），须改为 pending 标记 + 上述决策次序。

**测试义务（A-2.5）**：① 打乱绑定/规则顺序，决策不变；② 短路开启与关闭等价；③ DENY 命中 + 坏绑定任意位置 → DENY（确定性优先的论证固化）；④ 关系不一致 → DENY 与坏数据 → PENDING 的区分保持。全部列入批次 A 验证清单。

### 4.9 资源/动作注册表与登记状态机（2026-11-14 A-3 确认）

**承载（A-3.8，用户确认）**：注册表 = **路由元数据内联 + 启动聚合 + 根内状态机**——开发者只在路由定义处声明一次（resource、action、是否 memory—v1 适配）；组合根启动时聚合全部服务的路由元数据，校验（标识符规范、冲突、唯一性）后装入根。main 的三步手工维护（注册表加行、路由映射表加条目、推断特例）收缩为路由声明一处；§3.6 的适配路由白名单由路由元数据派生。**请求触发自动注册与并行目录同步明确拒绝**（前者是 fail-closed 的反面，后者是漂移根源）。

**登记状态机（A-3.9，用户确认）**：三态，每次迁移即一次原子发布（代际栅栏 + 根 CAS，§4.6），状态只存根内一处——无旁表、无同步任务、无中间态：

- **Active**（可被规则条目/路由引用）；
- **RetireRequested**（退役请求已过引擎，等待前置满足）；
- **Retired**（不可再被引用）。

迁移：新代码部署（声明）→ Active；管理注册（T2 过引擎 + 确认）→ Active；Active → RetireRequested（T2 过引擎）→ 前置（撤权已发布 + 零活跃绑定引用）满足 → Retired。守卫：规则条目或路由映射引用非 Active 资源 → 结构性拒绝（装载与评估双执法）。

**激活语义（A-3.10，用户确认：声明即激活，安全和影响面最小）**：

- 新资源声明随部署自动进入 **Active**——部署审批（Exec-L3）即授权面扩充的门禁；
- **唯一的自动授权回填是超管规则集**：新资源 × 其动作自动补齐进超管规则集，使管理员可配置、可管理新资源（§5.2 语义延续，main 的启动种子行为同型）；
- **其他一切用户的授权都需要管理员显式配置**（经有权确认的绑定授予）——声明即激活不给任何普通用户任何权限；无绑定即无权限是模型固有性质；
- 影响面：新资源激活后、配置前，普通用户请求表现为 NO_MATCH（403），管理员表现为可配置。

**自定义资源注册（A-3.2）**：T2 管理变更请求过引擎（确认人需持有"注册资源"治理动作授权）→ 代际栅栏 → 根 CAS 发布 → Active；main"先落库后进内存、失败重启对账"的分裂中间态不存在（单事务原子完成）。

**执法点（A-3.4）**：继承 main 五件套——启动声明校验（引用未声明资源拒绝启动）、路径前缀映射、HTTP 方法→动作推断（含特例覆盖）、编译期路由契约测试（include_str! 路由源 → 映射 → 注册表校验）、超管自动补齐；**新增**：引擎评估时校验 resource ∈ 注册表——评估引用未注册资源属结构性拒绝。

**标识符与容量（A-3.5）**：继承 main——首字符小写 ASCII 字母、仅 `[a-z0-9_-]`、**只拒绝不归一**；资源名 ≤128B、动作名 ≤64B、单资源 ≤64 个动作（数值随批次 A 编码合同复核）。

**退役（A-3.6）**：fail-closed——RetireRequested 在前置满足前不得 Retired，不静默删除（main 的 `RESOURCE_RETIREMENT_REQUIRES_PUBLISHED_REVOKE` 原则延续）。

**无并行目录（A-3.7）**：注册表 = 唯一事实源，管理面读根内注册表视图；main 的 domain_resource_type/permission_action 式旁表与 scan 同步 stub 不复存在。

**清单管理（A-3.3，2026-11-14 确认：清单由状态机活态管理）**：v1 注册清单**不是一次性设计决定，而是登记状态机的活态输出**——业务资源 = 代码路由元数据的启动聚合（当前仅 `permission_rule` 适配，随路由适配进度自动增长）；治理动作 = 治理路由的元数据，同样经声明 → Active（B-1 设计时只决定治理路由的适配顺序，不单独维护清单）。闭包保证不变：规则条目引用非 Active 资源 → 结构性拒绝（守卫）——规则只能授予已注册资源，清单天然封闭。超管自动补齐范围 = Active 集合的全量 product。**A-3 就此闭合。**

### 4.10 可见性范围与归属分工（2026-11-14 A-4 确认）

**粒度分层**：① 规则匹配 = 类型级精确（§4.4/§4.8）；② **双层 scope 可见性（v1）**：owner 维度（本人/全部）× tenant 维度（本租户/本租户+子孙）的谓词；③ 逐对象显式授权（"允许读某一张单"）= v2。

**双层 scope（A-4.1 确认）**：有效范围 = **条目 scope ∩ 绑定 scope**（owner 与 tenant 两个维度分别取交集）；条目 scope 随内容版本化（§4.4 表），绑定 scope 为绑定属性（schema 修订进 B-3）；scope 变更 = 内容/绑定变更，走各自的确认与栅栏路径。

**词汇与缺省（A-4.3 确认）**：`ownerScope ∈ {self, all}`、`tenantScope ∈ {self, self+descendants}`（跨企业显式映射另计）；**条目缺省 = 最严（self/self）**——不声明范围就只能看本人的、本租户的，要看更多必须白纸黑字声明。scope 谓词仅对携带对象（target 或对象集）的请求生效；纯目录/类型级无对象请求不受 owner/tenant 过滤（租户边界由绑定同租户保证）。

**命中定义扩充（A-4.4）**：命中 = resource + action 精确相等 + 窗口有效 + **scope 谓词满足**；scope 对 ALLOW/DENY **对称**——范围外或过期的 DENY 同样不生效。

**归属分工（A-4.2 确认）**：

- **租户结构树 = 鉴权数据，入根**：租户层级是鉴权访问高频点，根从 `memory_tenant` 预建租户树（父子索引 + 子孙解析），`self+descendants` 在根内解析；树的重挂/变更 = 根变更（过栅栏），树版本进入 §4.7 依赖向量；
- **owner_user_id = 业务数据，留业务库**：它是订单/单据的业务属性，不是鉴权数据；单对象请求由业务 handler 以服务端可信事实随 target 提供（对象 id + 归属属性），引擎评谓词；列表请求由业务服务按 admission 下发的 scope 过滤自己的查询（main data_scope 概念继承：范围 → 查询条件）；
- 根不为业务对象建归属表——无双写、无漂移；候选 schema"资源归属冷加载"待定项就此关闭：**归属由业务域持有，租户树入根**。

**跨租户授权 = 显式映射（A-4.6 确认）**：租户树形 = 企业节点下的部门子租户（如 88 → 88.1/88.2/88.3；100 为另一企业号）；`self+descendants` 只覆盖本公司子树；**跨企业访问 = 显式映射授权**——如"88.1（总公司财务部）→ 100（分公司）财务状况"是一条过引擎、经确认、留痕、根 CAS 发布的授权事实（映射是根事实，随代际栅栏管理）；映射变更 = 管理变更（T2）。**树解析永远不产生跨企业权限**。

**呈现（A-4.7）**：跨租户可见的响应/审计标注来源租户（"区分归属"），随批次 D/响应规范细化。

**文档同步义务**：§3.6 target 行修订（对象标识 + 业务侧归属属性，替代"路径字节"）；实现迁移新增——条目/绑定 scope 解析、租户树预建与子孙解析、admission 附 scope、映射授权事实。

### 4.11 确认权与治理动作合同（2026-11-14 B-1 确认）

**资格表达（复用，零新增模型）**：治理动作 = 注册表登记的 (resource, action) 对；确认权 = 操作者卡绑定治理规则集、其中 ALLOW 条目覆盖该 (resource, action)，且双层 scope 谓词对治理目标成立（§4.10）。

- **双层治理授予（N-5）**：有效范围 = 治理条目 scope ∩ 治理绑定 scope（owner 与 tenant 维度分别取交集）——两层都显式声明宽 scope 才真的宽；缺省最严会让治理授予静默失效。
- **双来源归属（N-6）**：治理目标（绑定/规则集/卡）的归属属性来自**根事实**（card.tenant、rule_set.owner_tenant）；业务目标的归属来自业务库（§4.10 分工）。两类互不混用，实现者不得在根内为业务对象建归属表。

**治理条目 scope 要求（N-1）**：确认类条目**必须显式 `ownerScope: all`**——缺省 `self` 使确认动作对一切他人目标 ScopeDenied（缺省最严的正确推论，不是缺陷）。合同写明；运行后果确定性 403，测试即刻暴露漏写。

**SoD 自签禁止（N-7，引擎层结构规则）**：confirm 类动作的受益人 == 操作者 → 确定性拒绝（独立于 scope——`ownerScope: all` 放大不了 SoD；审计 source=self_confirmation）。批量中任一条自查 → 整批 DENY。

**互惠扩权/治理集自改（B-1.4 暂缓）**：结构防线（资源类型隔离 `governance_rule_set` 等）暂缓设计与实现（§6.9）；当前信任假设 = 单首管信任域，自改治理规则集接受。

**批量确认（N-10）**：一次 T2 请求确认 N 个对象 = 单次根 CAS 原子发布；条目级追溯（operationId + 条目序号）；任一条无资格或自查 → 整批 DENY；批量上限 = 运营参数；多卡绑定集版本推进 → 各卡在途请求失效（§4.7），互不等待。

**确认撤销（确定性失效）**：主动撤销过引擎（revoke-confirmation 授权）+ 栅栏 + 根 CAS；被撤销绑定**整体**确定性失效——贡献的 ALLOW 与 DENY **一并失效**（撤销收走授权关系整体；OVERLAY DENY 被撤销时底下被压住的 BASE ALLOW 恢复，属正确语义）；无其他授权 → NO_MATCH。撤销推进绑定集版本 → 该卡在途请求失效（§4.7）。确认**缺失/错配** = 坏数据 PENDING（严格区分，延续 A-2.6 原则）；撤销 tombstone/状态列归 B-2/B-3。

**流程（单阶段）**：建绑定 + 确认同事务（受益人零参与；操作者需同时持有 create 与 confirm 授权）。两阶段申请流 v2。

**变更确认（版本发布）**：发布 + confirm-change 同事务（单阶段，操作者需双重授权）；**首版创建同样带变更确认**（版本新鲜度不变式：当前版本必须具备变更确认，否则求值 PENDING）；一次确认覆盖全部既有绑定（逐卡不重确认，规范 §15.10.1 冻结）；确认记录 version_bytes = 发布时所见版本（追溯，不冻结求值——§4.5）。

**治理路由适配顺序（§4.9 元数据自动注册）**：① binding×create+confirm + rule_set×create → ② rule_set×version-publish+confirm-change → ③ binding×remove + revoke-confirmation → ④ rule_set×update → ⑤ user_card×create/disable → ⑥ registry×register。OVERLAY-only 创建 = 独立治理动作（需显式授权；B-1.4 结构防线暂缓）。

**批次 B 验证义务**：SoD 自签拒绝测试、批量原子/整批拒测试、撤销确定性失效与坏数据 PENDING 的区分测试、双层治理授予测试、变更确认覆盖全部绑定测试、首版确认测试、跨租户确认 scope 测试。

### 4.12 生命周期状态建模合同（2026-11-14 B-2 确认）

**授权行生命周期原则（N-11，结构性决策）**：绑定/确认/用户卡行**状态标记、永不物理删除**（append-only 精神继承）；规则集版本档案天然 append-only。main 的逐卡授权 revision 账本结构**不移植**——它为已退役的逐卡投影编译服务，memory-v1 无逐卡投影（§5.1），该结构列入旧基线死代码清理清单。撤销事实以状态与标记保留在根内，是"补齐查库不复活撤销"（A-1/C-3）的数据基础。

**REMOVE 与 REVOKE 双动词语义（B-2.2）**：

| 动作 | 对象 | 效果 | 恢复路径 |
| --- | --- | --- | --- |
| REMOVE（解绑） | 绑定行标记 removed | 绑定关系消失 | 重新建绑定 + 确认 |
| REVOKE（撤销确认） | 确认行标记 revoked | 绑定关系**保留**，授权失效 | 重新确认（无需重建绑定） |

两者都是确定性失效（无其他授权 → NO_MATCH）；撤销确认收走**整个绑定含其 DENY**——OVERLAY DENY 的确认被撤销时，底下被压住的 BASE ALLOW 恢复生效（正确语义，反向直觉点写明）。

**用户卡状态（B-2.3）**：`user_card` 增 `status` 列（active/disabled）。停用 = 卡级确定性失效（该卡全部绑定跳过）+ 该卡会话撤销（双层：会话即时断 + 求值卡状态兜底）；恢复 = 重新 enable。停用卡的请求 = NO_MATCH（复用码，审计 source=card_disabled）。

**确认撤销表达（B-2.4）**：确认行增撤销标记（revoked_at/revoked_by），不删行——撤销者与时间可追溯（B-1.6 留痕）。

**规则集退役（B-2.5）**：前置 = 零活跃绑定（与注册表退役前置同构，§4.9）；满足后标记 retired（行保留）；有活跃绑定 → 拒绝退役，先解绑。fail-closed 与注册表一致。

**确认有效期（B-2.6）**：v1 确认无有效期（永久直到撤销）；时间性失效由两级窗口承担。规范继承清单 RS:104 的"到期"项就此关闭。

**三类失效的求值行为对照（B-2.7，互不混淆）**：

| 失效类型 | 例 | 求值行为 |
| --- | --- | --- |
| 计划性（窗口过期） | 绑定 valid_until 过了 | 跳过该绑定/条目，非 DENY |
| 管理性（解绑/撤销确认/停卡） | 状态标记 | 跳过，确定性；无授权 = NO_MATCH |
| 坏数据（哈希错/确认错配） | 防伪对不上 | PENDING（ContextInvalid），绝不跳过 |

**状态变更执行合同（B-2.8）**：全部状态变更 = T2 管理动作过引擎 + 代际栅栏（涉及对象）+ 根 CAS + 审计留痕（操作者/动作/对象/前状态/后状态/operationId）；推进依赖版本（绑定集版本/卡状态版本）→ §4.7 在途失效即时生效。

**无状态对象（B-2.9）**：`user`/`identity_card`/`tenant` v1 无状态（存在即有效）：用户禁用 = 停用其全部卡（集合动作）；身份卡无独立停用；**租户删除 v1 冻结**（级联：卡/规则集/绑定/对象，属 C-3 级联合同，v1 不开）。

**批次 B 验证义务**：撤销后 OVERLAY DENY 失效 → BASE 恢复测试；停用卡 → 绑定跳过 + NO_MATCH 测试；解绑 vs 撤销确认的恢复路径区分测试；tombstone 行装载后不复活撤销测试；状态变更推进依赖版本 → 在途失效测试。

### 4.13 候选 schema 定稿（2026-11-14 B-3 确认）

累积自全部已确认合同的 schema 变更一次落 DDL；`MEMORY_V1_CANDIDATE_SCHEMA_VERSION` **1→2**，manifest 合同、loader、夹具、E2E 演练 DDL 一次同步。

**DDL 变更清单**：

| 变更 | 表 | 落点 |
| --- | --- | --- |
| 当前版本指针（B-3.1） | `memory_rule_set` | 增 `current_version_bytes VARBINARY(255) NOT NULL`——创建指向 v1，发布同事务更新；禁止从最大值/时间戳推断 |
| 双绑禁止（B-3.2） | `memory_card_rule_set_binding` | `UNIQUE KEY (user_card_id, rule_set_id)` |
| 每卡一个 OVERLAY（B-3.3） | 同上 | 存储生成列 `overlay_guard = CASE WHEN binding_layer='OVERLAY' THEN user_card_id ELSE NULL END` + `UNIQUE(overlay_guard)`（NULL 不冲突）——结构执法 |
| 解绑标记（B-2.2） | 同上 | 增 `removed_at BIGINT NULL` + `removed_by VARBINARY(16) NULL`（有值 = REMOVED，恢复 = 新行重建） |

| 确认撤销（B-2.4） | `memory_binding_confirmation` / `memory_rule_set_change_confirmation` | 各增 `revoked_at BIGINT NULL` + `revoked_by VARBINARY(16) NULL`（有值 = REVOKED，恢复 = 新确认行） |

**选择来源切换（B-3.5）**：loader selections 从 `current_version_bytes` 列派生；`single_version_selections`（拒绝多版本的临时逻辑）退役；多版本世界正式支持；`CurrentSelection` 类型保留但来源变更。

**求值状态消费与确认校验换血（N-16/B-3.8）**：装载含 tombstone 行（防复活撤销，A-1/C-3 衔接）；求值确定性过滤——绑定 `removed_at` 非空 → 跳过；卡 `status=DISABLED` → 该卡绑定全跳过；确认 `revoked_at` 非空 → 该确认无效。确认校验从"版本匹配"换血为两条：①绑定存在未撤销确认（授权关系有效）；②当前版本存在未撤销变更确认（版本有效）。旧行为（确认版本==所选版本）退役。

**活跃谓词（N-19，三处消费同一实现）**：绑定存在 + `state=ACTIVE` + 所属卡 `status=ACTIVE`——退役前置（§4.12）、依赖复核（§4.7，复核追加 state==ACTIVE 条件，N-17）、求值过滤（§4.12 B-2.7）统一消费。

**注册表持久化（B-3.6）**：v1 = 路由元数据 only（启动聚合，§4.9）；`registry×register` 运行时注册随治理路由批次实现；候选 schema 不加第十表。

**无 schema 项（B-3.9）**：栅栏状态（内存运行态，崩溃 = 窗口自动消亡，无坏数据）、租户树版本（派生自租户行）、依赖版本计数器（根运行态）——不入库。

**实现义务（批次 B 实现阶段）**：DDL/manifest/loader/夹具/E2E 演练 DDL 同步；求值确认校验换血（N-16）；复核追加 `state==ACTIVE`（N-17）；活跃谓词统一实现（N-19）；E2E 重验。

**批次 B 验证义务**：多版本指针切换测试、双绑/单 OVERLAY 约束测试、REMOVED/revoked 状态过滤测试、指针缺失拒装载测试、schema 指纹变更后 E2E 重验。

### 4.14 审计事件格式合同（2026-11-14 B-4 确认）

**基础字段集（全部判定请求，T1+T2）**：身份卡（identity_card）+ 用户（user）+ 可信时间（最终复核观察值）+ 操作动作 + 操作资源；判定结果与原因（decision + reasonCode + deny/pending source 审计枚举）；关联（operationId + operation_fingerprint + 根版本/读取阶段观察）。

**双字段（N-20）**：身份卡 + 用户双字段并存——双卡模型延伸到审计，同一用户多卡操作可区分是哪张卡。

**变更类追加字段（特殊类型执行，N-24）**：**审批人**（单阶段流程 = 操作者同值；两阶段 v2 分离——schema 一次建对避免二次变更）+ 目标对象 + 范围 + 变更摘要 + 前状态/后状态（B-2.8）+ 确认记录引用（B-1.8）+ 根版本前/后（C-2 细化）。

**留痕等级（B-4.3 确认）**：

| 请求类型 | 持久审计行 | 理由 |
| --- | --- | --- |
| 变更类（T2 管理变更） | **必留**（含审批人） | 授权变更 = 敏感事件（规范 §3.4 冻结） |
| DENY（全部） | **必留**（audit_required=true，main 继承） | 拒绝必须可追溯 |
| ALLOW 读取 | 日志级（按栈规范），可选持久行 | 普通成功读取频率由栈决定 |
| PENDING | **不落持久行**（日志+指标） | 重试噪声会淹没审计表；A-1 升级告警（L2/L3）有独立通知留痕（N-21） |

**append-only（N-22）**：审计行写入后不可 UPDATE/DELETE（main 继承延伸）。

**来源枚举冻结**：deny = rule_deny / no_match / scope_denied / card_unbound / identity_mismatch / unregistered_resource（+self_confirmation、card_disabled、overlay_only_creation 等批次 B 新增）；pending = context_invalid / fence_active / context_unloaded / root_unavailable。新增来源须修订本合同。

**存储独立性（N-23/B-4.5）**：审计表**独立于九表候选 schema**（审计是治理记录，不是授权事实；命名避开 `memory_` 前缀，候选 manifest 不校验它）；append-only；同事务写入 = C-2 五件套第 5 件（授权变更审计失败 → 该变更 PENDING/DENY，规范 §3.4 冻结）。

**批次 B 验证义务**：变更类审计行含审批人/对象/摘要/前后状态；DENY 行含来源枚举；PENDING 不落持久行验证；审计行不可变测试。

### 4.15 OVERLAY-only 治理合同（2026-11-14 B-5 确认）

**形态（§4.5 延续）**：OVERLAY-only = 卡的唯一绑定是一个 OVERLAY 规则集（无任何 BASE）——该卡全部权限 = 该规则集内容。定位：极特殊用户、内部创建、不走正常发卡流程。

**创建授权（B-5.1 用户确认：独立动作）**：`binding×create-overlay-only` 为**独立治理动作**，默认仅首管持有；域管理员不持有（B-1.4 结构防线暂缓后，这是 OVERLAY-only 滥用面**唯一的授权收窄手段**——治理规则层可配置、可审计、可收窄）。

**批量限制（B-5.2 用户确认）**：逐条显式创建，**禁止批量**——每条都是特例，必须逐条审视留痕。

**审计标记（B-5.3 用户确认）**：审计 source = `overlay_only_creation`，突出标记创建者/受益人/规则集引用——演示与审计一眼识别特例授权。

**生命周期（B-5.4 用户确认）**：与普通绑定完全一致（REMOVE/REVOKE/恢复/确认撤销含 DENY 失效）；**求值零新逻辑**（N-25：单 OVERLAY 绑定按 §4.8 聚合正常评估，OVERLAY-only ALLOW 单独生效已在隔离测试覆盖）。

**SoD 延伸**：create-overlay-only 的受益人 == 操作者 → 拒绝（与 B-1.3 confirm 自签同款，C-1 首管初始化特例除外——初始信任根建立时无其他确认人存在）。

**批次 B 验证义务**：无授权管理员创建 → DENY 测试；首管创建 → ALLOW + 求值 ALLOW 测试；受益人==操作者 → 拒测试；审计 source 断言。

## 5. 与旧基线的关系

旧基线区分源规则、规则集绑定与按卡发布的有效授权；正式卡授权路径读取已发布证据并进行匹配，缺证据时不会以原始规则直接回退放行。旧正式匹配器消费的 canonical effective grants 是无条件、有效的 `ALLOW`；不能以旧表存在条件或拒绝字段为由断言该路径已经支持完整条件或 `DENY`。旧代码入口包括 `policy-engine/src/engine/published.rs` 与 `astral-types/src/grant.rs`，应按上述固定提交核对。

memory-v1 以共享根中完整一致的事实和新版规则作为目标输入，不以旧 grant revision/delta、manifest/segment/current 或异步投影作为默认运行前置。是否复用旧算法由实际规则语义和验证决定；新数据库按新结构全新建立，不迁移旧规则或其他旧数据；新系统的审计与初始化须另行设计。

旧引擎还包含独立条件求值模块，但其存在不代表它接入了上述正式卡授权匹配路径；条件类型及其可信输入也各有限制。旧实现另有组织授权分支、统计和断路器，纯编译内核则仍耦合旧 canonical grant 和发布结构。条件模块、匹配索引、统计与断路器可以作为复用候选，组织授权对应的新业务范围也需另行设计；不能把它们笼统当成已适配新版的基础能力。

### 5.1 新版投影、物化与原子读写

**目标设计：授权事实直接由共享内存权威持有和更新，不再把旧式投影发布或逐卡授权物化作为正式授权生效的必经步骤。** 投影和物化原先承担的不同职责需要拆开看：

| 旧机制承担的职责 | memory-v1 的目标处理 |
| --- | --- |
| 模板规则同步为规则集条目 | 取消独立模板和模板规则；统一规则集本身保存 `version + content + timestamp + hash`。 |
| 按规则、用户卡及绑定生成逐卡授权贡献 | 引擎读取当前卡经确认的绑定与适用规则集，按新版规则直接判断；不要求先复制出一份逐卡授权结果。共享规则变更立即作用于已有有效绑定，确认记录及完整冲突语义仍待定义。 |
| 异步编译、发布 manifest/segment/current，供正式读面使用 | 单机目标由同一共享根持有当前授权事实；授权管理操作经引擎放行后在该根原子生效，不依赖旧发布链作为额外生效阶段。 |
| 加速资源匹配和关系查找 | 可以构建索引或编译表示，但它们是派生的访问结构，不是独立授权来源；须与权威事实保持一致，失败或无法证明一致时不得导致错误放行。是否预计算、按需构建及具体策略待设计。 |
| 持久化、审计和崩溃后的处理 | 与授权读面分开设计。内存生效或索引更新不证明 MySQL 落盘或审计已完成；仍遵循用户已接受的单机崩溃边界和适用审计合同。 |

**读取路径**：请求经 Gateway 认证和清洗后，由 `PolicyEngine.evaluate()` 从同一个共享根一次取得判断所需的完整一致上下文，包括用户、双卡、租户、已确认绑定、适用规则集和资源归属等事实；引擎据此判断。允许前只复核根实例、版本、预存内容 hash、状态和可信时间，不重新读取完整上下文或重算完整 hash。复核前若撤权已完成且根版本发生变化，旧请求不得放行；复核已通过的请求按用户已确认的生命周期可继续，后续请求重新授权。

**修改路径**：Gateway → TrustGraph → `PolicyEngine.evaluate()` 读取共享根并完成本次管理请求授权 → TrustGraph 调用受限修改方法 → 同一个根将变更涉及的规则集四部分、绑定、确认事实、必要索引及根元数据作为一致状态原子更新。是否需要更新某类事实取决于具体操作；实际授权关系必须经有权人员明确确认。内存原子写入并确认一致后可返回成功，该响应不表示 MySQL 已持久化。

原子读写是需要实现和验证的合同，不代表可以使用未验证的裸指针、分别更新多个表项，或依靠一次独立的鉴权调用自行推断并发安全。需要设计一致读取、写入冲突与准备阶段校验、异常/取消时的全有或全无、根版本和内容 hash 的一致更新；同时保持用户已确定的请求生命周期边界，不额外引入请求与写入共用的开关门机制。索引可在锁外准备，但不能先让未提交或与权威不一致的索引参与正式授权；具体并发实现、资源预算和失败行为待验证。

崩溃后按单机目标从 MySQL 最新一致性快照重建，不主动恢复崩溃前未落盘操作；未落盘的撤权可能丢失，须通过可用审计、监督或启动检查提示用户检查最近权限变更。现有候选尚未证明完整写入口覆盖、原子一致性、hash 正确性及持久化/崩溃行为；适用的规范和采用门禁仍须满足。

### 5.2 超管规则建立与正常请求

超管管理模块根据系统存在的接口及其注册的资源、动作，建立并维护覆盖全部权限的超管规则集，并为超管用户建立普通的用户卡绑定。这里的“模板”是构建初始规则的来源或方案，不恢复独立卡模板、模板规则表或通过模板名称放行；规则最终使用统一规则集结构。新接口出现或资源动作变更时，如何检测覆盖缺口、触发规则更新和确认由模块的具体合同决定，不能仅凭“超管”标签认定已有新接口权限。

初始空库尚无已授权主体，必须单独设计受控的首次建立和确认流程、边界与审计；这是初始化问题，不等于正常请求可以绕过引擎。初始化完成后，超管与其他用户一样携带身份卡和用户卡，所有正式业务请求先经 `PolicyEngine.evaluate()` 判断，再执行操作；不得通过 `isSuperAdmin()` 或其他特殊标识直接放行。授予、修改、撤销和锁定恢复的具体流程尚待定义。

### 5.3 性能技术复用

目标复用旧基线中适合新模型的原子查询思路、HAMT、指针/索引共享、按实测曲线进行多策略接力以及大小核心调度等技术；各技术必须服从一致读、原子更新、确认与最终复核合同。旧基线静态核对：HAMT 用于编译器的内存共享状态，正式匹配器有线性扫描与索引接力及基于 `Arc` 身份的缓存；大小核部分有预算计算和测试原型，未证明生产线程已绑定大小核；已有曲线不等于实测功耗能效曲线，未确认独立的整链原子查询实现。重新接线、数据结构安全性、吞吐和能效均需在新版实测，不能以旧代码存在宣称目标已经完成。
