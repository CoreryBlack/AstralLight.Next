# memory-v1 用户、双卡、租户与规则集设计

> 状态：目标设计，部分语义待决；不代表已实现或完成生产验收。
>
> 范围：用户、身份卡、用户卡、分层租户、规则集及其绑定。单机共享内存权威的完整读写、持久化和恢复合同另行设计。
>
> 基线：本地 `main` 是旧基线；memory-v1 以新模型为目标，不以兼容旧模板、旧方法或旧授权发布协议为目标。本文是设计材料，不覆盖现行工程规范和生产执行门禁。

## 1. 目标与已确定的方向

- 保留用户、身份卡、用户卡、租户、规则集和规则集绑定。
- 每个用户有一张与租户无关的身份卡；身份卡用于认证身份，不直接授予业务权限。
- 保留旧基线网关的物理双卡分离概念：身份卡和用户卡是分别存在、分别标识的两类卡，认证身份与当前授权卡上下文不能混为一个卡身份；具体新协议单独设计。
- 一个用户可以在多个租户持有用户卡；用户卡承载用户在具体租户中的授权。
- 租户可分层表示公司、部门、小组等组织范围；目标模型不再引入独立的 domain 概念。
- 不从租户上下级、同部门或同事等关系推断、继承或自动授予权限；每一项实际授权都必须经有权人员明确确认。确认的是授权关系，不是每次业务请求都要求人工确认。
- 取消等级这一独立概念；不再以等级作为授权来源或判断依据。
- 取消独立的卡模板和模板规则概念。规则集本身是定义和复用一组规则的单位，可以为新用户或已有用户配置。
- 保留用户卡与规则集绑定上的 `BASE` / `OVERLAY` 层；绑定层不等于规则集来源或授权来源。
- 正式授权由 `PolicyEngine.evaluate()` 判断，共享根提供统一的授权事实与读取视图。

本文件区分用户已确定的方向、候选设计和待决问题。旧库字段、现有代码以及当前候选 SQL 不自动构成新模型合同。

## 2. 关系总览

```text
用户 User
  └── 身份卡 IdentityCard（每人一张，与租户无关）
       ├── 用户卡 UserCard ──> 租户 A
       │    ├── BASE 绑定 ────> 规则集 X ──> 规则条目
       │    └── OVERLAY 绑定 ─> 规则集 Y ──> 规则条目
       └── 用户卡 UserCard ──> 租户 B
            └── BASE 绑定 ────> 规则集 Z ──> 规则条目

租户 A（公司；独立的租户范围）
  ├── 子租户 A1（财务部；独立的租户范围）
  │    └── 子租户 A2（报销组；独立的租户范围）
  └── 子租户 A3（研发部；独立的租户范围）

规则集 X（由某个租户管理）
  ├── 可供哪些租户选用？── 规则集可用范围（候选，见 §4.2）
  └── 哪张用户卡实际绑定？── 用户卡与规则集绑定（授权关系）
```

用户与身份卡是认证身份关系。用户卡连接一个用户和一个具体租户；规则集绑定连接一张用户卡和一个规则集。管理操作可以面向用户提供，但实际授权关系保留用户卡与租户上下文，不将身份卡变成授权凭证。租户层级、规则集可用范围和用户卡绑定是三种不同关系，详见 §4.2。

## 3. 领域对象

| 对象 | 职责与关键关系 | 不承担的职责 |
| --- | --- | --- |
| 用户 | 表示人员或其他系统允许的用户主体；拥有一张身份卡，可持有多个租户的用户卡。 | 用户身份本身不直接证明某项权限。 |
| 身份卡 | 与一个用户关联，提供与租户无关的认证身份及其有效性事实。 | 不归属于某一租户，不替代用户卡，不直接作为权限凭证。 |
| 租户 | 表示公司、部门、组等范围；可引用上级租户形成层级。 | 层级关系本身不能未经明确合同就推导跨租户权限。 |
| 用户卡 | 关联用户和具体租户，作为授权载体；其状态和有效期影响能否用于授权。 | 有卡不代表拥有任意规则或必然通过授权。 |
| 规则集 | 对一组权限规则进行定义和复用，是直接配置给用户的管理单位。 | 名称不等于权限；规则集本身不证明具体用户已获授权。 |
| 规则条目 | 描述一条规则及其适用资源、动作等评估内容。 | 字段存在不代表条件、拒绝、优先级等语义已实现。 |
| 规则集绑定 | 关联用户卡与规则集，记录 `BASE` 或 `OVERLAY` 层和必要的关系身份。 | 绑定本身不替代引擎对资格、范围、规则和有效期的完整判断。 |

对象身份、状态、有效期、规则语法和持久化字段需在后续合同中定义；此处不是最终 DDL。

## 4. 用户、双卡与租户

### 4.1 身份与用户卡

每个用户有一张身份卡，身份卡不绑定租户。一个用户可在多个租户拥有用户卡；请求必须使用与请求用户及目标租户一致的有效用户卡。系统应能验证用户、身份卡和用户卡属于同一主体，且租户引用有效。身份、卡、租户或其关系缺失、无效或无法确认时，不得据此放行。

用户在同一租户能否持有多张用户卡、默认卡及切换方式尚未决定；不得从本设计推导每个用户每租户恰有一张卡。新用户是否在注册时立即获得用户卡，以及无用户卡时可以执行哪些非授权业务，也需由身份与接入流程定义。

#### 4.1.1 网关的物理双卡分离

网关保留身份卡与用户卡分别标识、分别校验的概念；选择或切换用户卡不能改变认证主体或复制其他卡的权限。可信上下文、切卡及旧基线参考见独立的[网关与物理双卡设计](网关与物理双卡设计.md)。

### 4.2 租户层级、规则集与继承

#### 4.2.1 子租户代表什么

租户是一个具有自己身份和边界的组织范围；子租户也是租户，不是父租户的一张用户卡，也不是一条规则。例如：

```text
星光公司 A                      租户 A：公司范围
├── 财务部 A1                  租户 A1：财务部门范围
│   └── 报销组 A2              租户 A2：该组自己的范围
└── 研发部 A3                  租户 A3：研发部门范围
```

父子关系回答“组织上属于哪里”，可用于表达公司、部门、组的上下级结构和定位可管理范围。每个节点具有独立的租户身份；某张用户卡和某项资源具体属于哪个节点，都必须有明确记录。用户可以在不同节点分别拥有用户卡。例如：同一人可以持有 A1 的卡，也可以另有 A2 的卡；拥有 A1 卡本身不证明拥有 A2 卡或对 A2 资源的权限。

同级 A1 与 A3 是不同范围；A2 与 A3 也不是同一个范围。组织层级不能单独作为访问其他范围数据的凭证。租户父子关系不能成环，父租户必须可解析；节点重挂、停用和删除如何影响下级、卡、资源及既有授权，需另行定义。

#### 4.2.2 先区分三种“绑定”

| 关系 | 回答的问题 | 候选表示与效果 |
| --- | --- | --- |
| 规则集归属 | 谁负责创建和管理这份规则集？ | 规则集有明确的管理归属租户；归属本身不向该租户的所有用户发权限。 |
| 规则集可用范围 | 哪些租户可以选择这份规则集？ | 可显式规定仅本租户、指定下级或其他被允许范围；**可用不等于已绑定，也不等于用户获权**。这是候选能力，是否采用待决。 |
| 用户卡绑定 | 具体哪张卡使用规则集、属于哪一层？ | 将规则集以 `BASE` 或 `OVERLAY` 绑定到具体用户卡；仍须经过资格、资源范围和引擎判断。 |

推荐以规则集为唯一规则定义单位，由租户管理规则集、向允许范围提供复用，再向具体用户卡绑定；不再引入“租户模板规则”的第二份规则定义。规则集能否跨租户复用、可用范围如何授权和记录，以及上述候选关系是否落库，均待决。若尚未建立可验证的跨租户复用合同，绑定仅在规则集与用户卡的租户范围一致时允许。

例如，A1 定义“报销基础规则集”。即便它被配置为可供 A2 选用，也只是允许 A2 的授权管理者在获得管理权限后选择它；**不会自动创建 A2 用户卡，不会自动绑定任何卡，也不会自动给 A2 的人授权**。若为 A2 用户的 A2 卡显式绑定该规则集，规则集来源是 A1、授权载体是 A2 卡、目标资源归属是另一项须检查的事实；这不等于允许访问 A1 的资源。适用目标租户与资源范围必须按独立合同限定并由服务端核验，不能信任请求方自报的资源归属。

#### 4.2.3 继承需要逐项定义

“父子继承”不是一个总开关，至少涉及以下不同语义：

| 继承对象 | 示例 | 当前建议 / 未决边界 |
| --- | --- | --- |
| 组织结构 | A2 属于 A1，A1 属于 A。 | 保留父子关系；只表示组织归属，不直接放行。 |
| 成员和用户卡 | 持有 A1 卡的人是否自动成为 A2 成员或得到 A2 卡。 | 不因父子关系自动推断成员、发卡或授权；成员和发卡流程另行设计。 |
| 规则集的可用范围 | A1 管理的规则集是否可供 A2 选择。 | 建议通过明确配置向下提供；这只提供可选项，不产生实际绑定。选择按节点指定还是包含整棵子树待决。 |
| 用户卡上的规则集绑定 | A1 用户卡绑定的规则集是否自动出现在 A2 用户卡上，或同部门同事 B 的规则是否自动给 C。 | 不自动继承、复制或绑定；每张受益用户卡的授权关系都须经有权人员明确确认。 |
| 对下级资源的访问 | A1 管理员是否可读取或修改 A2 资源。 | 不因父子关系自动允许；如支持显式跨租户授权，须经有权人员确认并由引擎结合资源归属判断，具体授权范围待设计。 |
| 规则集变更 | 修改 A1 的规则集是否影响已绑定它的 A2 卡。 | 修改在内存原子生效后立即影响该规则集的现有绑定；跨租户绑定须先符合明确的共享合同。 |

**已确定的授权原则**：不从父子、同部门或同事关系推导权限。A2 属于 A1，不意味着 A1 的人自动拥有 A2 的权限；B 和 C 是同部门同事，也不意味着 C 自动继承 B 的权限。每一项实际授权关系必须有有权人员明确确认，并可追溯确认主体、授权对象、范围和内容；缺少有效确认时不产生授权。具体记录格式、谁有确认权、是否允许在一次操作中逐项确认多个对象，以及确认如何撤销，均待定义。

确认发生在建立或变更授权时；普通业务请求按已确认的有效授权经 `PolicyEngine.evaluate()` 判断，不因此要求每次请求重新人工确认。已确认绑定所指向的共享规则集经有权人员修改并在内存原子生效后，更新立即作用于现有有效绑定，不默认逐人重新确认；规则变更的确认权限、影响范围和审计如何具体表达仍须定义，不能由组织关系自动创建新绑定。**允许管理下级、允许在下级选用规则集、允许访问下级资源、用户实际获得权限，是独立决定**；反向和同级关系同样不推导授权。

#### 4.2.4 建议的默认流程和变化边界

以下是供决策的候选流程，尚未实现：

1. 在 A1 创建规则集，定义它的规则和管理归属。
2. 如允许 A2 复用，由有权管理该规则集的主体明确配置可用范围；该配置本身不向任何用户授予规则。
3. 管理者选择 A2 中的用户、有效的 A2 用户卡和规则集，经授权及可用范围校验后建立 `BASE` 或 `OVERLAY` 绑定。
4. 用户持 A2 卡访问资源时，引擎结合有效身份、A2 卡、绑定、规则、服务端确认的资源归属及其他限制判断。资源若属于 A1 或 A3，不能只凭树关系放行。
5. 撤销某张卡的绑定只移除该绑定所贡献的授权；若还有其他有效来源，是否仍可访问须重新评估。撤销规则集可用范围时，既有绑定是失效、保留还是需要迁移尚待决定，不能默认静默删除或继续授权。

对共享规则集的编辑、禁用、删除，以及租户重挂、停用、删除，均可能影响多张卡或资源的判断。需要先确定影响集合、既有绑定处理、变更权限和审计；内存中的事实、关系、索引和根版本按已确定的原子更新目标一致变化。跨租户共享和层级变更的并发、规模及持久化行为仍需专门设计和验证。

memory-v1 决定从全新数据库按新结构建立，不迁移旧 domain、tenant-domain 映射、历史跨租户共享或其他旧数据。旧结构仅作为设计参考；新用户、租户和授权须按新模型重新建立并明确确认。此决定不授权删除、清空或覆盖旧库。

## 5. 规则集与绑定

### 5.1 规则集是统一的规则定义单位

规则集包含规则条目，既可用于统一配置一类人员的权限，也可由管理操作选中并配置给具体用户。旧模型中“卡模板 → 模板规则 → 模板来源规则集”的多层表达，在 memory-v1 目标中收敛为“规则集及其规则 → 用户卡绑定”。规则集、规则条目、绑定及确认的统一逻辑结构见[统一规则集结构设计](统一规则集结构设计.md)。

规则集名称可以帮助人员理解用途，例如“财务基础权限”，但不能仅凭名称或类似角色、等级的标签直接放行。具体允许或拒绝取决于新规则语言、事实和引擎判定。

### 5.2 绑定到新用户或已有用户

管理界面或 API 可直接以“用户 + 目标租户 + 规则集”为操作入口。系统必须在明确的目标租户上下文中，将规则集绑定到该用户的一张有效用户卡；创建新用户或该租户尚无可用用户卡时，可以在符合发卡和授权合同的前提下创建用户卡并绑定。

同一租户存在多张候选卡时，选择或创建哪一张尚待定义；不得静默把授权绑定到不确定的卡，也不得把规则集绑定自动扩散到用户的其他租户。新用户创建、发卡、绑定的事务/原子边界及部分失败处理需要后续合同确定。

### 5.3 BASE / OVERLAY

`BASE` 和 `OVERLAY` 是**用户卡到规则集的绑定层**，不是规则集的来源类型，也不等同于直接授权、审批或委托等潜在授权来源。多张卡可绑定同一规则集；同卡允许多少个各层绑定、同一规则集能否同时以两个层绑定，需按后续绑定合同确定。

`OVERLAY` 可以增加新的允许权限，也可以加入明确的拒绝规则，阻止当前用户卡从 `BASE` 取得指定权限，无需修改共享 `BASE`。具体资源匹配粒度、多个 `OVERLAY` 之间的冲突和其他来源的处理仍需定义。角色名称可用于描述受影响人员，但不直接作为放行或拒绝的绕过条件。

### 5.4 多卡共享规则集

多张卡可分别经有权人员确认后绑定同一规则集；规则集修改在共享根原子生效后立即影响现有有效绑定。修改确认和影响范围必须可追溯，其具体合同待设计；不能将逐卡重新确认作为默认生效前置。不同用户或租户不会因此自动建立新的绑定。

## 6. 授权读取与修改边界

目标管理路径为：Gateway 完成外部认证与转发，TrustGraph 组织规则集或绑定变更，调用 `PolicyEngine.evaluate()` 判断管理请求是否有权操作；获准后，TrustGraph 调用共享根的受限修改接口，原子更新受影响事实、关系、索引及根版本和内容 hash。具体实现和完整写入口覆盖尚未证明。

正式授权请求首次从同一个共享根读取完整且一致的所需上下文；允许前核对根实例、版本、预存内容 hash、状态和可信时间，不重复读取完整上下文或重新计算完整内容 hash。服务期发现未加载时，本次请求可触发查库并按[唯一根设计](单机唯一共享根设计.md)校验、原子补入同一根，然后从根重新读取、评估及复核；数据库行不直接构成放行，完整后续授权请求不查 DB。

进入正式授权服务前须完成 MySQL 一致性快照冷加载和完整性验证。内存原子更新并确认一致后返回成功是目标，不表示 MySQL 已持久化。崩溃后从 MySQL 最新一致性快照重建，不主动恢复崩溃前未落盘的内存操作；未落盘的撤权也可能丢失，须依靠可用审计、监督或启动检查发现异常并提示用户检查最近权限变更。

上述是目标语义，不证明现有代码已经实现。memory-v1 单机合同及采用条件以 Rust 规范正文为准；实际采用仍须完成待决合同、写入口和一致性验证及生产验收，本文不授权绕过执行门禁。

## 7. 待决事项

1. 共享规则变更确认如何覆盖现有绑定，如何记录变更责任与受益范围；数据库全版本保存及失败处理。
2. `BASE` / `OVERLAY` 的数量、精确拒绝匹配与多规则冲突；条件、优先级及其组合。
3. 用户在同一租户持有多张用户卡时的发放、选择、切换、停用和绑定目标规则；用户卡与规则集的重复绑定规则。
4. 授权确认的主体、逐项确认与批量操作、记录和撤销合同；规则集管理归属与可用范围是否独立建模、跨租户复用的条件及其撤销后既有绑定如何处理；租户重挂、停用和删除的影响。组织和同事关系不自动推导授权是已确定原则。
5. 直接授权、审批和委托是否保留，如何统一表示来源、有效期、分别撤销和审计。
6. 用户、身份卡、用户卡、租户及绑定的状态、有效期、删除与停用规则；资源归属、资格、SoD 的完整事实与判定合同。
7. 新用户创建、用户卡发放和绑定的原子边界、失败报告、持久化时序；共享根索引、内容 hash、冷加载和重建的实现与验证。
8. 超管管理模块根据系统已存在的接口建立初始全权限规则集；首次空库建立的确认主体、流程、审计、丢失管理权限后的恢复，以及接口变化后的规则维护合同。超管正常请求仍通过引擎判断，不使用特殊标识直接放行。
