# memory-v1 统一规则集结构设计

> 状态：候选逻辑合同，供决策和后续实现；字段名、持久化格式及未决规则语义尚未冻结。
>
> 本文是 memory-v1 对规则集、规则条目、用户卡绑定和确认关系的统一设计入口。它描述对象职责与数据边界，不替代 `Docs/规范/` 中的现行工程规范，不证明代码或数据库已采用。
>
> 基础引擎及请求流程见 [权限引擎与规则结构设计](权限引擎与规则结构设计.md)；用户、双卡和租户见 [用户双卡租户与规则集设计](用户双卡租户与规则集设计.md)。

## 1. 统一原则

1. **一套规则集结构**：规则集是规则定义与复用单位。统一结构为**版本号 + 内容 + 时间戳 + 由前三者计算出的 hash**；基础权限、附加权限和管理权限使用同一种结构，不再为卡模板、模板规则或等级建立另一套规则定义。
2. **一套规则条目结构**：规则集包含规则条目；具体资源、动作及适用限制由规则条目和明确归属的上下文共同表达，规则集名称不直接产生权限。
3. **授权落在具体用户卡**：新用户或已有用户通过其具体租户中的用户卡绑定规则集；用户卡属于哪个用户、哪个租户必须确定。身份卡负责认证身份，不能代替用户卡作为授权载体。
4. **绑定须经明确确认**：每项实际授权关系须由有权人员确认并可追溯。组织上下级、同部门和同事关系不推导或自动继承授权；普通业务请求不需要重新人工确认。
5. **绑定层与规则内容分离**：`BASE` / `OVERLAY` 标记用户卡与规则集的关系，不区分两种规则集格式。`OVERLAY` 可以增加允许规则，也可以增加明确的拒绝规则以撤销该卡从 `BASE` 得到的指定权限；精确匹配、多个覆盖层冲突等细节待定义。
6. **唯一判断入口**：`PolicyEngine.evaluate()` 从同一共享内存权威读取一致的授权上下文并判断；Gateway、TrustGraph 和规则集本身不替代引擎放行。

## 2. 对象及关系

```text
规则集 RuleSet
  ├── version：版本号
  ├── content：内容（规则条目及其适用定义）
  ├── timestamp：该版本的时间戳
  └── hash：由 version、content、timestamp 计算

规则集管理记录：规则集身份、管理归属等关联信息

用户 User ── 身份卡 IdentityCard
  └── 用户卡 UserCard（一个具体租户）
        ├── 绑定 Binding：BASE ────> RuleSet
        │     └── 授权确认 Confirmation
        └── 绑定 Binding：OVERLAY ──> RuleSet
              └── 授权确认 Confirmation
```

图中箭头表示多张卡可绑定同一规则集，规则集修改对现有有效绑定立即生效；不预定数据库外键或内存布局。确认可由绑定字段或独立记录承载；无论采用哪种形式，都必须能判断**谁确认了什么授权给哪张卡、范围是什么、确认是否仍有效**。确认的详细形式及单次确认多个对象的方式待定。

规则集可以被用作基础或附加权限；这一用途由绑定层表达，不在规则集内再造 `template`、`level` 或“基础规则集/附加规则集”两套结构。可读名称如“财务基础”只帮助管理，不作为授权条件。

## 3. 统一逻辑字段

以下是建议的逻辑字段，不是最终 Rust 类型、JSON 规范或 SQL 列。`必需` 表示任何有效授权路径需要能够证明该事实，不意味着必须在该对象中重复保存；具体状态枚举、类型和存储位置需在实现前确定。

### 3.1 规则集 RuleSet：四部分

已确定的统一结构是：

```text
RuleSet = {
  version:   版本号,
  content:   内容,
  timestamp: 时间戳,
  hash:      H(规范编码(version, content, timestamp))
}
```

| 组成 | 职责与边界 |
| --- | --- |
| `version` | 标识该规则集的内容版本；与共享根的全局版本是两个不同的版本域。版本分配、作用域和溢出策略待设计。 |
| `content` | 规则集的规则内容，包含规则条目及其生效判定所需、明确归属于规则集的定义；资源、动作、状态等的具体表示待定。完整加载后空规则集合表示无规则，不能把未加载当成空集合。 |
| `timestamp` | 与该规则集版本关联的时间戳；其来源、精度、时区/编码及具体含义（创建、修改还是生效时间）待定义。它不自动代表规则有效期，也不能单独替代可信时间校验。 |
| `hash` | 对前三者按固定顺序及确定性规范编码计算，**不包含 hash 自身**。算法、编码版本、字段规范化和验证时机待定义；不能以普通拼接代替无歧义编码。 |

规则集的稳定身份、管理归属、展示名称、绑定与授权确认仍需可关联，但上述四部分以外的信息如何存放尚待设计。如果身份、归属、状态或其他信息会影响内容解释或授权，必须将其纳入被 hash 覆盖的 `content` 或由另一个完整性保护与一致性合同明确绑定，不能把它们放在未受保护的位置并据此放行。`name`、`description` 仅用于展示时不应直接决定授权。

目标规则集内容变更时，产生对应的新版本、时间戳和 hash，并与相关索引及共享根元数据原子更新。时间戳相同、时钟回拨或内容恢复旧值时，不能仅凭时间戳或内容 hash 推断没有新变更；版本如何递增、确认和传播如何处理仍待设计。hash 标识前三者的完整性关系，不证明操作者有权修改、内容已被人工确认或 MySQL 已落盘。

规则集归属和“允许其他租户选择该规则集”的范围是不同事实；可用范围如何表示与跨租户复用是否支持仍待决定。没有完整的共享合同前，不因父子租户关系直接放行跨租户绑定。

### 3.2 规则条目 Rule

| 逻辑字段 | 必需性 | 意义 |
| --- | --- | --- |
| `rule_id`、`rule_set_id` | 必需 | 规则身份及所属规则集；不能凭显示名称关联。 |
| `resource` | 必需 | 资源类型及所需的对象选择信息，资源类型和动作遵循注册表；资源真实归属来自可信服务端事实。 |
| `actions` | 必需 | 明确适用动作的集合；具体是否一个动作一条规则由序列化和索引设计决定，不能改变语义。 |
| `effect` | 必需语义 | 至少支持 `ALLOW` 和 `DENY`：`OVERLAY` 的明确拒绝可阻止该卡命中的相应 `BASE` 允许；其他层间、同层和多个来源冲突的完整规则待定义。 |
| `status` | 必需 | 是否启用；枚举、停用边界和验证方式待定。 |
| `validity` | 条件必需 | 若支持规则级有效期，须定义起止边界与可信时间；是否放在规则级待定。 |
| `condition` | 可选能力 | 若支持附加条件，须定义类型、可信输入和求值；未知或无法求值不能按条件满足处理。 |
| `priority` | 待决能力 | 只有确认需要排序与冲突裁决后才定义，不因旧数据含该字段而产生优先级语义。 |

同一个规则集内的规则可以覆盖多个资源和动作；类型级、对象级、通配和动作别名的语义须在规则语言合同中明确。不得只从客户端给定资源名称或租户值断言资源归属。

### 3.3 用户卡规则集绑定 Binding

| 逻辑字段 | 必需性 | 意义 |
| --- | --- | --- |
| `binding_id` | 必需 | 一条实际绑定的稳定身份，支持分别追踪和撤销。 |
| `user_card_id`、`tenant_id` | 必需 | 明确受益用户卡及其租户；须与可信用户卡事实一致。 |
| `rule_set_id` | 必需 | 明确绑定的规则集；适用范围和可用性须经校验。 |
| `layer` | 必需 | `BASE` 或 `OVERLAY`；表示绑定层，不是规则来源。 |
| `status`、`validity` | 必需能力 | 能判断绑定当前是否有效；状态、时间字段位置和具体值待定。 |
| `confirmation_ref` | 必需能力 | 关联有权人员对该受益卡及授权内容的确认；确认可以内嵌或外置。 |
| `confirmed_content` | 必需能力 | 保留绑定确认及后续规则变更确认的可追溯性；已确认的规则集修改立即生效，不预设必须对每张已绑定卡逐人重新确认。确认如何覆盖共享规则集后续变更及记录受益范围待定义。 |

确认的具体内容、授权范围和变更责任应可核对，不能把同部门或上下级关系当作确认。用户已决定规则集修改立即生效；该决定与“每项实际授权关系必须有人确认”的衔接须在规则变更操作中明确，不得悄然增加每卡二次审批作为生效前置，也不能将操作人的确认、受影响范围或审计留成无法解释的隐含状态。

### 3.4 授权确认 Confirmation

逻辑上应能核对确认主体及其确认权限、受益用户卡和租户、规则集及确认内容或范围、确认时间、状态及可追溯的操作关联。确认不得因同事、上下级或同一规则集的其他用户已确认而自动产生。

确认记录如何与审计关联、绑定何种内容身份、是否需要对扩权或收窄分别处理、到期与撤销如何表达，属于待设计合同。不能因字段存在而声称已有可恢复的审计或持久确认。

## 4. 概念示例

下面使用结构化示例展示统一关系，**不是可执行 JSON、最终接口或完整权限规则**；版本、时间戳和 hash 使用概念占位，不指定编码或算法。

```text
规则集 RS-财务基础（管理租户：财务部 A1）
  version：1
  content：
    规则 R-查看：资源「报销单」，动作「查看」
    规则 R-提交：资源「报销单」，动作「提交」
  timestamp：T1
  hash：H(规范编码(1, content, T1))

绑定 B-1
  用户卡：用户 B 的 A1 卡
  层：BASE
  规则集：RS-财务基础
  确认：有权人员明确确认 B-1 对版本 1 内容的授权

绑定 C-1
  用户卡：用户 C 的 A1 卡
  层：BASE
  规则集：RS-财务基础
  确认：另行对 C-1 明确确认
```

B 和 C 可以分别经明确确认绑定同一规则集，不能因 B 的绑定或同部门关系自动建立 C 的绑定。该规则集经有权人员修改并在共享根原子生效后，B、C 的既有有效绑定立即使用更新内容；不能将逐人重新确认设为默认生效前置。具体确认如何覆盖后续变更和记录影响范围待定义。若 B 另有 A2 用户卡，也不会因此得到 A2 卡的绑定或 A2 资源权限。

## 5. 读取、确认与变更

### 5.1 评估输入

`PolicyEngine.evaluate()` 在首次读取时从共享根取得一致的必要上下文：用户和双卡关系、当前卡与租户状态、已确认有效绑定、其对应的规则内容及适用的资源归属和限制性事实。请求匹配时校验用户、卡、租户、确认范围、状态、可信时间、资源和动作；完整上下文中没有匹配授权则拒绝，缺失或不一致不能放行。

允许前仅复核共享根实例、版本、预存内容 hash、状态和可信时间；不得用未确认的新规则内容、旧快照或 SQL miss 回退放行。最终检查通过的请求生命周期边界按共享根设计处理。

### 5.2 创建和绑定

TrustGraph 在经引擎授权后管理规则集和绑定。为用户绑定时，必须确定受益用户卡、租户、规则内容和确认主体；创建规则集或将规则集设为某租户可选，不等于为任何用户自动发放权限。绑定或确认尚未完成、无法证明有效时，不得视为有效授权。

### 5.3 规则集内容变更

规则集由多张已确认用户卡绑定时，经授权的修改在共享根原子更新并确认一致后**立即对现有有效绑定生效**，包括新增和撤销；不等待逐卡重新确认或 MySQL 落盘。规则集修改必须由有权人员明确发起和确认，并可追踪具体变更与影响范围；绑定的确认如何表达对后续共享内容变更的授权范围仍需具体合同。不得因层级或同事关系自动创建新绑定。

数据库作为规则集版本库，目标是从第一版到最新版保存每一个完整的 `version + content + timestamp + hash` 结构；内存权威在原规则集上原子增删改，维护当前最新版本，不以长期保留旧整根为目标。由于内存生效可先于落盘，崩溃时尚未持久化的版本可能丢失，因此“完整版本库”是成功持久化后的目标，不能声称崩溃前所有已生效版本必然存在于数据库。写入队列、版本顺序、失败提示、丢失识别与持久化确认待设计。

变更的目标是在同一共享权威上原子维护相关事实、索引、规则集的版本/内容/时间戳/hash 及根元数据；不把旧式投影发布或逐卡授权物化作为生效前置。引擎直接读取一致的规则及已确认绑定，索引只是派生访问结构。大规模影响集、确认与并发读取仍须设计验证。完整读写流程见[引擎设计 §5.1](权限引擎与规则结构设计.md#51-新版投影物化与原子读写)。

### 5.4 解绑或撤销

解绑或撤销应明确针对的绑定及确认来源；不得自动删除无关绑定。某一来源被撤销后，是否仍存在其他经确认的有效授权由引擎重新判断。已完成的撤权在本进程内应通过根版本变化使尚未完成最终检查的旧请求不能继续放行；跨崩溃持久性另按单机目标和后续持久化合同处理。

## 6. 与已有候选的关系

此前的离线 SQL 候选 `Docs/sql/memory-v1-candidate.sql` 不是本文的实现或最终数据合同；旧的 `i64` 关系候选 `memory_v1_model.rs` 已退役，新候选以 `BINARY(16)` 行模型和 HAMT 索引为基础。旧 SQL 中的 `DENY`、条件字段、直接授权表和同租户外键，不代表规则语言、直接授权或跨租户复用已被决定；新候选的关系校验也不证明确认、规则评估或完整覆盖。

本实验分支的内部接口退役清单（BREAKING CHANGE，2026-11-12）：移除 `astral_authorization_root::{atomic_state, candidate_scope, evidence, experimental, manager, memory_v1_facts, memory_v1_kernel, memory_v1_model, memory_v1_rules, memory_v1_structured, protocol, shared_snapshot}` 及 `memory_v1_hamt::HamtCandidate::replace_existing_version`。影响范围为这些候选实验 Rust API；仓内无生产调用方，相关旧测试随实现退役。面向新版九表的候选读取及更新入口为 `memory_v1_db_rows`、`memory_v1_hamt` 和 `memory_v1_hamt_runtime`，通过追加版本与选择版本表达规则变更；它们不是旧接口的兼容替代，也尚不具备生产授权能力。自本次变更生效，仓内引用已同步删除；若实验调用方需要迁移，应采用 16 字节标识和新候选模型并重新验证，不能直接转换 `i64` 假定身份一致。回滚方案是在独立变更中从本次变更之前的提交恢复相应模块与导出、依赖及测试；现有生产链 `astral-db` 使用的旧数据库键模型不在本清单中。

后续依据本文及用户对待决问题的裁决重审候选，并按新结构设计独立的新数据库；不迁移旧数据。新的概念关系和离线 DDL 见[全新数据库设计](全新数据库设计.md)，其核心表骨架仍不构成完整建库方案。实际建库、初始化和正式采用需另行明确环境并满足适用门禁。本次不删除、覆盖既有数据或执行 SQL。

## 7. 待决与验证

- 规则语言：`OVERLAY DENY` 的精确匹配、多层冲突、条件、优先级、通配、动作别名及未知输入的处理。
- `BASE` / `OVERLAY` 的其余组合语义、重复绑定及数量限制。
- 规则集版本递增和时间戳含义；hash 算法、确定性编码、校验时机和参与授权的外部元数据保护。
- 修改人确认如何覆盖各既有绑定、记录影响范围，以及数据库完整版本持久化失败的报告与恢复边界。
- 租户管理归属、规则集可用范围、跨租户复用与资源访问边界。
- 有效期、状态、删除与停用的精确定义；确认主体、记录、审计和撤销。
- 直接授权、审批、委托是否保留，以及是否映射到同一规则表达的方式。
- Rust 测试需覆盖每卡确认、同事和上下级无自动授权、租户隔离、规则内容变化与确认关系、解绑、多来源、无效条件、并发更新及最终复核；真实 MySQL、初始化和部署另行验收。

memory-v1 单机合同及采用条件以 Rust 规范正文为准；实施与采用仍须完成待决合同和适用验证。本文不授权绕过执行门禁。
