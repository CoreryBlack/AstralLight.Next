# memory-v1 网关与物理双卡设计

> 状态：目标设计与旧基线参考；具体协议、实现和验收尚未完成。
>
> 范围：Gateway 认证入口、身份卡与用户卡分离、可信上下文传递及切卡边界。用户、租户和规则集模型见 [用户双卡租户与规则集设计](用户双卡租户与规则集设计.md)。
>
> 旧基线：本地 `main` 提交 `9ab15556e7d44f99f32b8ba1e16f9beca4604ce9`。旧实现仅作为事实和设计参考，不意味着 memory-v1 必须兼容旧接口、字段、domain 或授权发布机制。本文不覆盖现行工程规范和生产执行门禁。

## 1. 目标与已确定的边界

- Gateway 是外部认证事实入口，负责认证相关校验、可信上下文传递与请求转发；它不因验证了身份就替代业务授权决策。
- 保留网关清洗职责：在处理外部请求和转发时清理客户端伪造的内部身份元数据及不应透传的敏感、网关内部和逐跳头；可信身份上下文由网关在验证后重新构造。具体字段清单和例外须在新协议中定义。
- 保留物理双卡分离：身份卡和用户卡是分别持久化、分别标识的两类对象，不是同一张卡的两个名称，也不是要求客户端携带两张实体卡。
- 每个用户有一张与租户无关的身份卡，身份卡用于认证身份；一个用户可在不同租户持有用户卡，用户卡承载具体租户的授权上下文。
- 身份卡、用户卡、用户和租户的关系及有效性必须可验证；单独持有卡标识、通过认证或切换到某张卡均不等于获得业务权限。
- 用户卡上已确认的规则集绑定参与授权；组织上下级和同事关系不自动推导权限。正式授权入口是 `PolicyEngine.evaluate()`。
- 下游只有在验证 Gateway 身份元数据的签名、时间戳和来源后，才能信任其身份字段；有网关元数据但验证失败时拒绝，不得回退到客户端自带或未经验证的身份头。

## 2. 对象与职责

| 对象或模块 | 职责 | 边界 |
| --- | --- | --- |
| 用户与身份卡 | 表达认证主体及其身份有效性。 | 身份卡不归属于某个租户，也不直接授予业务权限。 |
| 用户卡 | 表达同一用户在具体租户下的授权载体；用户可持有多张卡。 | 当前卡必须属于该用户，不能用其他卡的绑定代替。 |
| Gateway | 作为外部认证事实入口，验证适用凭证并向下游传递经保护的身份与当前卡上下文。 | 不从租户层级、角色名称或身份卡推断业务权限。 |
| Identity | 负责身份、凭证、会话和用户卡选择或切换的生命周期。 | 切卡不能改变认证主体或复制其他用户卡的授权。 |
| 共享授权根 | 为可信模块提供统一的授权事实和隔离读面。 | 不代替 PolicyEngine 作业务授权决定；其实现及接线尚待完成。 |
| PolicyEngine | 结合可信身份、当前用户卡、租户、资源及规则进行授权判断。 | 认证成功或网关转发成功不是授权成功。 |

## 3. 请求链路与可信边界

```text
客户端
  │  请求与适用凭证
  ▼
Gateway ── 验证认证上下文；移除或隔离客户端伪造的内部身份元数据
  │       └─ 以受保护的方式传递主体与当前用户卡上下文
  ▼
业务服务 ── 验证网关来源、时间戳及签名；确认字段与可信事实一致
  │
  └── PolicyEngine.evaluate()
        └── 从同一共享根读取所需上下文，核对资格、租户、资源与规则
              ├── 满足全部适用条件 → ALLOW
              └── 缺失、无效、不一致或无有效权限 → PENDING / DENY
```

图描述目标职责，不预设具体 HTTP 头、token 类型、签名算法、读取接口或部署形式。仅认证服务所需的公开入口可能尚无用户卡上下文；这些入口如何界定和保护另行设计，不得扩展为一般业务请求的身份绕过。

Gateway 必须防止客户端伪造可信内部身份字段。下游只能信任经网关协议完整性保护的字段，不能把未被签名覆盖的附加字段视作身份或授权事实。服务端应基于可信来源确认资源归属，不能仅凭客户端所称的租户或资源范围放行。

### 3.1 清洗与重建

网关保留对外部请求的清洗职责，目标处理顺序为：

1. **清理不可信内部字段**：在认证处理前，移除客户端提供的内部身份、身份卡、用户卡、租户及网关认证元数据；同时处理重复头和大小写变体，不能让它们绕过清洗。
2. **验证凭证并构造可信上下文**：按入口验证所需凭证和会话，从验证结果及适用的可信事实构造用户、双卡和租户上下文，不使用客户端声称的内部身份替代验证结果。
3. **约束转发内容**：转发时过滤不应透传的敏感头、网关内部头和逐跳头；业务头、请求体和查询参数按接口及协议规则处理，清洗不意味着擅自改写业务内容。认证、刷新、切卡等入口若确需向 Identity 转发凭证，必须按明确的方法和路径例外单独定义，不能形成通用透传。
4. **重新注入并保护可信字段**：网关仅从已验证上下文生成所需内部身份元数据，并按新协议保护其完整性；下游独立验证签名、时间戳和来源。无法可靠清洗、验证或构造所需上下文时，拒绝或按对应安全错误处理，不回退客户端身份。

清洗不等于业务授权、内容安全审查或对任意业务字段的自动过滤；业务输入校验及授权仍由相应 owner 完成。清洗字段清单、大小限制、重复字段处理、凭证例外及日志脱敏需形成可测试的新协议；旧基线字段只作参考。该职责也适用于无用户卡上下文的允许入口，不以匿名作为保留伪造内部头的理由。

Gateway 对凭证或会话的具体校验，以及身份、用户卡、租户资格由哪个模块在哪一步读取，还需在新协议中确定；不能假设新系统已具备旧系统的检查，也不能因单机共享根目标而直接删除仍适用的会话安全边界。授权事实无法确认时按适用合同安全拒绝；认证、会话或共享根不可用的具体错误与恢复流程待定义。

## 4. 身份卡与用户卡的生命周期

### 4.1 登录和选择用户卡

身份认证建立的是用户主体；用户卡用于确定某次请求所处的授权上下文。选择卡时，系统须确认用户、身份卡、所选用户卡和该卡的租户之间的关系，并检查适用状态与有效期。用户卡是否在登录时必须选定、单卡是否自动选择、无卡身份可以访问哪些入口、会话如何保存当前卡，均待设计。

一人多租户时，每张用户卡保留自己的租户与绑定；不能将某张卡的规则集自动用于用户其他卡，也不能根据同事或上下级关系推断授权。

### 4.2 切换用户卡

切卡的目标是为**同一认证主体**选择另一张属于该主体的有效用户卡。切换前须核验目标卡归属、状态和租户；切换后请求的授权上下文应与新卡一致，不能复制旧卡权限，也不能让旧上下文冒充新上下文。

切卡与并发请求、凭证轮换、旧凭证失效、重试幂等、跨设备会话和异常恢复的精确合同尚待设计。哪些已开始的请求使用旧卡、切换完成后新请求如何排除旧上下文，必须明确线性化边界并验证；本文不假设旧切卡协议可直接移植，也不预先定义超出已确认授权生命周期的行为。

### 4.3 停用与失效

身份卡、用户卡、用户、租户或会话失效时，受影响请求不得凭旧卡标识继续放行。具体失效传播、共享根版本变化、会话撤销与缓存一致性方案需明确覆盖各入口并验证；发生错误或无法确认时不得扩大授权。

## 6. 与单机内存权威的关系

Gateway、Identity、TrustGraph 和 PolicyEngine 应使用组合进程中同一共享授权根提供的适用只读视图，而不是各自维护一套业务授权权威；具体模块如何接入以及会话、凭证等非授权事实的 owner 待设计。Gateway 不负责复制规则集或生成独立授权快照。

单机目标在完整冷加载完成前不处理正式授权请求；服务期内正式授权不得因共享根缺失而从 SQL 直接补查并放行。完整上下文可在冷加载或受控重建阶段补齐。首次读取所需一致上下文，最终放行前核对根实例、版本、预存内容 hash、状态与可信时间的语义，按共享根合同设计；本文件不声称其已经实现。

内存变更的跨崩溃持久化和异常提示，遵循已记录的单机目标及后续合同；内存成功不证明数据库已落盘。现行生产规范与该目标的差异尚待处理，本文件不授权开放生产 listener 或绕过现行门禁。
