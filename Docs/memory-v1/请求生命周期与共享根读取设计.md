# memory-v1 请求生命周期与共享根读取设计

> 状态：目标设计，2026-11-12；请求级读者、模块接线、缺失补齐和正式授权尚未完成实现或生产验收。工程合同以 [Rust 规范 §15.10](../规范/Rust后端编码规范_V1.0.md#1510-memory-v1-单机内存权威合同2026-11-12) 为准。
>
> 范围：单个受监督组合进程中的一次受保护请求，从 Gateway 接收、认证和清洗，到引擎判断、业务操作、响应及资源释放。公开认证入口及无需授权根的请求按各自协议处理，不为套用本设计虚构身份卡或授权上下文。

## 1. 一个请求，一个请求级读者

一次受保护请求有一个完整生命周期。生命周期内，组合入口在首次需要根事实时创建一个 `RequestRootReader`；同一进程中参与该请求的 Gateway、Identity、TrustGraph、PolicyEngine 和业务模块，按实际调用路径共享这个读者，直接读取同一个根的一致视图。模块只使用职责和请求范围所需的类型化只读接口；并非每个请求都会调用所有模块。

Gateway 接收请求后可以先执行清洗、凭证和协议校验；若认证过程需要根事实，在首次读取前建立读者。尚未认证的输入只是待验证参数，不能凭客户端自报的身份、租户、卡或资源扩大读取范围。任何模块都不得自行重新开始一次读取并将其结果与本阶段的读者结果拼成一个授权上下文。

```text
进程：RootOwner ── 当前共享根 ── 模块长期复用的只读 RootHandle
                                      │
请求 A：接入/清洗 → 请求读者 A → 按实际路径共享 → 复核/操作 → 结束并释放
请求 B：接入/清洗 → 请求读者 B → 按实际路径共享 → 复核/操作 → 结束并释放
```

`RootHandle` 是进程内只读能力；`RequestRootReader` 是请求上下文持有的读取能力，不是新根、线程或读锁。不同请求各有自己的读者，同一请求中模块借用同一读者即可。若请求在尚未读取根前即被拒绝或取消，不必创建读者。跨进程或网络调用不能传递 Rust 引用、`Arc` 或只读能力：跨边界协议、身份验证、请求关联和另一进程如何取得自己的授权事实均需单独设计；不能将本单机合同宣称为跨进程共享根。

## 2. 生命周期与职责

1. **接入与认证**：Gateway 接收请求，清洗客户端伪造的内部身份元数据，验证适用凭证；下游验证网关身份元数据的签名、时间戳和来源。认证或协议失败时结束，不进入业务放行。
2. **建立读者**：首次需要根事实时，从同一 `RootOwner` 的只读句柄取得一个请求级读者，绑定请求关联标识、根实例、版本、预存内容 hash、状态及必要的时间观察；身份和租户在各自可信校验完成后绑定。标识只用于关联，不代替身份或授权。
3. **一致读取与评估**：参与模块在同一个读取阶段按职责查询预建关系；引擎取得本次判断所需完整上下文，包括用户、双卡、租户、已确认绑定、规则、可信资源归属及适用限制，并由 `PolicyEngine.evaluate()` 判断。读取事实、认证成功或持有读者均不等于 ALLOW。
4. **最终复核**：ALLOW 前由授权链核对同一根的实例、版本、预存 hash、状态及可信时间，检查本次判断的有效期；不重新遍历完整关系或重算完整 hash。变化、失效、时间条件无法确认或 owner 消失时，本次判断不得放行。
5. **操作与结束**：通过复核后按本次授权执行对应操作，并按协议响应；成功、拒绝、异常、取消和超时均结束请求并释放读者及其读取视图。业务操作及其数据一致性仍由业务 owner 负责；管理变更须按 §5 再做受限提交检查。

该最终复核是用户确认的本次授权判断边界；撤权在复核前发布则旧判断不能放行，复核通过后发生的撤权不追溯否定本次已通过判断，后续请求重新授权。**复核与随后业务副作用不是自动原子绑定**：如果业务操作还需要对业务数据、资源归属或提交条件做一致性保证，必须由该操作合同单独明确并验证，不能仅以根元数据相同证明业务提交安全。

## 3. 并发读与资源生命周期

目标实现可以采用 `ArcSwap<RootSnapshot>` 和不可变、结构共享的 HAMT：每位请求读者在读取阶段原子取得一次当前快照，然后在其上遍历关系；读者互不需要根级读锁。经授权的写入在唯一 owner 下构造一致的新状态，通过 CAS 或等价协议原子发布；两个从同一版本出发的写入不能相互覆盖。快照 `N` 的在途读者和快照 `N+1` 的新读者可以并行，旧视图只是被引用的历史读取状态，不是可独立提交的第二权威。最终复核比较当前元数据；全局版本变化即使与本请求无关也使旧判断失效。

句柄数量由模块装配决定；活跃读者通常与已进入根读取阶段的在途请求数量相关，而不是模块数量。多个读者可引用同一个快照，不按请求复制整棵根；引用计数、HAMT、快照替换和共享节点仍有运行成本，不能据此声称完整请求链无锁或零开销。请求完成后读取视图应及时释放，旧快照仅在不再被任何持有者引用后回收。

必须设置可执行的请求并发、排队长度、等待与执行时间、补齐并发及内存预算，容量不足时按接口合同过载或安全失败；监控活跃请求、读者持有时间、旧版本保留和内存压力。普通并发请求不要求互相等待；发布及重试的资源策略须兼顾撤权，不能将一律暂停写入或优先放行旧读者当作默认策略。禁止强制回收仍被引用的快照。

请求取消、超时或客户端断连须传播取消并释放请求拥有的读取引用；被派生任务、流式响应或其他引用持有时，不能仅凭请求处理函数返回就声称快照已回收。实现须限制、取消或等待这些工作，记录实际回收和资源上界；长连接、流式和后台工作的具体生命周期与再次授权边界在采用前确定，不能无限期继承一次 ALLOW。

## 4. 未加载上下文的受控补齐

读取区分完整、已证明不存在、未加载、无效和不可验证。只有确实未加载且范围可确定时，本请求才可触发根协调器进行有界 MySQL 一致性读取；数据库行不直接用于 ALLOW。相同缺失范围可合并并发读取，但仍需验证每个请求的身份、租户和范围。

```text
请求读者，读取阶段 N → 发现未加载 → 丢弃该阶段的授权判断及派生结果
    → 受控查库、验证关系和租户 → owner 检查并发及内存冲突
    → 原子补入同一根 → 同一请求读者受控进入新阶段 N+1
    → 从新阶段重新读取所有授权依赖并重新评估 → 最终复核
```

读者逻辑身份和请求生命周期不变，底层读取阶段可以更新；刷新必须由请求协调路径独占执行，先结束或取消仍使用旧阶段的并发分支，不能让模块同时混用两个阶段。刷新前释放不再需要的旧引用；任何已从旧阶段派生的身份、范围、匹配、决策或管理授权都必须重新验证，不能与新阶段数据拼接。其他请求的读者不受该请求的阶段切换影响。

补入前核对同一根实例、缺失范围、版本和当前内存事实；DB 可能落后，不能覆盖较新内存事实或复活撤销、删除。冲突、安全合并无法证明、取消、超时、容量耗尽或未知结果时 PENDING/DENY；明确不存在且范围完整时按规则拒绝。重试须有上限，具体覆盖证明和合并协议见[单机唯一共享根设计](单机唯一共享根设计.md)。完整的后续请求直接读根，不查 DB。

## 5. 管理请求

```text
Gateway → TrustGraph 构造管理意图 → 同一请求读者读取根
    → PolicyEngine.evaluate() 判断具体管理操作 → 最终授权复核
    → TrustGraph 调用与该授权绑定的受限写能力 → RootOwner 原子提交 → 响应
```

授权绑定操作者、具体动作、目标范围、变更摘要、稳定 `operationId` 和观察到的根实例及版本；根提交时核验授权有效性、目标和摘要、重放及 CAS 前提，失败则不提交并重新发起完整评估。只读者无法转换为通用写能力。管理变更成功后原读者仍观察旧阶段；如需读取提交后的状态，受控进入新阶段并重新读取，不得把旧观察说成当前状态。内存提交成功不证明 MySQL 或审计已经落盘。

## 6. 采用与验证

现有代码中的唯一根和 `read_card()` 是候选，尚无本文件所述的完整请求级读者、受控阶段刷新、全部模块接线和正式 ALLOW。本设计不授权开放正式 listener，也不证明冷加载、持久化或真实数据库集成完成。

采用前至少用 Rust 验证：同请求跨模块同源同版本、多请求并发读与原子发布、写冲突及撤权发生在最终复核前后的边界、owner 失效、时间失效、跨租户与双卡隔离；缺失补齐后旧结果作废、并发分支收束、重复缺失、补齐与撤权竞争及后续不查 DB；请求取消、超时、派生任务与旧视图回收、容量耗尽和长连接限制；管理摘要替换、重放与 CAS 冲突。真实 MySQL 冷加载、补齐、故障及持久化另行提供证据；实际 API、并发预算、可信时间、跨模块接线和业务操作提交合同仍待实现与验证。
