## 3. P3 并发写风暴（3 线程×20s，同规则集持续 add）——两阶段对照

| 指标 | 基线（v1 门禁未在场、F6 缺陷在身） | v1 门禁（初版，本日首跑） | **v2 门禁（撤权类，本日复跑）** |
|---|---|---|---|
| ops / qps | 573 / 28.5 | **2 / 0.1** | **149 / 7.3** |
| errors | 0 | **16,965** | 14 |
| commit p50 / p95 (ms) | 86.7 / 290.3 | 2.1（快速 403） | 335.8 / 840.0 |
| 完整性 | outbox 575 行全 PROCESSED，**head proj=0 / status=PENDING（573 delta 从未发布）** | 4 行 | 151 行全 PROCESSED、terminal_once、连续 |

**v1 自饥饿机制**（P3 实测否决初版门禁）：写请求的权限检查本身是一次证据读；
写突发期间前一个写的未发布 delta 把后一个写的权限检查打成 PENDING → 403，
探针 `FOR UPDATE` 又与 projector 发布在 delta 行锁上互饿 → 正反馈（20s 内
16,965 次快速 403 + 熔断打开）。最小复现：3 线程 × 10 add，21/30 失败。

**v2 修订**（`b292337c`）：谓词收窄为撤权类（`event_type IN ('REMOVE','REVOKE')`
或 `revoke_fence` 超前本卡已发布水位——唯一 stale-ALLOW 方向），ADD/UPDATE 类
不阻塞（缺新授权 = deny-biased EC 的 ms 级窗口）；探针改非锁定一致性读（严格
reader 事务首语句建立快照），消除与发布者的行锁互饿；线性化由双读纪律 +
ALLOW 前复读承担。**复测**：149 ops 全部发布、14 errors（8.6%，并发写-发布
争用下的熔断窗）、integrity 完整。

**口径警示**：基线 28.5 ops/s 与本次 7.3 ops/s 不可直接比大小——基线的每次
op 只写 source（delta 滞留不发布），本次每次 op 含真实发布投影锁竞争。按
"成功且已发布"口径，基线等效为 **0**。

- 本次 9.0 qps 聚合（90 reads，p50 197.8ms / p95 910ms）：P3 的 149 次发布

- **排水后干净复测**（20s 等待 + 单线程 10s×3 节点）：node-b 46.1 /
  node-c 33.8 / node-a 16.4 qps——与 P1 每线程基线（node-b 387.8÷8≈48）
  一致，系统排水后恢复健康。
- 校准项：perf 脚本 P4 前应加有界排水等待（对标 S6/S5 的排水等待模式）。

## 5. 结论

1. F5/F6 修复把三节点读路径从"秒级尾刺 + 10 qps 级并发坍缩"修复到
   "p95≈p50×1.2 + 数百 qps"，撤销传播从永不收敛修复到 p50≈334ms。
2. P3 揭示并驱动了 freshness gate 的 v2 重设计：**零 stale-ALLOW 保证与写
   突发可用性可以同时成立**——前提是门禁只拦撤权类（stale-ALLOW 方向），
   扩权类走 deny-biased EC。
3. 发布路径从"从未被执行"变为真实参与竞争，写吞吐的下一步优化空间在发布
   事务与写事务的锁竞争（P3 commit p50 336ms 的构成）——属性能工程迭代，
   非正确性问题。
