## RQ3.1 正常增量（增量编译开销主口径）

- **语义映射**：Java `NativeIncrementalCompileBenchmark` 的正常增量编译成本
  → Rust 三节点等价为"预置 N 条规则后，再增量的完整发布成本"。
- **装置**：A 卡 9061；每规模一套规则集夹具（1 条 learn_subject:read 优胜 +
  N 条 learn_level:read 非优胜，BASE 绑定，三节点 ALLOW 收敛后开始计时）；
  每规模 20 次 timed 增量 add。双段口径：api_ms（source mutation 请求返回）
  与 publish_ms（本批 delta 全部 `SUCCEEDED` 的异步发布完成——即增量编译 +
  发布事务的真实成本）。
- **原始数据**：

| 规模 N | 发布完成 p50 | 来源 |
|---|---|---|
| 100 | **102.66 ms** | run4 日志（JSON 未落盘，已抢救并标注 provenance） |
| 500 | **101.32 ms** | run4 日志（同上） |
| 高频突发（RQ3.3 同口径，60 样本） | p50 **101.67** / p95 110.02 / max 110.17 / mean 101.59 | run5 JSON 完整分布 |

- **断言与结果**：规模翻倍（100→500）发布成本零变化（102.66 → 101.32ms）；
  60/60 次发布零超时。**PASS**。
- **结论**：增量编译 + 发布成本为 **O(1) 常数（~102ms 三节点口径）**，与
  本地 `cargo bench`（policy-engine 编译器微基准）的增量/全量对照互证；
  ~102ms 的常数主要来自三节点提交-传播与严格 reader 收敛纪律，非编译规模。

## RQ3.2 优胜者删除退化

- **语义映射**：Java RQ3.2（delete_winner vs delete_non_winner 的重建快照
  延迟）→ Rust 等价为"删除决策依赖条目（优胜）vs 无关条目（非优胜）"的
  端到端行为与成本。
- **装置**：与 RQ3.1 同一夹具。非优胜删除：删一条 learn_level 条目 → 断言
  KEY（learn_subject:*:read）决策三节点保持 ALLOW；优胜删除：删 learn_subject
  条目 → 断言三节点翻转 DENY，并记录决策可见时间（decision_flip_ms）。
- **原始数据**：

| 规模 N | 删优胜 api_ms | 决策翻转 ms | 翻转正确 | 删非优胜 |
|---|---|---|---|---|
| 100 | 326.17 | 1431.0 | ✓ DENY | 决策不变 ✓（publish 计入下述口径） |
| 500 | 488.41 | 1928.38 | ✓ DENY | 决策不变 ✓ |

- **断言与结果**：两种删除全部正确收敛（非优胜→ALLOW 保持、优胜→DENY）。
  **PASS**。
- **结论**：无编译级退化——决策可见时间随卡证据规模增长（1431→1928ms），
  该成本由删除引发的卡作用域扇出与三节点证据重读主导，属证据读取成本而非
  增量编译规模效应；api 侧（89–488ms）恒在亚秒级。

## RQ3.3 高频写入

- **语义映射**：Java RQ3.3 高频写入下的编译成本 → Rust 等价为 ADD-only
  顺序突发的每 op 双段延迟 + 突发后排水完整性。
- **装置**：A 卡 + HF 夹具（BASE 绑定）；60 次连续 add（learn_level:read），
  逐 op 计时；随后一次排水（全部 delta `SUCCEEDED`）+ 终态核验。
- **原始数据**：ops_requested=60 / ops_ok=60 / **api_errors=0**；
  add_api p50=530.02 / p95=546.90 / max=552.16 / mean=527.64ms（重证据卡上
  的 API 侧评估成本）；publish p50=101.67 / p95=110.02 / max=110.17ms；
  publish_timeout=0；burst_drain=98.76ms；deltas_terminal=true。
- **断言与结果**：零错误、零发布超时、全终态。**PASS**。
- **结论**：高频增量路径稳定，发布成本稳定在 ~102ms 常数；API 侧 530ms 为
  重证据卡（~640 授权）的请求内评估成本，与规模口径 RQ2 的梯度结论一致。
- **对照形态（撤销重压，非本口径）**：add+del 交替突发下 100% 快速 403
  （`AUTHORIZATION_PENDING`）——每次 delete 的撤权类 delta 未发布前，v2 门禁
  正确拦截后续写。属门禁设计语义（fail-closed），已在 run3 实测记录。

## RQ3.4 SCAN vs HDEL（Rust 等效：keyed DEL + epoch）

- **语义映射**：Java RQ3.4 对比两种 Redis 失效策略（SCAN 全扫 vs HDEL 定向
  删）在字段规模下的成本 → **Rust 设计中不存在 SCAN 路径**：`evidence_cache`
  的失效 = 卡键定向 DEL + cache epoch 版本（设计声明"无需扫描删除"，源码
  注释为证），写后失效由 fence/generation 快照承担，读者端 miss 即回源。
- **等效实测**：RQ5.E4 的 cold/warm 差值即"失效后首个决策的回填窗口"——
  **cold p50 17.7ms − warm p50 16.4ms ≈ 1.3ms**（30 次 FLUSHALL 循环，见
  E4 详报），且回填期间决策语义全程 ALLOW（缓存不可见翻转）。
- **结论**：**N/A-by-design + 等效成本实测**。无 SCAN 形态可比较；定向失效
  + epoch 的失效窗口为毫秒级常数，与字段/规模无关。

## RQ4.B 长时高频写入稳定性（60s × 3 线程，>20s 缺口补齐）

- **语义映射**：Java RQ4.B（高频写入 + 一致性检验）的长时窗口缺口 → Rust
  三节点 60s 三线程 ADD-only 风暴（每线程跨 node-a/b/c 轮转写入同一规则集），
  风暴后 bounded 排水（960s 窗口）+ 全量一致性核验。
- **装置**：HF 夹具（A 卡）；3 线程 × 60s；排水后核验：delta 终态、outbox
  连续/全 PROCESSED/terminal_once、card head 单调。
- **原始数据**：wall 61.2s；**ops=122 / errors=28（18.7%）/ qps=1.99**；
  错误样本全部为 `403 PERMISSION_DENIED — AUTHORIZATION_PENDING for
  permission_rule:create`（并发写-发布争用下的线性化快速 403，v2 门禁语义）；
  **drain_ms=898,564（898s）drain_complete=true**；
  parked_at_budget_exhaustion@snapshot=0（自愈完成）；deltas_terminal=true；
  outbox rows=184，contiguous=true / all_processed=true / terminal_once=true；
  card_head_generation=1772。
- **断言与结果**：一致性断言**全部 PASS**（无丢代、无重复终态、无越权放
  行）；吞吐/错误为观测数据非断言。**PASS（正确性）+ liveness 发现（见
  下）**。
- **机制性发现（同聚合高扇出的发布指针竞争）**：同一规则集聚合的所有条目
  delta 共享一个聚合发布指针；3 worker 竞争下败者在竞争窗内耗尽 5 次
  attempt 预算 → 900s 最大退避停摆（期间卡作用域对后续写保持 fail-closed
  PENDING）→ 静默期重试自愈收敛（898s 排水窗完整覆盖该周期，零 stale
  allow）。旁证：run2/run3 的 scale 夹具解绑扇出（121 条同聚合 REMOVE 同秒
  入队）触发同机制，965s pre-drain 后全部自愈。
- **工程结论**：正确性满分（唯一 owner、唯一终态、零丢代、零越权）；写吞
  吐在重证据卡 + 同聚合争用下退化（1.99 qps vs P3 轻载 7.3）是既知争用窗
  的放大形态。产品级改进候选已列报告 §十二：PointerMoved/争用类失败是否应
  消耗 attempt 预算（不消耗则败者不受停摆惩罚，代价是可能延长忙等）。

## RQ5.E4 缓存回填（warm vs cold）

- **语义映射**：Java E4（本地缓存重填充：warm/cold 延迟与开销）→ Rust 等价
  为 L2 FLUSHALL（epoch + L2 全失配）后首决策（冷：L2 miss → L3 源 + 回填）
  与后续决策（暖）的延迟对照。
- **装置**：干净 B 卡 9062（单优胜授权）；30 循环 ×（FLUSHALL → 1 冷样本 +
  9 暖样本），node-b sim 评估全链路；每循环断言决策 ALLOW（缓存不可见翻
  转）。
- **原始数据**：cold n=30 p50=17.70 / p95=18.65 / max=18.83 / mean=17.44ms；
  warm n=270 p50=16.41 / p95=17.46 / max=18.68 / mean=16.34ms；**回填开销
  ≈1.29ms（p50 差）**；30/30 循环决策语义全程 ALLOW。
- **断言与结果**：冷决策正确（回填期间不放行旧代、不拒绝新代）；开销常数
  级。**PASS**。
- **结论**：L2 全失配的重建窗口为毫秒级常数（1.3ms），epoch 机制使"清空缓
  存"不产生可见的授权翻转——E4 缺口关闭。

## RQ5.E11 旧令牌回放与上下文参数

- **语义映射**：Java E11（上下文参数依赖异常率）+ README 表的"旧令牌回
  放" → Rust 三臂：**(a) 撤销后重放**、**(b) 陈旧签名时间戳**、**(c) 跨租
  户上下文伪造**；异常 = 任何撤销后 ALLOW 或跨租户 ALLOW。
- **装置**：B 卡 9062（tenant 9002）。(a) 捕获撤销前签名评估请求（三节点
  ALLOW 验证）→ 删除优胜条目 → 三节点 DENY 收敛 → 原样重放（同一签名头、
  同一时间戳）×5；(b) 以 ts = now−1h 重签管理 API 请求；(c) 以 B 签名上下
  文（tenant 9002）伪造 cardId=9061（tenant 9001）的评估，三节点各一次。
- **原始数据**：
  - (a) 重放 status = [200,200,200,200,200]（签名层在时间窗内合法接受），
    但决策体 **ALLOW 次数 = 0**——决策跟随当前投影（DENY），旧 ALLOW 不复
    活；
  - (b) 陈旧时间戳 → **403 拒绝**（网关签名新鲜度校验生效）；
  - (c) 跨租户伪造 → status [200,200,200] 但 **DENY 3/3**（跨租户隔离）。
  - **anomalies = 0 / total = 8，anomaly_rate = 0.0**。
- **断言与结果**：**PASS**——三层防线的异常率 0：投影权威（重放不复活旧
  ALLOW）、签名新鲜度（陈旧 ts 拒绝）、租户隔离（伪造上下文拒绝）。
- **结论**：E11 缺口关闭。注意 (a) 的 200 是网关签名校验通过（重放窗内），
  安全性由决策层投影权威保证——两层职责分离正确。
