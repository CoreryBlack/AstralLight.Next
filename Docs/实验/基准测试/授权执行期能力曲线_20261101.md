## 1. 结论速览

本轮优化已经把最容易取得、同时风险最低的收益基本兑现：每次评估的深拷贝、重复 identifier/digest validation、无条件 attribution 计数、重复装配以及 matcher index 重建风暴，均已分别得到针对性处理。剩余成本不再集中在一个可以简单替换的算法，而是集中在授权正确性所要求的共享状态、严格证据门禁和热点 scope 串行段。

当前最稳妥的结论是：

1. **旧极限主要由分配和重复验证支配。** 4050 grants 的旧 ceiling 约为 198 ops/s、5.03 ms/op、251k allocations/op、9.4 MB/op；10 线程约 47 ops/s。D1–D3 阶段将主要成本逐步从 owned evidence clone 和验证分配中移除。
2. **完整 evaluate 的缓存收益是真实且稳定的受控差异，但不是单一 Arc 操作的收益。** 2026-10-10 的 45-case 矩阵中，forced/cached 几何耗时比为 1.392–4.393，cached/forced 吞吐比为 1.359–4.092；cached 仍保留最终 evidence reread、strict gate 和 token recheck。
3. **matcher 优化解决了大 evidence 的候选扫描和交错 card 的 index rebuild 退化，但不能消除完整装配成本。** 线性扫描、类型索引、secondary index 和 adaptive fallback 已形成按规模/访问形状选择的路径。
4. **当前 t8 cached deny 的残余主因是共享 owner。** v2 归因显示，同一热点 `RefillScope` 仍会落在同一 cache stripe；不同 scope 的竞争可以降低，但同一热点 key 的 critical section 仍存在。共享 PolicyEngine 的统计/breaker 观察路径也会增加成本。
5. **forced assembly 的数量级成本不是 owner mutex。** 在 1001/2048 grants 的 t8 deny 中，初始 evidence load 和 matcher/装配远大于 cache wait、insert wait 或 breaker wait。继续微调共享锁不会解决 forced assembly 的主要部分。
6. **不可变快照、失效广播和 single-owner/single-flight 都不是无代价的局部优化。** 它们分别把问题转移到内存权威、失效一致性/安全和热点吞吐/恢复语义。在不改变现有 generation、dependency、manifest、revoke fence、published-evidence strict gate 和最终 reread 不变式的前提下，当前局部优化已接近可接受上限。

这不是“理论绝对最优”的证明，而是一个工程边界判断：若不引入新的失效协议、内存权威模型或热点调度语义，就不应继续堆叠收益很小且会增加复杂度的 mutex/atomic 微优化。

## 3. 旧性能极限

### 3.1 4050 grants ceiling

旧 ceiling probe 的对象是 4050 grants 的 strict published-evidence 路径，主要数字为：

| 指标 | 旧 ceiling |
|---|---:|
| 单线程吞吐 | 约 198 ops/s |
| 单次耗时 | 约 5.03 ms |
| allocations/op | 约 251k |
| bytes/op | 约 9.4 MB |
| 10-thread 吞吐 | 约 47 ops/s |

旧 probe 把匹配 grant 放在 evidence 第一位，`find()` 很快命中并得到约 19 ns 的 matcher 观测。这个数字不能代表 4050 grants 的尾部 matcher ceiling；只有加入 first/middle/last/absent 位置后，线性尾部成本才被测出来。

### 3.2 旧瓶颈的调用链

旧路径的成本不是单一的 matcher 循环，而是多个局部成本叠加：

```text
owned evidence clone
→ identifier/digest validation
→ 每次评估的分配与计数
→ published evidence materialization
→ matcher
→ final evidence reread
```

其中 allocator、重复验证和观测计数的影响在多线程下会被放大。后续优化的核心不是跳过授权门禁，而是减少同一不可变证据在一次评估和连续评估中的重复工作。

## 4. 性能演进阶段 V1–V4

### 4.1 V1：Arc-backed zero-copy evidence read face

对应提交：`159331b`（`perf(db,engine): zero-copy published-evidence read face (Arc snapshots)`）。

核心思路：repository 和 memory projection hub 共享不可变 `Arc` snapshot；cache hit 只执行句柄复制，L2 materialize 后回填 L1，减少完整 owned evidence clone。

提交消息记录的 release probe：

| 场景 | 旧值 | V1 观测 | 变化 |
|---|---:|---:|---:|
| 1 grant throughput | 313k ops/s | 444k ops/s | 约 +42% |
| 1 grant allocations/op | 124.6 | 63.8 | 约 -49% |
| 1 grant bytes/op | 5.3 KB | 2.1 KB | 约 -60% |
| 4050 grants throughput | 198 ops/s | 364 ops/s | 约 +84% |
| 4050 grants allocations/op | 251k | 89k | 约 -65% |
| 4050 grants bytes/op | 9.4 MB | 0.62 MB | 约 -93% |

这些数字是 commit-message-only probe，不能写成当前分支重新复现的 canonical measurement。V1 的重要收益是把证据复用从“复制全部内容”转为“共享不可变对象身份”，但它没有移除最终 strict reread，也没有把内存 snapshot 变成 source authority。

### 4.2 V2：allocation-free validation 与 observer-effect 修正

对应提交：`659efc3`（`perf(types): allocation-free evidence contract validation + probe observer-effect fix`）。

核心变化：

- `ensure_identifier` 改为只验证，不在验证路径重复创建 `String`；
- allocation counting 只在 attribution phase 开启；
- 关闭计数时不再用共享 `fetch_add` 污染多线程 throughput；
- 观测实现不再改变被观测的正式热路径。

提交消息记录：

| 指标 | 旧值 | V2 观测 |
|---|---:|---:|
| 4050 grants throughput | 198 ops/s | 616 ops/s |
| 10-thread throughput | 47 ops/s | 3632 ops/s |
| allocations/op | 251k | 42.3 |
| validation | 1.41 ms / 44.5k allocations | 0.81 ms / 0 allocations |
| 1 grant throughput | 313k ops/s | 508k ops/s |
| 4050 grants scaling | x2 约 96% | x4 约 90%，x10 约 59% |

这里已经出现了一个重要方法论结论：性能探针必须隔离。若计数器本身进入每次评估的共享热路径，测到的不是被测系统的扩展性，而是测量器的争用。

### 4.3 V3：byte-table/one-shot validation 与安全修正

对应提交：`20d34ed`（`perf(types,engine): byte-table scans + one-shot evidence validation conclusion`）。

核心变化：

- identifier 和 sha256 validation 使用 byte classification table；
- 同一 `Arc` evidence 在单线程内只完成一次 validation；
- final reread 复用已经证明的 validation conclusion；
- validation 失败的对象被 evict，不作为成功结果缓存。

提交消息中的峰值观测：

- 4050 grants 单线程约 `198 → 2862 ops/s`，约 14.5x；
- 单线程 P50 约 `5.03 ms → 0.35 ms`；
- 10-thread 约 `47 → 15274 ops/s`；
- allocations/op 约 `251k → 42.0`。

随后提交 `44f8410` 修复了两个安全问题：

1. byte-table 路径错误接受 NBSP、U+2028、U+3000 等非 ASCII whitespace/control；
2. `validate_shared` 只依赖裸 pointer 地址，存在 ABA address reuse 风险。

修复方式是对非 ASCII 字节回退完整 Unicode-aware scan，validation slot 强持有 `Arc`，并用 `Arc::ptr_eq` 判断是否为同一 evidence snapshot。安全修正后的提交消息数字为：

- 4050 grants 单线程约 `2242 ops/s`；
- 10-thread 约 `11985 ops/s`；
- 相对旧 ceiling 仍约 `11.3x`；
- 相对 V3 峰值约增加 20% 成本。

这次退化不是无意义的回退，而是为恢复精确 Unicode 语义和对象身份安全支付的必要成本。授权性能不能以错误接受输入或 ABA 风险换取峰值。

## 6. 根因分析：为什么当前已经接近局部上限

### 6.1 Cached 热路径

当前 AssemblyCache 使用固定 stripe 和全局预算。分片能降低不同 `RefillScope` 之间的争用，但同一完整 scope 必须稳定映射到同一 stripe，才能保持 cache key、generation、publication identity 和 revoke fence 语义。因此：

```text
更多 stripe
≠
同一热点 scope 的无锁并发
```

命中路径仍必须完成 stamp/TTL/token 校验、必要的 LRU 维护和 Arc clone；这些维护不能把旧 evidence 当作新的授权 proof。GC、eviction、容量和 poisoned-lock-as-miss 也必须保持 fail-closed 语义。

当前 v2 t8 deny 中，shared cache/private engine 的 128-grant `getLockWaitNs` p50 约 1.118 ms，而 private/private 约 0.037 ms；1001 grants 为约 0.223 ms 对 0.019 ms。这个差异证明 cache owner sharing 仍是 cached 热路径的主要残余成本，但它不是一个可以通过任意扩散 cache owner 而安全消除的局部锁。

### 6.2 PolicyEngine 共享统计与 breaker

AtomicHitStats 已经消除原有 `ArcSwap<HitStats>` 的 load-copy-modify-store 热路径，避免 per-evaluation clone、分配和并发 lost update。它只承担观察职责，不参与授权放行。

但共享 engine 仍会经过 breaker map/state 和统计归因路径。read-first map lookup、`Arc<AutoCircuitBreaker>` 和 attribution 只减少 map 锁嵌套及复制，不改变 resource/global breaker 的双重语义、threshold、recovery window、half-open probe budget 或 fail-closed fallback。小 grant/t8 cached deny 中，shared engine 的观察成本仍然可见；继续拆成 private engine 会改变进程级 breaker 视图和统计聚合语义。

### 6.3 Forced assembly

forced arm 每次使用唯一 synthetic second，保留真实 miss、装配、refill 和 token recheck。它不是另写一套 no-cache 算法，因此暴露的是完整 miss 成本。

v2 显示 forced arm 的总成本随 grants 大幅增长，而 cache insert/get wait 和 breaker wait 只占很小比例。完整 evaluate 还必须执行：

```text
初始 strict evidence read
→ validation / matcher / assembly
→ PolicyEngine gates
→ ALLOW final evidence reread
→ generation/dependency/manifest/revoke fence/token recheck
```

删除最后的 reread 或 strict recheck 可以制造数字收益，但会破坏授权不变式，因此不属于可接受优化。

## 7. 当前架构取舍

### 7.1 不可变快照或 atomic replacement

只读 snapshot 本身不是问题，问题在于它何时可以成为授权读取的权威。若发布、generation、dependency、revoke fence、manifest identity 或回收状态不能被严格证明，旧 snapshot 就可能被误当成有效授权。若每次命中再通过 durable generation/read-gate 证明，部分收益又会被重新读取抵消。

因此不可变快照可以作为未来发布/读取协议的组成部分，但不能只把现有 `Mutex` 换成 `ArcSwap` 就宣布解决 owner contention。

### 7.2 失效广播

广播可以减少读路径检查，但丢失、乱序、重复或延迟广播都必须有安全兜底。安全兜底只能是 durable generation、token fence、strict reader 或 `PENDING/DENY`，不能是“相信本地 cache 已被失效”。否则 cache failure、stale state 或 lost invalidation 会扩大授权。

所以失效广播不是单纯的性能优化，而是新的消息/恢复/审计协议；需要额外证明 worker restart、ownership transfer、replay、dedup 和未知结果对账。

### 7.3 Single-owner / single-flight

对同一 scope 只允许一个 owner 构建，可以减少重复 assembly，但它把热点吞吐上限转移到 owner、lease 和等待队列：

- 同一热点不能并行构建；
- owner 超时或重启会产生 UNKNOWN 状态；
- lease/generation/token fence 必须防止陈旧 owner 回填；
- 等待者需要有界等待、`PENDING` 或安全降级。

这条路线适合解决重复工作或控制资源预算，不适合直接宣称提高热点并发吞吐。

### 7.4 当前结论

在以下条件不变时：

- `PolicyEngine::evaluate()` 是唯一正式授权入口；
- published-evidence strict gate、最终 ALLOW reread 和 token recheck 保留；
- generation/dependency/manifest/revoke fence 保留；
- cache 有 TTL、容量边界、GC 和 poisoned-lock fail-closed；
- 不新增一套失效/回收/owner 恢复协议；
- 不接受把热点吞吐或可用性转移给等待队列；

当前局部优化已经接近合理上限。后续若要突破，必须先批准架构取舍，而不是继续在 matcher、stripe 数量或统计原子上做小幅调整。
