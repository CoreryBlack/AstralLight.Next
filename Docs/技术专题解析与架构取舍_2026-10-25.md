# 技术专题解析与架构取舍

> 日期：2026-10-25
> 范围：AstralLight.Next 当前 Rust 仓库、已跟踪的迁移/架构/测试材料，以及本机可核验的历史实验记录。
> 性质：非规范性技术分析；不替代源码、工程规范、迁移验收或生产部署证据。

## 摘要

本仓库是独立 Rust workspace，不包含 Java 应用服务源码。Java→Rust 的材料因此只能作为迁移语义和历史适配记录，不能在当前 checkout 上独立证明逐接口、逐消息或生产行为等价。现行实现以 Axum/Tokio/Tower、SQLx、Lapin 和 AstralLight 自有 `PolicyEngine` 为主；这些取舍主要体现显式边界、异步运行时和对 source/projection 生命周期的控制，不构成在所有负载或所有语义下的综合优胜证明。

授权架构必须区分 canonical grant ledger/published-evidence 与 legacy snapshot：生产 `SqlxRuleRepository` 的正式评估走 published-evidence strict gate；旧 `MAX(version_no)`、snapshot READY 或旧 head 不能为生产请求证明授权。canonical 链已接入代码，但既有数据 backfill/rehearsal、真实 MySQL/Redis/RabbitMQ 集成、读侧迁移和正式切流仍未验收。对象级授权也要求由服务 owner resolver 先解析目标归属，再调用 `PolicyEngine::evaluate()`；仅构造 actor context 不足以证明资源 owner。

[授权执行期能力曲线（2026-10-25）](实验/基准测试/授权执行期能力曲线_20261025.md)提供单机完整 `PolicyEngine::evaluate()` CPU fixture 的新测量及严格限定的历史对照。它与静态能力清单、跨引擎比较和生产 HTTP 容量属于不同证据类型，不应合并成一个分数或一个 QPS 指标。

## 1. Java → Rust：迁移映射与行为等价边界

### 当前边界

- 当前仓库是 Rust 独立 checkout；根目录 [README](../README.md) 明确标记 Java 应用服务、生产部署状态和生成的实验归档不随该源边界提供。仓库保留的 Java 文件主要位于明确归档的 benchmark/历史材料中，不是可直接运行的 Java 服务基线。`astral-chat` 与 `astral-learn` 生产 runtime 已退役并从 checkout 物理移除；相关历史路径只保留在 dated evidence 中。
- [2026-08-05 等价适配状态](迁移/Rust迁移Java等价适配状态_2026-08-05.md)记录 Identity、Monitor、MQ、Gateway、PolicyEngine、TrustGraph 等一批有范围的 Java 对照与修复，也明确列出了未完成的 WebSocket handshake、真实 MySQL/Redis/RabbitMQ 故障注入、consumer 断流恢复和多实例竞争验证。它是带日期的适配账本，不是对当前 checkout 的整体再验收。
- [迁移架构决策](迁移/Rust后端迁移架构决策_V1.0.md)含旧模块规模估算、阶段计划与替代关系；估算和迁移计划不能被解释成源码/运行覆盖率。
- 另有 2026-10-24 的 Python unittest→Rust 原生测试 crosswalk，登记 622 个方法，其中 `EQUIVALENT` 只表示对应离线/注入输入断言；它不是 Java 服务运行等价表，也不代表真实依赖、网络或部署已验证。

### 等价判断方式

迁移等价应按契约逐项核验，而不是按框架名称或代码行数映射：认证与可信头、主体和双卡上下文、目标资源 owner、ALLOW/DENY/PENDING 结果、HTTP/wire、事务及 source mutation、消息 ACK/DLX/幂等、审计关联、失败传播和恢复行为，都有各自的 owner 与证据要求。对授权而言，服务先做资源/动作映射与资源注册校验，再构造 actor context；目标对象 owner 必须由服务专属 resolver 解析成功后才进入 `PolicyEngine::evaluate()`。[`physical_policy_context`](../astral-common/src/middleware/permission_check_shared.rs#L105-L114) 不解析目标 owner并将 ownership 设为 `Unresolved`；仍保留的 [`permission::require_permission`](../astral-common/src/middleware/permission.rs#L15-L40) 也不能代替 resolver。

### 取舍与待验证

Rust 所有权、类型和 async 生态提供了表达并发、错误和数据边界的不同工具，但这些工具本身不证明旧系统语义已经迁移完整。Java 源码当前不在此仓库，缺少当前 Java 服务 checkout 时，新增差异仍需有授权的 Java 基线、黄金样例、协议/数据对照或受控双端验证。RQ ledger 也将若干外部 comparator、paper-scale、storage/TPS 和真实依赖项目保留为 `BLOCKED`/`PARTIAL`；仅有 Rust static contract 或迁移账本不能把它们提升为 live `PASS`。

## 2. 服务框架：Spring Boot / WebFlux / Gateway 与 Axum / Tokio / Tower

| 关注点 | Java 迁移文档中的对应 | 当前 Rust 仓库事实 | 分析边界 |
|---|---|---|---|
| HTTP 服务 | Spring Boot / Tomcat | workspace 使用 Axum 0.8；服务代码显式装配路由、状态与 middleware | crate 选择不证明每条旧路由、filter 顺序和错误映射完全等价 |
| 异步执行 | WebFlux | Tokio 是服务 async runtime | 运行时替换不自动复制 Reactor 的 backpressure、取消、scheduler 和 context 语义 |
| 网关/中间件 | Spring Cloud Gateway、Spring AOP | Gateway crate 与 Axum/Tower 层共同承担校验、转发、middleware 等职责；workspace 使用 Tower 0.5 | 必须分别核验路由匹配、header 清理、签名、WebSocket、超时/重试及错误传播 |
| 序列化/HTTP 客户端 | Jackson、RestTemplate/WebClient | serde/serde_json、reqwest | wire 格式与兼容性由当前 API/message contract 决定，不由依赖名决定 |

证据入口：[`Cargo.toml`](../Cargo.toml) 的 workspace dependencies、[迁移决策 §3.1](迁移/Rust后端迁移架构决策_V1.0.md) 与[Gateway 当前链路](架构/Rust架构设计/Rust-Gateway当前实际链路与解耦对照设计_V1.0.md)。当前 [`Cargo.lock`](../Cargo.lock) 锁定 Axum 0.8.9、Tokio 1.53.1、Tower 0.5.3；Tower-HTTP 有 0.7.0，且依赖树还保留 0.6.11，故不把它缩写成唯一解析版本。

**取舍**：Axum/Tokio/Tower 将 HTTP 路由、async runtime 和可组合 middleware 收敛在同一 Rust 依赖生态中，便于显式组合服务边界；代价是原 Spring 的自动装配、注解切面和 Gateway filter 行为需要由 Rust 代码与契约测试显式呈现。选型表只记载迁移方向，未提供两套框架在相同业务、同一硬件、同一数据库与协议下的性能对照。任何尚未执行的 WebSocket、外部依赖或部署验证仍以对应 test profile 的实际结果为准。

## 3. 数据访问：MyBatis / ORM 与 SQLx、SeaORM、Diesel

### 当前版本与已记录选择

- 当前 workspace 在 [`Cargo.toml`](../Cargo.toml) 中声明 SQLx `0.8`，[`Cargo.lock`](../Cargo.lock) 锁定 `0.8.6`。`astral-db` 以 SQLx/MySQL 为数据库访问 owner，并使用显式 SQL、绑定参数和 `QueryBuilder` 等方式表达 repository 行为。
- [迁移决策 §3.2](迁移/Rust后端迁移架构决策_V1.0.md) 选择 MyBatis-Plus → SQLx，并将 SeaORM、Diesel 列为比较项；文档同时出现 SQLx `0.9` 的版本声明/校准表。这与当前 workspace 的 `0.8` 依赖声明和 lock 基线存在漂移。对当前实现及构建应以 manifest + lock 为准；该文档版本差异应在将来维护迁移决策文档时单独校准，本报告不擅自改写旧决策正文。
- 决策文档提出 `sea-query` 可作为动态 SQL 复杂时的 hedge；这属于条件性方案，不代表当前默认依赖或运行路径已采用它。

### 取舍分析

| 方案 | 文档中的角色 | 对当前授权/持久化边界的考虑 | 状态 |
|---|---|---|---|
| SQLx | 已选择的 async MySQL repository | 直接表达参数化 SQL、短事务、CAS/锁序和 durable head/outbox 或 canonical ledger 写入；复杂事务语义可显式审查 | 当前实现，版本按 manifest/lock 为准 |
| SeaORM | ORM 候选 | 提高实体/关联层抽象可能减少常规 CRUD 样板，但事务、SQL 形状和 projection 更新仍需核验 | 未作为当前 workspace 的选定 ORM |
| Diesel | 查询 DSL 候选 | 编译期查询模型不同；异步执行、连接池和当前 Tokio 路径的衔接需单独设计与验证 | 未作为当前 workspace 的选定 ORM |
| sea-query | 动态查询构造候选 | 可在构造复杂动态条件时增加结构化表达；引入前需要审查 SQL 类型/白名单边界与实际复杂度 | 迁移文档中的 hedge，非当前事实 |

> 上表总结的是项目内迁移决策的角色与当前 repository 边界，不是独立的 ORM 性能排名。不同方案均须保证 SQL 参数化、transaction 范围、数据库 schema/migration owner 和 durable postcondition。

**剩余证据**：仓库的集成测试和 campaign 可以登记真实 MySQL gate，但本次技术分析和本机执行期 benchmark 没有运行 MySQL、执行 migration 或证明生产数据迁移、backfill 和切流。迁移契约必须在独立批准的隔离数据库环境核验。

## 4. RabbitMQ 客户端：Lapin 与 amqprs

- [迁移决策 §2.2、§3.3](迁移/Rust后端迁移架构决策_V1.0.md)记录 Java 侧实际使用 RabbitMQ/Spring AMQP、RocketMQ 在该基线中未见实际生产接线，并选择 Lapin 作为 Rust 初始客户端、amqprs 为备选。该比较是迁移时期的技术决策，不是两客户端在当前版本/拓扑下的 benchmark。
- 当前 workspace 在 [`Cargo.toml`](../Cargo.toml) 声明 Lapin 4 + Tokio feature，[`Cargo.lock`](../Cargo.lock) 锁定 `4.10.0`；活跃 `astral-mq` crate 在 [`astral-mq/Cargo.toml`](../astral-mq/Cargo.toml) 使用 workspace dependency，amqprs 并未成为当前活跃依赖。消息 envelope、ack/confirm、DLX、idempotency、有限重试和消费者生命周期还由 `astral-mq` 与各服务实现承担，不能从客户端选型单独推导。
- RabbitMQ 是显式依赖 profile，不属于无外部服务的默认单测边界。通用消费者入口与授权失效 fanout worker 的生命周期并不应假定相同：[`consumer.rs`](../astral-mq/src/consumer.rs#L1049-L1135) 管理 consumer readiness/消费，专用 [`invalidation_fanout_worker`](../astral-mq/src/invalidation_fanout_worker.rs#L830-L920) 有自己的重连/断流处理。队列拓扑、跨语言 wire、真实 broker restart/disconnect、DLX 重投、consumer ownership 与 durable ACK 证据仍应按 Rabbit 集成 suite 验证。当前报告未连接 RabbitMQ，也未声称其 live 端到端路径 PASS；2026-08-05 适配账本还将更广泛的 consumer supervisor/真实断线和多实例竞争列为依赖环境验证项。

**取舍**：Lapin 与 Tokio 生态的对齐是记录的初始选择；切换 amqprs 并不能自动修复 durable 消息语义。应以稳定 `messageId/operationId`、幂等、lease/fence、ACK 前 durable proof 和业务 consumer postcondition 评估任何替换。

## 5. 授权引擎：AstralLight PolicyEngine、Casbin、OPA、Cedar

### 本项目当前定位

`PolicyEngine::evaluate()` 是 AstralLight 当前授权决策入口。生产 `SqlxRuleRepository` 声明 published-evidence capability，正式路径在身份/卡上下文和资源动作检查后读取经过验证的 published evidence；缺少 current、manifest/segment、scope、lineage、generation 或 revoke-fence 证明时保持 `PENDING`/`DENY`，不回退 legacy snapshot、raw source 或未证明缓存。详见[访问控制总览](架构/Rust架构设计/Rust访问控制总览与调整路线_V1.0.md)和[判定与规则集语义](架构/Rust架构设计/Rust权限判定与规则集语义_V1.0.md)。

Casbin、OPA、Cedar 在仓库 benchmark 材料中的角色是比较引擎/适配器，不是 AstralLight 当前正式授权链的替换证明。比较结果必须先确认策略表达能力、ALLOW/DENY 语义、身份与资源输入、数据加载/缓存、网络拓扑、写入持久化、决策与错误合同是否一致。一个 in-process CPU 行不能直接与一个 HTTP sidecar 行解释为引擎本身快慢。

### 2026-10-06 历史比较证据（限定拓扑）

本机外部 evidence 保存的 `comparison-full-20261006` 元数据描述 Linux x86_64 VM、8 logical CPU（AMD EPYC 9K65 192-Core Processor）、5 repeats、3,000 queries、ALLOW:default-DENY 为 2:1；run meta 的 Git revision/dirty 状态均为 `null`。记录的 Casbin 与 Cedar 版本分别为 2.20.0 和 4.12.0；OPA 版本字段为 `null`。OPA sidecar 是必需且可达的 loopback HTTP service；AstralLight、Cedar、Casbin 的测量为进程内。该轮 write overhead 明确为进程/sidecar 内存更新，不含 durable publication、DB/outbox/MQ 写入。元数据中的 benchmark binary SHA-256 为 `de79a2cc53722f98da13af160f9229c829df03b803029a9f84cdc68f35793a15`。

历史摘要中 `headline 50`（50 cards × 81 entries）的一组报告值如下，仅作为该历史拓扑的参考：

| 2026-10-06 adapter | 报告 latency / throughput | 拓扑备注 |
|---|---:|---|
| AstralLight | 0.13 µs / 约 5.99M qps | 进程内 |
| Cedar | 2.28 µs / 约 400k qps | 进程内 |
| OPA | 154 µs / 约 6.1k qps | loopback HTTP sidecar |

这些值不是当前 checkout 的可复现实测：Git 指纹缺失，测量拓扑不同，且不包含 durable write path；因此本报告不据此宣布综合引擎胜负或生产收益。当前 [RQ 子系列账本](测试/RQ子系列覆盖账本_2026-10-20.md) 仍区分组件级覆盖和外部/真实环境证据；需要同版本、同硬件、同策略语义和同拓扑的复测，才能进行有意义的横向比较。

## 6. Canonical grant ledger / published evidence 与 legacy snapshot

| 层 | 当前作用 | 可以证明什么 | 不能证明什么 |
|---|---|---|---|
| Canonical grant ledger + delta | source mutation 的授权贡献和增量事件；携带稳定身份/撤销语义 | 已进入 ledger 的 source 事实及 projector 输入 | 迁移文件/代码存在不代表既有数据已 backfill |
| Manifest / segment / current | projector 的 durable 发布产物；current pointer 经 CAS 指向经过 seal/lineage 验证的证据 | 版本、scope、generation、lineage 与 revoke-fence proof 满足时的 published evidence | 未证明的 current/segment、worker ACK 或历史快照不能授权 |
| 生产 strict reader | `SqlxRuleRepository` 的正式读门；`PolicyEngine::evaluate()` 只按已证明 evidence 判定 | 该次读取满足正式 evidence gate；异常/缺失时 fail-closed | 不自动证明目标环境 schema、backfill、可用性、迁移或生产流量切换完成 |
| Legacy snapshot / head/outbox | 迁移/对账、legacy/test reader、历史 writer-correlation；部分资格缓存失效语义 | 旧表/旧事件自身的版本或历史状态 | `MAX(version_no)`、旧 READY、旧 snapshot 或 ACK 不能替代 canonical publication proof |
| ELIGIBILITY | 双卡/资格缓存的独立 read/eviction lifecycle | 对资格读面的版本与上下文检查 | 不能代替 CARD/RULE_SET 的 canonical 授权证据 |

当前架构材料记载：source mutation 经 grant revision + delta event 进入 `AuthorizationProjector`，再以 manifest/segment/current 发布；正式 reader 严格验证 published evidence。当前代码核对入口包括 [`AuthorizationProjector`](../astral-trustgraph/src/service/authorization_projector.rs)、[runtime worker 装配](../astral-trustgraph/src/runtime.rs#L760-L795)、[`SqlxRuleRepository` capability](../astral-db/src/repository.rs#L342-L351) 及 [`PolicyEngine::evaluate()` strict-gate 分支](../policy-engine/src/engine.rs#L460-L471)。旧 `permission_rule_snapshot` / `rule_set_snapshot` 不再是生产 strict reader 的授权来源。ELIGIBILITY 资格链仍独立，不能把一次资格 cache eviction 当作 CARD refresh，也不能反过来。

**验收限制**：canonical projector、archive worker 和 strict reader 有代码级接线，但 backfill/rehearsal、真实 MySQL 与消息依赖集成、缓存/摘要读侧迁移、旧链退役及正式切流未完成验收。故本文将其描述为“代码接线已存在、生产切流待验收”，不把这两种状态合写成“已迁移”。
