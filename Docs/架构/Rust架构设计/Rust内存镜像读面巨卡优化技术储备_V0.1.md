# Rust 内存镜像读面巨卡优化技术储备（V0.1）

> 状态：**技术储备（预留设计），未实施**。本文档只记录问题量化与三条候选路线，供后续评估，不构成当前实现的一部分。
> 日期：2026-09-30
> 来源：极限探针 `limit_records_per_read_scaling`（`astral-db/src/memory_projection_hub.rs` 测试模块）量化了内存镜像读面的单读记录数悬崖。

## 1. 问题定义（已量化的极限）

内存镜像读面（`MemoryProjectionHub::try_memory_evidence`）每次读取都从零装配完整的
`PublishedCardAuthorization`：记录构建 + 排序 O(n log n) + 等价去重 + 分配密集。
单读成本随**单卡授权记录数**线性×对数增长，与镜像总卡数无关（卡数探针已确认
512/4096/16384 卡吞吐平坦，索引 O(1)）。

实测（本机 debug 构建，informational；release 会显著更快）：

| 单卡记录数（2 聚合 × N 授权） | 吞吐 | p50 | p99 |
|---|---|---|---|
| 8 | 42,441/s | 21.8µs | 51.1µs |
| 128 | 3,320/s | 241.8µs | 476.6µs |
| 512 | 1,112/s | 872.7µs | 1,447.8µs |
| 2048 | 236/s | 4.2ms | 5.1ms |

**影响边界**：权限域单卡授权通常在几十到几百条（p99 < 100µs 舒适区）；千授权级
"巨卡"才进入毫秒区。且悬崖是相对的——同规模下被替代的 DB 严格 reader 需要等量
分类加 SQL 拉取，成本只会更高；巨卡场景内存路径不劣于现状。

## 2. 路线一：装配结果缓存（推荐首选）

**观察**：证据对象由三个输入决定——已安装状态（各聚合 generation）、读镜头
（scope：tenant/card/user/domain）、读时钟（`read_unix_seconds`）。状态只在发布
换代时变（低频）；镜头在同一用户连续评估中高度重复；时钟只影响 validity 分类
（按秒分桶可安全复用）。当前每次读都全量重算，两次读之间 95% 的工作相同。

**做法**：hub 在 `Serve` 路径前加装配缓存——键 =（卡 + 各聚合代数戳 + scope 镜头
+ 秒级时间桶），值 = 装配好的证据；命中返回克隆（O(n) 纯拷贝，无排序无字符串
构建），未命中走全量装配；安装换代按卡作废。

- 预期：命中成本约为装配的 1/10–1/20，悬崖右移一个数量级（2048 records 读从
  4.2ms 降至约 0.2–0.4ms debug）；每次 evaluate 的 ALLOW 前复读天然命中。
- 容量治理：沿用现有 L1 evidence cache 模式（TTL + 容量上限 + 超限清最旧）。
- 风险：低。失效条件保守（代数变更即作废），命中返回对象与全量装配逐字段一致，
  不引入任何新放行语义。
- 与既有 L1 缓存的关系：镜像命中当前发生在 L1 之前（`MemoryMirroredRuleRepository`
  在装饰链外层），装配缓存属于镜像内部实现，不改变装饰链顺序与 L1 协议。

## 3. 路线二：模型层护栏——巨卡反模式（配套必做）

单卡挂千条授权意味着规则集设计把大量规则压到一个授权主体上，是数据模型层面的
反模式。读面优化只缓解，不消除。

**做法**：模型层增加单卡授权规模护栏——如单卡 effective grants 超过 500 时结构化
告警（或按部署策略拒绝更大的规则集绑定），从源头避免巨卡进入舒适区之外。

- 成本：近乎为零（一个计数检查 + 告警）。
- 依据：本文 §1 的实测舒适区边界。

## 4. 路线三：结构性合同改造（挂起，不推荐现在做）

- **方案 A（decision-optimized 证据形态）**：正式读只返回镜头内有效授权，跳过
  完整 provenance records。代价：动 `PublishedCardAuthorization` strict evidence
  合同——完整 records + walked 数与声明数对账是审计完整性的根基，合同变更的
  验证成本与回归面大。
- **方案 B（按 ProjectionKey 分段跳读）**：HotState segment 已按 key 分区，
  user-lens 读理论上可跳过无关 segment。代价：受"walked 数必须等于声明总数"的
  合同约束，绕过即违反证据完整性；需同步改造合同。
- 仅当路线一 + 路线二实测仍不够时才评估；评估前必须先完成合同影响分析。

## 5. 实施门禁

- 本储备的启用属于新的性能与合同变更：按所选路线重新经过计划评审、五链审查、
  Exec 分层门禁与真实 MySQL 端到端基准验证。
- 本文全部数字为 debug 构建本机数据，release 与目标硬件需重测后再做取舍。
- 路线一实施时的回归护栏：沿用 `limit_records_per_read_scaling` 探针对比装配
  命中/未命中两路延迟。
