# Rust 单机 MySQL 快照内存权威设计（V0.1）

> 状态：已确认目标设计，尚未等同源码实现或生产验收。
>
> 确认日期：2026-11-11。
>
> 实验分支的设计基准：`main` 是旧基线；本实验以内存权威的目标语义设计读取、写入和冷加载，不以兼容旧授权发布机制为目标。旧代码、数据库结构和协议仅作为业务语义、现有数据及迁移风险的参考，不自动成为新方案的准入前置或永久依赖。具体数据转换、落盘和迁移合同尚待设计和验证；本架构稿不替代现行规范和 `AGENTS.md` 的执行门禁，不代表授权生产切换或开放 listener。
>
> 本文记录单机组合进程的目标设计。2026-11-11 的最新决策是：服务期授权正确性由进程内统一权威维护，权限变更在同一权威上原子生效，不接受数据库已作为生效状态而内存尚未更新的可观察中间态；首次读取完整请求上下文，放行前只读取共享根的版本、内容 hash 和时间信息，不设计请求与写入共用的开关门机制。[Rust 规范 §15.10](../../规范/Rust后端编码规范_V1.0.md#1510-memory-v1-单机内存权威合同2026-11-12) 已登记该单机合同及采用边界；旧 V7 路径继续按自身合同运行。实现、剩余合同及验收尚未完成，不得据此提前开放单机服务。

## 1. 已确认的决策

单机进程冷启动时从 MySQL 一致性快照读取建立完整授权上下文所需的事实，建立一个进程级共享内存权威。读取哪些表、如何处理旧数据由实验的数据合同和迁移方案明确，V7 物理结构不是目标的当然前置。初始数据完成完整性校验并进入 `SERVING` 前，不启动正式请求监听。进入服务后，经过校验的写请求在同一个权威的受影响数据上执行受控原子更新；不以每次构建并替换整棵不可变根作为目标。

根进入 `SERVING` 后，完整的正式授权上下文从本地根读取。所需上下文未加载时，本次请求可触发受控 MySQL 一致性读取、验证并原子补入同一根，随后重新从根读取并经引擎评估；完整后续请求不查 DB。数据库行本身不是 ALLOW 依据，不能覆盖已有内存修改或复活撤销。根失效、状态 UNKNOWN、不一致或不能证明安全合并时，受影响范围返回 `PENDING`、`DENY` 或服务不可用。详细合同见 [memory-v1 唯一根设计](../../memory-v1/单机唯一共享根设计.md)。旧 current pointer、frontier 和 watermark 不作为新目标默认服务期依赖。

Identity、TrustGraph 和 PolicyEngine 必须访问同一个进程级内存权威及其一致的版本和内容摘要。两个服务各自创建独立内存根不能满足本设计；只读句柄长期指向该权威，不为每次写入更换整个根。

目标单机 profile 以系统内部共享权威的一次原子状态转换作为权限变更的生效边界；服务期正式授权不以数据库为当前裁判，也不存在“数据库授权已生效、内存授权尚未生效”的目标状态。MySQL 仍承担冷启动和跨崩溃持久化；内存提交、持久化及对外成功的关系尚需定义，不能仅凭内存原子性声称跨介质持久原子提交。

现行 V7 的 source mutation、durable receipt 和 WorkerOwned publication 是旧基线机制，不预设为实验目标必须兼容或继续使用的授权发布协议。实验须独立设计权限生效、持久化、失败和审计的剩余合同；现有生产路径仍受其原合同约束。内存权威不得发放 quorum term、authority certificate、全局 fence 或其他集群证明。

## 2. 权威边界

### 2.1 MySQL durable source

MySQL 是跨崩溃保存和冷启动重建的持久事实来源；`SERVING` 时当前有效授权由共享内存权威维护。实验所需的持久化数据形态、提交顺序、失败报告和既有数据转换须单独设计，不能以成功响应推断数据库已持久化。旧 V7 的 receipt、current pointer、generation、frontier 和撤销水位可在实际迁移时作为输入或对照；是否采用由明确的数据转换合同决定，不预先要求运行旧发布链。

### 2.2 单一共享内存权威

完整冷加载结果是单机正式授权读权威。它至少绑定：

- 进程实例身份及该实例内单调不复用的权威更新序号；
- 绑定全部授权相关事实、关系及覆盖范围的完整内容 digest；
- 数据范围、完整性结果、构建状态和健康状态；
- 可用于审计与诊断的冷加载来源和时间信息；这些信息不替代完整性证明或可信决策时间。

本地版本由 root owner 管理，与数据库中各对象的局部 generation、revision、revoke fence 是不同版本域；后者在实际需要时作为来源事实保留，不合成为全局根版本。现有候选 `SingleNodeRootVersion` 的统一 `source_snapshot_id/generation/dependency_frontier_digest/revoke_watermark` 不是此目标的强制合同，不能用局部最大值或伪造元数据填充；后续应按此目标重构模型及调用方，同时保留生产路径当前门禁。

同一根对象在服务期间由唯一 owner 管理；经批准的写入按受影响 aggregate 在该权威上原子提交关联事实、派生索引及版本/hash 元数据。请求首次取得完整一致的请求上下文和元数据副本，最终只重读元数据并核对有效期；若观察到更新中、失效或版本/hash 不一致，本次请求不予放行。这里的原子性是完整状态转换的可观察语义，不预设某个 Rust 容器的单字段原子写即可覆盖多字段更新。

### 2.3 单机与分布式 V7

分布式 V7 继续使用独立 authority/quorum 的逐请求证明。单机目标是请求初从共享内存权威读取本次授权所需完整上下文并记录根身份与版本，最终只对照当前版本、已保存内容 hash、时间信息和有效状态，不重复读取完整内容或重新计算 hash；具体合同见 §8A.4。权限是否已生效由共享权威的原子提交界定，数据库不是服务期请求的新鲜度裁判。两次元数据一致本身仍不证明首次读取的多字段上下文一致、写入口全覆盖、来源可信或变更已持久化；这些是系统内部协议与恢复的独立验收项。

本目标不引入写前关门及请求与写入的共同锁；memory-v1 单机适用 §15.10，旧 V7 单机及分布式路径继续遵循各自合同。代码尚未实现完整采集及正式 ALLOW 接线，不能开放单机服务。

## 3. 生命周期

```text
COLD
  → WARMING
  → SERVING
  → INVALID / REBUILDING
  → SERVING
```

`COLD` 和 `WARMING` 阶段不接受正式授权请求。`WARMING` 只允许受控的 MySQL 快照读取、关系组装、版本校验和根构建。

只有以下条件同时满足才能进入 `SERVING`：

1. 快照读取在同一个一致性边界内完成；
2. 所有授权读面需要的关系均已加载，引用闭合且没有未解释的缺失；
3. 已确定的输入合同所需事实和关系完整，范围与未知状态均已明确；
4. 内容 digest 已按确定性编码计算并与构建输入一致；
5. 权威 owner、必需消费者及其状态可用，没有影响根正确性的 UNKNOWN；
6. 初始共享内存权威已成功原子安装；
7. Identity、TrustGraph、PolicyEngine 使用的是同一个 root handle；
8. listener readiness 由该 root 的 `SERVING` 状态释放。

出现版本漂移、完整性失败、根安装失败、UNKNOWN、必需 owner 退出或失效信号时，当前根立即失去正向授权资格，进入 `INVALID` 或 `REBUILDING`。不得用旧根继续返回 `ALLOW`，也不得用 SQL miss 回退放行。

## 4. 冷加载输入与构建

冷加载从一个 MySQL 一致性快照读取新版数据合同规定的事实，校验关系后组织为内存索引和匹配材料。以下分类保留旧模型分析，用于识别可能需要的业务事实，并非新版表清单或已决定保留的授权来源；memory-v1 不迁移旧数据库。新版完整事实清单和未决来源以 [全新数据库设计](../../memory-v1/全新数据库设计.md) 与规范 §15.10 为准：

- `CARD_CONTEXT`：按用户、身份卡、授权卡建立低频变更索引，绑定用户、租户、域、有效期和状态；
- `GLOBAL_ADMIN`：建立管理员事实与状态索引，按既有专门合同核验；索引本身不构成通用授权旁路；
- `AUTHORIZATION_FACTS`：覆盖规则集、直接授权、委托、审批等适用来源及其身份、有效期和撤销状态，形成引擎所需的完整匹配材料；旧 manifest/segment 仅在迁移合同需要时作为输入；
- `ORG_AUTHORIZATION`：按租户、组织和成员关系建立组织准入索引；
- `OWNERSHIP`：建立受保护资源及受支持 lookup 所需的归属索引；
- `SOD_POLICY`：加载启用中的静态和动态 SoD 策略及其受限内容；
- `RULE_SET`：将 BASE/OVERLAY 规则集、继承关系、覆盖关系、有效期和最终匹配所需的条件内容物化到根中。

身份卡、用户卡和租户是低频变化事实，冷加载预建关系并在运行时以索引定位；鉴权高频路径不再逐条查询数据库关系。规则集和绑定的映射与冲突处理以新数据及评估合同定义，不能因旧 schema 中存在某字段就宣称引擎已经支持对应条件或 DENY。请求阶段使用完整内存上下文执行匹配及适用限制；未加载的例外按[唯一根设计](../../memory-v1/单机唯一共享根设计.md)受控补齐。

这些是目标授权覆盖分类，不要求预先存在为独立 projection。除同一 MySQL 快照中的关系闭合外，仍须证明目标输入的来源、完整覆盖和受控安装；旧数据转换不得静默丢失授权来源、撤销事实或审计关联。

加载器必须拒绝缺少必须关系、跨租户引用、卡与用户/身份卡不一致、策略内容超出安全上限、重复键冲突、未知状态及无法解释的 SQL 结果。若某旧发布结构被选为迁移输入，则还须按迁移合同检查其引用和状态；不因存在旧表而强制目标运行时依赖该结构。

冷加载或受控重建可以读取数据库；服务期发现未加载的请求也可按[唯一根设计](../../memory-v1/单机唯一共享根设计.md)触发受控查库，在校验和原子补入同一根后重新读取评估。DB 结果不直接作为放行依据。

### 4.1 数据库键优先的内存索引原则

本节中的 domain、旧发布指针及 generation 示例属于旧模型参考；新版不引入独立 domain 或旧发布链，按新版主外键与实际适用事实构建索引。

冷加载先按数据库现有主键、唯一键和外键读取及闭合关系，再生成面向高频授权请求的内存访问索引。内存索引不得重新定义授权对象身份、替代数据库主键或自行发号。

每个进入共享内存权威的对象都必须保留其数据库主键及必要的版本字段。由请求访问路径派生出的复合键只能作为二级索引，并且必须能回指到一个或多个已校验的数据库键。例如按用户、授权卡、租户、域或资源请求组合的查找键，返回值仍需包含对应的 `user_id`、`card_id`、`tenant_id`、`domain_id`、RuleSet/规则键和适用 generation。

外键关系是冷加载完整性的边界：身份卡、授权卡、用户、租户、域、规则集、规则条目、发布指针和授权事实之间的引用必须在同一个快照内可解析。缺失引用、重复唯一键、跨租户引用、同一数据库键映射到冲突内容，均不得通过生成新的内存键来掩盖，必须阻止根进入 `SERVING`。

内存根的索引层因此分为两部分：

1. **数据库身份层**：按现有主键保存实体和版本化内容，支持审计、失效和后续写入结果回指；
2. **授权访问层**：由已验证的主键/外键关系派生用户、卡、租户、域、规则集和资源匹配索引，支持高频鉴权直接命中。

BASE/OVERLAY 规则集不是匿名规则数组。每个适用的规则集、条目和绑定关系都必须保留目标数据合同定义的稳定身份与关联。旧发布身份只在历史数据转换或审计关联需要时保留；具体有效授权的建立方式由新评估合同明确，不预设复用旧发布机制。

### 4.2 旧数据库键映射与迁移参考

下表记录当前 Rust repository 和 v4 schema 使用的键，供识别已有数据及设计转换时参考，并非实验目标必须继续使用全部表或发布链的约束。具体字段、迁移输入和目标持久化模型以实验数据合同确定；实际数据库状态和迁移必须单独 preflight。

| 内存根对象 | 数据库身份键 | 必须保留的关系/版本信息 | 派生访问索引 |
|---|---|---|---|
| 身份卡 | `identity_card.card_id`；`user_id` 对 `platform_user.user_id` | 每个用户的身份卡唯一约束、状态、有效期；身份卡不承担 tenant/domain 归属 | `user_id → identity_card.card_id` |
| 授权卡 | `user_card.card_id` | `user_id`、`tenant_id`、`domain_id`、`card_status`、有效期，以及与身份/用户的绑定校验 | `user_id → [card_id]`、`(tenant_id, domain_id) → [card_id]` |
| 租户与域 | `tenant.tenant_id`、`platform_domain.domain_id`；业务键分别为 `tenant_code`、`domain_code` | `tenant_domain_map` 的唯一 `(tenant_id, domain_id)`、活动状态；租户层级 `parent_tenant_id` | `tenant_id → domains`、`domain_id → active tenants` |
| 规则集 | `rule_set.rule_set_id`；`code` 为全局业务唯一键 | `tenant_id`、`source_type/source_id`、状态和版本绑定 | `tenant_id → [rule_set_id]`、`code → rule_set_id` |
| 规则集条目 | `rule_set_entry.entry_id` | `rule_set_id` 外键关系、`resource_type/resource_id/action_code/effect/condition_json/priority/enabled/valid_from/valid_to` | `rule_set_id → ordered entries` |
| 卡与规则集绑定 | `card_rule_set_ref.id` | `card_id`、`rule_set_id`、`ref_type`；只接受 `BASE` 或 `OVERLAY`，保留绑定行身份 | `(card_id, ref_type) → [rule_set_id]` |
| 直接规则 | `permission_rule.rule_id` | `card_id`、`tenant_id`、资源/动作、`source_type/source_id`、状态和有效期 | `card_id → [rule_id]`、`(card_id, resource, action) → [rule_id]` |
| 发布授权版本 | `authorization_projection_current.pointer_id`，唯一作用域为 `(tenant_id, aggregate_type, aggregate_id)` | `current_generation`、`manifest_id`、状态、`cas_version`、`revoke_fence`、`revoke_fence_proven` | `(tenant_id, aggregate_type, aggregate_id) → current pointer` |
| 发布 manifest | `authorization_projection_manifest.manifest_id` | `generation`、`manifest_digest`、`parent_manifest_id`、作用域和 lineage | `(tenant_id, aggregate_type, aggregate_id, generation) → manifest` |
| 发布内容段 | `authorization_projection_segment.segment_id`；关联 `authorization_projection_manifest_segment.reference_id` | `content_digest`、`segment_ordinal`、manifest/segment 关联唯一性和有序内容 | `manifest_id → ordered segments` |
| 授权 revision/delta | `authorization_grant_revision.revision_id`、`authorization_delta_event.delta_event_id` | 作用域、aggregate、`grant_id`、revision/target version、generation、revoke fence、digest 和 tombstone 状态 | `(tenant_id, aggregate_type, aggregate_id) → published revisions/events` |
| 组织授权 | `org_scope_publication` 的 `(tenant_id, generation)`、`org_scope_current.tenant_id`、`org_scope_segment.segment_id` | 组织发布 current、segment 顺序、membership `membership_id`、卡/用户/租户作用域 | `tenant_id → current org publication` |
| SoD 策略 | `sod_policy.policy_id` | `status`、`conflict_type`、权限对、条件、资源/动作；策略名称不能假设为唯一键 | `active policies → bounded policy set` |

旧数据库没有声明外键的发布 revision、delta、manifest/segment 和部分组织 membership 关系，需要在使用这些数据时按迁移合同校验；若关系断裂或状态无法解释，不得将其静默转换成有效授权。`card_rule_set_ref.id` 和 BASE/OVERLAY 绑定与来源类型的区别是当前数据的重要身份关系；若目标采用这些事实，转换须保留其语义。

当前 loader 已使用单连接 `REPEATABLE READ` 事务、稳定主键排序和逐表 `cap+1` 截断检查，仍固定返回 `Pending`。现有候选模型要求全局 `source_snapshot_id`、generation、dependency frontier digest 和 revoke watermark；这些字段无已证明的统一数据库来源，属于候选模型与新目标的偏差，不能用局部代次最大值或虚构元数据填充。实验应重新定义模型；这项修正本身不证明已建立完整根或完成旧数据迁移。

最小实现要求包括：

1. 确认目标输入事实表满足一致性快照前置条件；
2. 在读取开始时建立一致性事务快照；
3. 在该快照内读取新合同所需的身份、规则、来源、关系和限制性事实；
4. 对每类关系执行有界枚举，并能区分“确实为空”和“读取不完整”；
5. 使用稳定排序和确定性编码计算 root content digest；
6. 构建结束前校验引用闭合、目标语义和覆盖完整性；
7. 唯一 owner 原子安装初始状态，分配进程实例与初始本地版本；
8. 快照事务失败、超时、取消或结果不完整时，构建结果作废，不进入 `SERVING`。

单机目标只允许经过一次完整的请求授权生命周期及受限修改路径执行有效授权变更；冷启动使用 MySQL 最新一致性快照建立权威，加载完成前不处理正式授权请求。单机设计不额外引入冷加载期间授权写入暂停机制，也不将冷启动时数据库遭攻击篡改纳入本方案的安全保证。该假设不证明现有代码中数据库旁路或其他写者不存在；采用前仍须验证写者覆盖和快照完整性。

现有 CARD 严格读取器混用普通读与 `FOR UPDATE` 当前读，不能直接视为同一历史快照；如迁移实际复用它，必须重新验证隔离边界。目标冷加载应在专属一致性事务中采集目标事实，并证明完整性；不会因为旧读取器已经存在就预设必须复用其发布协议。

新目标假设冷启动期间有效授权修改只由未开放的正式请求路径发起。旧系统或数据库若仍有旁路写者，这个假设不成立，必须在采用中识别并处理；不能仅凭本地 hash 证明加载期间没有外部变化。旧生产路径的安装对账与栅栏按其适用合同执行。

## 6. 写入后的根更新

经授权和业务校验的写请求由 Gateway 认证转发至 TrustGraph 的修改用例，TrustGraph 调用 `PolicyEngine::evaluate()`；引擎从共享权威读取上下文并判断调用者是否有权执行该修改。只有通过正式判定，TrustGraph 才能调用受限修改方法，在同一个权威上提交变更。引擎负责判定，不直接修改规则；TrustGraph 负责规则等治理及修改，根 owner 负责内部一致性和原子提交。

同一业务变更涉及的实体、关系、派生索引、版本和内容摘要必须作为一个完整状态转换对读者生效。原子修改完成并确认共享权威状态一致后，向调用方返回成功；这里的一致性确认指内存权威内的事实、关系、索引及元数据一致，不额外设定必须等待 MySQL 落盘成功作为返回条件，也不以该响应证明 durable 完成。所有有效授权写入口必须进入该系统内部提交路径；任何数据库落盘或外部成功响应都不能被当成独立于内存权威的权限生效点。旧 V7 source reservation、短事务、durable receipt 和 WorkerOwned publication 继续约束旧路径；新版审计及持久化细节仍待设计。

拟采用增量更新受影响数据并维护摘要；根内容 hash 的确定性编码、增量计算与全量重算等价性、并发写冲突和跨 aggregate 变更的原子提交范围必须单独定义和验证。若无法证明关联事实和版本/hash 一起对读者可见，或结果为 UNKNOWN，相关请求保持 `PENDING`/`DENY`。不预设逐条原子存储或两次相同元数据能自动证明一致读取，也不以不完整数据计算一个看似完整的 hash。

**关系、索引与有效权限不是同一概念。** 规则集由多张卡引用时，修改其中一条规则会影响多个卡的有效授权，但通常保留卡与规则集的绑定；停卡改变资格，也不必删除其规则集绑定。对内存读面，可用共享规则内容及绑定关系按需求值，或维护派生结果；具体求值语义、来源贡献与一致性由新合同明确和验证。解绑某张卡才删除该项绑定；删除整套规则集或删除卡片则可能涉及多项绑定、来源贡献和索引清理，历史与审计事实仍须保留。是否需要逐项更新由读模型和操作语义决定，不把“权限不再有效”一律等同于“批量解绑”。

当前仓库实现中，规则集删除会先为条目与绑定的组合追加 REMOVE（`astral-trustgraph/src/repository/rule_set_repository.rs`）；卡删除路径会撤销来源贡献、清理该卡规则与绑定并禁用卡（`astral-trustgraph/src/repository/user_card_repository.rs`）。共享规则集变更的现有扇出要求所绑定卡为有效 ACTIVE，停卡关系可能导致后续变更失败；这只是当前代码行为，是否需要调整须另行设计，不将其当作内存目标固有要求。

## 7. 失败、恢复与审计

单机目标记录异常退出及授权变更风险，当前不主动恢复崩溃前未完成的内存操作；分布式恢复方案待单机验证完成后再设计。进程自身可能来不及写下崩溃记录，因此异常退出记录须依靠实际可用的持久审计、进程监督或下一次启动发现，无法获得证据时不得声称已记录。既有 source COMMIT、publication 和 root install 的 UNKNOWN 处理对旧路径仍遵守其合同，不得盲目重放或按超时推断成功/失败。

重启以 MySQL 可见的最新一致性快照为输入重新完整冷加载，完成关系、范围和完整性校验后才进入 `SERVING`；无需恢复上一进程的内存状态。若崩溃前的内存变更尚未落到 MySQL，重启后将无法仅从该快照找回，既有撤权也可能因此失效：须提示用户检查最近权限变更，不能声称单机已恢复或保证保留该变更。数据库回滚、损坏及灾难恢复不在当前单机目标范围；旧路径的 durable 未决对账仍按其合同执行。

以下事件必须使本地根失去正向授权资格，除非完成受控恢复或重新冷加载：

- root owner 或维持共享权威完整性的必需组件失效；
- 权威状态、版本或内容摘要无法一致确认；
- 根内容不完整、跨租户或必要关系不能验证；
- 目标协议定义的提交或安装结果 UNKNOWN；
- 检测到违反唯一有效写入口假设的变更且影响未厘清。

旧 source/publication、worker、lease 或 transport 的具体失效条件属于当前生产合同与迁移参考；只有新设计实际依赖相应组件时才作为该组件的目标运行前置，现行合同在正式替代前仍须执行。

## 8. 本次范围与非目标

本次目标包括单机 MySQL 快照建立共享内存权威、预建关系、受控原子更新、统一读面、服务期未加载时由原请求触发受控补根再从根评估，以及根失效和恢复状态；当前尚未实现和验收。

本次不实现：

- etcd 请求前结构/内容确认；
- 多机同源冲突防护和跨节点写者裁决；
- 集群 authority/quorum 替换或简化；
- 将旧 projection 强制改造成冷启动的唯一事实来源；
- 以普通缓存、ACK 或旧 snapshot 证明正式授权完成。

## 8A. 独立共享根管理模块设计

### 8A.1 目标与独立边界

独立库 crate `astral-authorization-root` 的目标是承担单机进程唯一授权根的管理和统一授权数据读面。目标设计取消共享根模块的读写开关门和 `MutationGuard`；由组合根向 Identity、TrustGraph、PolicyEngine 等进程内消费者公开同一根的可克隆只读句柄，并按可信请求身份、租户和资源范围提供隔离视图。公开共享指可信模块可通过明确的公共 Rust 接口读取，不表示向外部网络公开，也不表示绕过认证、租户隔离或 `PolicyEngine::evaluate()`。

目前 crate 保留供旧数据库加载器使用的数据库键候选模型，并提供基于新版九表候选的 HAMT 索引和共享句柄实验；旧的独立候选门禁、候选证据检查和整根替换原型已从共享根 crate 退役。新候选不能证明覆盖、来源、确认有效性或授权，生产消费者尚未接线，也未获生产验收。该模块不归属 Gateway、Identity、TrustGraph、PolicyEngine、`astral-db` 或 MQ；业务模块彼此不维护独立授权根，也不通过互相查询内存根取得授权数据。

DB 侧的发布链结构批量检查及 RR 事务内有界 SoD 采集仍属于旧路径，不证明新根的 freshness、可信来源或写者全覆盖。

旧数据库键候选模型提供每次构建的总行数、JSON 编码字节和协作式耗时预算；新版 HAMT 候选也有行数和摘要预算。这些上限均不构成进程总内存预算。新版请求读取可暂时持有结构共享的候选节点；读取范围来自调用方，不是调用者授权证明。正式接入必须绑定可信主体和范围，且不能将已返回的候选事实视为可跨 mutation 永久有效的授权证据。

独立指编译依赖和职责独立，并不要求复制所有共享领域 DTO 或另建网络服务。该 crate 可以依赖稳定的 `astral-types` 等基础类型及通用运行时库，不依赖具体数据库、业务服务、PolicyEngine 或 MQ 实现；MySQL 快照采集和必要输入验证由各自 owner 实现，在单机组合根注入。旧发布 owner、source writer、worker 或协议适配器是否参与迁移由转换方案决定，不作为新运行时的默认依赖。构建依赖方向应保持无环；`CertifiedSodPolicy` 及其结构校验已迁入中立的 `astral-types`，原 `astral-db` 路径保留兼容导出；这不证明 SoD 事实完整或实时。现有 `OnceLock` 读面只按首次注册固定实例，接入共享根时须验证实例身份及配置一致，不能以 profile 相同证明 root 相同。

```text
astral-single-node（创建并装配唯一 root runtime）
    ├─ 数据采集与目标输入验证适配器
    ├─ 共享根管理模块：root owner + 生命周期/受控原子更新 + 只读句柄
    ├─ Identity / TrustGraph / 其他授权消费者 → 同一个只读句柄
    └─ PolicyEngine → 经适配器使用同一次请求绑定的只读视图
```

共享根是授权数据入口，`PolicyEngine::evaluate()` 仍是唯一授权判定入口；Gateway 仍负责外部认证和转发。根 owner 负责受限原子状态更新，TrustGraph 负责经引擎授权后的治理变更；数据库事务和持久化由独立 owner 实现，具体交互合同待设计。本地 digest 只标识内容，不证明来源或持久化。正式授权以外的普通业务读取、session 等 durable 数据不因为本设计自动转为内存读。

### 8A.2 内部职责与持有者

| 内部职责 | 职责边界 |
|---|---|
| `RootOwner` | 同一组合进程只创建一个；协调构建、验证、对账、初始安装、受控原子更新、生命周期与故障恢复。唯一 owner 由组合根装配及运行时 guard 共同约束，不能只依赖调用方约定。 |
| `RootState` | 一个长期存在的共享内存权威；保留目标事实的稳定身份、必要关系、完整匹配材料，以及与已提交状态一致的内容 hash。更新权限不下发给普通读者。 |
| `RootHandle` | 可克隆的只读能力，所有模块指向同一 owner；不暴露任意根替换或 source 写入。 |
| `RootRead` | 绑定一次请求的 scope、可信请求上下文和一致读取的版本；首次取得所需上下文，最终只读取元数据核对。 |
| `RootStatus` | 与当前根身份一致发布生命周期、readiness 和失效状态；健康检查不能凭 liveness 或非空根宣称可服务。 |

读面按身份/卡上下文、规则与授权事实、资源归属和适用限制等领域拆分最小接口，不使用一个包含任意 SQL、任意 JSON 或任意资源查询的万能 trait。一次请求在首次需要根事实时创建一个请求级读者，在同一读取阶段持有一致视图供进程内参与模块共享；采用不可变快照时，该视图可能暂时持有旧快照，须有请求、取消及内存预算。正向决定须经过最终元数据核对。长时间诊断读取和生产正向授权读取需区分能力与数据暴露范围；请求级读者的完整生命周期及缺失补齐后的阶段刷新见[请求生命周期设计](../../memory-v1/请求生命周期与共享根读取设计.md)。

目标接口为以下语义，非已实现的 Rust API：

- 组合根一次性创建 `RootRuntime`，取得不可克隆的管理能力和可克隆的 `RootHandle`；重复创建、注册、配置或 owner 身份冲突必须拒绝，不能用 first-wins 隐藏分歧。
- 授权入口调用 `RootHandle.begin_read(tenant, scope, request_context)` 取得 `RootRead`，经领域只读接口在同一根读取完整证据。读取结果区分已证明不存在、根未覆盖、失效及证据错误；只有完整覆盖下的确实不存在才能进入既定的缺省判定。
- `RootRead` 完成时只核对当前根元数据及有效期，不重复取得完整内容；根变化或失效时本次不予放行。旧路径的受保护业务写入仍适用其 admission 合同；新版的授权与修改边界及并发合同须明确，不复用裸读取 token 代替受限修改能力。
- loader/验证器只能产生候选输入，installer 核验来源与完整性后原子安装；普通读者不能发送自报成功的安装命令。此处不设计请求与写入共用的开关门，旧路径继续遵循其适用规范。

### 8A.2.1 公开共享只读与数据隔离

组合根向可信进程内消费者注入同一个 `RootHandle` 的克隆；模块通过公开的 Rust 读接口并发查询同一个长期存在的共享内存权威。句柄仅提供只读能力，不向外部开放网络访问，也不允许消费者自行修改权威或从根直接产生 `ALLOW`。受控写入能力只交给已登记的写入 owner；写入在同一权威上按完整业务变更原子更新，不要求每次复制和替换整棵根。请求读取的上下文副本与并发写之间必须有一致性保证。

每次正式读取由可信入口将已经验证的主体身份、选定租户、卡和请求用途绑定为请求上下文；客户端提供的 tenant/card/resource ID 仅是待校验的请求参数，不是读取其他租户的凭证。公开句柄本身不是授权能力；授予共享句柄不等于授予任意租户的数据读取权限。对象访问先核对实体真实 tenant、用户与卡绑定以及相关主外键关系，再从对应范围索引读取。目标租户缺失、绑定不一致、主体或资源范围不能证明时返回 `PENDING`/`DENY`；不能回退为跨租户全局查询或根据调用者自报的 tenant 放宽范围。

读接口按领域暴露范围受限的类型化视图和迭代器：身份与卡、规则和授权事实、组织、资源归属、资格和 SoD 分别按已验证范围访问，索引结果必须回指已校验的稳定实体键。内部原始根、跨租户全量枚举和敏感字段不作为普通请求的公开接口；内部构建/验证或受审计的治理操作如需跨范围数据，使用独立的最小能力及现行授权和审计合同，不能由普通请求自行构造。全局事实必须显式分类，并在使用时受租户和资源语义约束，不能将 global admin 标记作为授权旁路。

所有模块在同一请求中共享同一 `RootRead` 及其根身份，防止身份、规则和资源归属分别从不同版本或不同租户拼接。`PolicyEngine::evaluate()` 仍负责最终权限决策；共享只读结果不是外部数据披露许可，也不允许调用方绕过最终版本/hash 与时间核对。未加载、未覆盖与已证明不存在使用不同结果，不能将跨租户、未知或不完整结果当作空授权集。

### 8A.3 输入、输出与身份

冷加载输入为同一 MySQL 一致性快照中的有界 typed 事实集和覆盖说明，数据库事务与连接留在适配器；memory-v1 不迁移旧数据。服务期目标更新输入是经认证、授权与业务规则校验的系统内变更，由统一权威执行原子生效；操作身份、scope、tenant 和审计关联须贯穿适用的内存提交与持久化过程。旧 WorkerOwned publication 等不是新目标的默认设计，但继续约束适用的旧生产路径；不以 ACK、HTTP 状态或调用者传入布尔值代替任何声称的 durable 证明。

输出是供各消费者通过 `RootHandle` 申请的同根只读视图和状态；不存在每个模块各自的一份根。保留目标合同所需的稳定实体身份、引用、授权来源、规则条件和有效期；旧数据库键及发布身份按实际转换和审计追溯需要保留。时间窗口与 user/domain lens 以请求时间和上下文重新计算；不能将冷启动时的有效结果冻结成永久有效授权。实际容量、按域粒度、完整字段和不支持项须在实现清单中逐项核对，不能把未加载视为空集。

根版本由进程内权威更新序号和根内容摘要构成，进程实例、更新序号、hash、更新时间戳和状态必须与对应逻辑更新一致地对读者可见；进程重启产生新实例，同一进程更新序号单调且不复用，即使内容恢复原值也不得复用序号，溢出时停止正向授权。旧各 scope generation/revoke 仅在输入转换或追溯需要时按自身语义保存，不能取最大值制造全局版本。更新时间仅用于标识和诊断，不替代版本序号、当前可信时间或有效期判断。这些值不能自行证明来源或覆盖，也不是分布式 authority proof。

### 8A.4 冷启动、请求与受控重建

1. 单机组合根建立唯一 owner 及目标方案实际需要的受监督组件；启动和恢复期间 readiness 不释放，正式授权返回 `PENDING` 或不可服务。
2. 经专属 MySQL RR 一致性快照非锁定读取目标合同规定的完整事实；验证表/键/租户、关系、覆盖和有界资源，形成候选。旧数据使用时按独立转换合同处理，已有 `FOR UPDATE` 正式读取器不能直接替代同一快照采集。
3. 完成目标输入的来源、状态和完整性核对；目标假设与实际写者覆盖不能证明时不得安装为可服务根。旧生产路径的对账和安装栅栏按其适用合同执行。
4. 唯一 owner 原子安装候选及本地版本元数据；只有共享句柄已注入全部必需消费者、根完整且目标依赖可服务时，readiness 才释放。
5. **首次读取**：请求从同一权威一致地取得进程实例、更新序号、预先计算的内容 hash、更新时间戳和状态，并按可信身份、租户、卡、资源及请求 scope 取得授权计算所需的完整上下文视图。读取与并发更新不能拼接不同逻辑状态；未加载可按第 7 步补齐，跨租户、无效或无法证明完整时 `PENDING`/`DENY`，已证明不存在按既定缺省语义处理。随后 `PolicyEngine.evaluate()` 使用该请求上下文计算。
6. **最终核对**：准备 `ALLOW` 时只读取当前实例、更新序号、已保存的内容 hash、更新时间戳和状态，确认与首次捕获一致且范围仍可用；不重新读取完整结构、不遍历授权数据或重新计算 hash。撤权在本次请求首次读取后、最终核对前完成时，受影响版本必然推进，内容 hash 按规范内容更新，更新时间戳随提交记录；与首次元数据不一致则直接拒绝本次放行，不以重试替代这一决定。版本单调不复用是变化识别的依据；内容相同的操作或时间戳精度不足时不能假设 hash、时间戳必然各自不同。决策时获取可信当前时间，重验首次上下文给出的授权有效窗口及时间条件；时钟异常、时间敏感条件无法确认或已越界时拒绝或依现行安全语义处理。
7. 发现未加载时，允许触发请求等待受控 MySQL 一致性读取、范围闭合校验及同一根的原子补齐；完成后从根重新读取并经引擎判断和最终复核。不能证明安全合并、读取失败或取消时本次 `PENDING`/`DENY`；已撤销或删除的内存事实不得被旧 DB 数据复活。根失效或不完整范围无法限制时停止受影响范围或全局正向授权。具体并发和预算见[唯一根设计](../../memory-v1/单机唯一共享根设计.md)。

冷加载阶段不额外设计写入暂停机制；目标假设有效授权修改仅由完成正式请求授权生命周期的系统内部路径发起，启动未释放正式请求。若实际部署存在其他写者，该假设不成立，不能凭此声称快照包含这些并发变更；必须按 §15.10 的采用条件处理。

### 8A.5 写入顺序、并发与恢复

目标单机 profile 中，系统内部唯一授权权威负责权限变更的原子生效。所有合法入口必须经过同一受限提交协议，事实、关系、索引、版本和 hash 在同一逻辑提交点对请求一致可见；写入校验失败或未提交不得生效。数据库仅保存和恢复事实，数据库提交本身不定义服务期权限生效，因此不以“数据库先完成、内存后生效”描述正常授权语义，也不引入请求与写入共用的开关门。

并发请求各自保存从同一权威一致取得的请求上下文。最终元数据核对确认本地版本、hash、状态和有效期；完整读取与原子更新的同步算法、并发写冲突和多 aggregate 提交尚须设计并验证。单机目标把一次请求的最终授权检查作为该次授权生命周期的判断点：检查通过后，该次已授权操作可以继续完成；其后发生撤权不回头否定该次决定。以后再次发起需要该权限的请求，必须开始新的授权生命周期并读取当时的权威状态。此语义允许撤权后先前已通过检查的操作仍然完成，不声称业务提交时权限仍然有效；旧路径继续遵循自身受保护写入合同。

单机目标以 MySQL 当前一致性快照重新建立内存状态，不自动回放或恢复崩溃前未落盘的内存操作；分布式恢复留待单机验证后设计。内存与 MySQL 是不同失效域，原子内存写入不能证明已落盘：若变更已在内存生效但随后崩溃且未持久化，冷启动可能恢复出不含该变更的状态，审计和告警只能提醒检查，不能恢复缺失事实。目标在内存原子写入与一致性确认后返回成功，不将该响应解释成 MySQL 已持久化，成功撤权跨崩溃不保证保留。持久化失败时的具体报告与现行 durable 合同的衔接尚待定义。

单机目标发生崩溃时记录或由监督侧发现异常，重启从 MySQL 最新一致性快照冷加载，不主动恢复上次内存操作，并提示检查最近授权变更。旧路径的取消、超时、owner/worker/lease/transport 故障或 COMMIT/publication UNKNOWN、receipt 和 CARD/ELIGIBILITY 分别失效等仍按其合同处理；新版须单独定义其状态、资格、审计与持久化失败合同，不能用 ACK 或内存状态代替 durable 证明。

数据库写者必须受权限和维护流程约束，HTTP、后台、批量、直接仓储和其他进程均须逐项登记并验证变更经过统一权威提交。旁路直接写数据库不属于有效的单机授权变更；若仍存在可绕过的写入口，系统无法满足目标假设，必须阻止采用并处理异常，不能依赖异步审计或监控声称已保证入口全覆盖。现有 source guard 在 hub 未安装时可返回 `None`，MySQL advisory lock 只约束遵守协议的写者，因此当前实现尚不能证明该假设。

### 8A.6 运行约束、采用与验证

共享权威、冷加载/重建暂存、更新所需临时数据和请求上下文副本均计入内存预算；为快照行数、总字节、构建耗时、重建和更新并发、请求耗时及许可设置上限。到达上限、取消、内存分配失败或慢请求超期时，受影响范围保持不可用或关闭正向授权，不能通过截断构造看似完整的状态。实现若使用局部不可变子结构或延迟回收，必须为其在途读者和回收设置独立预算，不将整棵旧根留存作为目标。诊断、日志和指标只暴露必要身份、状态与计数，不输出敏感实体内容或秘密。

接入按消费者逐项编目身份与卡、授权来源、组织、资源归属、SoD、资格和所有写入口；以新根协议为目标接入同一 handle，并审查旧 SQL 旁路、直接访问和公共契约。兼容 adapter 不是实验目标或默认步骤，只有具体切换方案需要时才设计。现有 `single_node_memory_root.rs`/loader 是尚未完成的原型，应按目标合同重构；稳定公开 API、跨仓接口和数据库协议的变更仍须按适用规则逐项处理，不能因实验分支存在就隐式删除。

memory-v1 单机合同及采用条件见规范 §15.10；旧 V7 单机的写前门以及分布式 source/发布/恢复合同继续适用于对应旧路径。新版采用前须验证统一内存生效点、所有写入口、冷启动及所接受的崩溃丢失边界，明确新版 SoD、资源归属和审计等合同。当前实现尚不能满足采用前置，不能开放 listener 或将候选根视为正式授权证据。

Rust 验证至少覆盖：同一 handle/权威身份、多模块并发只读及公开接口无法修改权威、请求身份与租户/卡/资源关系的隔离和伪造参数拒绝、跨租户枚举及敏感字段访问限制、多字段及跨 aggregate 更新与请求读取的一致性、首次完整读取及最终只读取元数据、内容回到原值时序号不复用、增量 hash 与规范全量重算等价、并发写冲突与部分更新失败、有效期与时钟异常、适用限制事实覆盖、UNKNOWN 失效、原请求触发缺失补齐并从根重新评估、后续完整请求不查 DB、并发撤权及旧 DB 数据不得复活、容量与在途数据回收、崩溃恢复与 worker 失效。真实 MySQL 一致性/并发/DDL、内存生效与持久化的故障恢复、消息及 authority 对账、旁路写与 listener readiness 需要独立环境和适用批准，不能用 mock 或单元测试代替。

## 9A. memory-v1 数据库与共享根的建模边界（候选）

`memory-v1` 数据库是内存权威的冷启动和持久化事实来源，具体 schema 尚未定稿、没有执行迁移。本基线使用全新数据库，不迁移旧数据；旧 source 行和已发布结果不自动构成新版授权。

候选持久数据按职责划分：

| 事实 owner | 最小内容和不变式 |
|---|---|
| 用户与身份卡 | 用户身份和独立身份卡；身份卡不承担租户或域归属，同一用户与身份卡的关系必须可验证。 |
| 租户及授权卡 | 租户、卡的所属用户和租户、状态与有效期；所有租户内关系带租户身份，跨租户引用拒绝。 |
| 规则集 | 规则集及条目的稳定身份、租户归属、资源、动作、状态和有效期；规则语言、条件及冲突语义在评估合同中定义。 |
| 卡与规则集绑定 | 绑定自身身份、卡、规则集与 `BASE`/`OVERLAY` 层；绑定层不是规则来源。租户边界与引用必须一致。 |
| 其他授权来源 | 直接授权、委托、审批是否保留待决定；若支持，须分别定义来源、主体、作用范围、有效期、撤销及组合语义，不把任何裸 source 行直接当作 `ALLOW`。 |
| 操作和审计 | 为操作身份、授权变更、失败与审计关联建立持久记录；写入顺序、未知结果和崩溃后的具体合同尚未完成，不以表存在证明已落盘。 |

**memory-v1 域决策（2026-11-11）**：目标模型取消独立 domain 概念，由可分层租户表示公司、部门、小组等范围，结合身份卡标识用户；授权卡承载用户在具体租户中的授权。单一身份可拥有多个租户的授权卡；身份卡本身不是权限凭证。租户父子关系只表示组织结构，不自动继承授权或允许跨租户访问，具体继承规则如有需求须另行定义。旧 domain 和 tenant-domain 映射不迁移；实际删除或修改现有数据库仍需符合执行门禁。本文其他提及 domain 的内容记录旧模型或尚未更新的现有实现，不构成 memory-v1 目标要求。

根 owner 的进程实例和递增序号属于内存权威身份，不要求数据库提供全局 generation；内容 hash 只在完整事实与范围的确定性编码定义并校验后才可代表根内容。候选 `memory_v1_version` 仅定义非零实例、进程内序号及不透明摘要的值类型，不生成实例、不验证 hash、不提供唯一 owner、原子状态转换或授权证明。代码和数据库 schema 的实际接入均未完成。

## 10. 证据边界

本文是已确认的单机目标设计，不表示当前 checkout 已完成源码实现。真实 MySQL 一致性、并发写入、崩溃恢复、直接 SQL 绕过、listener readiness 和部署验收必须分别执行 Rust/真实依赖验证，并按项目状态区分 `PASS`、`FAIL`、`BLOCKED`、`UNKNOWN`、`PENDING` 和 `SKIP`。
