# Rust 多机双通道冗余投递技术储备（V0.1）

> 状态：**技术储备（预留设计），未实施**。本文档只记录方案与启用边界，不构成当前单机实现的一部分。
> 日期：2026-09-30
> 来源决策：单机消息层采用"进程内 LocalBus（无持久化）+ source intent 收口 + 失败显式"模型后，评估"双通道冗余投递"作为消息安全增强手段。结论：该方案在单进程内对丢失率改善为零（共同命运故障），在跨故障域（多机）成立，故记录为多机集群技术储备。

## 1. 背景与定位

当前单机消息层的设计决策（已实现）：

- 消息传播走进程内有界 LocalBus（`astral-mq/src/local_bus.rs`），不做磁盘持久化；
- A 类消息（撤销命令、与 source mutation 关联的审计）的"不丢失"由 source transaction 内的 durable intent + outbox + 补偿 worker 保证，不依赖总线；
- 总线内不存在静默丢失：队列满、无 owner、handler 失败、结果未知全部显式报错；唯一静默丢失窗口是进程崩溃，崩溃同时使所有调用方可见失败。

本方案回答的问题是：能否用"同一消息发布两份、双通道投递、到达时合并"把丢失概率从 p 降到 p²。评估结论：

- **单机进程内：不采用。** 两条进程内通道的崩溃/OOM/断电是共同命运故障（相关性 = 1），p² 退化为 p；崩溃正是该模型唯一的静默丢失场景，双通道对此无改善。
- **多机集群：成立。** 通道跨越独立故障域（不同机器/不同 broker/不同可用区）时，独立性近似成立，p² 具有实际意义。故保留为多机形态的技术储备。

## 2. 方案定义

双通道冗余投递（dual-path redundant delivery）：

1. **双副本发布**：同一业务操作发布两个消息副本，二者携带**相同的 `operation_id`**、**各自独立的 `message_id`**，经两条相互独立的传输通道（独立 broker / 独立队列 + 独立连接）投递。
2. **先到先处理**：任一副本先到达即可触发业务处理，理论期望双副本近乎同时到达。
3. **到达合并**：消费侧按 `operation_id` 原子认领；第二副本（并发到达或迟到到达）被识别为同一操作，合并回一次执行，不重复产生副作用。
4. **安全语义**：单通道丢失 → 另一副本仍可达；双通道同时丢失 → 操作判定失败（对 A 类消息仍由 intent 收口，见 §6）。

收益定位（必须按此表述，不得夸大）：

- 双通道降低的是**部分故障下的失败率/重试率/恢复延迟**（一条通道的队列积压、连接故障、消费者卡死不再阻断操作）；
- 双通道**不降低崩溃类静默丢失**——跨机后崩溃类故障被拆分到不同故障域，才真正获得 p² 收益；
- 双通道**不替代 durable intent**：intent 是 A 类消息的安全底座，双通道只是传播层的冗余优化。

## 3. 适用前提与数学边界

p² 成立的条件是两条通道的故障相互独立。逐故障场景的相关性：

| 故障场景 | 通道间相关性 | 双通道效果 |
|---|---|---|
| 进程/节点崩溃、OOM、断电 | 1（同域内共同命运） | 同域无改善；跨故障域后拆分为独立事件 |
| 单队列积压/满 | 低 | 第二通道旁路存活 |
| 单连接/单 broker 故障 | 低 | 第二通道可达 |
| handler panic / 消费者卡死 | 低 | 另一通道继续处理 |
| handler 业务失败（DB 拒绝等） | 高（同一后端） | 双副本同样失败，无双投递收益 |

结论：**启用条件 = 两条通道部署在相互独立的故障域**（至少不同进程/不同机器，理想为不同可用区且不共享 broker、电源、网络路径）。同进程双队列、同机双通道不满足启用条件。

## 4. 多机落地形态

多机集群模式下（RabbitMQ 保留为跨机传输，见单机/多机隔离决策）：

- 双通道 = 同一消息发布到**两个相互独立的 broker 实例**（或同集群两条物理隔离的队列 + 独立连接），两 broker 不共享存储与故障域；
- Producer 增加双写发布模式：逐通道 publisher confirm，任一通道 confirm 即返回成功，两通道均失败返回失败；单通道 confirm 失败记指标与告警；
- mandatory + unroutable 语义在两条通道上各自保留；
- 现有 `Producer`（`astral-mq/src/producer.rs`）Rabbit 分支扩展，local 分支不受影响（单机继续走 LocalBus，无双投递）。

## 5. 落地前置条件（启用前必须全部完成）

1. **发布与消费允许同 `operation_id` 多副本**。当前 LocalBus 对 in-flight 相同 `message_id` 的入队返回 `Duplicate`（`enqueue()` 的 in-flight 去重），双副本模型要求副本各自持独立 `message_id`；Rabbit 路径需同步评估消息存储层的幂等键口径。
2. **全部消费者幂等键从 `message_id` 切换到 `operation_id`**。否则双副本（不同 message_id）会各自落库/各执行一次，合并语义失效。涉及面至少包括：audit 幂等（`mq_idempotent_log` 与审计落库去重）、login 事件落库、撤销消费的 `auth_session_outbox` 边界（其 operation 边界已按 `operation_id` 建立，需复核）、L2 evidence 推送等所有去重表/集合。
3. **operation 级 claim + 已完成集合（含迟到副本识别）**。消费前按 `operation_id` 原子认领，覆盖并发副本；已完成的 operation 在窗口期内保留记录，迟到副本被识别为已完成而非重执行；崩溃后集合消失可接受（崩溃 = 失败，与单机模型一致）。claim 集合本身必须有界（容量 + TTL）。

与授权投影的衔接：重复到达的 delta 事件已由发布事务内 CAS 指针栅栏 + 版本栅栏保证安全（败者进入 `PointerMoved` 就地重排），claim 的作用只是**省去无效的 CAS 尝试与重排开销**，不是正确性依赖。不得把 claim 实现为投影正确性的前置条件。

## 6. 明确的非目标

- **不替代 source intent**：A 类消息的持久化等级、intent 与 source mutation 同事务的边界、补偿 worker 收口路径全部不变。双通道失效时的最终安全网仍是 intent。
- **不承诺 exactly-once**：仍为 at-least-once + 消费侧幂等。
- **不改变 A/B 持久化分级**：B 类（登录事件、普通决策审计）维持尽力而为语义，双通道只是降低其丢失概率的手段之一。
- **不作为单机 LocalBus 的特性实施**：单机进程内双通道不满足独立性前提（§3）。
- 不引入消息持久化存储：本方案与"无持久化、失败显式"的单机模型原则一致，不因冗余而重新引入 WAL/磁盘队列。

## 7. 单机替代方案（备选记录，均未实施）

针对"部分故障下的失败率"这一双通道的真实收益点，单机的更便宜等价物：

- **dispatch 边界 `catch_unwind`**：单条投递的 handler panic 转为该条的显式 `Handler` 错误回执，通道与进程存活，避免整进程重启抖动；
- **按队列容量配置 + 拒绝/丢失指标**：缓解突发下 `Full` 拒绝误伤，拒绝率可观测。

这两项改善的是失败率，不是丢失率；与"失败显式 + intent 收口"模型完全兼容，启用不需要本储备方案。

## 8. 决策记录

- 2026-09-30：评估"双通道冗余投递"。结论：单进程内对丢失率改善为零（共同命运故障），不实施；跨故障域（多机集群）成立，记录为技术储备。当前单机最终方案维持"intent 收口 + 失败显式"。
