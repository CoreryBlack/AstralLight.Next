# 授权生命周期与治理扩展：专题索引与未闭合合同

> 状态：**按 owner 拆分的技术分析与缺口索引；不是整体获批方案，也不代表全链实现或生产验收完成。**各子题具有不同的数据 owner、调用顺序、证据和风险状态；下文所述的目标方向不构成新的批准。
>
> 对应：[技术能力与储备清单](../../技术能力与储备清单.md) 中“授权生命周期与治理扩展”；[Rust 访问控制总览与调整路线](Rust访问控制总览与调整路线_V1.0.md)。

## 1. 范围与阅读方式

“授权生命周期与治理扩展”涵盖授权 source owner 与资源归属解析、委托 caller-scope、身份/资格变化的 fan-out、RuleSet 有效期自然结束、Arbiter 可信度、GlobalAdmin 生命周期，以及 ORG_SCOPE 组织治理。它们共享正式授权的 fail-closed 原则，但不是一个共同的数据源、事务、worker 或状态机。

本专题逐项记录 **owner 与调用/数据流、信任/数据边界、失败与恢复语义、当前实现/缺口**。阅读时区分：设计文档是否存在、设计是否批准、源码是否接线、真实迁移/部署/集成是否验收；任何一层的证据都不能替代其他层。

## 2. 正式授权共用边界

正式请求的主链是：Gateway 验证身份及可信头 → 服务端按路由映射资源/动作 → 服务端 resource-owner resolver 从权威事实解析目标归属 → `PolicyEngine::evaluate()` → 生产 strict published-evidence reader 组装并验证已发布授权证据。具体子系统负责其 source mutation 和持久化；投影/读侧不得反向成为新的 source owner。

对象级请求不得仅凭 actor 的 tenant/card context 推导目标 owner。目标 owner 未解析、证据缺失/不可用，或 generation、dependency、READY/read-gate 等证明不足时，正式路径只能 `PENDING`/`DENY`，不能用旧快照、raw/source 直读或缓存回退放行。source mutation 的事务只覆盖必要 source、durable head/outbox 和审计关联；投影、缓存/MQ 副作用和验收在提交后依其各自 owner 执行。

## 3. 子主题技术分析矩阵

### 3.1 Source owner、source type 与调用顺序

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | 业务写入 owner 负责其 aggregate 的授权 source mutation；Gateway 负责外部身份可信边界；服务 API/资源 owner resolver 负责资源和动作映射及目标归属；`PolicyEngine::evaluate()` 是正式授权入口；canonical projector/strict evidence reader 分别负责物化已批准事件和证明正式读侧状态。请求顺序必须是可信身份建立、服务端路由映射、目标 owner 解析、再执行 evaluate，不能先授权再补目标归属。 |
| 信任与数据边界 | actor 身份、请求体中的 tenant/card/resource、source type 字符串都不是独立的 owner 证明。source type 必须绑定明确的 aggregate/source owner、合法 mutation、head/outbox 与审计关联；投影事件只能物化已批准的 source mutation，不得创造新授权。资源 owner 事实须由服务端 resolver 查询或由已验证的 actor-scoped route contract 证明。 |
| 失败与恢复 | 路由没有映射、owner 查找失败、事件来源不匹配、canonical evidence 不完整或版本/read-gate 未证明时，授权侧 fail closed 为 `PENDING`/`DENY`。source transaction 失败则整体回滚；提交后投影失败按 durable event、幂等与 generation/fence 恢复，不以 ACK 或旧缓存代替 durable proof。 |
| 当前状态与证据 | 正式 Gateway → resolver → `PolicyEngine` → strict published-evidence 路径及多个局部 source/projector owner 已有实现；这不等于所有写入口和 `source_type` 已受统一强制白名单/owner 矩阵约束。仍须按 aggregate、API 和投影逐项闭合 owner 合同。详见[访问控制总览与调整路线](Rust访问控制总览与调整路线_V1.0.md)、[权限判定与规则集语义](Rust权限判定与规则集语义_V1.0.md)、[权限投影快照与版本栅栏](Rust权限投影快照与版本栅栏_V1.0.md)。 |

### 3.2 Delegation caller-scope 与委托生命周期

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | TrustGraph delegation API/service/repository 是委托生命周期写入 owner。API 从可信 `PolicyContext` 得到 caller card；create 将 `delegator_id` 绑定 caller card，再由 repository 在事务中按 card id 升序锁定相关卡片、校验 delegator/delegate 归属和 scope，并通过 strict canonical published evidence 证明委托人实际持有对应权限及有效期上界。update/revoke 根据请求中的 delegation id 读取并锁定真实委托记录后再核验 caller 和两端卡片；对象级授权的 `/delegations/{id}` resolver 从服务端委托行解析 owner。 |
| 信任与数据边界 | 请求体不能自行指定委托人身份或 tenant/domain。委托人必须是已验证 caller；委托两端 user card 必须满足当前状态及相同 tenant/domain 等合同；被委托权限和期限不能超出可证明的委托人授权。集合型 actor-scoped route 仍由 handler 证明操作确实绑定 caller card，不能把 actor scope 当成任意目标 owner。 |
| 失败与恢复 | caller 与 delegator 不匹配、卡片 scope/状态不符、权利或期限无法证明、source/rule/ledger/head 不一致时拒绝并回滚，不把不可证明的幂等命中当成功。更新/撤销按锁定 source 复核；重复撤销不重复追加 tombstone。授权变更与对应 ledger/head、CARD projection event、审计关联在短 source transaction 中保持一致，事务外副作用不能成为提交前置。 |
| 当前状态与证据 | 代码已实现上述关键局部检查，包括 API caller 绑定、升序卡锁、canonical hold proof、对象行复核及 tenant/domain 约束；这比“只有 generation-gated 检查”更具体。但“所有入口都具有一致可信 caller-scope 合同”仍须逐路由核对，不能由 create 路径推断所有兼容/管理入口均闭合。详见[权限判定与规则集语义](Rust权限判定与规则集语义_V1.0.md)、[V5 模型修正筹划](V5模型修正筹划_专供Rust_V1.0.md)、[访问控制总览与调整路线](Rust访问控制总览与调整路线_V1.0.md)。 |

### 3.3 Identity / Eligibility、tenant/domain 变化与 fan-out

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | Identity owner 管理认证身份、会话及其状态；TrustGraph 管理 user-card 与授权关系；`CardEligibilityService` 是双卡资格权威读取边界，资格缓存由其自身策略管理。身份、user-card、tenant/domain 或资格变更分别从相应 source owner 出发，再按已定义事件/失效合同通知 session、eligibility、授权投影及下游 scope；这些 fan-out 目标和触发条件不能互相替代。 |
| 信任与数据边界 | `identity_card` 是身份/认证事实，`user_card` 是授权载体及 tenant/domain scope，二者不能混为同一卡或由旧角色映射代替。Eligibility 证明卡片是否满足资格条件，不是规则授权 evidence，也不是对任意 tenant/domain 归属的证明。CARD refresh、ELIGIBILITY cache eviction 与 RULE_SET 投影是不同语义。 |
| 失败与恢复 | 资格来源不可用、卡片/身份状态不明、tenant/domain 事实冲突或必需的失效/事件尚未证明时，授权不得沿用旧资格或旧授权快照放行。缓存需受 TTL/容量/清理边界约束且失败不能扩大权限；恢复应从权威 owner 及持久事件对账，而不是用某一类 CARD 事件冒充其他 fan-out。 |
| 当前状态与证据 | 双卡模型与资格服务/局部缓存语义已有实现；完整的身份到期事件、身份/tenant/domain 状态变化的跨 owner fan-out、user-card validity API 等仍有未完成合同。不能把已有资格读时校验写成已具备全生命周期自动传播。详见[双卡身份与授权上下文](Rust双卡身份与授权上下文_V1.0.md)、[V5 模型修正筹划](V5模型修正筹划_专供Rust_V1.0.md)、[模型设计修正记录](Rust架构模型设计修正记录.md)、[权限投影快照与版本栅栏](Rust权限投影快照与版本栅栏_V1.0.md)。 |

### 3.4 RuleSet `valid_to` 自然到期

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | RuleSet/授权 grant 的 source owner 管理授权来源及 `valid_from`/`valid_to` 窗口；正式授权读取由 canonical strict evidence reader 在组装已发布 evidence 时以统一 UTC 时间判断有效性。自然时间越过 `valid_to` 是时间窗判定，不等于 owner 已提交一次 source mutation，也不会自行产生 canonical delta。 |
| 信任与数据边界 | strict reader 的读时过滤只能证明“本次读时该 grant 已不在有效窗口”；不能推导出持久化到期事件、generation 推进、旧投影清理或操作级审计已经发生。缓存 TTL、ELIGIBILITY eviction 和 delegation expiry worker 均不是 RuleSet expiry event 的替代。 |
| 失败与恢复 | strict reader/DB 不可用或 evidence/version 不完整时仍应 `PENDING`/`DENY`，不得以缓存、旧快照或 raw source fallback 绕过。要增加到期调度、事件、generation 推进或专项审计，须先明确 source owner、稳定 operation identity、重入/并发、恢复和验证合同；现有资料中的候选方式不能当作已批准执行路径。 |
| 当前状态与证据 | **strict published-evidence reader 已按统一 UTC 读时检查 grant validity，缓存命中也复核时间窗；缺少的是自然到期触发的 durable source mutation / expiry event / generation 与专项投影、审计闭环。**当前没有专门 RuleSet expiry scheduler/event。详见[临时授权到期回收专题](技术储备-临时授权到期回收.md)、[增量重建与实时授权边界](Rust增量重建与实时授权边界_V1.0.md)（含 RuleSet `valid_to` 与 worker 区分）、[权限投影快照与版本栅栏](Rust权限投影快照与版本栅栏_V1.0.md)。 |

> **委托到期不等于 RuleSet 自然到期。** 当前已接入 TrustGraph runtime 的 `delegation_expiry_worker` 是委托专属 reconciler：默认每 60 秒轮询、默认批量 64 且上限 500；有限退避并有界关闭。它发现候选后逐条在短事务内重新核对 DB 时钟、锁定的 source/规则/账本，写入委托 REVOKE tombstone、CARD `REVOKE` 事件、`EXPIRED` 状态及审计；重复执行按稳定委托身份幂等，事务不执行网络/MQ/Redis 副作用。相比之下，RuleSet `valid_to` 到期目前由 strict reader 读时过滤，不触发该委托 worker，也没有等价的 source mutation、到期事件或 generation 推进。worker、读时过滤和缓存过期是不同 owner/机制，不能互相代称。

### 3.5 Arbiter 冲突治理与可信 quorum

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | `policy-engine` 中的 Arbiter 纯函数只对调用方提供的输入 evidence/vector 执行确定性冲突处理（例如版本顺序、DENY 优先、同版本多数及 DEFER 规则）；Monitor HTTP 控制面接收请求并调用该能力。正式请求授权的 owner 仍是 `PolicyEngine::evaluate()` 及其 strict evidence gate，而不是 Arbiter endpoint。 |
| 信任与数据边界 | 多数计算中的输入项不自动代表经过认证的独立节点。当前请求体提供的 context/evidence 未构成节点身份认证、签名证明、请求/资源绑定、nonce/replay 防护或唯一成员计数；因此 vector 内的多数不是分布式可信 quorum。Arbiter 输出不得绕开 active card、resource-owner resolver 或 canonical published evidence。 |
| 失败与恢复 | 输入缺失、版本冲突或 DEFER 应按其纯函数语义返回非 ALLOW/待处理结果；调用层不得把不可信输入转换为普通授权。要支持可信节点 quorum，需单独批准并实现成员身份、签名和请求绑定、防重放、唯一节点计数、超时/部分失败和可审计验证；未闭合时安全恢复是拒绝把 Arbiter 结果用于授权，而非降低 quorum 门槛。 |
| 当前状态与证据 | 纯函数层冲突计算存在；HTTP 输入证据真实性、请求绑定、replay 防护与可认证节点 quorum 尚未建立。测试/实验材料只能证明其实际覆盖的情景，不证明生产 quorum 已可信。详见[Arbiter 与 GlobalAdmin 治理链](RustArbiter与GlobalAdmin治理链_V1.0.md)、[分布式测试说明](../../实验/分布式测试/README.md)、[权限判定与规则集语义](Rust权限判定与规则集语义_V1.0.md)。 |

### 3.6 GlobalAdmin 生命周期、授权与操作审计

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | `identity_global_admin` 中的 ACTIVE 资格是 GlobalAdmin 身份事实；Identity/TrustGraph 管理入口负责授予、启用/禁用及相应卡片/资格事件、会话撤销和 last-active-admin 保护；resource-owner contract 对平台全局控制面声明 `ActiveGlobalAdmin` 要求；`PolicyEngine::evaluate()` 在严格 published-evidence 路径中重新读取权威 ACTIVE 状态，并将其与规则 evidence 的 ALLOW 门结合。 |
| 信任与数据边界 | GlobalAdmin 资格不等于 SuperAdmin 卡。SuperAdmin 是专用 `user_card` 与 `__SUPERADMIN__` BASE RuleSet 路径；不得以角色字符串、`isSuperAdmin()`、旧映射、客户端标记或通配绕过替代 GlobalAdmin 检查。Global 管理请求仍需服务端资源/路由契约及正式 PolicyEngine/evidence 路径。 |
| 失败与恢复 | 管理员资格查找不可用、状态非 ACTIVE、strict evidence 不足或 global target 带入 tenant/owner facts 时 fail closed；缓存正值不能取代 evaluate 内的新鲜 source proof。授予/禁用事务、资格/CARD 影响和 session revoke 的部分失败必须按持久状态与关联事件对账，不能只看 API 成功响应。 |
| 当前状态与证据 | 管理生命周期已有事务性变更路径、资格/卡片相关事件、会话撤销与最后活跃管理员保护；正式 Global 资源路径也已有 fresh ACTIVE source proof 与 strict evidence 门。生命周期操作级审计是否对 actor、目标、operation、事件关联及失败/重试形成完整可追溯链，必须按具体写入口证据判断；不要把普通 ALLOW 审计或投影事件自动称为完整管理操作审计。详见[Arbiter 与 GlobalAdmin 治理链](RustArbiter与GlobalAdmin治理链_V1.0.md)、[模型设计修正记录](Rust架构模型设计修正记录.md)、[访问控制总览与调整路线](Rust访问控制总览与调整路线_V1.0.md)。 |

### 3.7 ORG_SCOPE 组织授权治理

| 维度 | 分析 |
|---|---|
| Owner 与调用/数据流 | ORG_SCOPE 是独立组织授权 source slice，具备专属 repository/outbox/projector/admission/compiler 的源码接线；批准的目标模型描述 tenant 内组织层级、组织成员资格、共享单元及祖先范围语义。source 写入、事件物化、策略 admission/compiler 和 HTTP 资源 owner 解析分别有其边界，不能因存在 projector 就推断所有受保护 API 已接入组织 owner resolver。 |
| 信任与数据边界 | tenant 是硬隔离边界；组织祖先/成员资格/共享单元规则只在批准的 tenant 内解释，不得把组织归属、共享单元或跨组织 grant 从请求体自行声明。default-off 是安全边界的一部分；跨 tenant 正式授权必须等受保护 HTTP route 的服务端 owner resolver 与必要证据门完整接入并验证后才可考虑启用。 |
| 失败与恢复 | 未知 tenant/组织归属、成员资格或祖先链、projector/readiness 不足、migration/default-off 状态不符时拒绝或保持不可用，不以普通 tenant fallback 或旧授权快照补足。迁移/启用属于 Exec-L3：须遵循 runbook 的 allowlist、preflight、备份/恢复与 postcondition 验收；未执行真实迁移/部署不能报告生产可用。 |
| 当前状态与证据 | 组织层级目标设计已批准；当前工作区有 default-off 源码切片和 additive migration 设计（13 张表），但真实迁移/部署/集成验收尚未完成，受保护 HTTP resource-owner resolver 的全面接线也未闭合。不能把目标中的共享单元、成员资格及祖先继承语义写成生产落地。详见[多租户聚合分区与组织层级设计](Rust多租户聚合分区与组织层级设计_V0.1.md)、[ORG_SCOPE 迁移与回滚操作手册](../../迁移/ORG_SCOPE迁移与回滚操作手册_V0.1.md)。 |

## 4. 使用与维护规则

- 每一子题分别记录当前源码事实、已批准决策、未实现项及运行验收状态；设计存在、设计获批、源码接线、真实环境通过是不同证据等级。
- 不把这些主题合并成新的统一状态机、source owner 或跨主题 worker；特别区分 delegation expiry reconciler 与 RuleSet `valid_to` 时间窗。
- 不把 `PolicyEngine`、Arbiter、GlobalAdmin 状态、资格服务或角色字符串互相作为授权旁路；正式请求仍须通过唯一授权入口和对应证据门。
- 涉及 source mutation、异步投影、缓存、迁移或审计的增量设计，必须回到对应 owner 的规范/深度设计中批准、实现并按其门禁验证；本索引本身不产生批准。
- 若证据不足以判断某项入口或恢复行为，应标记具体缺口并停止推断，不以此专题补写未批准合同。

## 5. 结论

这是按主题拆分 owner、数据流、信任边界、故障恢复与实现状态的阅读矩阵，用于把授权生命周期/治理储备追溯到主要设计资料和当前实现边界。它不是新架构决策，不改变任何权限、数据、迁移或部署行为，也不代表运行验收完成。
