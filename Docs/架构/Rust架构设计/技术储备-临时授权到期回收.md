# 临时授权到期回收：Delegation 与 RuleSet 时间窗的不同边界

> 状态：**Delegation `effective_until` 已有周期对账 worker 与 source 收敛代码；RuleSet `valid_to` 仍缺独立 expiry scheduler/event 自动触发 canonical 投影更新的闭环。**两者是不同的数据 owner 和生命周期，不能把已有 delegation worker 当作 RuleSet 到期已实现。RuleSet 候选方向尚未选择。
>
> 对应：[技术能力与储备清单](../../技术能力与储备清单.md) 原 42；[增量重建与实时授权边界](Rust增量重建与实时授权边界_V1.0.md) §6.2、§9.6；[授权生命周期与治理扩展](技术专题-授权生命周期与治理扩展.md)。

## 1. 问题：wall-clock 到期不自动等于 durable 授权变更

有效期字段可以在某时刻之后自然失效，但单靠时间流逝不会必然写入 source、推进授权 generation、产生 revoke fence 或发布新的授权证据。当前生产 strict published-evidence reader 已按统一 UTC 读时检查 grant validity；evidence-cache 命中也会重新核对有效窗，因此 RuleSet `valid_to` 缺少 scheduler 并不等于正式读者必然把已过期 grant 计入 ALLOW。缺少的是到期触发的 durable source mutation、expiry event、generation 推进及专项投影/审计收敛，而非读侧完全没有时间窗判断。

必须将“读时已过期过滤”与“持久化生命周期收敛”分开：前者可影响本次证据是否有效，后者负责 source 状态、版本/撤销事实与投影世代的 durable 演进。Redis TTL、旧快照重建时做时间过滤，或巡检时读 source，都不能替代这些 durable 事件及其恢复、审计合同。

## 2. 已实现的 Delegation 到期对账（不是 RuleSet `valid_to`）

### 2.1 现有机制与生命周期

代码中确实存在 `DelegationExpiryWorker`，但它只对 `permission_delegation.effective_until` 到期的 ACTIVE delegation 做有界对账：

1. TrustGraph runtime 在启动前解析并验证 `ASTRAL_DELEGATION_EXPIRY_POLL_SECS` 与 `ASTRAL_DELEGATION_EXPIRY_BATCH`；默认 60 秒轮询、每轮 64 条，上限 500。非法值在 spawn 前拒绝启动。
2. worker 周期调用 `DelegationWriteService::reconcile_expired_delegations`。候选发现是有界只读查询；由于 `permission_delegation` 没有 `tenant_id`，候选发现跨租户。候选不是授权事实，逐条处理在自己的 source transaction 中重新锁定并验证 delegator/delegate 卡及 tenant/domain 事实，任何缺失/漂移都 fail-closed，失败项 source 保持不变。
3. 在事务内以数据库时钟重新判断是否到期，并按固定锁序校验 ACTIVE delegation、关联规则和 ledger head。已终结/尚未到期为幂等短路；缺少可证明有效期、source/规则/ledger 不一致时要求修复而不猜测。
4. 成功收敛在同一短事务中追加卡级 REVOKE 投影事件和 delegation grant tombstone/delta，删除该 delegation 对应规则、将 delegation 置为 `EXPIRED`，并写带稳定 `operationId`、事件关联和 before-image digest 的审计记录。稳定 ID 派生自 delegation ID 与锁定有效期。worker 不复制 SQL、不在 source transaction 内做网络、MQ 或缓存副作用。
5. 下游授权投影/发布仍有独立生命周期。worker 完成 delegation source reconciliation 不等于所有节点已取得新的 published evidence；正式授权仍必须服从 canonical generation/fence 与 strict read-gate。

运行时持有 worker handle，关闭时执行 cancel 和有界 join；周期错误有有限退避与汇总记录。它不是“任意时间窗规则调度器”，也不承诺无延迟到期：轮询间隔、批次积压及投影收敛共同影响实际观察时间。相应代码见 [`delegation_expiry_worker.rs`](../../../astral-trustgraph/src/service/delegation_expiry_worker.rs)、[`delegation_service.rs`](../../../astral-trustgraph/src/service/delegation_service.rs)、[`delegation_repository.rs`](../../../astral-trustgraph/src/repository/delegation_repository.rs) 与 [`runtime.rs`](../../../astral-trustgraph/src/runtime.rs)。

### 2.2 RuleSet `valid_to` 的不同缺口

RuleSet 时间窗属于 `rule_set_entry` 及 canonical 授权投影语义。现有架构记录明确指出：canonical 链和 legacy projection 链都没有独立 expiry scheduler/event 自动触发 RuleSet 到期投影更新；生产 `PolicyEngine.evaluate()` 消费 published evidence，不会因为 wall-clock 越过 `valid_to` 自行推进 generation。`evaluate_realtime()` 对 raw source 做时间过滤是显式诊断/一致性路径，不是正式授权 fallback。

身份卡 `expires_at`、用户卡资格 `valid_until` 有各自的资格读时检查/缓存 TTL 语义；这不是 RuleSet `valid_to` 调度。已实现的 Delegation worker 则以 `permission_delegation.effective_until` 为候选并执行 source mutation/tombstone。即使 delegation 写入另有 `permission_rule.valid_to` 表达有效边界，也不能把它等同于 RuleSet entry 自然到期，更不能由此宣称 RuleSet scheduler 存在。

## 3. RuleSet 自然到期的候选架构（均未选择）

[增量重建与实时授权边界 §9.6](Rust增量重建与实时授权边界_V1.0.md#96-时间到期与调度) 记录了待评审方向，而非实现决定：

- **候选 A：到期事件调度**。source mutation 时记录可恢复的到期计划；到期后由调度器产生带稳定身份、tenant/aggregate、目标 generation/dependency 与时间窗事实的 durable projection event，再由现有授权 projector 以 lease/fence/CAS 发布。需要处理计划修订、提前撤销、事件重排和数据库时间判定。
- **候选 B：持久生命周期之外的读侧时间窗扩展**。当前 strict reader 已按统一 UTC 检查 published grant 的有效窗，缓存命中也复核时间边界；它们不能单独更新 durable generation 或产生 source expiry event。若评估进一步改变 read-gate 协议，仍须明确多实例时钟/缓存一致性合同；不得把当前已存在的读时过滤误称为到期 source reconciliation。
- **候选 C：保守 full rebuild**。若时间/runtime 条件无法安全增量化，可在到期触发完整重建；这是文档所列的保守候选，不代表现有 compiler 已把 RuleSet `valid_to` scheduler 接通。

无论何种路线，到期边界比较、DB/权威时间源、generation/fence、重启补偿、并发与幂等必须定义；过期窗口中的正式授权结果只能是已证明仍有效，或 `PENDING`/`DENY`，不能用旧快照、缓存或 raw source ALLOW 回退。

### 候选方案取舍

Durable event 更容易审计、重放与对账，但增加调度状态、迁移、积压恢复和时钟边界复杂度；读侧检查减少后台调度，但需要每个正式 reader 与缓存都遵守同一可证明合同，并处理 generation 一致性；全量重建简单保守但成本更高。当前没有获批方案，本文不推荐具体事件表、scheduler 产品或精确读时算法。

## 4. 故障恢复、安全边界与验收要求

- 到期候选扫描结果可能在处理前过时；必须在事务内使用锁定后的 source 行和权威时间重新证明。缺 tenant/domain、ledger lineage、before-image 或有效期限证明时不写、不猜、不跨租户修复。
- 重复周期、并发人工 revoke/update、worker 重启和批次积压必须安全收敛。未知提交结果先按稳定 operation/durable state 对账，不盲目重试；成功 mutation 及 tombstone、投影事件和审计关联应保持同一 source transaction 的原子边界。
- Delegation worker 只解决 delegation expiry source 收敛；source mutation 后 projection 失败/延迟时，正式读 gate 必须继续 `PENDING`/`DENY`，不可将 source 状态或 worker 返回值当成 published proof。
- RuleSet `valid_to` 的实现还需定义到期前计划修改、自然到期与显式撤销竞争、时钟偏差、worker ownership/lease、generation token、迟到/重复事件、审计、修复和回滚合同。更改实际授权属于 durable 授权动作，任何实现须走批准的 source owner 路径并完成相应安全/数据链审查。

验收至少应区分 delegation 与 RuleSet 两组端到端断言：到期候选边界与 DB 时钟、并发/重复、跨租户漂移 fail-closed、事务部分失败、稳定 operation ID 对账、projector 延迟/重启，以及 RuleSet 到期前/后正式 gate、event 丢失恢复、generation/fence 和多节点收敛。仅有单元测试、`evaluate_realtime()` 对照或 TTL 不构成正式到期回收验收。

## 5. 当前实施、批准与验收状态

- **Delegation**：有 Rust `DelegationExpiryWorker`、service/repository source reconciliation 和 TrustGraph runtime 装配证据；单条事务按锁定卡重证 scope，写 tombstone/delta、REVOKE 事件及审计。代码/测试存在，但本文未运行数据库集成或检查线上运行状态，因此不声称已完成真实 DB/多实例运行验收或 production SLO 证明。
- **RuleSet `valid_to`**：strict reader 按读时 UTC 检查已发布 grant 的有效窗，缓存命中也复核边界；自然到期触发的 durable source mutation/expiry event、generation 推进及专项投影/审计闭环仍缺失。架构文档列出候选，尚无专项选型批准或到期自动投影验收。
- **资格/身份自然到期**：属于独立 ELIGIBILITY/身份状态路径；不能作为 RuleSet 到期完成的证据。

**结论：**储备项的描述应精确为“RuleSet 自然到期的自动投影闭环仍缺失”，而不是“仓库完全没有到期 worker”。已有 delegation worker 是相邻且已接线的能力，不改变 RuleSet `valid_to` 缺口。
