# 存量系统继承 HAMT、fence 与 fail-closed：储备范围与证据边界

> 状态：**内部构件存在；外部存量系统接管宿主与通用 adapter 未找到实现证据。**本文区分授权内核内部事实与跨系统继承目标，不是稳定的外部集成 API 设计。
>
> 对应：[技术能力与储备清单](../../技术能力与储备清单.md) 原 50；[FactoredHotState 设计](FactoredHotState设计_V1.0.md)；[投影快照与版本栅栏](Rust权限投影快照与版本栅栏_V1.0.md)；[SDK 接入 V1](../../SDK接入V1.md)。

## 1. 术语在当前项目中的含义

- **HAMT 型 HotState**：授权编译器内部使用持久化映射及结构性共享维护内存热状态。它是编译数据结构，不是 durable HAMT 数据库、外部系统 SDK 或跨进程授权证明。
- **generation/fence**：授权 source 变更和发布使用版本、撤销栅栏、lease/CAS 等机制拒绝陈旧 owner，读侧通过 canonical published evidence 验证当前授权。
- **fail-closed**：当授权证据缺失、错误、scope 不符或无法证明时不产生 ALLOW，使用 PENDING/DENY 等拒绝准入结果。它要求完整调用路径遵循同一合同。

这些构件分别解决内存状态表达、durable 发布一致性和不确定性决策问题。将某个结构复制到另一个服务，不会自动建立 source ownership、身份/租户隔离或发布证明。

## 3. 目标问题与内部内核职责

储备目标是评估：既有系统能否在不复制内部状态语义的前提下，复用平台授权内核所需的编译、版本拒绝和 fail-closed 保证。问题不是把一个数据结构或 crate 嵌入对方进程，而是让外部 source mutation、授权事实 owner、编译发布和正式读入口形成可证明的闭环。

现有内核中的三个责任层必须分开理解：

1. **HotState / HAMT：内存编译表示。** `policy-engine` 的 `HotState` 使用 `im::HashMap` 持久化映射保存共享 RULE_SET 内容、绑定、逐 grant 记录、卡私有 grant 和 segment；结构共享有利于编译增量/克隆，卡归属与 grant 生命周期仍单独保留。它由 ledger 输入构建，是进程内派生状态，不是 durable HAMT 数据库、跨进程证明、source owner 或外部 SDK。持久化层仍要提供可重放的 canonical facts。
2. **generation / fence：持久发布与陈旧拒绝。** source mutation 必须以稳定 operation/event 身份、durable intent/ledger、版本推进和适当 CAS/lease/token fence 建立发布序；旧 owner 或乱序 worker 不得覆盖新 current。generation 和 revoke fence 是对指定 aggregate/source 的版本证明，不是任意外部源可直接复用的计数器。
3. **strict evidence / PolicyEngine：授权读门责任。** 正式 `evaluate()` 的 strict 路径读取已发布的 current/manifest/segment evidence，并核验 scope、完整链、摘要/seal、lineage、generation 与 revoke-fence proof；有效 ALLOW 前还要复读证据。evidence 缺失、过期/不匹配、scope 错误、读失败或结果未知时只能 PENDING/DENY。缓存只能保存已验证 evidence，缓存命中不是 durable proof；raw source、旧 snapshot 或普通缓存不能替代正式读门。

因此不能将 HAMT clone 成外部缓存并称为继承授权；也不能只传一个 generation 数字，而不定义其 owner、原子推进与读侧验证。严格证据合同跨越 source、transaction/outbox、projector、published state、reader 和最终业务入口，每一环都需要外部宿主的 owner 与运行证据。

## 4. 外部宿主所需的端到端边界

具体宿主至少要证明：

- 每种授权事实由谁拥有，如何标识 source mutation、资源 owner、principal、tenant/domain、operation/event、revision 与撤销；映射缺失或歧义时如何拒绝。
- source mutation 与 durable ledger/head/outbox/audit correlation 的事务边界；外部 RPC、缓存、projection、MQ 和重试不能塞入源事务。worker 只物化获批 source mutation，不自行制造授权。
- 编译输入可由 durable facts 重建；增量更新与全量 oracle 一致；租户/归属隔离正确；发布使用 CAS/lease/generation/token fence，并把 manifest/current 与完整 lineage、内容摘要和撤销证明绑定。
- 正式 handler/路由/消息消费者都调用统一且不可绕过的 PolicyEngine/adapter 入口；在副作用提交前复查业务 revision。未保护的管理员、批处理、内部 RPC、WebSocket 或后台任务都属于明确的 coverage gap。
- 授权审计与 source operation、投影 event、决策 request 可关联；投影状态和审计状态各自有重试/对账，不以审计写成功替代授权证据，也不以消息 ACK 替代 durable state。

无法达到这些条件时，内核只能提供局部计算能力，不能声称宿主已经继承其安全保证。

## 5. 集成形态候选比较（分析，不是选型）

| 候选形态 | 可能的责任分布 | 对 owner 证明与强制执行的要求 | 优势与取舍 |
|---|---|---|---|
| Library / SDK（嵌入式） | 内部适配器在宿主进程解析可信 actor/facts 并调用授权合同；宿主在本地事务/CAS 前提交 | 必须逐入口装配并盘点未保护路由；宿主提供权威 owner/revision，SDK 不可证明已失陷宿主未谎报；若 SDK 含内核本地态，还需版本/数据装载协议 | 本地调用、可读业务上下文、避免每次决策网络跳转；需多语言绑定/版本兼容/依赖管理；嵌入 HAMT 不会自动带来 durable fence 或 strict reader |
| PDP service（集中决策服务） | 宿主把签名绑定的上下文请求交远程 PDP，接收有限时效决策 | 服务端须验证 caller/app/tenant、请求完整性、evidence 与策略版本；宿主在本地写提交前再次校验；网络结果未知/超时不能被缓存 ALLOW | 中央治理、策略实现集中；新增网络依赖和决策/业务事务非原子窗口；facts 的准确性仍依赖宿主，重试与撤销传播需协议支持 |
| Sidecar / proxy | 每个宿主旁路或统一入口拦截网络请求并代为查询 PDP | 必须证明所有流量不可绕过，且能获得目标 owner、资源 revision 和操作级事实；传输路径覆盖不等于内部消息、后台任务、批量资源和对象级 owner coverage | 可降低应用直接调用代码的重复；部署/证书/版本/健康与服务发现复杂；代理通常缺业务语义，sidecar 失联、旁路或旧配置可能造成不可见缺口 |

可存在组合，如 SDK 提供 facts resolver、PDP 承担集中评估、sidecar 仅负责认证/传输；但需要确定唯一最终读门、责任人和拒绝状态传播。候选之间不能用“更无侵入”简单排序：关键评估项是事实从哪来、哪些入口能被强制拦截、局部事务谁复核、版本怎样传播、依赖故障后怎样保持拒绝，以及能否从 durable evidence 恢复。本文不选 library、服务或 sidecar，也不批准跨语言 API、wire schema 或性能目标。

## 6. 失败、恢复与安全威胁分析

**故障和未知状态**：source DB/事件源不可用、worker 超时、lease 过期、CAS 冲突、网络分区、cache 污染、current 指针缺失、manifest 链不完整、generation 不一致或撤销证据不足，都不能继续用旧状态 ALLOW。投影端使用稳定事件身份、有限 retry 和 generation/token fence；未知 COMMIT/发布结果先对账 durable current 与事件处理状态，不因“客户端没收到响应”而盲目重发。重建应从可证明的 durable ledger/replay inputs 开始；若外部 source 不提供完整历史或稳定 revision，恢复合同尚未成立。

**安全威胁**：攻击者可伪造 actor/tenant/target、重放过期授权、利用路由旁路、抢占/复用旧 worker、注入跨租户数据或利用陈旧投影放行。阻断依赖认证来源、source owner 与 scope 对牌、稳定 id、lease/CAS/token fence、完整 evidence 校验和全入口强制检查。误放行会跨主体/跨租户越权；不确定时拒绝会降低可用性，但只能通过重获可信事实、完成投影和重新评估恢复。

**迁移和回滚**：先隔离评估或 shadow compare，不让候选内核结论自动成为正式决定；正式切换前需逐 tenant/resource 验证 source ledger、回填、generation、lineage、撤销 fence、读侧 gate 和业务消费者。回滚应停止新 owner、对账未知 durable 操作、恢复可证明的数据/配置版本并验证旧读门仍安全；若旧路径会忽略撤销或使用过期快照，就不能作为可接受的回滚 ALLOW 路径。DB/MQ/Redis 真实故障、worker 重启、备份/恢复和外部切流都需单独授权和验收。

## 7. 当前证据、验收边界与结论

内部证据：`FactoredHotState设计_V1.0.md` 记载已实施 HotState 共享/绑定/记录/私有层表示，同时明确 durable 段跨卡共享、RuleSet 级 delta 和 ID 池化属于后续路线；`policy-engine/src/authorization_compiler.rs` 可见 `HotState` 与 `im::HashMap` 字段。此处的 HAMT 是编译期内存表示。

版本和读门证据：`Rust增量重建与实时授权边界_V1.0.md`、`Rust权限投影快照与版本栅栏_V1.0.md` 记录 canonical projector/current/evidence reader 的职责与缺口；`astral-db` / `policy-engine` 的实现提供 strict published-evidence 读路径。相同资料明确存量 backfill、真实 MySQL/Redis/RabbitMQ 集成、缓存读侧迁移与正式切流尚未验收。SDK V1 是受限、默认关闭的显式接入合同，不是继承既有 HotState 或外部授权运行时。

当前仍无通用外部宿主、adapter、durable HAMT、跨语言 SDK/PDP/sidecar 完整合同或生产接管证明。本文未批准任何集成形态或迁移方案；内部 kernel 构件存在，不意味着外部 system 已完成 integration。后续专项必须选定具体 source/host，逐链给出 owner、协议、事实与版本证据、故障注入、恢复步骤、全入口盘点、租户隔离及批准/验收状态。
