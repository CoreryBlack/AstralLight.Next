# 无侵入式业务接入与源码注入：储备范围与证据边界

> 状态：**尚无通用接管代理、sidecar 或源码注入实现证据。**本文梳理路线图设想与现有显式 SDK 接入边界；不批准具体注入方式。
>
> 对应：[技术能力与储备清单](../../技术能力与储备清单.md) 原 46；[项目路线图的 Klein 跨系统接管定位](../../../index.html#panel-reserves)；[SDK 接入 V1](../../SDK接入V1.md) 与[实施证据](../../SDK接入V1_实施证据.md)。

## 1. 术语和目标边界

路线图将 Klein 描述为跨系统辐射赋能层，并列出“非侵入 sidecar/代理、存量权限同化与统一视图”等方向。清单中的“无侵入外挂式源码注入”对应的是降低既有业务应用接入授权能力的改造负担，但“源码注入”并未在现有材料中被定义成一种具体语言工具、运行时 hook、agent 或网络代理协议。

因此，本文件只把它作为尚未拆解的产品储备记录。不能把源码织入、sidecar、反向代理和 SDK middleware 当作互换实现，也不能替用户选择其中一种。

## 2. 当前仓库中的显式接入模式

SDK V1 是有边界的显式集成：业务应用需要实现可信 actor/facts resolver，并将 Axum authorization layer 装配到路由；目标资源 owner 和 revision 由业务 resolver 提供。SDK 不证明被攻陷的业务服务没有谎报本地事实。

SDK 还要求管理员批准应用范围，并显式维护外部主体到既有平台用户/身份卡的映射；相关功能默认关闭，当前本地合同测试不等于生产集成/切流验收。详见 [SDK 接入 V1](../../SDK接入V1.md) 与 [SDK V1 实施证据](../../SDK接入V1_实施证据.md)。

这证明仓库有可复用的接入 SDK 和 Axum adapter，不证明存在无需应用改造的通用接管运行时。

## 3. 问题、目标与非目标

要解决的核心问题不是“怎样把授权调用藏起来”，而是既有业务系统接入授权时，如何让每一个受保护操作在正确的身份、资源 owner、tenant/domain 和业务版本上被强制判定，同时将各框架重复的接线成本降到可接受范围。接入外观可以更少侵入，但授权所依赖的事实仍必须由有权威性的 owner 提供；若宿主不提供可信事实、也没有可验证的业务边界，平台不能仅凭网络流量推断出正确权限。

候选目标包括：明确哪些入口受保护、哪些公共入口显式放行；把 actor、action、resource、owner、tenant/domain、revision 和 operation 绑定到决策；让变更提交前在 owner 的短事务/CAS 中复核事实；使未经接入的路径不能绕过控制；并在状态不明时可观测地拒绝或返回 PENDING。非目标包括自动发现任意业务语义、替业务 owner 决定资源所有权、把外部系统的数据迁入平台、或仅凭“代理已部署”宣称全系统权限已接管。

“无侵入”须按维度说明：是否改源码、是否改部署拓扑、是否需要为资源解析提供适配、是否能覆盖异步/后台/批量/长连接入口、是否要求业务在提交时复核。零源码改动不等于零接入，也不等于强制执行完整。

## 4. 候选接入机制比较（分析，不是选型）

| 候选机制 | 接入与强制边界 | owner/facts 证明 | 优势 | 主要代价与失效边界 |
|---|---|---|---|---|
| 显式 SDK / middleware | 每个业务路由组装 adapter；未登记路由拒绝，公共路由精确登记。handler 消费一次性 proof，并在写事务/CAS 前重验 | actor resolver、resource facts resolver 和本地 owner 提供资源/tenant/domain/revision；业务服务仍在信任边界内 | 路由、动作和目标绑定清楚；可在业务拥有事实时做精确授权；当前仓库已有 Rust/Axum 合同与样板 | 需要业务改造和逐入口覆盖；漏装 layer、漏登记特殊路径或错误 resolver 会留下覆盖缺口；远程决策与本地提交不是原子事务 |
| sidecar / 反向代理 | 在网络入口实施认证/策略检查；sidecar 需覆盖所有入口，反向代理需确认没有可绕过的直连路径 | 通常只能看到传输层身份、路径和请求元数据；对象 owner、批量目标、业务状态/版本仍需可信扩展协议或 owner 回调 | 可集中部署、语言无关，适合已有统一入口和标准请求形状的服务 | 网络边界不等于业务资源边界；代理无法凭 URL 证明对象归属或事务时点；旁路端口、内部调用、异步任务与 WebSocket 消息粒度可能漏管；代理故障会扩大可用性影响 |
| 源码织入 / 编译期或运行期 hook | 在已知框架调用点自动插入检查；需对构建、运行时和版本升级建立可验证覆盖 | 仍需要业务模块明确声明资源 owner、facts 与操作语义；静态发现或 hook 本身不证明这些事实正确 | 可能减少重复路由样板，并在特定语言/框架中形成统一拦截点 | 多语言和版本成本高；反射、动态路由、生成代码、异步边界及未覆盖构建路径会削弱证明；织入错误可能改变调用/异常时序；兼容性与诊断/回滚复杂 |

三种机制都不能代替资源 owner 的责任。可分析的组合形态包括“SDK 明确事实 + 网关/sidecar 统一传输校验”，或“织入负责定位调用点、显式注解/适配器提供语义”；组合仍须有唯一、可审计的最终强制点，不能让多个层对 ALLOW/PENDING 作不一致解释。以上只是候选分解，不是当前项目批准的路线。

## 5. 共同合同、安全边界与故障恢复

无论接入外形为何，专项设计至少需逐项闭合以下合同：

1. **调用覆盖**：登记受保护方法、动作和资源；默认拒绝未识别路径、方法、动态目标和版本不兼容的 hook。健康检查等公开路由使用精确 allowlist，不能用宽泛路径忽略。
2. **事实与所有权**：主体必须来自受信认证上下文；目标 ID、tenant/domain、owner、业务 revision 由资源 owner 查询或可验证地解析。客户端提供的身份头、租户字段和“已授权”标志不得作为事实。策略服务不能替宿主证明其本地数据没有撒谎。
3. **决策绑定与提交**：请求/决策绑定应用、manifest revision、主体、目标、动作、operation ID 和 facts digest；写请求在本地短事务/CAS 中再核对 revision。网络等待不能持有业务锁，远程 ALLOW 不是业务提交证明。
4. **失败默认**：超时、断连、签名/完整性失败、配置陈旧、resolver 错误、scope 不匹配、strict evidence 不足、代理状态未知或执行覆盖不确定时返回拒绝/PENDING，不使用旧 ALLOW、未认证缓存或 raw source 绕行。可用性恢复后必须重新评估。
5. **幂等与对账**：持久写入使用由业务 owner 提供的稳定 operation ID，并把 operation、request/facts digest、局部提交状态和审计关联在业务事务/outbox 中记录。未知 COMMIT 或响应断流先对账 durable state；只有确认无副作用或按稳定 ID 完成对账后才可重试。不得把网络重试等同 exactly-once。
6. **隔离、观测与撤回**：按应用和 tenant/domain 限制范围；记录决策原因、覆盖版本、失败阶段和撤销状态；密钥轮换/配置收紧/代理停用须有确定的生效确认。回滚应恢复已知的兼容版本并保持保护；若暂时无法证明授权链，不得为了恢复可用性而放开绕过入口。

主要威胁包括伪造主体/租户/目标，漏保护的内部路由，代理旁路，陈旧决策重放，owner 与策略服务间 TOCTOU，失陷的业务服务谎报 facts，以及 hook/代理升级造成覆盖漂移。误放行的代价是跨用户或跨租户数据/操作泄露，故未知时 fail-closed；误拒绝主要损害可用性，应该通过可关联原因、对账和重新评估修复，而不是回退到未经证明的许可。

## 6. 当前证据、批准状态与待验证项

已知证据是仓库具有平台独立 SDK contracts/client、Axum `AuthorizationLayer`、显式 actor/facts resolver、精确 public-route 声明和一次性 proof；接入方需在本地事务/CAS 前复核事实，feature 默认关闭。SDK 合同把签名、请求绑定、TTL、限长和超时纳入约束。其边界与验证说明见 [SDK 接入 V1](../../SDK接入V1.md) 和 [SDK V1 实施证据](../../SDK接入V1_实施证据.md)。

该证据只支持“显式 SDK/Axum adapter 已有实现和本地合同测试”。SDK 证据明确未做真实 MySQL/MQ、多节点、生产映射、部署/迁移/切流验收；它不证明任意 sidecar、反向代理或源代码织入已经存在，也不证明业务应用无法绕过自己的 resolver。`Docs/技术能力与储备清单.md` 将通用接管代理/sidecar 和源码注入列为储备。

截至本材料修订，尚无获批的通用强制边界、支持语言/框架矩阵、sidecar 协议、织入插件、部署/切流方案或专项风险接受记录。任何候选进入实施前，仍须由具体宿主 owner 批准资源合同、入口覆盖盘点、信任模型、故障/回滚路径和验收样本；本文的比较为分析，不是设计决策。

## 7. 结论

当前状态为储备/无专项选型。显式 SDK 是已有但需业务改造的候选能力；sidecar/代理和源码织入是待评估路线，均未据现有证据实现通用接管。评审任何方案的首要问题应是“谁能证明 owner/facts 且谁能阻止绕过”，而不是表面上改了多少业务代码。
