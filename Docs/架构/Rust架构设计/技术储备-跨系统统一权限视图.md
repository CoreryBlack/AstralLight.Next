# 跨系统统一权限视图：储备范围与证据边界

> 状态：**规划储备；未找到统一跨业务控制面或跨系统权限视图的当前实现证明。**本文只解释能力边界，不定义新的控制面或聚合数据模型。
>
> 对应：[技术能力与储备清单](../../技术能力与储备清单.md) 原 49；[SDK 接入 V1](../../SDK接入V1.md)；[访问控制总览与调整路线](Rust访问控制总览与调整路线_V1.0.md)。

## 1. 能力含义

“跨系统统一权限视图”需要先确定“统一”的对象：它可以指管理者查看多系统授权状态，也可以指所有系统共享同一个策略决策面，或对多个 source 做可审计的汇总。三种目标的 owner、完整性、延迟和错误语义都不同；现有储备条目没有选择其中哪一种。

本文件采用窄口径解释：这是对多个业务系统中的权限事实或授权状态提供统一、可追溯视图的待定义能力。它不预设把所有 source 合并到一个库，也不表示运行时决策已跨系统统一。

## 2. 当前相关能力和边界

- SDK V1 可让经批准的外部应用向平台请求限定范围的授权决定，但需业务 owner 提供事实 resolver；该 API 不构成跨系统授权管理台或全量权限视图。
- SDK 应用范围和映射是显式、受限且默认关闭的。接入一个应用不证明所有系统均纳入，也不证明各系统的数据可相互比较。
- ORG_SCOPE 表达经治理批准的租户/行政授权扩展，作用域和状态具有明确合同；不能由其推导通用的跨系统权限搜索或资产总览。
- 清单把统一跨业务控制面列为未找到的能力。

## 3. 问题、目标和不可合并的语义

可信统一视图要让被授权的读者理解多个业务系统“目前已知哪些权限事实、来自哪里、覆盖到何处、截至什么版本”，同时不把部分结果伪装成完整结论。至少要区分：管理审计/盘点界面、跨源授权事实查询、以及由一个共同 PDP 对业务请求作出统一运行时决策。这些目标的读路径、时效要求、决策 owner 和失败默认不同，不能从“有一张汇总页面”推导出运行时策略统一。

视图目标可定义为可追溯、按 tenant/source 有明确 coverage、携带来源版本与采集时间、精确保留无法比较/不可读/陈旧/未知状态，并对访问视图本身实施授权。非目标是不经 owner 许可汇总所有系统、不把缺失数据解释为“无权限”、不替源系统决定规则语义，也不让管理型视图直接充当实时 ALLOW 证据。

## 4. 聚合机制候选比较（分析，不是批准方案）

| 候选机制 | 读写方式 | 优点 | 主要取舍和错误模式 |
|---|---|---|---|
| Federation / 在线联邦查询 | 查询时并行或按需访问各 source API，结果保留 source 响应与版本 | 数据较接近 source 当前状态；不需要完整复制全部策略 | 延迟受最慢 source 限制；源服务故障会产生部分结果；授权/分页语义不统一；超时不能当作空集合；聚合请求本身带来下游负载和敏感查询面 |
| Materialized / 持久化读模型 | 经源端变更流/受控轮询同步到单独投影，再提供索引查询 | 适合跨源搜索、历史审计和分页；读延迟可预测 | 最终一致，需处理回填、重复、乱序、删除 tombstone、schema 演进和重放；索引不是源端 current truth；增量停滞必须显式暴露陈旧/未知 |
| Hybrid / 混合视图 | 先读已物化结果，再按需向 source 复核关键记录或显示 freshness 状态 | 平衡常规搜索效率与重要记录的即时复核 | 两类读的时间/失败语义更复杂；复核失败不能悄悄保留旧结果当 current；需明确哪些字段可快照化、哪些必须在线证明 |

候选不是决策；不同业务可以采用不同接入型态，但输出合同应统一表达证据状态，而非强迫底层源系统共享同一存储。尤其要区分“source 明确没有匹配规则”“查询成功但空结果”“source 未接入/该 tenant 不覆盖”“拒绝访问”“请求超时”“版本落后”和“结果无法映射”。只有 source 合同保证完整枚举时，成功空结果才可解释为空集合；其他状态都不能折算成无权限或无记录。

## 5. Coverage、freshness、租户与部分失败合同

每项视图记录至少需要能够表示下列维度（实际字段须由专项 schema 评审确定）：

- **source 身份和 owner**：系统/环境/租户、接口或数据集、采集器版本和负责团队；同一外部 user/resource ID 必须在其 issuer、tenant/domain 和命名空间内解释，不能跨源碰撞。
- **覆盖范围**：已配置的 source/tenant 集合、用户/资源范围、支持的事实类型、分页游标/分区、最近成功覆盖的边界，以及未接入/被授权过滤的范围。报告“3 个 source 有结果”不等于“所有 source 已覆盖”。
- **新鲜度与版本**：各 source revision/ETag/cursor 或等价版本、读取/同步时间、同步启动/完成时间、目标 freshness budget 和观测到的滞后。各源时钟/版本不可比较时分别显示，不合成一个伪全局版本。
- **逐项来源**：每条 grant、deny、membership、关系或条件都保留源记录 identity、原始语义/映射版本、来源 revision、有效期和采集路径。汇总后的规范标签不能抹去 source provenance。
- **访问边界**：视图读取者也需按平台身份、tenant/domain、资源 scope 和字段敏感度授权；错误/理由/个人资料可能比授权结论更敏感。审计导出须绑定查询者、过滤器、coverage 和证据生成点。

聚合结果应允许 per-source 状态，而不是只有整体 HTTP 成功/失败。部分成功可返回明确的 incomplete/UNKNOWN 状态和未完成来源；如果用途要求全量决策，则只要必需 source 不完整，整体就不可用于授权。超时、游标断裂、source 版本回退、快照超出 freshness 上限、映射失败、权限不足及同步 worker 失联均标记相应的未知/陈旧状态；不得以“没有记录”隐藏失败。消费者必须根据用途决定是否展示已知部分，而不能把部分视图转换为通用授权 ALLOW。

租户隔离必须贯穿缓存键、同步 cursor、索引分区、权限过滤、导出与审计；每个 source 的 tenant/domain 映射由其 owner 批准。tenant binding 缺失或不唯一时，该 source 范围为不可判定，不得继承邻近 tenant 的结果。缓存需要 TTL、容量、清理和版本校验；cache hit 只提供读取性能，不单独成为 source 最新或 durable 授权证明。

## 6. 变更、撤销、删除与恢复

物化或混合视图需处理新建/修改/撤销、主体停用、组成员变化、资源转移、自然到期和源端删除。撤销和删除不能只靠“下次全量扫描”；应由源协议提供可靠 change cursor / tombstone / reconciliation 能力，或将其明确列为 freshness 缺口。事件重复可幂等去重；乱序需按可比较 source revision 拒绝陈旧覆盖；事件身份或结果未知时先按 source state 对账再推进投影版本。

worker 崩溃恢复应能从已确认 cursor 重放，并防止旧 worker 在 lease/generation 失效后覆盖新投影。checkpoint 只能在对应批次的数据与 provenance 持久化后推进。源 API、数据库或队列不可用时，不得将未完成同步标记为 fresh。若回填、schema 变化或映射代码升级失败，按 source/tenant 隔离重跑并保留旧索引/审计证据；旧索引若超 freshness 窗口则可供历史说明，不能冒充 current。对 federation，超时/断连/响应截断为 UNKNOWN；对 hybrid，在线复核失败不能无声退回陈旧 materialized value。

安全威胁包括跨租户索引泄漏、越权浏览权限理由、未授权导出、源身份碰撞、陈旧撤销、注入伪 source record、采集凭据失陷、日志/缓存泄露和用 partial data 制造“完整”印象。主要阻断点是 source allowlist/凭据隔离、tenant-aware 查询层、来源/版本校验、审计和默认显式 UNKNOWN。误放行可泄漏敏感权限信息或错误授予业务操作；误拒绝/视图不可用降低运营效率，恢复依赖重新授权查询、完整同步和差异对账，而非旧数据兜底。

## 7. 当前证据、批准状态与验收问题

SDK V1 使经批准应用可请求限定范围的授权决定，但需要业务 owner 提供 resolver facts；它不是跨系统搜索或权限视图。`ORG_SCOPE` 只表达有明确 tenant/行政治理边界的扩展。能力清单将统一跨业务控制面列为未找到的能力。参见 [SDK 接入 V1](../../SDK接入V1.md)、[访问控制总览与调整路线](Rust访问控制总览与调整路线_V1.0.md) 和 [技术能力与储备清单](../../技术能力与储备清单.md)。

当前没有此储备的已批准控制面、通用 schema、source coverage 清单、freshness SLA、联邦协议、物化同步/回放实现或完整视图验收。项目内授权 projection 的 manifest/generation/evidence 合同是单独的授权证据链，不能自动转为跨业务 source index；严格授权读门缺证据时 PENDING/DENY，也不从旧视图或 source fallback 授权。

专项设计前须确定该能力用于只读盘点、审计、策略管理还是在线决策；列明 source/tenant 全量清单和 owner；定义“无匹配/不可读/未覆盖/过期/部分成功/UNKNOWN”；确认身份、资源、动作与理由的可比范围；确定变更传播和 freshness 目标、访问控制、审计、保留周期、回填、故障恢复与导出验收。暂时无法覆盖的 source 应明确显示未覆盖，不得以全局成功状态掩盖。

## 8. 结论

跨系统统一权限视图仍是规划储备。Federation、materialized read model 和 hybrid 都是待比较候选，不存在本材料批准的唯一模式。任何“统一/完整/当前”表述都必须附带 tenant/source coverage、新鲜度和部分失败状态；缺失或 UNKNOWN 不能被解释成无权限，也不能充当授权证明。
