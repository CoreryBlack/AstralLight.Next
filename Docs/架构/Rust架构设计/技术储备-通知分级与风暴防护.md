# 分级通知编排与消息风暴防护：现状、边界与候选架构

> 状态：**已有告警阈值评估、按 rule 的近期触发去重以及有界 WEBHOOK dispatch；没有完整 severity 路由或跨告警聚合风暴抑制闭环。**下面的策略引擎/聚合器均为未批准候选，不是当前实现。
>
> 对应：[技术能力与储备清单](../../技术能力与储备清单.md) 原 43；[统一消息协议与智能层消息规范](../../规范/统一消息协议与智能层消息规范_2026-03-18.md)；[`collector.rs`](../../../astral-monitor/src/collector.rs)、[`dispatch.rs`](../../../astral-monitor/src/dispatch.rs)。

## 1. 技术问题：消息级别字段不等于通知策略

消息协议中的 `kind = notification`、`severity`（`info`、`success`、`warning`、`error`、`critical`）和 trace 字段描述消息内容及关联信息；字段本身不会决定接收人、渠道、优先级、投递时机、合并窗口或重复抑制。

通知编排的难点是将业务事件映射为适当的接收范围和投递策略，并在持续告警、多个规则同时触发、依赖故障或失败重试时限制通知量，同时保留每个事件的可追踪结果。单纯增加消息级别、channel CRUD、队列或请求并发上限，均不能提供完整的 severity routing 与 aggregate storm suppression。

## 2. 当前已有机制：评估、去重、派发和未知结果

### 2.1 告警评估和局部去重

`MonitorService::evaluate_alert_rules(60)` 读取启用规则，在最近 60 秒 metric 窗口内取最新值并比较规则 threshold/condition。若规则 ID 在同一近期窗口已有 `status = 'triggered'` 的告警历史，则抑制这次新触发；否则先写告警历史，再返回本轮新触发项。这里的去重粒度是单条 rule 的近期历史，不是按事件指纹聚合跨规则、跨服务或跨租户的风暴抑制；代码也没有据此建立告警状态聚合/恢复窗口。

### 2.2 Collector 与并发边界

collector 每 30 秒执行探测/告警评估，周期本身不因一次未完成派发而 detached 地无限生成任务；自有 `JoinSet` 将同时活跃的告警 dispatch 任务限制为最多 4 个。shutdown 会有限等待 dispatch drain（5 秒），超时则 abort 并记录待处理结果未知。这个上限约束 collector 内的任务并发，不是按 severity 分配预算、按接收人限速或跨实例的全局容量控制。

### 2.3 WEBHOOK 发送和故障语义

`dispatch_alert` 对每条告警逐一遍历启用的 WEBHOOK 渠道；单个告警内渠道发送是串行的。EMAIL、SMS、DINGTALK、WECHAT 在真实 alert dispatch 中显式模拟/跳过，并非已接通投递。Webhook 通过 HTTP POST 发送，客户端 timeout 为 5 秒，2xx 记为成功；非 2xx、网络错误和配置错误计为失败并写日志/指标，通知失败不会向上传播中断告警评估。告警 history 在派发前已保存，但当前所见路径没有 durable delivery outbox、持久重试队列或 receiver idempotency contract。

需区分“失败”与“结果未知”：连接超时、客户端取消、collector drain 超时或进程中断时，远端可能已收到请求而本地未收到响应；当前 dispatcher 将发送错误记作失败，shutdown 对未完成任务明确记录 outcome unknown，但没有外部幂等键/查询接口证明对方是否处理。因此不能安全地把 timeout 当作“肯定未发送”并盲目自动重发，也不能把本地 2xx 等同于接收方业务已完成。

相关入口：[`service.rs`](../../../astral-monitor/src/service.rs) 的 `evaluate_alert_rules`；[`collector.rs`](../../../astral-monitor/src/collector.rs) 的 bounded JoinSet/drain；[`dispatch.rs`](../../../astral-monitor/src/dispatch.rs) 的 webhook 投递；[`notifications.rs`](../../../astral-monitor/src/notifications.rs) 仅含渠道 CRUD 与测试发送入口。测试 Webhook 会真实尝试 HTTP POST，SMTP/SMS/DingTalk/WeChat 测试明确未投递；本任务未调用渠道。

## 3. 明确缺少的完整能力

- 严重级别目前随 alert/history/payload 与指标传递，也有 history 展示映射；没有证据表明 `critical`、`warning` 等驱动不同接收人、渠道、升级、确认时限或重试预算。
- 按 rule 的近期触发去重只防止该规则短时间重复产出；不同 rule 触发同一根因、多个规则持续触发、不同 collector 实例并发、接收人/租户级速率限制和聚合摘要，均不由这一检查解决。
- bounded dispatch concurrency 是单 collector 进程内的并发护栏；没有证据表明其对多实例、下游全局限流、消息优先级、公平性、持久积压上限或 aggregate suppression 形成闭环。
- 失败活动记录和指标提供有限观测，但不能单独证明投递状态持久可恢复、幂等重试或端到端送达。

## 4. 候选设计路线（未批准）

后续专项设计可评估以下分层，而非直接向 `dispatch_alert` 叠加路由逻辑：

1. **分类与策略决策**：把事件来源、稳定 event/operation ID、tenant/domain、规则/资源指纹和 severity 作为结构化输入；策略在明确 owner 下决定接收范围、渠道、升级条件与限速。展示 severity 与路由 policy 分开版本化，避免把客户端字段当作可信权限事实。
2. **聚合与抑制**：按批准的事件指纹和窗口合并重复/相关通知，维护 first/last seen、计数、已发送摘要和恢复/关闭状态；定义关键级别是否可豁免抑制、计数如何保留以及窗口重置条件。聚合键必须避免跨租户合并，且保留被抑制事件的审计/指标。
3. **Durable dispatch**：候选架构可先持久化业务事件/聚合结果及 outbox，再由有 lease/owner fence 的有限并发 dispatcher 领取，按稳定消息 ID 发送；明确重试预算、隔离队列、确认和人工对账。只有具备 receiver 幂等或查询/补偿合同，才可对未知投递结果重试。
4. **生命周期与恢复**：区分待发送、发送中、成功确认、明确失败、未知、抑制和恢复通知；提供积压上限、超时、重启扫描、审计关联及 operator 对账。各状态名称与具体持久化方案尚未选择。

### 候选取舍

同步投递简单、延迟低，但调用链被慢渠道拖累且结果未知难恢复；durable outbox 提供可恢复的所有权和积压观测，但引入状态、保留、lease、重试和 schema 迁移责任。短窗口去重能降低重复噪音，但过度抑制会隐藏持续/升级故障；聚合需保留计数、严重度升级和恢复语义。多渠道并发提高吞吐但增加下游压力，必须有全局/每渠道预算。窗口长度、阈值、并发数、优先级和 broker/数据库拓扑都未决，不在此文件替系统选择。

## 5. 安全边界、批准与验收

通知不构成审批、授权发布或业务提交 proof；高 severity 不可绕过租户隔离、敏感数据最小化或审计。Webhook URL 和渠道凭据属于外部请求边界：后续设计需要评审目标地址限制、协议与重定向策略、凭据存放/轮换、payload 脱敏以及避免将用户可控输入直接用于服务端网络请求；本文不宣称这些额外策略已经实现。严重级别只能来自受信任的业务规则/事件来源，不应作为用户可任意设置的授权提升信号。

当前**审批/实现/验收**状态：部分告警评估、recent-trigger 去重、channel CRUD、WEBHOOK dispatch、单进程 bounded concurrency、失败指标/活动日志有代码；没有完整 severity routing 或聚合 storm suppression 设计/实现证据。单元/局部行为测试不能证明多实例去重、durable delivery、对端处理或真实外部渠道成功；本文件没有执行任何外部通知或集成验收。

任何后续方案应验收重复事件、跨规则同因聚合、severity 升级与恢复、租户隔离、多个 dispatcher 并发、渠道限流、超时后端已接收/未接收两种对账、进程重启、outbox/审计失败和积压达到预算时的行为；批准前不得宣称通知中心或风暴防护已经交付。
