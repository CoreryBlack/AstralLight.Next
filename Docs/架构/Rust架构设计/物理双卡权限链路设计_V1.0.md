## 一、设计目标与范围

### 1.1 设计目标

| 目标 | 说明 |
|------|------|
| 单一权威链路 | 签发 → 网关 → 服务中间件 → 引擎全程使用同一物理卡对，无第二套判定口径 |
| 签发强制匹配 | login/refresh/switch-card 在签发时刻即强制两条事实线路（身份 + 组织）+ 对应关系证明（两卡同 user_id、与 Token/SessionGrant 一致） |
| fail-closed | 缺失/过期/错配/停用/依赖故障一律拒绝或 PENDING，无 identity-card fallback、无默认 ALLOW |
| 无特权通道 | 禁止特判 superadmin 放行；超管权限仅通过规则集经 PolicyEngine 评估 |
| 可验证 | 每个环节的判定可审计、可测试（单元 + 真实 DB 集成 + 分布式场景） |

### 1.2 范围边界

- **覆盖**：登录签发、refresh、切卡、网关校验、服务中间件、PolicyEngine 评估、投影门禁、审计。
- **不覆盖**：Java 侧实现、前端权限展示、外部策略引擎、SaaS 组织能力扩展。
- **基础设施冻结**：DDL、Redis key 后缀、RabbitMQ 拓扑、对外接口路径不允许本设计擅自变更；确需变更须走专门决策。

## 二、核心概念与不变式

### 2.1 核心概念

| 概念 | 定义 |
|------|------|
| `identity_card` | 身份卡。只确认身份事实/会话锚点（"你是谁"）：user_id、归属、ACTIVE、expires_at、身份卡 ID；**不承担 tenant/domain**。每人一张，随账户存在。 |
| `user_card` | 用户卡。确认授权与组织事实（"你能做什么"）：user_id、ACTIVE、valid_from/valid_until、tenant_id、domain_id、租户/域状态及规则集绑定。每人多张，权限绑定在 user_card 上。 |
| `PlatformUser` | 平台用户。access token 必须携带身份卡 ID（identityCardId）+ user-card 三字段（userCardId/userCardTenantId/userCardDomainId），无 identity tenant/domain。 |
| `AppUser` | 应用用户。access token 只有 identity 上下文（identityCardId），**不得携带 user-card 字段**，只能进入显式允许的 identity-only app 路径。 |
| `ChatScope` | Chat 请求的物理双卡上下文：`user_id + identity_card_id + user_card_id/user_card_tenant_id/user_card_domain_id + principal_kind + token_id`（无 identity tenant/domain）。 |

### 2.2 核心不变式（实现必须全部满足）

1. **两条事实线路分离**：identity_card 只确认身份事实/会话锚点（user_id、归属、ACTIVE、expires_at、身份卡 ID），**不承担 tenant/domain、不提供任何组织范围**；user_card 才确认授权与组织事实（user_id、ACTIVE、valid_from/valid_until、tenant_id、domain_id、租户/域状态及规则集绑定）。identity 与 user_card 的 tenant/domain **互不比较、互相独立**（identity_card 不承担 tenant/domain、无可参与比对的身份侧组织字段），禁止互相校验相等。
2. **对应关系证明（correspondence proof）**：`identity_card.user_id == user_card.user_id == 已认证用户`，且 Token/SessionGrant 与两张物理卡声明一致；证明通过后**才进入** user_card + BASE/OVERLAY rule_set + permission_rule/delegation 的授权评估。
3. **签发即校验**：login/refresh/switch-card 签发任何 access token 前必须通过统一卡资格校验（两条事实线路 + 对应关系证明）；引擎校验是纵深兜底，不是唯一防线。统一校验由 `astral-db::CardEligibilityService::verify_platform_card_pair` 承担（**已实现**，三条签发路径复用；见 §4.1/D1）
4. **无 fallback**：identity 线路永远不能回退/派生 user-card 的组织事实；user-card 缺失永远不能回退到 identity_card。
5. **无特权通道**：任何代码路径禁止检测 superadmin 直接放行；超管仅通过 `__SUPERADMIN__` 规则集经 PolicyEngine 评估。
6. **fail-closed**：缺失/过期/错配/停用/DB 失败/Redis 失败/投影未 READY → DENY 或 PENDING；无默认 ALLOW。
7. **投影门禁（双通道）**：影响卡片有效授权的 source mutation 必须同事务经公共事务 helper `astral-db::append_projection_event_in_tx` 落 CARD + ELIGIBILITY 事件（head/outbox 同事务）；**CARD 通道**重建规则快照 + 完整 CARD 缓存 evict + 发 CARD refresh，**ELIGIBILITY 通道**仅失效资格缓存（`perm:card:active`，不重建规则快照、不发 CARD refresh）；快照重建/缓存失效/刷新发布仅由 durable projector（TrustGraph 单 worker，按 aggregate 分派）在提交后执行。
8. **AppUser 隔离**：AppUser access token 不携带 user-card 上下文，只能进入显式允许的 identity-only app 路径。

## 四、链路设计

### 4.1 签发链路

> 三条签发路径（login / refresh / switch-card）必须共用同一权威卡资格校验（D1），任何一条路径不得另写一套卡校验逻辑。**D1 已实现**：统一 `CardEligibilityService::verify_platform_card_pair`（`astral-db::CardEligibilityService`，`astral-db/src/eligibility.rs`）已被 login / refresh / switch-card 三处签发复用（login `auth_service.rs::login_inner`；refresh / switch `srv/session.rs`）；switch 签发前还补了 user_card tenant/domain ACTIVE 校验。实现见修正记录问题 14。

#### 4.1.1 统一卡资格校验（所有签发路径的前置）

```rust
pub struct PhysicalCardPair {
    pub identity_card_id: i64,
    pub user_card_id: i64,
    pub user_card_tenant_id: i64,
    pub user_card_domain_id: i64,
}

pub async fn verify_platform_card_pair(
    db: &MySqlPool,
    user_id: i64,
    identity_card_id: i64,
    user_card_id: i64,
) -> Result<PhysicalCardPair, CardEligibilityError>
```

单条权威 SQL 必须满足（与引擎 `check_card_active` 同语义）——两条事实线路 + 对应关系证明，identity_card 不再读取/携带 tenant/domain：

```sql
SELECT uc.card_id, uc.tenant_id, uc.domain_id,
       ic.card_id, ic.user_id, ic.status, ic.expires_at,
       t.status, tdm.status
FROM user_card uc
INNER JOIN identity_card ic ON ic.user_id = uc.user_id   -- 对应关系证明：同一 user_id
INNER JOIN platform_user pu ON pu.user_id = uc.user_id
                            AND pu.status = 'ACTIVE' AND pu.deleted_at IS NULL
INNER JOIN tenant t ON t.tenant_id = uc.tenant_id
LEFT JOIN tenant_domain_map tdm ON tdm.tenant_id = uc.tenant_id
                                  AND tdm.domain_id = uc.domain_id
                                  AND tdm.status = 'ACTIVE'
WHERE uc.card_id = ? AND uc.user_id = ? AND uc.card_status = 'ACTIVE'
  AND uc.card_type != 'LEVEL_TEMPLATE_CARD'
  AND (uc.valid_from IS NULL OR uc.valid_from <= UTC_TIMESTAMP())
  AND (uc.valid_until IS NULL OR uc.valid_until >= UTC_TIMESTAMP())
  AND ic.card_id = ? AND ic.user_id = ? AND ic.status = 'ACTIVE'
  AND (ic.expires_at IS NULL OR ic.expires_at >= UTC_TIMESTAMP())
  AND uc.tenant_id IS NOT NULL AND uc.domain_id IS NOT NULL
  AND t.status = 'ACTIVE'
  AND tdm.status = 'ACTIVE'
```

身份线路只校验 identity_card 的归属/状态/过期；组织线路只由 user_card 的 tenant/domain 承担（含 tenant ACTIVE + tenant_domain_map ACTIVE）。**不校验 `ic.tenant_id = uc.tenant_id` 之类的跨卡相等**（identity_card 无组织事实可比对）。

校验通过才允许构造双卡 claims 并签发 access token；任何一步不满足 → 拒绝，不签发。该 SQL 即 `astral-db::CardEligibilityService::verify_platform_card_pair` 的权威查询（`astral-db/src/eligibility.rs::query_card_active_row`，**已实现**）。

#### 4.1.2 login 流程设计（15 步）

| 步骤 | 处理 | 必须的校验 / 输出 |
|------|------|------------------|
| S0 输入拦截 | 检测 OAuth 输入字段（provider/subject/access_token 等） | 任一存在 → `OAUTH_DISABLED`，只接受本地 username/phone/email+password |
| S1 标识解析 | trim username/phone/email | 全缺 → Validation 拒绝；解析顺序 phone→username→email |
| S2 聚合查询 | `find_login_aggregate_resolved()` 一次取 用户+凭证+身份卡 | identity_card 必须 ACTIVE 且 `expires_at` 未过期；未命中返回统一 `Invalid credentials` |
| S3 状态校验 | 用户与身份卡状态 | `user_status != ACTIVE` → 拒；身份卡缺失/非 ACTIVE → `CARD_NOT_FOUND` |
| S4 密码验证 | `verify_password`（Argon2 优先，兼容 BCrypt/占位 hash） | placeholder/NEED_RESET → 拒；`Migrated` → 异步升级 hash |
| S5 last_login_at | 更新 | 失败仅 warning，不阻塞主链 |
| S6 可用卡查询 | `find_login_cards(user_id)` | 过滤 `ACTIVE + 非 LEVEL_TEMPLATE_CARD + valid_from/valid_until 窗口` |
| S7 选卡 | `select_login_card()` | 0 卡→`CARD_NOT_FOUND`；单卡 target 不匹配→拒；多卡必须显式 target，无 target→`CARD_SELECTION_REQUIRED` |
| S8 卡资格校验 | **D1（已实现）**：`verify_platform_card_pair`（`astral-db::CardEligibilityService`） | 身份线路（identity_card 归属/状态/过期）+ user_card 线路（归属/状态/有效期）+ 对应关系证明（两卡同 user_id、与 Token/SessionGrant 一致）+ user_card tenant/domain 有效全部通过 |
| S9 会话/家族 | 创建 `auth_token_family` + `insert_login_session` | 会话绑定 `current_user_card_id`；family_key 为 UUID |
| S10 附加声明 | permissions ← 投影快照；roles ← `derive_roles_from_action_codes`（跳过特权码，空回退 `["USER"]`）；tenantStatus ← **user_card tenant** 的租户状态 | 禁止按 cardType 特判 super_admin |
| S11 签发双 token | `issue_access_token`（identityCardId ← id_card；userCardId/userCardTenantId/userCardDomainId ← user_card）；`issue_refresh_token`（无任何授权上下文） | access/refresh 语义严格分离 |
| S12 持久化 refresh | `update_initial_refresh_token`（仅存 SHA-256） | 失败 → 删除 family 回滚 |
| S13 SessionGrant 写 Redis | `store_session_grant_in_redis`（`access:jti` + `access:grant`） | Redis 失败 → 删 family 回滚（fail-closed） |
| S14 响应 | 返回 identity_card / current_card / available_cards / permissions / roles / session | 供前端切卡与权限初始化 |

#### 4.1.3 refresh 流程设计（10 步）

| 步骤 | 处理 | 必须的校验 / 输出 |
|------|------|------------------|
| R1 解码 | 仅接受 refresh typ；`validated_refresh_claims` | 携带授权上下文 → 拒绝 |
| R2 定位会话 | `load_active_refresh_session(refresh_hash)` | 会话必须 ACTIVE |
| R3 家族校验 | `check_family_valid` | REVOKED → `TOKEN_REUSE_DETECTED` 撤销家族；DB 失败 → 拒 |
| R4 过期检查 | refresh_expires_at | 过期 → 拒 |
| R5 重读身份卡 | JOIN `identity_card` + `platform_user` | 身份卡 ACTIVE + `expires_at` 未过期 + 用户 ACTIVE 未删除 |
| R6 重读用户卡 | 按 `current_user_card_id` 重读 user_card | `ACTIVE + 非 LEVEL_TEMPLATE + 有效期窗口`；不可用 → `CARD_SELECTION_REQUIRED` |
| R7 卡资格校验 | **D1（已实现）**：`verify_platform_card_pair`（`astral-db::CardEligibilityService`） | 同 S8 |
| R8 投影门禁 | `delete_session_projections_before_epoch` | 旧 epoch 的 access:jti/grant 删除 + 写 jwt:revoked |
| R9 CAS 轮换 | `UPDATE auth_device_session ... WHERE refresh_token_hash=旧值` | 影响行=0 → 判复用 → 撤销 family |
| R10 grant 重写 | `store_session_grant_in_redis`（新 jti/epoch/双卡） | 失败 → 撤销 family 回滚 |

#### 4.1.4 switch-card 流程设计（9 步）

| 步骤 | 处理 | 必须的校验 / 输出 |
|------|------|------------------|
| C1 会话定位 | `load_active_refresh_session` + `current_user_card_id == from_card_id` | 切卡基于当前持卡会话 |
| C2 家族/过期 | family ACTIVE + refresh 未过期 | 同 R3/R4 |
| C3 用户重读 | `platform_user` | ACTIVE 且未删除 |
| C4 目标卡候选 | `load_active_switch_cards(user_id)` | `ACTIVE + 非 LEVEL_TEMPLATE + 有效期窗口` |
| C5 目标选取 | target 必须 `card_id + user_id` 匹配 | 归属校验，防切他人卡 |
| C6 身份卡重读 | identity_card | ACTIVE + `expires_at` 未过期 |
| C7 卡资格校验 | **D1（已实现）**：`verify_platform_card_pair(identity_card, target)`（`astral-db::CardEligibilityService`）；switch 签发前补 user_card tenant/domain ACTIVE 校验 | 同 S8；租户域有效性在签发侧强制检查 |
| C8 签发新 access | identity claims 取 identity_card（仅 `identityCardId`，**禁止** `.or(target.*)` 回退）；user-card claims 取 target；refresh_token 原样返回 | 切卡只换授权卡，身份稳定 |
| C9 会话旋转 + grant | CAS 更新 `current_user_card_id`/epoch/版本（失败→`SESSION_VERSION_CONFLICT`）+ 投影门禁 + `store_session_grant_in_redis` | 会话绑定新卡，投影一致 |

### 4.2 运行时请求鉴权链路（9 步）

| 步骤 | 处理 | 必须的校验 / 输出 |
|------|------|------------------|
| ① 清洗伪造头 | 移除 `INTERNAL_AUTH_HEADERS`（Gateway 本地清单，当前 30 项身份头，含 `x-identity-card-id`、`x-user-card-*`、`x-internal-service-*` 等） | 客户端/中间人无法伪造已认证身份 |
| ② 路由凭证策略 | `route_credential_policy(method, path)` | `POST /auth/sessions` 匿名；`/refresh`、`/switch-card` 仅 refresh；`/logout`、`/revoke` 双凭证；未知路径默认 AccessOnly |
| ③ JWT 解码与 claims | 按 typ 分流；验 kid/算法/issuer/audience | PlatformUser：identityCardId + userCardId/userCardTenantId/userCardDomainId 必带为正；AppUser：identityCardId 必带、**不得携带 user-card 字段**；refresh：授权上下文必须全缺 |
| ④ Redis 撤销/投影/grant | `jwt:revoked:{jti}` → `access:jti:{jti}`（标量==sub）→ `access:grant:{jti}` v2 校验 | 任一失败 → 401 或 503；Redis 不可用 → 503 |
| ⑤ 租户状态拦截 | claims.tenantStatus + `tenant:status:{user_card_tenant_id}`（来自 userCardTenantId） | SUSPENDED/TERMINATED → 401；Redis 失败 → 503 |
| ⑥ 身份头注入 | claims → `x-identity-card-id` + `x-user-card-id`/`x-user-card-tenant-id`/`x-user-card-domain-id` + x-token-use/x-principal-kind/x-claims-version/x-template-id/x-perms-ref | AppUser 不注入 user-card 头 |
| ⑦ HMAC 签名转发 | 身份头 + 时间戳 → **HMAC-SHA256 v3**（Rust 仅 v3；canonical 含 method/path/user_id/principal_kind/token_id/identity_card_id/user_card_id/user_card_domain_id/user_card_tenant_id/token_use/claims_version/action_codes/user_roles/timestamp）→ `x-gateway-auth: verified`/`x-gateway-ts`/`x-gateway-signature`/`x-original-path` | 下游验签通过才信任身份头；**v2 不再接受**；Java 旧签名是独立历史契约，不属 Rust v3 |
| ⑧ 服务中间件构建 ctx | `physical_policy_context(headers, resource, action, target_id)`；先按 path_map 解析 `(resource, action)`（`resolve_permission_action`） | PlatformUser：身份卡 ID + user-card 三字段全为正（缺失→403）；AppUser → identity-only ctx；无映射→403 |
| ⑨ 引擎评估 + 审计 | `PolicyEngine.evaluate`（见 4.3）+ `record_permission_audit` + ALLOW 命中 `record_permission_hit` | 审计异步 DB，失败仅 warning，不阻塞决策 |

**下游验签前提**：`x-gateway-auth=verified` 且 HMAC **v3** 签名有效（Rust 仅 v3，v2 拒绝）。Chat 的 `ChatScope::from_headers` 显式校验；其他服务经 gateway_signature 中间件。

### 4.3 PolicyEngine 评估链路

| 阶段 | 处理 | 必须的校验 / 输出 |
|------|------|------------------|
| Step A 前置校验 | ctx 字段存在性 | 缺 user_id → `AUTHN_REQUIRED`；缺 card_id → `CARD_REQUIRED`（AppUser 在此被拒）；缺 resource/action → deny |
| Step B 权威双卡校验 | `check_card_active_cached_with_options` 单条 SQL（委托 `astral-db::CardEligibilityService::check_cached`） | **两条事实线路**：user_card 归属/ACTIVE/有效期 + identity_card 归属/ACTIVE/expires_at；**对应关系证明**：两卡同 user_id、与 ctx 一致；**user_card 组织有效性**：user_card tenant/domain 有效 + tenant ACTIVE + tenant_domain_map ACTIVE。**不做 identity 与 user-card 的 tenant/domain 互相匹配**（identity_card 不承担组织事实）；`Ok(false)`→`CARD_DISABLED`；`Err`→`DEPENDENCY_UNAVAILABLE` |
| 资格缓存 / 投影门禁 | `perm:card:active:{card_id}` **资格缓存**（`projection_type=ELIGIBILITY`）+ **CARD 投影门禁**（`authorization_projection_head` aggregate_type='CARD'） | 资格缓存仅经 ELIGIBILITY head 版本检查（`check_cached` 内），**资格 head 不作为 PolicyEngine CARD gate**。生产 `SqlxRuleRepository` 将缺失 CARD head 映射为 `ready=false`，因此 CARD head 缺失或未 READY → `AUTHORIZATION_PENDING`（见 [`repository.rs`](../../../astral-db/src/repository.rs#L73-L87) 与 [`engine.rs`](../../../policy-engine/src/engine.rs#L332-L350)）。`Ok(None)` 仅来自 policy-engine 的默认/测试 repository，是历史兼容 fixture，不代表生产可放行（见 [`engine.rs`](../../../policy-engine/src/engine.rs#L89-L101)）。ELIGIBILITY head 缺失不改变 CARD gate 语义；资格检查仍按 `check_cached` 的双卡事实校验语义执行，资格缓存命中须上下文/版本匹配。 |
| L1 规则集 | `card_rule_set_ref` → `rule_set_snapshot`（最新版本） | 顺序：OVERLAY DENY → OVERLAY ALLOW → BASE DENY → BASE ALLOW；命中立即返回；加载失败 → `RULE_SET_UNAVAILABLE`（不降级 L2）；全 noMatch → L2 |
| L2 permission_rule | card_id 维度 CARD_ONLY/MANUAL/DELEGATION，`priority DESC, effect DESC` + 时间窗口 | 命中 → allow/deny；加载失败 → 记录 repo_error 继续 L2.5；未命中 → L2.5 |
| L2.5 委托 | `permission_delegation`（delegate_card_id + resource + action + 有效期） | 命中 ALLOW → allow；未命中/失败 → `DEFAULT_DENY` |

**评估顺序总则**：`AUTHN → CARD_CONTEXT/check_card_active → 投影门禁 → OVERLAY DENY → OVERLAY ALLOW → BASE DENY → BASE ALLOW → permission_rule → 委托 → DEFAULT_DENY`；DEFAULT_DENY 永远兜底；规则集是主路径，permission_rule 是卡级特例回退，委托是显式授权补充。`check_card_active` 只校验两条事实线路、对应关系与 user_card 组织有效性，不做身份侧组织比对。

## 五、契约规格

### 5.1 Token claims v2

| 字段 | PlatformUser access | AppUser access | refresh |
|------|--------------------|-----------------|---------|
| `claimsVersion` | 2 | 2 | 2 |
| `tokenUse` | ACCESS | ACCESS | REFRESH |
| `principalKind` | PLATFORM_USER | APP_USER | 同签发时 |
| `identityCardId` | ✅ 必带 >0 | ✅ 必带 >0 | ❌ 全缺 |
| `userCardId` / `userCardTenantId` / `userCardDomainId` | ✅ 必带 >0 | ❌ 全缺 | ❌ |
| `templateId` / `structureNodeId` / `tenantStatus` / `permissions` | 可选 | ❌ | ❌ |
| `sid` / `sessionVersion` / `sessionEpoch` / `familyId` | ✅ | ✅ | ✅ |

> 无 `identityTenantId`/`identityDomainId`：identity_card 不承担组织事实，claims/ctx 只有 identity_card_id + user_card_id/user_card_tenant_id/user_card_domain_id。
> 上表 `templateId`/`structureNodeId`/`tenantStatus`/`permissions` 对 AppUser 标 ❌ 表示**签发态不含**（AppUser 签发时这四个字段均不填充）；当前 `validated_access_claims` 主要强制拒绝 user-card 三字段，未对这四个可选字段逐一拒绝。

| 头 | 来源 | 语义 |
|----|------|------|

### 5.3 Redis key（冻结）

| Key | Value | 用途 |
|-----|-------|------|
| `access:jti:{jti}` | sub 字符串 | 存在性 + 主体绑定 |
| `access:grant:{jti}` | SessionGrant v2 JSON | 版本化会话授权 |
| `jwt:revoked:{jti}` | "1" | 撤销黑名单（TTL 7 天） |
| `tenant:status:{tenant_id}` | 状态 | 租户状态缓存 |

## 六、关键设计决策

### D1 — 签发层统一卡资格校验（已实现）

login / refresh / switch-card 三处签发已收敛到 `astral-db::CardEligibilityService::verify_platform_card_pair`（§4.1.1 单条权威 SQL），消除重复校验与规则漂移；`check_cached`（兼容 wrapper `check_card_active_cached[_with_options]`）供 PolicyEngine / Chat 运行期复用。引擎 `check_card_active` 保持同语义作为运行期兜底。
> **实现状态**：D1 已实现（`astral-db/src/eligibility.rs`，见修正记录问题 14）。login（`auth_service.rs::login_inner`）、refresh / switch（`srv/session.rs`）统一调用 `verify_platform_card_pair`，switch 签发前补 user_card tenant/domain ACTIVE 校验。**资格事件 fan-out（tenant/domain status 变更对 user_card 的影响范围）与 identity_card.expires_at 显式失效链仍待实现**（见修正记录问题 14 未覆盖项），不得写成 ELIGIBILITY 事件已覆盖。

### D2 — 网关 principal 路由守卫（纵深加固）

在 `jwt_auth_middleware` 注入身份头后、转发前，增加集中式判定：AppUser access token 命中平台管理前缀（`/main/`、`/v1/admin/`、`/api/v1/chat/`）→ 提前 403；未命中显式允许前缀（`/v1/app/users/`）的 AppUser 请求 → 默认拒绝。**不改变路径注册**，仅在网关层提前拒绝减少暴露面。

### D3 — 引擎权威校验单点化

`check_card_active` 是运行期权威双卡校验的唯一实现；禁止在业务 service 内绕过该函数直接以查询结果放行。

### D4 — AppUser 隔离

AppUser access token 只携带 identity 上下文；`physical_policy_context` 对 AppUser 返回 identity-only ctx；引擎 `CARD_REQUIRED` 拒绝。Learn app-users handler 层保留 `authenticated_user_id` 同用户校验。

### D5 — fail-closed 依赖语义

| 依赖 | 失败行为 |
|------|---------|
| Redis 撤销/投影检查 | 503 DEPENDENCY_UNAVAILABLE |
| DB `check_card_active` | Err → DENY（计入断路器） |
| L1 规则集快照加载 | Err → DENY，不降级 L2 |
| L2 permission_rule 加载 | Err → 记录 repo_error，继续 L2.5/L3（两表独立聚合，设计语义如此；若业务要求严格 fail-closed 需评审） |
| CARD head 缺失或未 READY | AUTHORIZATION_PENDING |
