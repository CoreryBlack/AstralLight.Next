## 一、背景与目标

### 1.1 背景

Rust 后端已实施**物理双卡分离**并完成第一轮收紧审计，当前语义是**两条事实线路**：

- `identity_card` 只提供**身份/会话事实**（"你是谁"）：ID、user_id、ACTIVE、expires_at；不承担 tenant/domain，不提供任何组织范围；
- `user_card` 提供**授权/组织事实**（"你能做什么"）：ID、user_id、ACTIVE、有效期、tenant_id/domain_id、租户域状态/规则集绑定；每人多张，权限绑定在 user_card 上；
- 中间以同一 `platform_user` 与 Token/SessionGrant 声明对齐完成**对应关系证明（correspondence proof）**；之后才由 `user_card` + `rule_set`/`permission_rule`/`delegation` 承担授权；
- token v2（claims version 2）在 JWT claims 与 Gateway 身份头中**独立携带**身份卡 ID（`identityCardId`）与 user-card 三字段；
- 权限判定唯一入口 `PolicyEngine.evaluate()`，前置 `check_card_active_cached()` 权威物理资格校验（身份事实 + 授权事实 + 对应关系证明）；
- AppUser 只有 identity 上下文，只能进入显式允许的 app-user 路径。

现有设计文档（2026-04/05 两份）均早于双卡分离与规则集共享模式，其中"GLOBAL_ADMIN_BYPASS / 角色层级兜底 / 单卡 X-Card-Id"等描述与当前实现冲突。本设计文档的目的是：

1. **固化**当前双卡权限链路的权威现状（谁在哪个环节校验什么）；
2. **评估**链路各环节的剩余缺口与风险；
3. **设计**目标态链路（在不改 DDL / Redis key / RabbitMQ 拓扑的冻结约束内），并标注必须走基础设施变更的可选决策项。

### 1.2 设计目标

| 目标 | 说明 |
|------|------|
| 单一权威链路 | 签发 → 网关 → 服务中间件 → 引擎 全程使用同一物理卡对，无第二套判定口径 |
| 签发强制校验 | login/refresh/switch-card 在**签发时刻**即通过统一卡资格校验（身份事实 + 授权事实 + 对应关系证明），引擎校验仅作兜底而非唯一防线 |
| fail-closed | 缺失/过期/错配/停用/依赖故障（DB/Redis/投影未 READY）一律拒绝或返回 PENDING，禁止 identity-card fallback、禁止默认 ALLOW |
| 无特权通道 | 禁止 `isSuperAdmin()` 特判放行；超管权限仅通过规则集 → PolicyEngine 评估 |
| 可审计可验证 | 每个环节的判定可审计、可测试（单元 + 真实 DB 集成 + 分布式场景） |

### 1.3 设计约束

- **冻结**：DDL、Redis key 后缀、RabbitMQ exchange/queue/routing/DLX 拓扑、对外接口路径。
- **可改**：Rust 代码内部逻辑、trait 契约、中间件、测试。
- 需要突破冻结约束的设计项（如 Chat 会话 tenant 归属、identity_card 列缺失）单独标注为**可选决策**，不默认实施。

```
      签发侧租户域检查差异已收敛为统一资格校验；剩余缺口见问题 14 未覆盖项

L1 网关层（astral-gateway：jwt_auth_middleware / sanitize_internal_auth_headers /

L2 服务中间件（permission_check_shared::physical_policy_context）

L3 引擎层（policy-engine + astral-db）
   PolicyEngine.evaluate() / evaluate_realtime()
   ├─ AUTHN: user_id/card_id 缺失 → deny
   ├─ `check_card_active_cached_with_options`（权威物理资格校验，所有 ALLOW 前必经；
   │    委托 astral-db::CardEligibilityService::check_cached）
   │     identity_card 身份事实（归属/ACTIVE/expires_at）
   │     + user_card 授权事实（归属/ACTIVE/有效期/tenant/domain 有效）

   ├─ L2.5: permission_delegation（委托）
   └─ DEFAULT_DENY
```

## 三、目标链路设计

### 3.1 核心不变式（所有实现必须满足）

1. **两条事实线路分离**：identity_card 只提供身份/会话事实（ID、user_id、ACTIVE、expires_at），**不承担 tenant/domain、不提供任何组织范围**；user_card 才提供授权/组织事实（ID、user_id、ACTIVE、有效期、tenant_id/domain_id、租户域状态及规则集绑定）。identity 与 user_card 的 tenant/domain 互不比较、互相独立（identity_card 不承担 tenant/domain、无可参与比对的身份侧组织字段），禁止互相校验相等。
2. **同一主体（correspondence proof）**：identity_card 与 user_card 通过同一 `platform_user` 对齐，`identity_card.user_id == user_card.user_id == 已认证用户`，且 Token/SessionGrant 声明与两张物理卡一致；证明通过后**才进入** user_card + rule_set/permission_rule/delegation 的授权评估。
3. **签发即校验**：login/refresh/switch-card 在签发任何 access token 前必须通过统一卡资格校验（两条事实线路 + 对应关系证明，见 §3.3 D1）；引擎校验仅是纵深兜底，不是唯一防线。（已实现：`astral-db::CardEligibilityService::verify_platform_card_pair` 三处复用；switch 签发前已强制 tenant/domain ACTIVE，见 §2.1 / §3.3 D1）
4. **无 fallback**：identity_card 事实永远不能回退为 user-card 授权/组织事实，user-card 缺失永远不能回退到 identity_card。
5. **无特权通道**：任何代码路径禁止检测 superadmin 直接放行；超管仅通过 `__SUPERADMIN__` 规则集经 PolicyEngine 评估。
6. **fail-closed**：缺失/过期/错配/停用/DB 失败/Redis 失败/投影未 READY → DENY 或 PENDING；无默认 ALLOW。
7. **投影门禁（双通道）**：影响卡片有效授权的 source mutation 必须同事务经公共事务 helper `astral-db::append_projection_event_in_tx` 落 CARD + ELIGIBILITY head/outbox；CARD 通道重建规则快照 + 完整 CARD 缓存 evict + 发 CARD refresh，ELIGIBILITY 通道仅失效资格缓存（`perm:card:active`，不重建规则快照、不发 CARD refresh）；均由 durable projector（TrustGraph 单 worker，按 aggregate 分派）在提交后执行。
8. **AppUser 隔离**：AppUser access token 不携带 user-card 上下文，只能进入显式允许的 identity-only app 路径。

### 3.3 关键设计决策

#### D1 — 签发层统一卡资格校验（已实现，收敛项）

**现状（已收敛）**：运行期 `check_card_active_cached` 已权威校验身份卡状态/过期、user_card 状态/有效期/归属、user_card tenant/domain 有效、correspondence proof；签发侧 `astral-db::CardEligibilityService::verify_platform_card_pair`（`astral-db/src/eligibility.rs`）已实现，login（`auth_service.rs::login_inner`）、refresh / switch（`srv/session.rs`）统一复用（修正记录问题 14）。switch-card 签发前通过资格服务补齐了 tenant/domain ACTIVE 与对应关系证明检查（原 `load_active_switch_cards` 仅校验 user_card 自身状态/时间窗的缺口已闭合）。这不是"跨卡 tenant mismatch"缺口——修正后语义为两条事实线路各自有效 + 对应关系证明，不比对身份侧租户。

**设计（已落地）**：`astral-db::CardEligibilityService` 提供单条权威 SQL（`query_card_active_row`），集中实现不变式 1-3：

```rust
pub struct PhysicalCardPair {
    pub identity_card_id: i64,
    pub user_card_id: i64,
    pub user_card_tenant_id: i64,
    pub user_card_domain_id: i64,
}

pub async fn verify_platform_card_pair(
    pool: &MySqlPool,
    request: &PlatformCardPairRequest,   // user_id / identity_card_id / user_card_id
) -> Result<CardEligibility, PolicyError>  // 通过即携带组织事实 + effective_expiry
```

单条 SQL（对齐 `check_card_active_cached` 语义，但查询字段包含完整返回；identity_card 只校验身份事实，user_card 独立承载 tenant/domain；已实现为 `astral-db::CardEligibilityService::query_card_active_row`）：

```sql
SELECT uc.card_id, uc.tenant_id, uc.domain_id, ic.card_id, t.status, tdm.status
FROM user_card uc
INNER JOIN identity_card ic ON ic.user_id = uc.user_id
INNER JOIN platform_user pu ON pu.user_id = uc.user_id
                            AND pu.status = 'ACTIVE' AND pu.deleted_at IS NULL
INNER JOIN tenant t ON t.tenant_id = uc.tenant_id
LEFT JOIN tenant_domain_map tdm ON tdm.tenant_id = uc.tenant_id
                                  AND tdm.domain_id = uc.domain_id
                                  AND tdm.status = 'ACTIVE'
WHERE uc.card_id = ? AND uc.user_id = ? AND uc.card_status = 'ACTIVE'
  AND uc.card_type != 'LEVEL_TEMPLATE_CARD'
  AND (uc.valid_from IS NULL OR uc.valid_from <= UTC_TIMESTAMP())
  AND (uc.valid_until IS NULL OR uc.valid_until >= UTC_TIMESTAMP())
  AND ic.card_id = ? AND ic.user_id = ? AND ic.status = 'ACTIVE'
  AND (ic.expires_at IS NULL OR ic.expires_at >= UTC_TIMESTAMP())
  AND uc.tenant_id IS NOT NULL AND uc.domain_id IS NOT NULL
  AND t.status = 'ACTIVE'
  AND tdm.status = 'ACTIVE'
```

调用方（均已落地）：
- `login_inner`：选卡后调用（`astral-identity/src/srv/auth_service.rs`，已替换分散校验）；
- `refresh_token_from_session`：PlatformUser 分支调用（`astral-identity/src/srv/session.rs`，已替换重读块）；
- `switch_card_once`：目标卡确定后调用（`astral-identity/src/srv/session.rs`，已替换分散校验并补 tenant/domain ACTIVE 校验）。

收益：三处签发路径收敛到同一权威校验，消除规则漂移；引擎 `check_card_active_cached` 保持同语义作为运行期兜底。

**仍待实施（诚实保留）**：资格事件 fan-out——tenant/domain status 变化尚未做可靠的 user_card 影响范围 fan-out（依赖运行期 JOIN，不能写成 ELIGIBILITY 事件已覆盖）；`identity_card.expires_at`/status 没有正式更新入口/独立 source mutation 事件；`user_card.valid_from/valid_until` 没有正式更新 API（现有写入路径为 NULL/读时校验）。详见修正记录问题 14 未覆盖项。

#### D2 — 网关 principal 路由守卫（可选加固，不冻结路径）

**现状**：Gateway 按路径转发，不区分 principal；AppUser 是否可达平台路径完全依赖下游中间件 `CARD_REQUIRED` 拒绝。审计确认**当前无 AppUser 可达平台授权路径**（三服务中间件均拒绝），此设计属于纵深加固而非修复现存漏洞。

**设计**（可选实施）：在 `jwt_auth_middleware` 注入身份头之后、转发之前增加一条集中式判定表（与 `astral-gateway/src/middleware.rs` 的 `route_credential_policy` 并列）：

```rust
/// AppUser access token 允许的前缀（identity-only app 路径）
const APP_USER_ALLOWED_PREFIXES: &[&str] = &["/v1/app/users/"];
/// 显式拒绝的前缀（即使下游已拒绝也提前拒绝，减少暴露面）
const APP_USER_DENIED_PREFIXES: &[&str] = &["/main/", "/v1/admin/", "/api/v1/chat/"];
```

- 命中 DENIED 前缀且 principal_kind=APP_USER → 403 提前拒绝；
- 未命中 ALLOWED 前缀的 AppUser 请求 → 默认拒绝（fail-closed），显式路径列表外不允许。
- **注意**：`/v1/app/learn/**` 与 `/v1/app/users/**` 是否允许 AppUser 取决于业务语义（app-learn 当前也走 PolicyEngine，AppUser 会被拒绝）——设计上保持现状：只有 `/v1/app/users/**` 是 identity-only。

#### D3 — 引擎 `check_card_active_cached` 保持为权威运行期校验

保持现状（2026-08-10 已收紧；2026-08-11 委托资格服务）：单点权威物理资格校验，覆盖身份事实（归属/状态/expires_at）、授权事实（归属/状态/有效期/tenant/domain 有效）、对应关系证明、租户域有效性。实现委托 `astral-db::CardEligibilityService::check_cached`（`astral-db/src/repository.rs::check_card_active_cached[_with_options]`）；ELIGIBILITY head 仅用于资格缓存版本门禁，head 缺失时按缓存 miss 回退权威 SQL，不代表授权放行。CARD 投影门禁由生产 `SqlxRuleRepository` 将缺失 head 映射为 `ready=false`，PolicyEngine 返回 `AUTHORIZATION_PENDING`（见 [`repository.rs`](../../../astral-db/src/repository.rs#L73-L87) 与 [`engine.rs`](../../../policy-engine/src/engine.rs#L332-L350)）。policy-engine 默认/测试 repository 的 `Ok(None)` 仅保留为历史兼容 fixture，不代表生产语义（见 [`engine.rs`](../../../policy-engine/src/engine.rs#L89-L101)）。**禁止**在业务 service 内绕过该函数直接以查询结果放行。

#### D4 — AppUser 隔离

保持现状：AppUser access token claims 中 user-card 三字段全缺；`physical_policy_context` 对 AppUser 返回 identity-only ctx；引擎 `CARD_REQUIRED` 拒绝。Learn app-users handler 层保留 `authenticated_user_id` 同用户校验。

#### D5 — fail-closed 依赖语义（明确边界）

| 依赖 | 失败行为 | 说明 |
|------|---------|------|
| Redis 会话链（jwt:revoked / access:jti / access:grant） | 503 DEPENDENCY_UNAVAILABLE | 已实现 |
| DB `check_card_active_cached` 查询 | Err → DENY（计入断路器） | 已实现 |
| L1 规则集快照加载 | Err → DENY，不降级 L2 | 已实现 |
| L2 permission_rule 加载 | Err → 记录 repo_error，继续 L2.5/L3 | **见 R2** |
| CARD head 缺失或未 READY | AUTHORIZATION_PENDING | 已实现 |

## 四、契约设计（现状固化）

### 4.1 Token claims v2（JwtClaims）

| 字段 | 类型 | PlatformUser access | AppUser access | refresh |
|------|------|--------------------|-----------------|---------|
| `claimsVersion` | i32 | 2 | 2 | 2 |
| `tokenUse` | string | ACCESS | ACCESS | REFRESH |
| `principalKind` | string | PLATFORM_USER | APP_USER | 同签发时 |
| `identityCardId` | i64 | ✅ 必带 >0 | ✅ 必带 >0 | ❌ 全缺 |
| `userCardId` / `userCardTenantId` / `userCardDomainId` | i64 | ✅ 必带 >0 | ❌ 全缺 | ❌ |
| `templateId` / `structureNodeId` / `tenantStatus` / `permissions` | — | 可选 | ❌ | ❌ |
| `sid` / `sessionVersion` / `sessionEpoch` / `familyId` | i64 | ✅ | ✅ | ✅ |

> 注：Rust PlatformUser 不再有 `identityTenantId` / `identityDomainId` claims；tenant/domain 由 user-card 三字段唯一承载（`JwtClaims` 亦无这两个字段）。
> 注：上表 `templateId`/`structureNodeId`/`tenantStatus`/`permissions` 对 AppUser 标 ❌ 表示**签发态不含**（AppUser 签发时这四个字段均不填充）；当前 `validated_access_claims` 主要强制拒绝 user-card 三字段（任一出现 → `APP_USER_CARD_CONTEXT_FORBIDDEN`），未对这四个可选字段逐一拒绝。

校验规则（`validated_access_claims` / `validated_refresh_claims`）：
- PlatformUser：`identityCardId` + user-card 三字段全部必带为正，缺一 → `IDENTITY_CONTEXT_REQUIRED` / `USER_CARD_CONTEXT_REQUIRED` / `*_INVALID`；
- AppUser：user-card 三字段出现任一 → `APP_USER_CARD_CONTEXT_FORBIDDEN`；
- refresh：身份/授权上下文字段出现任一 → `REFRESH_AUTHORIZATION_CONTEXT_FORBIDDEN`。

## 五、残余边界处置方案

### R1 — Chat 会话/群组管理物理 scope（当前冻结）

**现状**：`srv/sessions.rs`、`srv/groups.rs`、`session_service.rs`、`group_service.rs`、`conversation_repository.rs` 以 `user_id` 为主链路；`create_conversation` / `create_group` 仍写 `domain_id = 0`；member 操作按 `(conversation_id, user_id)`。

**冻结期方案（推荐，不改生产逻辑）**：
- 维持现状，将 `domain_id = 0` 的创建入口记录为**已知安全边界**：消息链路（已 scope 化）以 `conversation.domain_id` 约束；会话/群组管理 API 面向平台用户自服务，成员关系以 `user_id` 为自然键，且 Chat 不承载跨租户数据；
- 在 Chat WebSocket 消息路径（已 scope 化）保持 fail-closed，不因管理链路未 scope 化而放宽。

**解冻后迁移设计（R1-M，供解冻时实施）**：
1. `conversation_repository` 新增 scoped 创建：`create_conversation_scoped(name, type, scope)` 写入 `scope.user_card_domain_id`；
2. 所有会话/群组 handler 改 `current_chat_scope(&headers)`；service 方法签名 `user_id` → `&ChatScope`；
3. member 操作改 scoped（`is_member_scoped` / `list_member_scopes` 已存在，扩展 `add_member_scoped` / `remove_member_scoped` / `transfer_owner_scoped`）；
4. 跨 tenant/domain 回归测试（同 user 不同卡拒绝、跨域读取拒绝）；
5. **可选决策（需突破冻结）**：若要证明 conversation 归属 tenant，需新增 `chat_conversation.tenant_id` 列（DDL 变更）——冻结期内不实施，以「user-card tenant 校验 + conversation.domain 隔离」为既有模型。

### R2 — L2 委托路径依赖故障

**现状**：`load_permission_rules`（L2）失败时记录 repo_error 继续 L2.5；若委托 ALLOW 命中则最终 ALLOW，DB 的 L2 依赖故障可被委托遮蔽。

**决策**：**保持现状语义**，理由：
- L2 源表（permission_rule）与 L2.5（permission_delegation）是**不同聚合**的独立读取；L2 失败不代表委托表不可用；
- L1 快照（规则集主路径）失败已 DENY 不降级，规则集未命中的卡才走 L2/L2.5；
- 委托是显式授权的另一种载体，其 ALLOW 在委托表正常时成立。
- **记录**：将「L2 失败 → 依赖 L2.5 独立可用性」写入运行时观测；如未来要求严格 fail-closed，改为 L2 失败即 DENY（行为变更，需业务确认）。

### R3 — arbiter 端点 ctx 复验

**现状**：`astral-trustgraph/api/arbiter.rs` 接受请求体 `ArbitrateRequest.context` 与证据 gate，无双卡复验；路由有 monitor 权限中间件先行。

**设计**：在 handler 内增加双卡复验（低成本，不冻结路径）：
- 用 `physical_policy_context(headers, "monitor", "read", None)` 构建**操作者** ctx；
- 请求体 ctx 仅作为裁决输入证据，不与操作者授权混用；
- 若请求体 ctx 的 `principal_kind == PLATFORM_USER`，校验其双卡字段（身份卡 ID + user-card 三字段）与操作者头一致（或至少为正）。

### R4 — Learn app-users nest APP_USER 放行

**现状**：`astral-learn/middleware.rs` 对 `learn-app-users` + APP_USER 无条件 `return Ok(())`，nest 内所有路径 handler 级做 `authenticated_user_id` 同用户校验。

**设计**：保持（设计内 identity-only 路径），但：
- 在 `LEARN_APP_USER_PATH_MAP` 中显式列出**全部**子路径资源映射（现状为 `*` 兜底），将登录/登出之外每个子路径的资源/动作显式声明，避免"nest 全放行"成为未来新路由的默认宽松；
- 增加一条巡检断言：app-users nest 下任何 handler 必须有同用户校验（代码评审清单项）。

### R5 — Monitor `/actuator/status`

**设计**：保持公开（reachability 非敏感，健康探针需匿名可达）；在 `/actuator/status` 响应中**不返回**任何身份/权限相关字段（现状仅服务状态）。若未来暴露敏感指标，移入权限中间件覆盖路径。

### R6 — baseline DDL 与部署 schema 漂移

**现状**：`astral-db/migrations/.../baseline` 的 `identity_card` 无 `tenant_id/domain_id/expires_at/token_version` 列，代码按 platform_v4 部署 schema 引用。身份事实线路修正后 Rust 不再读 `identity_card.tenant_id/domain_id`，漂移暴露面缩小为 `expires_at`（`check_card_active_cached`、refresh/switch 使用）与 `token_version`；`expires_at` 尚无 source mutation / 独立投影失效链（`aggregate_type='IDENTITY'` projection head 与 outbox/MQ expiry event 均未建立，修正记录问题 14 未覆盖项），外部直接改 `expires_at` 不会触发独立身份投影失效，需在新规范中定义。

**可选决策（需用户批准）**：
- 方案 A（推荐）：核实部署库实际 schema；若与 baseline 漂移，更新 baseline 迁移脚本或补充增量 migration（不重建既有数据）；
- 方案 B：代码增加启动期 schema 自检（`SELECT` 列存在性），漂移时 fail-fast 输出明确错误，避免运行期静默查询失败。
- 冻结期内不自动实施；若部署库确认无这些列，`check_card_active_cached` 与 refresh 查询会直接失败（fail-closed），但会导致权限全部拒绝——**上线前必须核对此项**。

#### B.2 各步骤处理说明

**① 清洗伪造身份头** — 逻辑：把 `INTERNAL_AUTH_HEADERS`（当前 30 项：x-user-id、x-card-id、x-identity-card-id、x-user-card-*、x-token-*、x-gateway-*、x-resource-owner-id、x-user-roles、x-action-codes、x-template-id、x-permissions-truncated、x-perms-ref、x-tenant-status、x-has-required、x-required-permission 等）从入站请求**全部移除**。Java 基线 `JwtGlobalFilter` 的 `INTERNAL_IDENTITY_HEADERS` 曾为 19 项（历史基线，非当前值）。
意义：客户端/中间人无法伪造"已认证身份"（任何直连下游请求不携带这些头即被拒）。**执行位置**：`astral-gateway/src/middleware.rs::sanitize_internal_auth_headers`（最内层，最先执行）。

**② 路由凭证策略** — 逻辑：按 `(method, path)` 查 `route_credential_policy`：`POST /auth/sessions` 匿名；`/auth/sessions/refresh`、`/switch-card` 仅 refresh；`/logout`、`/revoke` access 或 refresh；未知路径默认 AccessOnly。
意义：凭证类型与路由职责绑定，防止 refresh token 被当业务凭证用、防止匿名路径被 access token 污染。**执行位置**：`astral-gateway/src/middleware.rs::route_credential_policy`（Gateway 专属运行时）。

**③ JWT 解码与 claims 校验** — 逻辑：按 `typ`（`astral-access+jwt`/`astral-refresh+jwt`）分流；验 `kid`/算法/issuer/audience；`validated_access_claims`/`validated_refresh_claims` 按上表强制字段存在性与正数（PlatformUser 必带 `identityCardId` + user-card 三字段，无 identity tenant/domain）。
意义：**凭证级 fail-closed**——缺身份/授权字段的 access 或带授权上下文的 refresh 在网关层即拒，不进入下游。**执行位置**：`astral-common/src/middleware/mod.rs::decode_v2_token`（Gateway 与 Identity 共享的 JWT 解码契约，`JwtClaims` 亦在此）。

**④ Redis 会话链（撤销/存在性/grant）** — 逻辑：先查 `jwt:revoked:{jti}` 黑名单；再查 `access:jti:{jti}` 且**标量值必须等于 sub**（OFF 模式同样强制值比对，防"投影残留/改写后仅剩 key"绕过撤销语义）；EMIT/REQUIRE 模式读 `access:grant:{jti}` 校验 v2 grant（principal 一致、身份卡 ID 与 user-card 三字段与 grant 一致、session/family/epoch 匹配、时间窗未过期）。EMIT 模式读取失败 fail-closed、校验结果不阻塞；REQUIRE 模式校验失败 → 401。
意义：Redis 是会话有效性的**安全权威**；`jwt:revoked`、`access:jti`（标量==sub）、`access:grant`（EMIT/REQUIRE 时校验）**全部属于当前链路**，任一环节失败 → 401 或 503，绝不默认放行。**执行位置**：`astral-gateway/src/middleware.rs::jwt_auth_middleware` 主流程。

**⑤ 租户状态拦截** — 逻辑：claims.tenantStatus 为 SUSPENDED/TERMINATED → 401；受保护请求再取 `tenant:status:{user_card_tenant_id}`（**tenant status key 只能取 user_card_tenant_id**），Redis 失败 → 503。
意义：租户级停服必须阻断（fail-closed）。**执行位置**：`astral-gateway/src/middleware.rs::jwt_auth_middleware` Step 5/6。

**⑥ 身份头注入** — 逻辑：把 claims 映射为下游身份头（身份卡 ID + user-card 三字段 + token-use/principal-kind/claims-version/template-id/perms-ref；**不注入 x-identity-tenant-id / x-identity-domain-id**）。AppUser 不注入 user-card 头。
意义：下游只信任经签名验证的身份头；`x-perms-ref`（`user-card:{id}`）供下游核对评估引用。**执行位置**：`astral-gateway/src/middleware.rs::jwt_auth_middleware` Step 4。

**⑦ HMAC 签名转发** — 逻辑：用身份头 + 时间戳计算 **HMAC-SHA256 v3**（canonical 14 段：`method`/`path`/`user_id`/`principal_kind`/`token_id`/`identity_card_id`/`user_card_id`/`user_card_domain_id`/`user_card_tenant_id`/`token_use`/`claims_version`/`action_codes`/`user_roles`/`timestamp`），注入 `x-gateway-auth: verified` / `x-gateway-ts` / `x-gateway-signature` / `x-original-path` 后转发。下游只验 v3，v2 签名拒绝；Java legacy 11 字段 HMAC（含 `x-org-id` 空位占位）是独立历史契约，不与 Rust v3 互通、不宣称兼容。
意义：下游验签通过才信任身份头（防中间人篡改头）。**执行位置**：`astral-gateway/src/proxy.rs`（签名计算/验签函数在 `astral-common/src/middleware/gateway_signature.rs`）。

**⑧ 服务中间件构建 ctx** — 逻辑：`physical_policy_context(headers, resource, action, target_id)`：PlatformUser 要求身份卡 ID + user-card 三字段全为正（缺任一 → 401/403）；AppUser 返回 identity-only ctx；**无 identity→user-card 回退**。
意义：平台授权路径的 ctx 构造唯一入口，杜绝"用身份事实代替授权事实"。前置动作：`check_permission` 先按 path_map 把路径解析为 `(resource, action)`（`resolve_permission_action`），无映射 → 403；OPTIONS 等未知方法放行。**执行位置**：`astral-common/src/middleware/permission_check_shared.rs`（各服务 main.rs 以 `from_fn_with_state` 挂载）。

**⑨ PolicyEngine 评估 + 审计** — 逻辑：AUTHN 缺失 → deny；`check_card_active_cached`（权威物理资格校验，见 B.4）；L1 规则集 → L2 rule → L2.5 委托 → DEFAULT_DENY；CARD head 缺失或未 READY → PENDING；每判定后 `record_permission_audit`（异步 DB，失败仅 warning）+ ALLOW 命中 `record_permission_hit`。
意义：所有 ALLOW 必经物理资格校验 + 规则评估，无旁路；审计可追溯。**执行位置**：`policy-engine/src/engine.rs` + `astral-db/src/repository.rs`。

| S12 持久化 refresh hash | `update_initial_refresh_token`（只存 SHA-256）；失败 → 删除 family 回滚 | refresh 不明文存储；失败回滚防悬挂 | ✅ |
| S13 SessionGrant v2 写 Redis | `store_session_grant_in_redis`：`access:jti` + `access:grant`；Redis 失败 → 删 family 回滚 | 网关会话链（jwt:revoked / access:jti / access:grant）的投影数据；写不进去就不给 token（fail-closed） | ✅ |
| S14 响应 | 返回身份卡与 user-card 信息（identity_card/current_card/available_cards）+ permissions/roles/session | 前端切卡与权限初始化 | ✅ |

#### B.3 refresh 链路各步骤处理说明（`srv/session.rs::refresh_token_from_session`）

| 步骤 | 逻辑（做什么） | 意义（为什么） |
|------|--------------|--------------|
| R1 解码 | 仅接受 refresh typ；`validated_refresh_claims` 拒绝携带授权上下文 | refresh 是会话凭证，不是业务凭证 |
| R2 定位会话 | `load_active_refresh_session(refresh_hash)`：按 refresh token 的 SHA-256 查 `auth_device_session`，状态 ACTIVE | 会话必须真实存在且 ACTIVE |
| R3 家族校验 | `check_family_valid`：family 状态必须 ACTIVE，REVOKED → `TOKEN_REUSE_DETECTED` 撤销整个家族；DB 查询失败 → 拒 | 防重放/防继续使用已吊销会话 |
| R4 过期检查 | refresh_expires_at 已过 → 拒 | 长期凭证过期即失效 |
| R5 重读身份卡 | JOIN `identity_card` + `platform_user`：identity 卡 ACTIVE + `expires_at` 未过期 + 用户 ACTIVE 且未删除 | **重新认证身份**：身份卡停用/过期则 session 不可续期 |
| R6 重读用户卡 | PlatformUser：按 `current_user_card_id` 重读 user_card，`INNER JOIN tenant`/`tenant_domain_map`（均 ACTIVE），过滤 `ACTIVE + 非 LEVEL_TEMPLATE + 有效期窗口`；随后统一走 `CardEligibilityService::verify_platform_card_pair`（D1 已实现）作签发资格权威校验；卡不可用 → `CARD_SELECTION_REQUIRED` | 授权卡必须仍然可授权；被吊销/过期的卡不能续出 access；refresh 侧统一资格校验 |
| R7 签发新 token 对 | access（身份卡 ID + user-card 三字段 claims 重取）+ refresh；`session_epoch+1` | 轮换是新凭证对，旧 access 投影在下述门禁前失效 |
| R8 投影门禁 | `delete_session_projections_before_epoch`（删旧 epoch 的 access:jti/grant + 写 jwt:revoked） | 旧 access 立即失效，防新旧并存 |
| R9 CAS 轮换 | `UPDATE auth_device_session ... WHERE refresh_token_hash=旧值`；影响行=0 → 判 token 复用 → 撤销 family | 并发防重放：只有一个轮换成功 |
| R10 grant 重写 | `store_session_grant_in_redis`（新 jti/epoch/身份卡 ID + user-card 三字段）；失败 → 撤销 family 回滚 | 新 access 必须有投影，否则回滚撤销 |

#### B.3 switch-card 链路各步骤处理说明（`srv/session.rs::switch_card_once`）

| 步骤 | 逻辑（做什么） | 意义（为什么） |
|------|--------------|--------------|
| C1 会话定位 | `load_active_refresh_session` + 校验 `user_id` 与 `current_user_card_id == from_card_id` | 切卡必须基于当前持卡会话 |
| C2 家族/过期 | family ACTIVE + refresh 未过期 | 同 R3/R4 |
| C3 用户重读 | `platform_user` ACTIVE 且未删除 | 停用用户不能切卡 |
| C4 目标卡候选 | `load_active_switch_cards(user_id)`：`ACTIVE + 非 LEVEL_TEMPLATE + 有效期窗口`（2026-08-10 修复）；目标卡确定后统一走 `CardEligibilityService::verify_platform_card_pair` 强制检查 `tenant`/`tenant_domain_map` ACTIVE（D1 已实现） | 已过期/未生效卡不可被切上；租户域有效性在签发侧强制检查（不再由运行期兜底） |
| C5 目标选取 | target 必须 `card_id + user_id` 匹配 | 归属校验，防切他人卡 |
| C6 身份卡重读 | identity_card `ACTIVE + expires_at` 未过期（2026-08-10 修复） | 身份卡停用/过期则切卡拒绝 |
| C7 签发新 access | identity claims 取自 identity_card（无 `.or(target.*)` 回退，2026-08-10 修复）；user-card claims 取自 target；refresh_token **原样返回不轮换** | 切卡只换授权卡，身份稳定，长期凭证保留 |
| C8 会话旋转 | `UPDATE auth_device_session` 更新 `current_user_card_id`/epoch/版本（CAS 失败 → `SESSION_VERSION_CONFLICT`） | 会话绑定到新卡 |
| C9 grant 重写 | 投影门禁 + `store_session_grant_in_redis`（新身份卡 ID + user-card 三字段上下文） | 新 access 的投影与切卡后上下文一致 |

### B.4 PolicyEngine 评估流程（引擎层权威判定）

```text
PolicyEngine.evaluate(ctx)
  │
  ▼
Step A 前置校验（fail-closed）
  ├─ user_id 缺失 → deny AUTHN_REQUIRED
  ├─ card_id 缺失 → deny CARD_REQUIRED        ← AppUser 在此被拒
  └─ resource/action 缺失 → deny
  │
  ▼
Step B check_card_active_cached(ctx)  ← 权威物理资格校验（委托 astral-db::CardEligibilityService::check_cached）
  ├─ identity_card 身份事实：归属本用户 + ACTIVE + expires_at 未过期
  ├─ user_card 授权事实：归属本用户 + ACTIVE + 有效期窗口
  ├─ user-card tenant/domain 各自匹配 ctx
  ├─ 对应关系证明：identity_card_id == ctx.identity_card_id（同 user 对齐，不比对身份侧租户）
  ├─ tenant ACTIVE + tenant_domain_map ACTIVE
  ├─ 资格缓存 perm:card:active:{card_id}（projection_type=ELIGIBILITY + ELIGIBILITY head 版本 +

  │   缺失不构成 CARD 授权门禁的兼容放行）
  ├─ Ok(false) → deny CARD_DISABLED
  └─ Err(DB)   → deny DEPENDENCY_UNAVAILABLE（计入断路器）
  │
  ▼
投影门禁（PolicyEngine CARD gate）
  ├─ authorization_projection_head（aggregate_type='CARD'）缺失或未 READY → AUTHORIZATION_PENDING
  │   （生产 `SqlxRuleRepository` 将缺失 head 映射为 `ready=false`，见
  │    [`repository.rs`](../../../astral-db/src/repository.rs#L73-L87)；
  │    引擎统一返回 PENDING，见 [`engine.rs`](../../../policy-engine/src/engine.rs#L332-L350)）
  └─ `Ok(None)` 仅为默认/测试 repository 的历史兼容 fixture，不代表生产放行
     （见 [`engine.rs`](../../../policy-engine/src/engine.rs#L89-L101)）
  （ELIGIBILITY head 仅约束资格缓存版本，不作为 CARD gate）
  │
  ▼
L1 规则集（主路径）       card_rule_set_ref → rule_set_snapshot
  ├─ OVERLAY DENY → deny RULE_SET_DENY（立即）

  │
  ▼
```

#### B.4 各步骤处理说明

**Step A 前置校验** — 逻辑：ctx 缺少 `user_id` → `AUTHN_REQUIRED`；缺 `card_id` → `CARD_REQUIRED`（**AppUser 在此被拒**，因为 `physical_policy_context` 对 AppUser 置 `card_id=None`）；缺 `resource/action` → deny。
意义：引擎不接受"无主体/无目标"的评估；AppUser 在进入任何规则读取前被拦（fail-closed，非降级）。

**Step B check_card_active_cached（权威物理资格校验）** — 逻辑：委托 `astral-db::CardEligibilityService::check_cached`，单条 SQL 从 `user_card`/`identity_card`/`platform_user`/`tenant`/`tenant_domain_map` 取行，逐项比对：
- user_card 归属本用户 + ACTIVE + 有效期窗口（`valid_from`/`valid_until`）；
- identity_card 归属本用户 + ACTIVE + `expires_at` 未过期（身份事实，不读其 tenant/domain）；
- `identity_card_id == ctx.identity_card_id`（对应关系证明：同一 `platform_user` 对齐）；
- user-card tenant/domain 各自匹配 ctx（**tenant/domain 来源只能是 user_card**，无身份侧租户比对）；
- tenant ACTIVE + `tenant_domain_map` ACTIVE；
- 资格缓存 `perm:card:active:{card_id}`：payload 必须 `projection_type=ELIGIBILITY`，绑定 ELIGIBILITY head 的 source/projected/revoke 版本与物理双卡上下文，命中前须 `matches_context` + 版本匹配 + 读取侧时间未越过自然到期；旧 scalar/旧 JSON 显式 miss 回权威 SQL；
- `require_projection_ready=true`（Chat 短 TTL）时 ELIGIBILITY head 未 READY 直接拒绝；`false`（PolicyEngine 默认）时 head 未 READY 仅导致缓存 miss，不影响权威 SQL 结果；
- `Ok(false)` → `CARD_DISABLED`；`Err(DB)` → `DEPENDENCY_UNAVAILABLE`（计入断路器）。
意义：所有 ALLOW 的**必经门禁**，是运行期最后一道物理资格校验（身份事实 + 授权事实 + 对应关系证明；签发层 D1 统一 service 已落地，二者同语义互为兜底）。执行位置：`astral-db/src/eligibility.rs::CardEligibilityService::check_cached`（`repository.rs::check_card_active_cached` 委托）。

**投影门禁** — 逻辑：PolicyEngine 的 CARD gate 读 `authorization_projection_head`（aggregate_type='CARD', aggregate_id=card_id），生产 `SqlxRuleRepository` 将缺失或未 READY 的 head 映射为 `ready=false`，因此返回 `AUTHORIZATION_PENDING`（不读旧快照；见 [`repository.rs`](../../../astral-db/src/repository.rs#L73-L87) 与 [`engine.rs`](../../../policy-engine/src/engine.rs#L332-L350)）。policy-engine 默认/测试 repository 的 `Ok(None)` 仅为历史兼容 fixture，不代表生产放行（见 [`engine.rs`](../../../policy-engine/src/engine.rs#L89-L101)）。**ELIGIBILITY head 仅约束资格缓存版本，不作为 PolicyEngine CARD gate**；生产默认 `require_projection_ready=false` 时，ELIGIBILITY head 不承担 CARD gate；缺失时不构成 CARD 授权门禁的兼容放行，资格检查仍按 `check_cached` 的双卡事实校验语义执行，最终是否允许仍须通过 CARD gate。

**L1 规则集（主路径）** — 逻辑：`card_rule_set_ref`（BASE/OVERLAY）→ `rule_set_snapshot`（最新版本）。评估顺序：OVERLAY DENY → OVERLAY ALLOW → BASE DENY → BASE ALLOW；任一命中立即返回；加载失败（Err）→ `RULE_SET_UNAVAILABLE` **不降级 L2**；全 noMatch → 回退 L2。读取前有 Redis 缓存 `perm:refs:{card_id}`（携带投影三项版本，版本不匹配按 miss）。
意义：共享规则集是模板级权限主载体，OVERLAY 增量覆盖 BASE（特权卡模型）；快照失败必须 fail-closed（不能因读不到规则就放行）。

**L2 permission_rule 回退** — 逻辑：`card_id` 维度的 CARD_ONLY / MANUAL / DELEGATION 规则，按 `priority DESC, effect DESC` 匹配，含 valid_from/valid_to 时间窗口过滤；命中 → allow/deny；加载失败（Err）→ 记录 repo_error 继续 L2.5；未命中 → L2.5。
意义：规则集未覆盖的卡级特例规则回退路径；**注意 R2**——L2 失败时若 L2.5 委托 ALLOW 命中，最终仍为 ALLOW（两个独立聚合读取，当前设计语义如此，需业务评审是否改严格 fail-closed）。

**L2.5 permission_delegation（委托）** — 逻辑：按 delegate_card_id + resource + action 查 ACTIVE 委托（含有效期窗口），命中 ALLOW → allow；未命中/失败 → `DEFAULT_DENY`。
意义：委托授权是显式授权的另一种载体；**最终兜底永远是 DEFAULT_DENY**（规则集/规则/委托全未命中 → 拒绝）。
