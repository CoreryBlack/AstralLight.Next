1. 接口分层

层接口形态入口认证/授权失败语义
L0 外部 HTTP客户端 → Gateway/api/v1/auth/**、/main/api/v1/**、/api/v1/monitor/**、/v1/chat/**、Learn 前缀Bearer 会话；公共白名单例外401/403；授权未知 → PENDING/DENY
L1 服务 HTTPGateway → Identity / TrustGraph / Monitor服务端口；X-Gateway-* 签名Gateway 签名验证 + 服务内权限中间件验签失败拒绝；策略缺证 → PENDING/DENY
L2 库端口Rust trait / 函数PolicyEngine、astral-db、SDK crate进程内类型与所有权Result 错误；默认实现 fail-closed
L3 消息RabbitMQ / LocalBusastral-mq envelope传输层 + 消费方幂等未 ACK 前必须有 durable proof
L4 运维面metrics / actuator / health独立监听端口或服务路由运维网络边界，非业务授权不进入业务授权链

关键边界：授权发布不经过 RabbitMQ。正式授权证据由 MySQL durable delta → TrustGraph 所属 projector → manifest/current；MQ 承载审计、登录、失效通知等旁路消息。

2. 全局契约

2.1 身份与租户头

外部客户端只应发送 Authorization: Bearer <access-token>；以下头只能由 Gateway 清洗并注入，下游不得信任客户端自带的同名头：

头含义约束
x-user-id已认证用户正整数；缺失 → 401
x-principal-kindPLATFORM_USER / APP_USER缺失或未知 → 401
x-identity-card-id身份卡正整数；缺失 → 401
x-user-card-id有效授权卡PLATFORM_USER 必填；缺失 → 403
x-user-card-tenant-id卡所属租户PLATFORM_USER 必填；缺失 → 403
x-user-card-domain-id卡所属域PLATFORM_USER 必填；缺失 → 403
X-Gateway-Auth网关验签标记必须为 verified
X-Gateway-Ts / X-Gateway-Signature时间戳 / HMAC-SHA256 签名缺失或验签失败 → 拒绝，不回退原始头
x-request-id / X-Trace-Id请求关联审计关联用；不用于身份

APP_USER 只能得到 identity-only 上下文，不得进入需要 user_card 的正式授权路径。

2.2 响应外壳

HTTP handler 使用 astral_common::contract::ApiResponse<T>，JSON 为 camelCase：

{
  "success": true,
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": 1791633600,
  "traceId": "..."
}

可选字段包括 errorType、decision、reasonCode、requiredPermission、requestPath、requestMethod。字段存在性依构造路径而异；调用方不得假定每个响应都含全部可选字段。

2.3 授权决策语义

PolicyEngine.evaluate() 返回 PolicyDecision：

字段含义
allowed仅当完整证据与门禁通过时为 true
reason拒绝/待处理原因
matchedRule / matchedRuleId命中规则
auditRequired是否要求审计
evaluationPath评估阶段轨迹
snapshotVersion快照版本（适用时）
orgProvenanceORG_SCOPE 分支来源（适用时）

正式路径必须同时满足 generation、dependency、READY 与 read-gate。缺证、未知、失败或 stale 只能是 PENDING / DENY；禁止回退 raw source、旧快照或缓存放行。

3.1 Gateway

Gateway 是外部会话准入与转发面，不承载业务授权判定。

接口族路径上游方法与说明
认证转发/api/v1/auth/**Identity显式路由 + any 转发；公共白名单见下

Learn/v1/admin/learn/**、/v1/app/learn/**、/v1/app/users**excluded astral-learn仅前缀转发
运维GET /metrics（默认 127.0.0.1:9100）—独立监听，不在业务 router

会话准入契约

  • 输入：Authorization: Bearer <access-token>；公共白名单之外一律要求有效会话。
  • 数据面：strict MySQL JOIN（auth_session_jti_index × auth_device_session × auth_token_family × user_card × identity_card）；可选有界镜像仅作加速。
  • 多写者独立 Gateway 必须使用 MirrorPolicy::DenyOnly：撤销 marker 可加速 deny，ALLOW 仍每请求 strict DB。
  • 失败：未认证 401；会话/租户/卡上下文不满足 403；依赖不可用 fail-closed。
  • 成功后：清洗客户端伪造内部头，注入 §2.1 身份头，并对下游请求注入 X-Gateway-Auth/Ts/Signature。

输入 PolicyContext 由服务端构造：用户、身份卡、用户卡、租户、域、资源、动作、目标 ID、principal kind。调用方不得用客户端头直接构造可放行上下文。

3.6 AuthorizationProjector（durable worker）

输入表：authorization_delta_event（typed grant delta 队列）。契约步骤：

  1. claim：独立短事务领取事件；稳定 event_id/operation_id + run-scoped lease token；attempts/退避有界。
  2. compile：事务外读取完整 aggregate ledger，按已发布 frontier 分区，复核 claimed DTO ↔ ledger ↔ 依赖哈希，调用 AuthorizationCompiler 增量编译。
  3. publish：单事务内重锁指针/fence/parent，complete impact-plan + complete delta，写 authorization_projection_manifest / authorization_projection_current / authorization_archive_outbox；durable proof 提交后才返回成功。
  4. fail-closed：冲突、哈希漂移、版本不一致 → 退避或 QUARANTINED；lease/CAS 丢失 → UNKNOWN 并停止后续写入；绝不发布、绝不伪造成功。
  5. 边界：不写旧 CARD/RULE_SET 快照表、不消费旧 outbox、不发布旧 refresh MQ。

关键 DB 契约函数：claim_authorization_manifest_in_tx、stage_authorization_manifest_in_tx、publish_current_pointer_in_tx、load_published_card_grant_evidence(_in_tx)。

astral.authorization.invalidation授权失效通知（authorization.invalidation）
astral.notification通知投递

astral.learning.progress、astral.chat.message、astral.business.chat、astral.delivery.ack、astral.read.receipt、astral.question.comment、astral.question.share学习/聊天等旁路（部分属排除应用）

MessageEnvelope 字段：messageId、operationId、messageType、schemaVersion、tenantId?、originRegion、targetRegion?、orderingKey?、traceId?、createdAt、expiresAt?、payloadSha256、payload。

不要把 astral.authorization.invalidation 当作授权发布通道：正式授权证据走 §3.6 的 durable projector；该队列只承载失效通知。

3.9 SDK（消费侧库接口）

接口契约
AstralClient::authorize(&SignedAuthorizationRequest, &AccessToken)校验时间窗/大小 → POST ingress → 解析 ApiResponse<SignedAuthorizationDecision> → 验签/绑定/过期；traceId 必须等于 requestId
AstralClient::consume_allow(decision, request)消费一次性 proof；非 ALLOW/过期 → 错误
AuthorizationLayer::public_route(method, path)声明无需平台授权的宿主路由
AuthorizationLayer::ordinary(...) / special(...)声明需平台授权路由及其 resource/action
AuthorizationLayer::layer(router)在路由装配后应用中间件；未声明路由拒绝；actor/facts 解析失败 fail-closed

AuthorizationRequest 关键字段：appId、keyId、manifestDigest、revision、requestId、nonce（≥128-bit base64url）、timestamp（ms）、sessionTokenId、subject、method、path、action、operationId、facts。AuthorizationDecision 关键字段见 §3.3。

3.10 astral-single-node

它不是新的业务接口，而是组合启动器：在同一进程启动 Gateway / Identity / TrustGraph 的独立 listeners，安装有界 LocalBus / LocalProjectionBus，并以 shutdown/drain barriers 管理生命周期。对外接口仍分别由三个服务的 router 定义；组合启动不改变鉴权或租户边界。

4. 关键接口时序

4.1 外部受保护请求

Client
  → Gateway: Bearer token
  → strict session JOIN (MySQL; optional deny-only mirror)
  → inject x-user/x-card/x-tenant/x-domain + X-Gateway-*
  → Identity or TrustGraph router
  → permission middleware: path→resource, method→action, resolve ownership
  → PolicyEngine.evaluate(ctx, repo)
  → RuleRepository.load_published_card_authorization(scope)
  → READY evidence?  yes → handler; no → PENDING/DENY

4.2 SDK 授权决策

Host app → AuthorizationLayer: declared route + actor/facts
  → AstralClient.authorize(SignedAuthorizationRequest, accessToken)
  → POST /main/api/v1/integrations/authorization-decisions
  → TrustGraph integration service → PolicyEngine → decision
  → SignedAuthorizationDecision (requestDigest/factsDigest/scope/TTL)
  → SDK verify signature + binding + time
  → consume_allow → host handler

4.3 Grant mutation → published evidence

API / source writer
  → short source tx: grant revision/delta + durable head/outbox + audit correlation
  → AuthorizationProjector.claim(event_id, lease)
  → compile outside tx (ledger + frontier + compiler)
  → publish tx: recheck lease/fence/parent; manifest/current/archive outbox
  → strict readers see READY evidence
  → missing/stale → PENDING/DENY (no raw fallback)

5. 接口缺口与设计建议

5.1 当前缺口

缺口影响
仓库没有 OpenAPI / AsyncAPI 机器可读契约客户端与测试只能从源码/文档推断 DTO 与错误
路由参考明确不列 DTO 字段200+ 路径缺少逐接口 schema、必填性、枚举与错误码
权限动作由方法+路径推断新路由若未加特例，可能得到非预期动作；需要注册期检查
Gateway 对 /main、/monitor 使用 any 转发方法支持只能由上游 router 证明
运维面（actuator/metrics）无业务鉴权依赖网络边界；需要部署侧保证
多个能力由配置门控（ORG_SCOPE、SDK integration、Identity mappings、test control）同一路径在不同部署可能不存在
兼容/弃用路径（如 template apply）仍注册需要明确下线日期与替代入口
PolicyDecision 的 reason 尚无统一错误码目录客户端难以稳定区分 PENDING / DENY / 依赖故障

5.2 建议的下一步

  1. 契约优先：按服务生成 OpenAPI 3.1（HTTP）与 AsyncAPI（MQ）；以路由注册 + typed DTO 为源，避免手写漂移。
  2. 逐路由权限元数据：把 resource/action/tenant rule 作为路由声明的一部分，启动期校验每个业务路由都有显式映射，减少对方法推断的依赖。
  3. 错误目录：为 PolicyDecision.reason、AppError、SDK DecisionOutcome 建立稳定 code 表，并区分 PENDING / DENY / 依赖不可用。
  4. 幂等矩阵：为每个 mutation 标注 operationId 来源、幂等键、重复请求语义与对账入口。
  5. 版本与弃用：为兼容路径登记 owner、替代入口、下线日期与回滚方案。
  6. 接口测试：以本文的路径→资源/动作映射生成表驱动测试，覆盖缺证、stale、gate 漂移、租户越界和重放。
