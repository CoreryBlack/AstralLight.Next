# 统一消息协议与智能层消息规范

版本：V1.0
日期：2026-03-18
适用范围：`AstralLight` 全平台前端、后端、网关、审计、通知、智能层接入（OpenClaw / Nanobot / Grok / ChatGPT / 未来自研智能层）。

---

## 1. 目标

1. 统一前后端、网关、通知中心、AI 编排层的数据封装方式。
2. 让“响应”“通知”“事件”“指令”“审计”“流式输出”共享同一套基础字段。
3. 保证 AI 层可以稳定消费业务消息，而不依赖某个具体技术栈或单一接口返回格式。
4. 允许在不破坏既有业务的前提下做增量迁移，兼容旧返回格式。

---

## 2. 设计原则

1. **统一外壳，类型分流**：所有消息共用一个 Envelope，内部用 `kind` / `messageType` 区分用途。
2. **业务载荷与元信息分离**：`payload` 只承载业务数据，`meta` / `trace` / `security` / `ui` / `ai` 承载控制信息。
3. **前后端同构**：Web、App、小程序、后端、AI Agent 都使用同一套字段命名。
4. **兼容优先**：旧接口可以短期保留，但新规范必须是唯一主契约。
5. **可观测优先**：消息必须能还原“谁发的、发给谁、为什么、在哪条链路上、结果如何”。
6. **安全优先**：不得在默认响应中泄露 token、密钥、完整授权串、敏感 prompt 内容。

## 3. HTTP / Gateway 协议剖面

### 3.1 适用边界

本节用于统一 HTTP API、Gateway 下游透传、前端 API 客户端和结构化错误输出。

约束：

1. 对外 HTTP 主契约默认使用 `application/json; charset=UTF-8`。
2. 文件上传场景允许 `multipart/form-data`，但响应仍必须回到统一消息外壳。
3. Gateway 是外部 `Authorization` 的唯一认证入口，下游服务不再信任客户端自带身份头。

### 3.2 外部请求头

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 条件必填 | 外部请求进入 Gateway 的认证凭证。匿名接口可省略。 |
| `X-Trace-Id` | 否 | 调用方自带链路追踪 ID；缺失时由 Gateway 生成。 |
| `X-Client-Id` | 否 | 终端或应用标识。 |
| `X-Idempotency-Key` | 条件必填 | 对创建、重试敏感、异步命令类接口推荐必带。 |
| `Accept-Language` | 否 | 国际化提示或多语言响应。 |

### 3.3 Gateway 到下游的内部头

内部头分三类，常量唯一权威是 `AstralCommonApi` 的 `GatewayIdentityHeaders`（Java）与 `astral-common` 的 `gateway_signature`（Rust）：

| 类别 | Header | 说明 |
| --- | --- | --- |
| 路由标记 | `X-From-Gateway` | Java Gateway 路由 filter 附加的标记；不属于 HMAC 身份头集合，也不参与签名。 |
| 网关签名三元组 | `X-Gateway-Auth`、`X-Gateway-Ts`、`X-Gateway-Signature` | HMAC-SHA256 签名；时间戳头是 `X-Gateway-Ts`（不存在 `X-Gateway-Timestamp`），默认允许 30s 时钟偏移。 |
| 可信身份/权限头 | `X-User-Id`、`X-Token-Id`、`X-Token-Use`、`X-User-Roles`、`X-Action-Codes`、`X-Card-Id`、`X-Template-Id`、`X-Domain-Id`、`X-Tenant-Id`、`X-Has-Required`、`X-Required-Permission`、`X-Perms-Ref`、`X-Permissions-Truncated` | 只能由 Gateway 完成 JWT/会话校验后写入。 |
| 追踪上下文 | `X-Request-Id`（可选） | 下游/调用方的追踪输入，不是 Gateway 签发的身份头，不计入网关签名口径。 |

规则：

1. 可信身份头只能由 Gateway 写入；下游必须先验签，再信任身份字段。
2. 只要带了网关元数据但验签失败，就必须直接拒绝，不允许静默回退到原始头或伪造头。
3. `X-Org-Id` 已废弃（2026-05-12 起 Gateway 不再发送，签名规范载荷中该位传空串），组织维度使用 `X-Tenant-Id`。Rust 链路使用 `X-Identity-Card-Id`、`X-User-Card-Id`、`X-User-Card-Tenant-Id`、`X-User-Card-Domain-Id` 等双卡身份头。
4. JWT / 权限回退只能作为显式灰度开关，不得作为默认主链路。

### 3.4 响应头

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Content-Type` | 是 | JSON 响应固定为 `application/json; charset=UTF-8`。 |
| `X-Trace-Id` | 是 | 与响应体中的 `traceId` 保持一致。 |
| `Deprecation` | 条件必填 | 旧接口进入兼容窗口后必须补充。 |
| `Sunset` | 条件必填 | 旧接口计划下线时间。 |
| `Link` | 条件必填 | 指向替代接口文档或主路径。 |

## 4. 通用消息外壳

建议统一使用以下顶层结构（这是目标契约；当前 Java runtime 的 HTTP 过渡外壳是 12 字段 `ApiResponse<T>`（含 `operationId`），Rust runtime 有对应 `ApiResponse` 结构，两侧均未完整实现本节全部 Envelope 字段——不得把本节写成所有 runtime 已支持的实现事实）：

```json
{
  "schemaVersion": "1.0",
  "messageId": "msg_01J...",
  "parentMessageId": "msg_01H...",
  "conversationId": "conv_01J...",
  "traceId": "trace_01J...",
  "spanId": "span_01J...",
  "timestamp": "2026-03-18T17:54:00.123+08:00",
  "source": {
    "system": "astral-learn",
    "module": "questions-controller",
    "instanceId": "learn-1"
  },
  "target": {
    "system": "astral-web",
    "channel": "ui"
  },
  "kind": "response",
  "messageType": "error",
  "severity": "warning",
  "status": "failed",
  "code": 403,
  "title": "无权访问该资源",
  "summary": "当前账号缺少所需权限",
  "payload": {},
  "meta": {},
  "security": {},
  "ui": {},
  "ai": {},
  "audit": {},
  "extensions": {}
}
```

### 4.1 顶层字段约定

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `schemaVersion` | string | 是 | 消息协议版本，建议 `1.0` 起步。 |
| `messageId` | string | 是 | 全局唯一消息 ID。 |
| `parentMessageId` | string | 否 | 父消息 ID，用于回复、链式事件、工具调用。 |
| `conversationId` | string | 否 | 会话 ID，用于多轮交互、工单、对话。 |
| `traceId` | string | 是 | 链路追踪 ID，贯穿网关、服务、前端日志。 |
| `spanId` | string | 否 | 单节点调用片段 ID。 |
| `timestamp` | string | 是 | ISO-8601 时间戳。 |
| `source` | object | 是 | 消息来源系统信息。 |
| `target` | object | 否 | 消息目标系统或通道。 |
| `kind` | string | 是 | 消息大类：`response` / `notification` / `event` / `command` / `prompt` / `tool_call` / `tool_result` / `audit` / `stream`。 |
| `messageType` | string | 是 | 同类内子类型，例如 `success`、`error`、`info`、`warning`、`question`、`decision`。 |
| `severity` | string | 否 | `info` / `success` / `warning` / `error` / `critical`。 |
| `status` | string | 是 | `success` / `failed` / `pending` / `partial` / `cancelled`。 |
| `code` | number | 是 | 业务状态码。HTTP 场景可与 HTTP 状态一致。 |
| `title` | string | 否 | 简短标题。 |
| `summary` | string | 否 | 面向人看的简要说明。 |
| `payload` | object/array/null | 否 | 业务数据正文。 |
| `meta` | object | 否 | 路径、环境、客户端、分页、扩展元数据。 |
| `security` | object | 否 | 权限、鉴权、敏感级别、脱敏策略。 |
| `ui` | object | 否 | 前端展示提示。 |
| `ai` | object | 否 | AI 编排/推理/工具调用提示。 |
| `audit` | object | 否 | 审计字段。 |
| `extensions` | object | 否 | 业务自定义扩展，必须命名空间化。 |

### 4.2 HTTP 过渡外壳规则

当前 Java 服务仍广泛使用 `ApiResponse<T>`，其中业务数据字段名为 `data`；统一消息外壳长期语义字段为 `payload`。

过渡口径：

1. Java 侧当前允许继续返回 `data`，由前端 API 层或统一解析器映射为 `payload` 语义。
2. 新增 DTO、TypeScript 类型、AI 层协议描述统一使用 `payload` 命名。
3. 401/403 与关键写接口的结构化响应必须同时带 `traceId`、`requestPath`、`requestMethod`、`errorType`、`decision`。
4. 未来如统一到新外壳，可将 `data` 改为 `payload`，但必须通过兼容层平滑升级。

## 5. 统一消息分类

### 5.1 ResponseMessage

用于 API 调用返回、页面表单提交、命令执行结果。

推荐字段：

- `kind = "response"`
- `messageType = "success" | "error"`
- `code` 使用业务状态码，HTTP 场景优先与 HTTP 状态一致。
- `payload` 放结果数据。
- `ui.action` 可选，告诉前端是否弹窗、跳转、刷新。

### 5.2 NotificationMessage

用于站内通知、系统提示、通知栏、推送、邮件、短信的统一抽象。

推荐字段：

- `kind = "notification"`
- `messageType = "info" | "warning" | "error" | "success"`
- `ui.channel` 可为 `toast` / `banner` / `dialog` / `drawer` / `push` / `mail` / `sms`
- `ui.priority` 可为 `low` / `normal` / `high` / `urgent`

### 5.3 EventMessage

用于领域事件、审计事件、状态变更、异步编排事件。

推荐字段：

- `kind = "event"`
- `messageType = "created" | "updated" | "deleted" | "state_changed" | "audit"`
- `payload` 放事件主体。
- `meta.aggregateType`、`meta.aggregateId`、`meta.version` 建议必带。

### 5.4 CommandMessage

用于前端/AI 对后端发起动作请求，适合“创建任务”“执行审批”“切卡”“生成报告”。

推荐字段：

- `kind = "command"`
- `messageType = "execute" | "create" | "update" | "delete" | "approve" | "reject"`
- `meta.idempotencyKey` 建议必带。

### 5.5 PromptMessage

用于 AI 输入消息，承载人类意图、上下文和约束。

推荐字段：

- `kind = "prompt"`
- `messageType = "user" | "system" | "developer" | "policy"`
- `ai.intent`、`ai.constraints`、`ai.tone`、`ai.outputSchema` 建议可用。

### 5.6 ToolCallMessage / ToolResultMessage

用于 OpenClaw、Nanobot、Grok、ChatGPT、未来自研智能层的工具调用与回传。

推荐字段：

- `kind = "tool_call"`
- `messageType = "invoke"`
- `ai.toolName`
- `ai.arguments`
- `ai.expectedOutput`
- `ai.timeoutMs`

回传：

- `kind = "tool_result"`
- `messageType = "success" | "error"`
- `ai.toolName`
- `ai.result`
- `ai.error`

### 5.7 AuditMessage

用于权限拒绝、数据越权、关键写操作、AI 决策留痕。

推荐字段：

- `kind = "audit"`
- `messageType = "decision" | "access_denied" | "data_scope_denied" | "action_taken"`
- `audit.actorId`、`audit.subjectId`、`audit.resource`、`audit.decisionPath`、`audit.reasonCode`

### 5.8 StreamMessage

用于 SSE / WebSocket / 流式 AI 输出。

推荐字段：

- `kind = "stream"`
- `messageType = "delta" | "chunk" | "done" | "error"`
- `payload.delta`、`payload.chunkIndex`、`payload.isFinal`

## 6. 统一状态码与语义

### 6.1 建议主码段

| code 范围 | 语义 | 典型场景 |
| --- | --- | --- |
| 200-299 | 成功 | 查询、提交、执行完成 |
| 400-499 | 客户端/权限/鉴权问题 | 参数错误、未认证、无权限、资源不存在 |
| 500-599 | 服务端错误 | 未捕获异常、依赖失败、超时 |
| 600-699 | 业务拒绝/流程拒绝 | 业务校验失败、状态不允许 |
| 700-799 | AI 编排失败 | 工具调用失败、上下文不足、策略拒绝 |

### 6.2 401/403 统一语义

#### 401 未认证

- `messageType = "error"`
- `errorType = "UNAUTHORIZED"`
- `decision = "AUTHENTICATION_REQUIRED"`
- 典型原因：缺少 token、token 失效、网关签名不合法、会话过期。

#### 403 无权限

- `messageType = "error"`
- `errorType = "FORBIDDEN"`
- `decision = "ACCESS_DENIED"`
- 典型原因：权限不足、资源域不匹配、角色不满足、策略拒绝。

## 7. 前端展示映射

前端统一按照 `kind` 和 `messageType` 渲染，而不是直接依赖 HTTP 状态。

### 7.1 推荐映射

| kind | messageType | UI 渲染 |
| --- | --- | --- |
| response | success | 成功提示、刷新页面、关闭弹窗 |
| response | error | 错误提示、表单字段标红、保留现场 |
| notification | info | toast / banner |
| notification | warning | warning toast / dialog |
| notification | error | 高优先级弹窗 / 红色横幅 |
| event | state_changed | 刷新局部状态 |
| audit | access_denied | 403 页面、审计入口、traceId 展示 |
| stream | delta | 流式追加显示 |

### 7.2 前端必须保留的字段

前端至少要能读取：

- `code`
- `message`
- `traceId`
- `requestPath`
- `decision`
- `requiredPermission`（若存在）
- `reasonCode`（若存在）
- `severity`

## 8. 后端落地映射

### 8.1 API 层

- 所有控制器返回值都必须可以包装进统一 Envelope。
- 业务成功场景可继续返回原对象，但响应拦截器应补齐 Envelope。
- 401/403 必须统一走结构化响应。
- 所有新接口必须至少输出：`code`、`message`、`data/payload`、`timestamp`。
- 所有错误响应必须至少输出：`traceId`、`requestPath`、`requestMethod`、`errorType`、`decision`。

### 8.2 网关层

- 网关负责首层 401/403 判定。
- 网关响应必须携带 `traceId`、`decision`、`errorType`、`requestPath`。
- 网关可附带 `requiredPermission`、`hasRequired`、`gatewayVerified`。
- 网关必须清洗客户端伪造的内部身份头，再附加自己的签名身份头。

### 8.3 业务服务层

- 业务服务只抛语义异常，不自己拼装多套错误 JSON。
- `ResponseStatusException`、`AccessDeniedException`、`IllegalArgumentException` 等统一由全局处理器映射。

### 8.4 审计层

- 权限拒绝、关键写操作、AI 决策必须同时记录 `audit` 消息。
- 审计消息与响应消息可以共享同一 `traceId` 和 `conversationId`。

---

## 9. 字段命名与兼容规则

1. JSON 字段统一使用 `camelCase`。
2. URL 路径段统一使用 `kebab-case`，不得把 `camelCase` 路径段继续扩散到新接口。
3. 时间统一使用 ISO-8601。
4. 业务枚举值统一使用全大写下划线或协议中明确列出的固定字符串，不允许同义枚举并存。
5. 旧字段兼容只能存在于 API 适配层、Gateway 适配层或统一解析器中，不允许在业务页面和业务服务里散落判断。

## 10. AI 层接入约定

### 10.1 统一输入

AI 编排层接收到的每个输入都应被包装为 `PromptMessage` 或 `CommandMessage`。

建议至少包含：

- `conversationId`
- `traceId`
- `source.system`
- `kind`
- `messageType`
- `payload.text` 或 `payload.task`
- `ai.intent`
- `ai.constraints`
- `security.classification`
- `audit.context`

### 10.2 统一输出

AI 输出必须包裹为：

- `response`：直接回答用户或系统
- `tool_call`：请求执行工具
- `notification`：给前端/用户推送提示
- `audit`：记录 AI 决策依据

### 10.3 工具调用规范

工具调用必须幂等、可审计、可回放。

建议字段：

- `ai.toolName`
- `ai.arguments`
- `meta.idempotencyKey`
- `audit.decisionPath`
- `audit.policyVersion`

### 10.4 面向 OpenClaw / Nanobot / Grok / ChatGPT / 自研层的兼容原则

1. 允许不同模型实现不同推理方式。
2. 不允许不同模型使用不同的消息外壳。
3. 工具调用结果必须回写统一结构。
4. 模型输出必须能被前端和后端统一解析。

```json
    "policyVersion": "2026.03"
  }
}
```

---

## 12. 前端实现建议

1. Web 端建立统一 `message parser`，把 API、通知、事件、AI 输出都转为同一类型。
2. `toast`、`dialog`、`banner`、`drawer` 用 `ui.channel` 驱动，不在业务页面硬编码。
3. 401 统一跳转登录页，403 统一进入“无权限/申请权限/返回”页，且显示 `traceId`。
4. 组件和 store 之间只传统一 Envelope 或其 `payload`，避免多个散落状态字段。

## 13. 迁移策略

### 13.1 第一阶段

- 新接口使用统一 Envelope。
- 旧接口继续兼容，前端在 API 层做兼容解包。
- 旧 `data` 字段与统一 `payload` 语义在 API 层完成对齐。

### 13.2 第二阶段

- 所有 401/403、通知、AI 工具结果统一升级。
- 前端切换到统一 parser。

### 13.3 第三阶段

- 清理老格式分支。
- 将统一消息协议固化为 CI 规则与接口契约测试。
