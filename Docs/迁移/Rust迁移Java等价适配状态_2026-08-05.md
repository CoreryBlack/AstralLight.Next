## 1B. 2026-08-06 四链复审修复批次（第二轮）

> 边界约束不变：不执行 DDL、不新建 crate、不改变 Redis key / RabbitMQ 拓扑 / `audit_log` owner。

### 授权链（高）

1. **L2 快照 exact-first（P0/P1，越权风险）**：`permission_rule_snapshot` 按 `resource_key` 字典序装载，
   `learn_subject:*` 排在 `learn_subject:42` 之前，具体对象 DENY 可被类型级 ALLOW 按行序遮蔽。
   对齐 Java `findSnapshot`（按精确 resource_key selectOne）语义，新增两段式
   `try_match_rules_exact_first`：先精确 pass（仅完全一致的 resource_key），再通配 pass
   （类型级/`*`）；类型级请求不命中具体对象规则。正式路径 L2/L2.5 与 realtime L2/L2.5 全部切换；
   删除按行序 first-match 的旧 `try_match_rules` / `scan_rules_reverse` / `resource_action_matches_rule`。
   新增 3 项单测：对象 DENY 胜类型 ALLOW、对象 ALLOW 胜类型 DENY、类型请求不命中对象规则。
2. **L1 慢路径源表回退收紧（中）**：Java `checkRuleSetEffect` 只读 `rule_set_snapshot`；Rust 慢速路径
   （`load_rule_set_snapshots` 直读 `rule_set_entry` 源表）缺少快照编译期 runtime-condition 排除与窗口语义，
   投影托管卡（head READY）读源表会宽松化。`evaluate_rule_sets` 新增 `projection_legacy` 参数：
   仅无 head 的 legacy 卡允许源表兜底扫描；head 已托管的卡只走快照胜者（快速路径）。一致性巡检与
   realtime 路径仍用 `load_rule_set_entries_raw`（原始比对语义，不受影响）。
3. **投影复检失败计入断路器（中）**：`projection_still_valid` 返回三态 `ProjectionCheck`
   （Valid/Stale/Error），gate 读取失败（Error）在 L1/L2/L2.5 三个 ALLOW 复检点置位 `repo_had_error`，
   不再被 L3 success 清零（对齐 Java Resilience4j 仓库异常计失败）。

### Gateway / SoD 链（高）

4. **x-resource-owner-id 清洗回归修复（高）**：上一批把 `x-resource-owner-id` 加入网关清洗清单与
   转发跳过列表，导致 5 个服务中间件（identity/learn/chat/monitor/trustgraph）读取该头恒为 None，

   移除，恢复透传；与 Java `SodService` 读裸请求头行为一致，未签名属已知限制（复审记录在案）。
5. **监听地址 env 覆盖**：gateway `0.0.0.0:9001` / identity `0.0.0.0:9004` 支持 `LISTEN_ADDR` 覆盖。
6. **chat/identity URI fallback 告警**：`http://localhost:9003/9004` 兜底不再静默，
   未配置时输出 warning；gateway HTTP 与 WS 的 chat URI 解析收敛为同一入口（env 优先、config 兜底）。

### 认证链（中）

## 1C. 2026-08-06 四链复审修复批次（第三轮）

> 依据 4 个探索代理对认证/Gateway/PolicyEngine/TrustGraph 治理链的第三轮复审报告，逐项验证后修复。
> 边界约束不变：不执行 DDL、不新建 crate、不改变 Redis key / RabbitMQ 拓扑 / `audit_log` owner。

### 权限治理链（高）

1. **委托更新 bind 数不匹配（P0，运行时必崩）**：`delegation_repository.update_with_rule` 对
   `DELEGATION_RULE_INSERT`（6 个占位符）只 bind 5 个值，缺 `tenant_id` 且顺序错位 ——
   PUT /delegations/{id} 运行时必然报 bind 数不匹配，委托更新功能不可用。修复为与
   `create_with_rule` 一致：事务内从被委托卡读 `tenant_id`，按
   `card_id, tenant_id, resource_type, action_code, source_id, valid_to` 补齐 6 个 bind。
2. **审批 requester 身份可伪造（中高）**：`approval.create_request` 的 `requester_id` 取自
   body 而非已验证 `x-user-id`，可伪造他人身份提交 permission_request。改为与 approve/reject
   的 reviewer_id 一致：从已验证 `x-user-id` 头取，忽略 body 值。
3. **委托 revoke/update 缺 ACTIVE 守卫（中）**：对已 REVOKED 委托再次 update 会删旧插新
   DELEGATION ALLOW 规则（权限复活）；重复 revoke 会重复追加 REVOKE 事件（fence 额外递增）。
   两条路径均加 `WHERE status='ACTIVE'` 守卫；update 命中 0 行时直接提交返回 no-op。
4. **rebuild-snapshot 端点绕过 durable 链（中）**：`POST /permission-rules/card/{id}/rebuild-snapshot`
   直接同步 rebuild+evict+publish，MQ 消息无 generation/fence。对齐 Java
   `PermissionRuleController.rebuildSnapshot`（只调 `requestCardProjection("CARD_REBUILD")`），
   改为落 durable 投影事件，由 worker 统一重建/evict/MQ。
5. **rule_set unbind 校验过严（中）**：unbind 复用 `validate_card_binding_in_tx` 要求规则集
   enabled=1，对已禁用规则集解绑误报 NotFound。解绑只要求卡 ACTIVE（解除关系与规则集
   启用状态无关）。

### 授权链（高）

6. **condition_json Java 顶层键格式不兼容（高）**：Java 权威基线（`ConditionEvaluator`）以
   顶层键存储条件（`{"timeRange":{...}}` / `{"ownerOnly":true}` /
   `{"conditionGroup":{"allOf":[...]}}`），Rust 只认 `{"conditionType":...,"params":{...}}`，
   共享库中 Java 写入的条件规则在 Rust L2 全部解析失败 → 恒 DENY。新增
   `normalize_condition_json` 归一化层（condition.rs），`evaluate_entry_condition_raw` 与
   `has_runtime_condition` 统一接入；覆盖 timeRange/ipRange/rateLimit/deviceType/
   resourceProperty/ownerOnly/belongsToTenant/scope/conditionGroup(allOf/anyOf/not)。
   新增 8 项单测。
7. **TimeRange 分钟精度与跨午夜（中）**：原实现只取小时（`start[..2]`），`22:00-02:00` 恒 false。
   对齐 Java `isInTimeRange`：解析完整 `HH:mm` 分钟比较，start>end 时按回绕（now>=start || now<=end）。
8. **IpRange 不支持 CIDR（中）**：对齐 Java `ipMatchesCidr`，增加 `1.2.3.0/24` 掩码匹配；
   非法输入 fail-closed。
9. **投影 gate 初始读取失败不计断路器（中高）**：gate 读取 Err 分支 `repo_had_error` 恒为
   false（无先于门禁的仓库调用），`record_failure_on_evaluate` 不可达，实际恒走 success 清零
   失败计数 —— `authorization_projection_head` 故障打不开断路器。改为 gate 读取失败直接
   `record_failure_on_evaluate`。

### Gateway / 认证链（中）

10. **App 登录端点被 JWT 拦截（高）**：`/v1/app/users/login`（learn app_users 登录）未列入
    公开路径，无 Bearer 请求被 401。对齐 Java public-paths 补齐 `/v1/app/users/login`、
    `/duo/v1/app/users/login`、`/api/health`、`/api/health/**`。
11. **WS 签名用 rewrite 后内部路径（中）**：`forward_chat_ws` 对 `/v1/app/chat/ws/{*path}`
    路由用内部路径 `/api/v1/chat/ws/...` 签名并写入 X-Original-Path，违反「外部 canonical
    path 在 rewrite 前签名」不变式。改为用 `original_uri.path()` 外部路径签名（与 HTTP
    forward 一致），上游 URL 仍用内部路径。
12. **缺 `/ws/{*path}` 路由（中）**：Java chat-websocket 基线路由为 `Path=/ws/**`，Rust 网关
    未注册，前端按 Java 基线连接 404。补 `/ws/{*path}` → forward_chat_ws。
13. **登录/切卡/默认卡未排除 LEVEL_TEMPLATE_CARD（中）**：Java `loadAvailableCards`（登录、
    切卡、列表、resolveCardForUser 共用）过滤 `card_type != 'LEVEL_TEMPLATE_CARD'`，Rust 三处
    （find_login_cards / load_active_switch_cards / me find_active_cards + 默认卡解析 + refresh
    卡校验）补齐同过滤。
14. **PUT /users/{id} 状态变更不撤销会话（高）**：`update_user` 透传 `status` 直接写库不撤销，
    对齐 Java `PlatformUserLifecycleServiceImpl.update()`（DISABLED 时 `revokeAllForUser`）。
    非 ACTIVE 状态时先撤销全部会话（与 update_user_status 一致，先撤后写 fail-closed）。

### 低风险项（P3）

15. **accept_invitation 并发守卫**：UPDATE 加 `WHERE status='ACTIVE'`，rows_affected==0 返回

### 投影器对齐（`astral-trustgraph/src/api/side_effects.rs`）

| 项 | Java 基线 | Rust 原实现 | 本批对齐后 |
|----|-----------|------------|------------|
| 卡快照内容 | 只收卡规则 `permission_rule`（enabled=1） | 额外 JOIN `rule_set_entry` 进卡快照（rule_id=0 哨兵） | 只收卡规则；规则集走 `rule_set_snapshot`（引擎 L1 已读） |

### 12.1 背景与缺口
