DarkStar / In-memory authorization

Policy applies now.
The proof must close.

DarkStar concentrates authorization decisions in one shared in-memory root, leaving the database as the source for cold start and crash recovery. The trade-off buys a local decision on the read path and raises two propositions: whether the state behind an admission is sufficient, and whether the response leaves recoverable evidence.

01 / Problem

A mirror answers the past,
not the present

A memory copy can say what policy allowed when the copy was made. While a reader walks it, an administrator may have revoked that grant, or a scheduled denial may have just become active. The snapshot stays internally consistent while its conclusion expires.

Too little scope

Checking that the winning rule survived is not enough

The winning rule can survive untouched while another binding introduces an applicable denial. Checking only that the winner remains misses newly added negative evidence.

Too much scope

Requiring whole-root equality is too expensive

Strict root comparison lets an unrelated card change hold an in-flight read. A version number handles only changes that advance it, not changes unrelated to this request.

The contract is asymmetric

Allow needs a witness; refusal needs a record

Every admission must point to a moment between invocation and return at which the sequential predicate holds. Otherwise the answer is PENDING. A true refusal must also write its basis into recoverable history.

The resulting boundary

Only the admission instant is promised

The theorem does not keep policy fixed through the host's application write and gives no progress guarantee under contention. A host that needs durability across that write must add its own contract.

04 / Application

At the incident desk:
between proposal and effect

Incident response squeezes all three questions into one click: who proposes the escalation, who may confirm it, and whether the confirmation actually reached disk. The interface below uses mock data and is not connected to the formal emergency API.

See the technology roadmap for Mobius and Klein ↗
See what changes
The current L2 and proposed L3 appear side by side. Reviewers inspect the proposed change instead of facing a single approve button.
Check who can approve
A read-only card cannot confirm the escalation. Switching to a review card still requires a match on the incident's tenant and the requested action. This is question one.
Distinguish denied from pending
Insufficient permission returns DENY; missing authorization facts return PENDING. Neither escalates the incident, so an operator knows whether to find a different reviewer or wait for verification.
Leave a record
The confirmed level change and its audit land in the same contiguous durable prefix, and the response carries a stable operation identifier for later reconciliation. This is question two.

05 / Scope

What this does not promise

In-memory single-node authority is a precise capability with a precise set of exclusions. Stating them up front is more reliable than leaving them in a footnote.

Not covered · Process and deployment

Multi-process sharing and production deployment

The design covers one shared root in a single supervised process. Multi-process sharing, cross-node replication, production capacity, and real tenants are outside the proof; a second serving owner is rejected at the construction boundary.

Design and adoption criteria ↗

Not covered · Time and failure

Malicious clocks, media loss, and manual rollback

The crash model assumes exclusive file ownership, canonical frame encoding, non-reused identities, and a storage stack that honors successful synchronization. Permanent media loss, undetectable rollback, and a malicious database administrator lie outside it.

Recorded · Still open

Three implementation mappings

The paper identifies three mappings still needed to lift the composition to the theorem: authorized publication order, the correspondence between an observed state and its historical prefix, and agreement between a replayed root and a committed database checkpoint. The current code has not closed them.
