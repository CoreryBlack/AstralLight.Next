Vision PROJECT / VISION

Make every authorization
verifiable, secure, and lightweight.

AstralLight.Next uses Rust to organize source mutations, evidence publication, admission decisions, host execution, and audit reconciliation into a verifiable, recoverable chain. It is not a new policy language; it adds the evidence-admission layer between a policy engine and real execution.

Verifiable chainEvery decision can be traced to publication evidence and the admitted grant.
Safe accessReturn PENDING or DENY under uncertainty; never fall back to a stale ALLOW.
Low overheadIncremental compilation, bounded caches, and on-demand reads reduce unnecessary cost.

01 Failure scenario

How can one stale ALLOW pass through checks that are locally correct?

Let the request context be ctx = (principal, tenant, scope, resource, action). The candidate grant g₀ is still present in evidence set E₀; the source transaction commits a narrowing change d that removes g₀ from the effective grants.

The projection has not published d, and the cache still holds E₀. The policy matcher evaluates E₀ and correctly selects g₀; the host then performs the protected operation. The source commit is correct, the projection progresses on its own schedule, the cache entry is complete and correctly signed, and the matcher is correct—yet the system executes the wrong state.

This is more than “the cache was not refreshed.” Even with a fully fresh cache, valid integrity checks, and correct policy-language semantics, a match can still be stale if derived evidence does not yet represent a committed revocation.

  1. tc(d)

    The source transaction commits the narrowing d, recording a durable delta or outbox, source generation, revoke fence, affected scope, and audit correlation in the same short transaction.

  2. m0 → p0 → m1 → p1

    On a cache hit, the reader observes the manifest digest in order M and the unpublished-narrowing predicate b; these four statements do not share one atomic SQL snapshot.

  3. tf = t*

    The first authoritative observation used by the final load. The cache branch uses m0; the strict-read branch uses the first predicate read view. This provides the final evidence for admission E1.

  4. tv → ta

    Identity stability is checked at tv, and ALLOW is returned to the host at ta. The guarantee covers only revocation-class changes committed before tc(d) < t*; changes within [t*, ta] are outside the theorem’s scope.

The key question is not “how long was it cached?” Until the evidence represents a committed narrowing, the host can turn a locally correct match into a globally incorrect decision.

02 The boundary problem

A policy engine answers “does it match?”, not “is this state still executable?”

RBAC derives permissions from roles; ABAC combines subject, resource, action, and environment attributes; XACML defines combining behavior and Indeterminate results; Zanzibar exposes consistency tokens for relationship tuples. In-process and sidecar engines such as Cedar, OPA, and Casbin evaluate policies and entity representations supplied by the caller.

These systems define how to make a decision from a given input state. They do not—and should not—prove three things on their own:

  • Whether the input state includes all relevant source-side narrowings.
  • Whether the derived representation in use is the verifiable representation in the publication chain.
  • Whether a re-authorization for the same resource and action is still the same grant.

The paper frames this problem as the transition from candidate entitlement to executable authority, known as evidence admission. It does not replace policy languages or claim to solve consistency for arbitrary policy semantics. It addresses one systems-safety question: when may a candidate match cross the host boundary and become executable authority?

This resembles the check–use gap in distributed systems: source-side checks, derived representations, and host use may observe different states. Leases, sequencers, consistency tokens, probabilistic staleness, CRL/OCSP, and OAuth device pending are useful components, but they do not automatically bind freshness to a specific grant and host effect.

The problem is not policy expressiveness; it is the source, representation, and identity of the input state. Without this layer, even a correct matcher can only make decisions about a potentially stale world.

03 Candidates and authority

Candidate entitlement is a match result; executable authority is a security decision.

The paper describes the problem with four general concepts: principal, who requests an action on a resource within a tenant and authorization scope; grant, which carries an origin, tenant, principal, scope, resource, action, validity period, provenance, logical identifier, and revision; candidate entitlement, the deterministic match for a request against a given evidence set E; and executable authority, the result when a candidate passes final admission. The request context ctx binds the principal, scope, tenant, resource, and action; the evidence set E contains the admission gate, ordered manifest digest, publication watermark, integrity metadata, and effective grant set.

CANDIDATE ENTITLEMENT

Candidate entitlement

Within the given evidence set E, this is the first grant selected by deterministic matching in a fixed order that is in scope, time-valid, and returns ALLOW.

It only says that this request “matches” against this evidence.

EXECUTABLE AUTHORITY

Executable authority

A candidate becomes executable authority only after final admission validates source-linked evidence, scope, publication identity, and the exact candidate identity during final reload.

It means the host can now safely perform the protected operation.

The difference is not “one more cache lookup”; it is an explicit admission contract. A candidate may come from memory, cache, or a strict read, but only a candidate that passes final admission may cross the host boundary.

Key distinction

A policy system can correctly answer match(ctx, E). Evidence admission must also establish that E does not omit a committed narrowing for this scope, that E is the verifiable published representation, and that the admitted candidate is still g₀ itself.

04 Five connections

Connect a source mutation to the authorization decision at the host.

The paper’s admission contract has five connections. They are not necessarily novel individually, nor claimed to be the minimal mechanism set; their safety value comes from joining them into one verifiable chain.

  1. 01

    Source transaction

    A source mutation durably records a delta or outbox, source generation, revoke fence, tenant, and all affected scopes in a short transaction. Network calls, cache pushes, projection, and retries stay outside the transaction.

  2. 02

    Publication fencing

    generation and revoke fence advance monotonically, so an old owner cannot publish after a newer generation. Successful publication is proven by the committed manifest/segment/current pointer—not by an ACK or best-effort cache push.

  3. 03

    Unpublished-narrowing probe

    Before trusting a cached candidate, conservatively check whether this scope has any visible narrowing not yet successfully published to the current watermark. No result means no known blocking narrowing, not that global policy has converged.

  4. 04

    Read-observation contract

    A cached candidate must pass two ordered authoritative observations that agree, or a strict reader must obtain a fresh committed-state read view. The candidate’s own digest must also match the observed publication identity.

  5. 05

    Final identity reload

    Reload evidence before returning to the host, binding the same scope, publication evidence, logical id, revision, origin, and provenance. Matching only resource/action does not prove it is the same grant.

If any connection breaks, local checks may still appear healthy. That is “local correctness,” explored next: every component may pass its own checks while the system as a whole no longer represents the latest source narrowing.

05 Local correctness

Keeping just one local check can still admit stale authority.

The paper uses six analytical omission schedules to show that removing one connection while retaining the other local checks can leave the system looking healthy while missing a narrowing that should block. These are design analyses, not completed ablation results.

Keep published generation

A mutation d commits while publication is pending; the cached grant and pointer remain at the old generation and appear consistent when viewed alone.

Required: a source-visible probe for unpublished narrowing.

Keep cache token

Mutation d has committed, but the token has not rotated; an authenticated cache entry still carries the current token.

Required: token equality proves lineage, not source freshness.

Keep publication watermark

A new pointer has been observed, but the host uses g₀ without binding the payload and scope to the validated evidence chain.

Required: evidence representation and identity validation.

Run only one manifest–predicate pass

A mutation d commits between the reads of M and b, so the pair of observations combines two different committed states.

Required: two ordered observations that require Qpre = Qpost.

Keep projection reload

Both loads are internally valid, but the committed d has still not been published to the current watermark.

Required: run the source-linked probe during final load too.

Keep resource/action rematching

After revocation, re-authorization has the same resource and action, but the successor has a new revision or different provenance.

Required: bind origin, logical id, revision, payload, and publication identity.

These schedules do not prove that an attack has been reproduced. They illustrate how the connections compose: gaps between local checks are exactly where stale authority can pass. Controlled omission experiments remain a planned evaluation gate.

06 Adversary and goals

Decision integrity at the admission boundary is what is protected.

The protected asset is not “an unmodified policy file,” but decision integrity at the host admission boundary: a request must not execute as ALLOW based on evidence that omits a visible, relevant narrowing.

The primary adversary is an authenticated requester. It can replay a still-valid signed request, switch targets, or race a source mutation against an authorization decision. It need not control trusted storage; it can exploit ordinary asynchronous behavior—projection delay, residual cache entries, worker scheduling, expired leases, and infrastructure failures.

The system also protects tenant and scope isolation, candidate provenance, and monotonicity of the publication evidence used to prove decisions. Trust assumptions: Gateway performs external authentication and signs the identity context; the authoritative store, readers, projector, and integrity keys are not Byzantine; each evaluated aggregate has one source writer; and all protected operations receive complete host mediation.

Five security goals

  1. G1

    Revocation admission

    A candidate becomes executable authority only if all relevant revocation-class changes committed before the final authoritative observation have been published and represented in final evidence; unpublished narrowing can only result in PENDING or DENY.

  2. G2

    Publication ownership

    source generation, revoke fence, and publication pointer advance monotonically; a stale worker cannot complete a newer owner’s publication, and a durable event has only one terminal transition.

  3. G3

    Scope isolation

    Matching and admission always bind the request’s principal, tenant, scope, resource, and action; replay or context switching cannot broaden these fields.

  4. G4

    Evidence identity

    Admitted evidence must identify the candidate’s origin, logical id, revision, provenance, ordered manifest chain, and integrity metadata; a successor with the same resource/action cannot replace the original candidate.

  5. G5

    Fail-closed uncertainty

    Missing, changing, malformed, unavailable, or unverifiable evidence cannot produce ALLOW. PENDING is an explicit non-admission result, not a retry or availability promise.

Out-of-scope cases are also part of the problem definition: Byzantine processes, direct compromise of MySQL/RabbitMQ, compromise of the in-process hub, active interception of trusted-node traffic, malicious or multiple writers, replica divergence, compromised keys, unbounded clock skew, and atomicity of subsequent business effects are out of scope. The theorem is a grant-specific admission contract, not a claim of “complete security against any attacker.”

07 Source and publication

First make a mutation publishable fact; then make publication verifiable fact.

The short transaction records source facts only

Commit the source mutation together with the durable delta/outbox, source generation, revoke fence, tenant, all affected scopes, and audit correlation. Keep the transaction short: no network calls, cache pushes, projection work, retries, or validation.

Fenced publication accepts only committed evidence

A supervised projector claims a delta with a compare-and-set lease and generation fence, applies only the approved mutation, validates the resulting immutable segment, and advances the pointer to a committed manifest. The manifest’s ordered digest carries the successful watermark. An older owner cannot publish after a newer generation wins; reconcile unknown worker outcomes before deciding whether to retry.

The representation is content-addressed and scope-aware: the manifest digest records the aggregate, generation, revoke fence, and segment chain; each effective grant carries a logical id, revision, scope, validity period, and provenance. Structural sharing in the persistent HAMT reduces unnecessary rebuilding, but it is a performance optimization subordinate to evidence identity—a shared segment that has not changed cannot conceal a changed card binding or fence.

An ACK is not publication proof. A broker confirm, cache push, queue receipt, or completed handler alone cannot prove that authorization state was successfully published.

08 Omission detection

Block unpublished narrowing, not ordinary additions.

Here, narrowing means removal, revocation, an authorization-content update conservatively marked as invalidating, or a mutation carrying a higher revoke fence. A true aggregate-wide mutation is represented for each affected scope; removal from a shared rule set expands into per-scope contributions.

Before trusting a cached candidate, the reader asks a conservative question:

THE NARROWING PROBE

Is there any visible narrowing for this scope that has not yet been successfully published to the current watermark?

The predicate includes pending, invalid, quarantined, or fence-leading deltas. No result does not mean “all possible policy changes have globally converged”; it means only that no blocking narrowing is known under this scope’s source/publication contract.

This asymmetry is deliberate. If an addition is not yet in evidence, the new permission is delayed. If a narrowing is not yet in evidence, an already-matched grant remains executable after source revocation. The former can wait for normal publication; the latter must be blocked. This is a security choice, not a claim that “other cards are completely unaffected.”

Not all delays are equivalent. ADD delay affects availability; NARROWING delay affects authorization correctness. The admission contract adds a blocking condition only for the latter.

09 Read paths

The cache branch requires two ordered observations; the strict branch requires a fresh read view.

Cached candidate

A cached candidate includes tenant and scope, evidence gate, ordered manifest digest, generation and revoke fence, content hash, integrity tag, cache-generation token, validity period, and the full effective-grant set. L1 has capacity and time bounds; L2 entries are authenticated and expire. Cache failure, an invalid tag, epoch mismatch, or a changed validity window sends the request to the strict reader.

Two ordered observations

The cache reader performs two authoritative observations, each made up of independent pool-level autocommit statements:

  1. m0 reads the ordered manifest digest M0; p0 reads the unpublished-narrowing predicate b0.
  2. Read m1 and p1 again, requiring the observation order m0 → p0 → m1 → p1.
  3. The candidate must satisfy Qpre = Qpost and b0 = b1 = 0, and its own digest must match the observed publication identity.

These four statements do not form one atomic SQL snapshot. A mutation may commit after m1 and before p1 without changing the sampled M value. Therefore, the theorem covers only narrowings committed before the first authoritative observation m0, not every event before p1.

Strict read

The strict reader starts a new transaction and reads the narrowing predicate first as a consistent read; it then obtains the current pointer and manifest, validates scope, segment order, and the hash chain, and rejects inconsistent or stale chains. The proof relies on this fresh committed-state read view, not on an isolation-level claim without a frozen experimental archive.

A cache hit is not authorization evidence. TTL, token, and hit describe residency and lineage only; source-linked observation must prove source freshness.

10 Final reload

A matched g₀ is not authority; final reload must prove again that it is the same grant.

Matching E0 produces a candidate, not authority. The decision path reloads evidence to obtain E1, then verifies it against the request’s tenant, scope, gate, ordered manifest digest, generation, fence, integrity metadata, and exact canonical grant.

The exact check includes more than resource and action: it also checks the grant’s origin, logical id, revision, and provenance. A logical identifier may be reused after a tombstone, but a revision is never reassigned to another record.

Why resource/action are not enough

Re-authorization after revocation may have the same resource and action but a successor revision. If matching uses only resource/action, the successor can “pick up” the old candidate and appear valid, even though its origin, revision, or provenance differs. Final reload must reject this substitution.

host fence

The host captures an opaque authority fence before resource ownership and evaluation, then compares the original fence after auxiliary authoritative reads and before entering the downstream handler. A cold refill that invalidates the original fence cannot silently become a new request baseline; reject that request and reevaluate subsequent requests. This is admission mediation, not atomicity for later handler effects.

Final reload is not “one more lookup.” It must prove that publication identity, scope, and candidate identity did not drift during the decision.

11 Failure semantics

On failure, there are only two safe outcomes: PENDING or DENY.

The only success is ALLOW after the stable check. No match or invalid context returns DEFAULT_DENY; if evidence is not ready, is changing, missing, malformed, or unverifiable, return AUTHORIZATION_PENDING or DEFAULT_DENY.

  • No match or invalid context: DEFAULT_DENY.
  • Evidence missing, stale, changing, or unverifiable: PENDING or DENY; never fall back to a stale ALLOW.
  • PENDING cannot be cached as authority, used to admit a later request, or replaced with a previous ALLOW.
  • The current API does not promise a universal retry interval; callers must apply their own bounded policy.
  • A business-level PENDING does not advance the infrastructure circuit breaker.

The current compatibility entry point maps both DENY and PENDING to HTTP 403 while preserving the semantic reason code; integration mapping or policy denial uses 403, identity/session failure uses 401, and pending or unavailable evidence may use 503. Transport status does not replace the semantic decision; experiments must record the actual decision and host outcome.

PENDING does not mean “it will be allowed automatically later.” It explicitly means the evidence is insufficient and the protected effect must not run; the availability cost is part of this contract.

13 Conditional guarantee

A conditional safety guarantee for a specific grant, under stated assumptions.

Under the source, publication, storage-integrity, read-observation, and host-mediation assumptions above, the paper states a conditional theorem. It is neither a global snapshot of all policy changes nor a machine-checked proof of a deployment.

Five assumptions

  • M1 Source capture: Each relevant source mutation atomically records the durable delta/outbox, source generation, revoke fence, tenant, and all affected scopes; narrowing classification is conservative.
  • M2 Monotonic publication: Successful publication atomically records a strictly advancing affected-scope watermark and pointer; the digest never rolls back or gets reused for another state.
  • M3 Faithful representation: The projector materializes only approved deltas as ordered, integrity-checked evidence; every contribution covered by publication must remain represented by its watermark.
  • M4 Trusted storage and processes: The authoritative writer, readers, projector, and integrity keys are not Byzantine; mismatches, missing records, and unknown outcomes all fail closed.
  • M5 Complete mediation: Every protected host operation invokes the evaluator with a bound context and proceeds only after ALLOW.

In addition to M1–M5, the reader’s two observation contracts and the grant revision ledger are assumptions: see Sections 09 and 10, respectively.

CONDITIONAL ADMISSION-SAFETY

Under M1–M5, the read-observation contract, and the grant revision ledger contract, every successful ALLOW has a consistency point t* = tf: all revocation-class changes committed before tf and visible to the request scope have been successfully published and are represented by final evidence E1; E1 must also bind the exact admitted candidate grant. If this condition cannot be established, the result can only be PENDING or DENY.

Where is the consistency point?

tf is the first authoritative observation that provides successful final evidence: the cache branch uses m0; the strict-read branch uses the initial predicate read view. Identity stability is checked at tv, and ALLOW is returned to the host at ta, so tf ≤ tv ≤ ta.

Four supporting lemmas

  • Visibility capture: A visible narrowing committed before a fresh predicate read either makes b = 1 or has already been successfully published.
  • Cache observation and representation: A cached candidate that passes two ordered observations and the equality check represents every visible revocation-class change committed before the m0 observation.
  • Strict observation and representation: A successful strict load represents every visible revocation-class change committed before its initial predicate read view.
  • Candidate identity binding: A different grant revision cannot replace the original candidate while passing the stable check.

What the theorem does not cover

  • Overlapping mutations committed within [tf, ta].
  • Atomicity of subsequent business effects; that requires a host transaction or effect fence.
  • Visibility of ADD, Byzantine storage, multi-writer ordering, and replica divergence.
  • Unbounded clock skew, global policy linearizability, and combining semantics for richer policy languages.

This is a sufficient conditional contract. It connects “visible pre-observation revocation” to “the exact admitted grant,” while stating the availability cost and out-of-scope cases alongside the result.
